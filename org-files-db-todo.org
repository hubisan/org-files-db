* Config.rs

#+BEGIN_SRC markdown
  Ja — **genau so** solltest du es machen.
  Die beste Architektur ist:

  # 🟢 **Rust-Parser hat EIGENE Konfigurations-Struktur (z. B. config.toml)**

  und

  # 🟣 **Emacs kann diese Konfiguration überschreiben / erweitern**

  Damit bekommst du:

  ,* ✔ volle Unabhängigkeit von Emacs
  ,* ✔ Parser funktioniert standalone (CLI-Tool, Tests, Benchmarks, LSP, etc.)
  ,* ✔ Gleichzeitig volle Flexibilität in Emacs
  ,* ✔ Kein hartcodiertes Verhalten → Emacs kann alles überschreiben
  ,* ✔ Robust und langfristig sauber

  ---

  # 🧩 Perfektes Setup: Zwei Ebenen von Konfiguration

  ## **1. Rust-native Config**

  (auch wenn Emacs nichts lädt)

  Beispiel:

  ```rust
  struct Config {
      link_types: Vec<String>,
      allow_angled_links: bool,
      block_whitelist: Vec<String>,
      whitespace_normalization: bool,
      todo_keywords: Vec<String>,
  }
  ```

  Wird geladen aus:

  ```
  ~/.config/my-org-parser/config.toml
  ```

  oder default über:

  ```rust
  impl Default for Config { … }
  ```

  → Dein Parser kann komplett **standalone** laufen.

  ---

  ## **2. Emacs liefert „Runtime Overrides“**

  Beispiel:

  ```elisp
  (org-rs-parse buffer-string
                :link-types org-link-types
                :todo-keywords org-todo-keywords
                :normalize t)
  ```

  In Rust:

  ```rust
  fn parse_org(text: &str, overrides: ConfigOverrides) {
      let mut cfg = Config::default();
      cfg.apply(overrides);
      parse_with_config(text, &cfg)
  }
  ```

  ---

  # 🧠 Warum diese Kombination ideal ist

  ### ✔ Emacs-Anwender können ALLES konfigurieren

  (z. B. zusätzliche link-types, custom blocks, exporter options)

  ### ✔ Rust bleibt unabhängig

  ,* Du kannst CLI-Tools bauen
  ,* Tests schreiben
  ,* Parser in anderen Editoren verwenden (Helix, Neovim, VS Code, Kate, etc.)

  ### ✔ Emacs-Integration bleibt leicht

  Emacs muss kein TOML parsen
  → gibt einfach JSON oder Lisp-Listen an Rust

  ---

  # 🔥 Beispiel: CLI + Emacs Modul, gleiche Config

  ## CLI

  ```
  myorg-parse myfile.org --config ~/.config/myorg/config.toml
  ```

  ## Emacs

  ```
  (org-rs-parse buffer-string :link-types org-link-types)
  ```

  → Rust benutzt denselben Codepfad.

  ---

  # 📦 Wie du die Overlays strukturierst

  ```rust
  struct ConfigOverrides {
      link_types: Option<Vec<String>>,
      todo_keywords: Option<Vec<String>>,
      allow_angled_links: Option<bool>,
      // usw.
  }

  impl Config {
      fn apply(&mut self, o: ConfigOverrides) {
          if let Some(x) = o.link_types { self.link_types = x; }
          if let Some(x) = o.todo_keywords { self.todo_keywords = x; }
          if let Some(x) = o.allow_angled_links { self.allow_angled_links = x; }
      }
  }
  ```

  ---

  # 🎯 Fazit

  ✔ **Ja — du kannst alle Emacs-Variablen direkt an Rust übergeben.**
  ✔ **Ja — du solltest trotzdem eine config.toml behalten**, damit Rust standalone bleibt.
  ✔ Beste Lösung: **Defaults in Rust**, **Overlays aus Emacs**.
  ✔ Clean, robust, zukunftssicher.

#+END_SRC

** *Option 3: JSON/S-Expression Return → Emacs Wrapper in Lisp*

Dies ist die /einfachste/  Methode:

Du exportierst nur *eine*  Rust-Funktion:

#+begin_src c
org_parse(text: String) -> String   // JSON-Result

#+end_src

Und in Elisp:

#+begin_src c
(let ((json (org-rs-parse buffer-contents)))
  (json-parse-string json))

#+end_src

Das ist *super einfach*, *super stabil*, und *super performant* .

Kein full Emacs-API Wrapping nötig.

** 🎯 Empfohlene Strategie für deinen Parser

Da dein Projekt ein *leistungsstarker Org-Parser in Rust*  werden soll:

*** ✔ Parser in reinem Rust (nur Rust-Code)

→ Lexer, Parser, AST: keine Emacs-Abhängigkeiten  
→ schnelle Tests, Cargo, alles unabhängig

*** ✔ Am Schluss: *ein dünner Emacs-Modul-Wrapper*

→ 100–200 Zeilen max  
→ JSON übergeben  
→ Emacs baut daraus eigenes AST/Overlays/whatever

*** ✔ Kein =emacs-module-rs=  notwendig

→ optional, aber nicht nötig  
→ hohe Flexibilität ohne Crate
