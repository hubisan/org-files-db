#+TITLE: CLI Reference
#+STARTUP: showall

This page documents the user-facing ~orgfdb~ commands that are stable enough to treat as repository-local reference material.

* ~orgfdb headings --json~

~orgfdb headings --json~ prints stored heading rows from the SQLite database as JSON. It is a database inspection command: it reads persisted facts only and does not analyze the current contents of Org files.

The command is read-only. It does not scan Org files, rebuild files, resolve targets, or mutate the database.

The output is a JSON array ordered deterministically by:

1. ~file_path~
2. ~byte_start~
3. ~id~

Synthetic root rows are included by default, and ~--no-root~ excludes them. Root rows use the synthetic repository conventions: ~level = 0~, ~parent_id = null~, and they represent file/document scope rather than parser-level Org headings.

The JSON objects expose the heading fields used by the current CLI contract:

- ~id~
- ~file_id~
- ~file_path~
- ~parent_id~
- ~level~
- ~line_number~
- ~byte_start~
- ~byte_end~
- ~title~
- ~title_raw~
- ~todo_keyword~
- ~todo_type~
- ~priority~
- ~scheduled_raw~
- ~scheduled_ts~
- ~deadline_raw~
- ~deadline_ts~
- ~closed_raw~
- ~closed_ts~

For real headings, ~title~ is the cleaned semantic title. ~title_raw~ preserves the source title area after the headline stars, including TODO keywords, priorities, and statistics cookies, while still excluding trailing Org tags.
- ~archivedp~
- ~footnote_section_p~
- ~all_tags~

~--include-root~ is retained only as a compatibility no-op. The default output already includes root rows.

If you need the underlying configuration settings for the database path, source file selection, link protocols, TODO keywords, or search options, see [[./config.org][docs/config.org]].

* ~orgfdb links --json~

~orgfdb links --json~ prints stored link source facts plus stored resolution snapshot fields from the SQLite database as JSON. It is a database inspection command: it reads persisted facts only and does not analyze the current contents of Org files.

The command is read-only. It does not scan Org files, rebuild files, resolve targets, or mutate the database.

The output is a JSON array ordered deterministically by:

1. ~file_path~
2. ~byte_start~
3. ~id~

Root links are included. For root links, ~heading_level~ is ~0~ and ~heading_path~ is an empty array.

The JSON objects expose these public fields:

- ~file_id~
- ~file_path~
- ~heading_id~
- ~heading_path~
- ~heading_level~
- ~source_context~
- ~format~
- ~link_type~
- ~raw~
- ~raw_target~
- ~raw_description~
- ~path~
- ~search_option~
- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~
- ~resolution_status~
- ~resolution_diagnostic~
- ~byte_start~
- ~byte_end~
- ~line~

The output uses ~link_type~, not a legacy ~type~ field.

Notes:

- ~format~ identifies the source syntax: ~bracket~, ~angle~, or ~plain~.
- ~source_context~ records where the link came from in the indexed Org file, such as normal text or a drawer context.
- ~path~, ~search_option~, ~byte_start~, ~byte_end~, and ~line~ provide editor-jump data from the stored database facts.
- ~path_absolute~, ~target_file_id~, ~target_heading_id~, ~target_custom_id~, ~target_id~, ~resolution_status~, and ~resolution_diagnostic~ mirror the stored resolver-owned DB columns as-is and may be ~null~.
- ~resolution_status = null~ means no resolver pass has populated the row yet.
- ~resolution_status = resolved~, ~broken~, ~unresolved~, ~ambiguous~, and ~unsupported~ reflect the stored Phase 4 outcome.
- File-only links resolve to the target file's synthetic root heading, and file links to indexed files populate ~path_absolute~ and ~target_file_id~.
- Supported file search options are only ~::*Heading~ and ~::#custom-id~; unsupported examples include ~::42~, ~::/regexp/~, and dedicated targets such as ~::target~ or ~::<<target>>~.
- Org ~id:~ links resolve only against indexed non-root headings. External ~org-id-locations~ are not supported, so missing indexed IDs remain ~unresolved~ with ~id not found~.
- The command opens the existing database in read-only mode. If ~--config~ is provided, only the stored ~db_path~ is read from that config file.

* ~orgfdb query --json~

~orgfdb query --json QUERY~ parses Query Model v0 syntax, validates it against the current query contract, executes it against the existing SQLite database, and prints the shaped JSON response.

The command is strictly read-only. It does not scan Org files, rebuild files, resolve links on demand, apply migrations beyond opening the existing DB read-only, or mutate stored facts.

Execution uses the persisted query stack only:

- Query syntax is parsed by the Query Model v0 parser.
- Validation uses the Query Model v0 semantic validator plus backend capability checks against the opened SQLite database.
- Execution uses the persisted SQLite query layer.
- Output shaping uses the persisted result-enrichment layer.

The normative language contract remains [[./reference/query-model-v0.org][docs/reference/query-model-v0.org]]. This CLI page is the complete user-facing reference for the implemented ~orgfdb query~ command.

** Synopsis

#+begin_src shell
orgfdb query --json [OPTIONS] QUERY
#+end_src

~QUERY~ is a single Query Model v0 expression. In normal shells, quote the whole expression with single quotes and keep query strings inside it in double quotes.

#+begin_src shell
orgfdb query --json '(todo "NEXT")'
orgfdb query --json '(files (file-title "Projects" :exact t))'
orgfdb query --json '(links (status "broken"))'
#+end_src

Accepted options:

- ~--json~ :: Required for the stable output mode.
  Without it, the command exits with code ~2~ and prints ~query currently only supports --json~.
- ~--output~ :: Accepted values: ~flat~, ~outline~.
  Default: ~flat~.
  Repeatable: no.
  Changes output shape only, never matching semantics.
- ~--include~ :: Accepted values: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~, ~source~, ~target~.
  Default: none.
  Repeatable: yes.
  Values may be comma-separated and/or supplied in repeated flags. Duplicates are removed before serialization.
- ~--config PATH~ :: Accepted value: filesystem path.
  Default: none.
  Repeatable: no.
  Loads ~db_path~ and query-time settings such as ~query.timezone~ before opening the DB read-only.

~--include~ validation:

- ~path~ is valid for all targets.
- ~properties~, ~effective_properties~, ~keywords~, ~links~, and ~backlinks~ are valid for ~headings~ and ~files~ output only.
- ~source~ and ~target~ are valid for ~links~ output only.
- Unknown include values are rejected by Clap with exit code ~2~.

** Query Grammar Overview

Complete supported top-level forms:

#+begin_src text
(headings EXPR?)
(links EXPR?)
(files EXPR?)

(and EXPR...)
(or EXPR...)
(not EXPR)

(predicate ARG... :option VALUE...)
#+end_src

Important public rules:

- Top-level heading shorthand is supported. Bare heading predicates such as ~(todo "NEXT")~ are equivalent to ~(headings (todo "NEXT"))~.
- Nested relation queries must always use an explicit target wrapper such as ~(links (status "broken"))~ or ~(files (file-path "notes.org"))~.
- Empty target wrappers are supported for implemented targets, for example ~(links)~ or ~(files)~.
- Boolean operators are ordinary query expressions, not predicates:
  - ~(and EXPR...)~ requires all children to match.
  - ~(or EXPR...)~ requires any child to match.
  - ~(not EXPR)~ negates exactly one child expression.
- Strings use double quotes.
- Integers are bare numeric values.
- Boolean options use ~t~ or ~nil~.
- Enum-like keyword values use symbols such as ~:all~ or ~:any~.
- Invalid syntax is a parse error with exit code ~1~.

Examples:

#+begin_src shell
orgfdb query --json '(and (todo "NEXT") (priority "A"))'
orgfdb query --json '(headings (not (tags "archive")))'
orgfdb query --json '(links (source (headings (title "Query Engine" :exact t))))'
orgfdb query --json '(files)'
#+end_src

** Targets

- ~headings~ ::
  - Returns matched real headings and, when the heading query domain includes file/root objects, those file/root matches as ~kind = "file"~.
  - Bare top-level shorthand: yes.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~.
- ~links~ ::
  - Returns matched links.
  - Bare top-level shorthand: no.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~source~, ~target~.
- ~files~ ::
  - Returns matched files.
  - Bare top-level shorthand: no.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~.

Target notes:

- Bare ~(headings)~ returns the complete heading-query domain: all real headings plus one file/root object per indexed file.
- ~headings~ root/file results are always serialized as ~kind = "file"~. The internal level-0 storage rows are never exposed as ~kind = "heading"~ results.
- In flat output, the file/root result sorts before headings from the same file.
- In outline output, the file/root result is the tree root for headings in that file.
- Predicates such as ~title~ may also match the synthetic root/file object when their documented root participation is enabled.
- File predicates on ~headings~ apply to both real headings and file/root objects: real headings inspect their containing file, and matching file/root objects are returned as ~kind = "file"~.
- ~links~ always return link objects. Nested source/target/file/headings relations affect matching only; they do not change the returned object kind.
- ~files~ return file objects and use the file root heading as the storage source for tags, keywords, properties, and file-level links.

** Predicate Option Index

The current public predicate options are:

- ~:exact~ :: 
  - Valid on: ~title~, ~link-target~, ~link-description~, ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~outline-sequence~.
  - Value type: ~t~ or ~nil~.
  - Default: ~nil~.
  - Usually requires exactly one text argument. ~outline-sequence~ applies it per path segment and allows multiple arguments.
- ~:regexp~ ::
  - Valid on: ~title~, ~has-text~, ~tags~, ~property~, ~keyword~, ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~outline-contains~, ~outline-sequence~, ~link-target~, ~link-description~.
  - Value type: ~t~ or ~nil~.
  - Default: ~nil~.
  - Meaning is predicate-specific. SQLite uses Rust regular expressions and matching is case-sensitive unless the pattern says otherwise.
- ~:match~ ::
  - Valid on: ~tags~.
  - Value type: ~:any~ or ~:all~.
  - Default: ~:any~.
  - ~(tags-all ...)~ is a parser alias for ~(tags ... :match :all)~.
- ~:inherit~ ::
  - Valid on: ~tags~, ~property~, ~keyword~ on ~headings~.
  - Value type: ~t~ or ~nil~.
  - Default: ~t~.
  - Invalid on file queries.
- ~:from~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Inclusive lower bound.
- ~:to~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Inclusive query-model upper bound. The complete interval implied by the value is included.
- ~:on~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Matches the given day or the given datetime, depending on the value form.

Options are validated per predicate. A supported option on one predicate does not imply support elsewhere.

** Complete Predicate Reference

*** Boolean expressions

- ~(and EXPR...)~ :: Valid on all targets.
  All child expressions must match.
  Example: ~'(and (todo "NEXT") (tags "project"))'~.
- ~(or EXPR...)~ :: Valid on all targets.
  Any child expression may match.
  Example: ~'(or (priority "A") (priority "B"))'~.
- ~(not EXPR)~ :: Valid on all targets.
  Negates exactly one child.
  Example: ~'(not (done))'~.

*** Heading predicates

- ~todo~ :: Syntax: ~(todo [KEYWORD...])~.
  Targets: ~headings~.
  No args means any heading with a TODO keyword. With args, matches any listed TODO keyword. Case-sensitive against stored keyword values.
  Example: ~'(todo "NEXT" "PLAN")'~.
- ~done~ :: Syntax: ~(done)~.
  Targets: ~headings~.
  Matches headings whose TODO type is ~closed~.
  Example: ~'(done)'~.
- ~title~ :: Syntax: ~(title STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~.
  Default is case-insensitive substring matching against normalized heading titles. Matching file/root titles return ~kind = "file"~ nodes.
  Example: ~'(title "Query Engine" :exact t)'~.
- ~has-text~ :: Syntax: ~(has-text STRING... :regexp t|nil)~.
  Targets: ~headings~.
  Matches persisted heading body text. Default is case-insensitive substring matching for all supplied terms. Requires persisted body text capability. With ~:regexp t~, each pattern is matched against the persisted body text using Rust regex syntax.
  Example: ~'(has-text "sqlite" "fts")'~.
- ~level~ :: Syntax: ~(level NUMBER)~, ~(level MIN MAX)~, ~(level COMPARATOR NUMBER)~.
  Targets: ~headings~.
  Matches heading levels. Comparator form uses ~<~, ~<=~, ~>~, or ~>=~.
  Example: ~'(level 1 2)'~.
- ~priority~ :: Syntax: ~(priority VALUE...)~ or ~(priority COMPARATOR VALUE)~.
  Targets: ~headings~.
  Multi-value form is OR. Comparator form supports ~<~, ~<=~, ~>~, and ~>=~ using semantic priority order: ~A > B > C~. Query-time ranks are ~A = 1~, ~B = 2~, and so on through ~Z = 26~; numeric values from ~0~ through ~64~ use their integer rank, so ~A~ and ~1~ match equivalently. The original source value remains stored and returned. Query Model v0 uses this fixed mapping and does not evaluate Emacs priority variables or file-local ~#+PRIORITIES~ declarations.
  Example: ~'(priority > "B")'~ matches ~A~ and ~1~.
- ~tags~ :: Syntax: ~(tags TAG... :inherit t|nil :regexp t|nil :match :any|:all)~.
  Targets: ~headings~, ~files~.
  Heading queries use effective tags by default, including inherited/root tags when present. File queries match tags stored on the file root heading. With ~:regexp t~, each pattern is matched against one effective tag value.
  Example: ~'(tags "project" "urgent" :match :all)'~.
- ~tags-all~ :: Syntax: ~(tags-all TAG... [same options as tags except :match])~.
  Targets: parser alias.
  Readability alias for ~(tags ... :match :all)~. It is normalized before validation.
  Example: ~'(tags-all "project" "urgent")'~.
- ~property~ :: Syntax: ~(property KEY [VALUE] :inherit t|nil :regexp t|nil)~.
  Targets: ~headings~, ~files~.
  With one argument, matches by property key existence. With two, matches key/value. Heading queries use effective properties by default; ~:inherit nil~ restricts to direct rows. File queries are always direct root/file property matches and reject ~:inherit~. With ~:regexp t~, the pattern is matched against the resolved effective property value.
  Local effective values use one source-independent rule for property drawer rows and file-level ~#+PROPERTY~ rows: the last non-append definition is the base value, and all append definitions for the same key are appended in source order even if they appear before or between non-append definitions.
  Compatibility note: this intentionally differs from Org for some repeated file-level ~#+PROPERTY~ sequences mixed with append rows. For example, orgfdb resolves
  ~#+PROPERTY: KEYWORD_RESET old~, ~#+PROPERTY: KEYWORD_RESET+ appended-before-reset~, ~#+PROPERTY: KEYWORD_RESET replacement~, ~#+PROPERTY: KEYWORD_RESET+ appended-after-reset~
  as ~replacement appended-before-reset appended-after-reset~, while Org may resolve the same file-level sequence as ~replacement appended-after-reset~.
  This incompatibility is deliberate so drawer properties and file-level keyword properties follow one uniform query-resolution rule. Raw ~properties~ output still preserves the original ~source~ and ~append~ metadata for each stored row.
  Example: ~'(property "CATEGORY" "work")'~.
- ~keyword~ :: Syntax: ~(keyword KEY [VALUE] :regexp t|nil :inherit t|nil)~.
  Targets: ~headings~, ~files~.
  Matches root/file keyword facts. Heading queries inherit keywords from the containing file by default; ~:inherit nil~ checks only the candidate heading. Because document keywords are currently stored on the synthetic file heading, local-only matching normally returns only the file result. File queries always match their root/file keywords and reject ~:inherit~. With ~:regexp t~, the pattern applies to the keyword value, not the keyword name.
  Example: ~'(keyword "AUTHOR" "Alice")'~.
- ~file-name~ :: Syntax: ~(file-name STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~files~.
  Matches the containing file name. On ~headings~, matching file/root objects are also returned as ~kind = "file"~.
  Example: ~'(file-name "notes.org" :exact t)'~.
- ~file-path~ :: Syntax: ~(file-path STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the containing file path. A value of ~~ or beginning with ~~/~ expands its leading ~~ from the process ~HOME~ environment variable before substring, exact, or regexp matching. Named-user forms such as ~~alice/~ are not supported. Expansion does not invoke a shell, resolve symlinks, canonicalize paths, or require them to exist; stored and returned paths remain unchanged. On ~headings~, matching file/root objects are also returned as ~kind = "file"~. On links this applies through the source file relation.
  Example: ~'(file-path "~/projects/notes.org" :exact t)'~.
- ~file-dir~ :: Syntax: ~(file-dir STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the containing directory path. A value of ~~ or beginning with ~~/~ expands its leading ~~ from the process ~HOME~ environment variable before substring, exact, or regexp matching. Named-user forms such as ~~alice/~ are not supported. Expansion does not invoke a shell, resolve symlinks, canonicalize paths, or require them to exist; stored and returned paths remain unchanged. On ~headings~, matching file/root objects are also returned as ~kind = "file"~. On links this applies through the source file relation.
  Example: ~'(file-dir "~/projects" :exact t)'~.
- ~file-title~ :: Syntax: ~(file-title STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the effective file/root title. On ~headings~, this evaluates both real headings by containing file title and file/root objects themselves; it is different from ~title~, which can match real headings and, by default, the root object itself.
  Example: ~'(file-title "Projects" :exact t)'~.
- ~file-modified~ :: Syntax: ~(file-modified :from DATE :to DATE :on DATE)~.
  Targets: ~headings~, ~files~.
  Matches persisted file modification timestamps. On ~headings~, matching file/root objects are also returned as ~kind = "file"~. Relative dates such as ~today~ or integer day offsets are resolved before SQL execution.
  Example: ~'(file-modified :from -7 :to today)'~.
- ~outline-contains~ :: Syntax: ~(outline-contains STRING... :regexp t|nil)~.
  Targets: ~headings~.
  Matches headings whose outline path contains all supplied components somewhere in the path. The synthetic file/root title is not part of this match path. With ~:regexp t~, each pattern is matched against individual outline components. No ~:exact~ option.
  Example: ~'(outline-contains "Project" "Query")'~.
- ~outline-sequence~ :: Syntax: ~(outline-sequence STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~.
  Matches contiguous outline path segments in order. With ~:exact t~, each supplied segment must exactly match the corresponding path component. The synthetic file/root title is not part of this match path. With ~:regexp t~, each pattern is matched against the corresponding outline component.
  Example: ~'(outline-sequence "Projects" "Org database" :exact t)'~.
- ~ts~ :: Syntax: ~(ts :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches any stored timestamp row associated with the heading.
  Example: ~'(ts :on today)'~.
- ~ts-active~ :: Syntax: ~(ts-active :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Like ~ts~, but only active timestamps.
  Example: ~'(ts-active :from "2026-01-01" :to "2026-12-31")'~.
- ~ts-inactive~ :: Syntax: ~(ts-inactive :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Like ~ts~, but only inactive timestamps.
  Example: ~'(ts-inactive :from -30 :to today)'~.
- ~deadline~ :: Syntax: ~(deadline :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading deadline metadata.
  Example: ~'(deadline :to 7)'~.
- ~scheduled~ :: Syntax: ~(scheduled :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading scheduled metadata.
  Example: ~'(scheduled :on today)'~.
- ~closed~ :: Syntax: ~(closed :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading closed metadata.
  Example: ~'(closed :from -7)'~.
- ~planning~ :: Syntax: ~(planning :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches any of ~scheduled~, ~deadline~, or ~closed~.
  Example: ~'(planning :from today :to 7)'~.
- ~parent~ :: Syntax: ~(parent)~ or ~(parent (headings EXPR))~.
  Targets: ~headings~.
  Zero-arg form matches headings that have any parent. Nested form matches headings whose direct parent matches the nested heading query.
  Example: ~'(parent (headings (tags "project")))'~.
- ~children~ :: Syntax: ~(children)~ or ~(children (headings EXPR))~.
  Targets: ~headings~.
  Zero-arg form matches headings with at least one child. Nested form matches headings having a direct child that matches the nested heading query.
  Example: ~'(children (headings (todo "NEXT")))'~.
- ~ancestors~ :: Syntax: ~(ancestors)~ or ~(ancestors (headings EXPR))~.
  Targets: ~headings~.
  Zero-arg form matches headings that have any ancestor. Nested form is transitive over all ancestors.
  Example: ~'(ancestors (headings (priority "A")))'~.
- ~descendants~ :: Syntax: ~(descendants)~ or ~(descendants (headings EXPR))~.
  Targets: ~headings~.
  Zero-arg form matches headings that have any descendant. Nested form is transitive over descendants.
  Example: ~'(descendants (headings (todo "WAITING")))'~.
- ~has-link~ :: Syntax: ~(has-link)~ or ~(has-link (links EXPR))~.
  Targets: ~headings~, ~files~.
  Zero-arg form matches objects containing any stored link. Nested form filters by contained links. File queries include preamble/root links.
  Example: ~'(has-link (links (link-type "file")))'~.
- ~links-to~ :: Syntax: ~(links-to (headings EXPR))~ or ~(links-to (files EXPR))~.
  Targets: ~headings~, ~links~.
  Matches objects that link to a target heading or file matching the nested query. The matched object is still the outer heading or link.
  Example: ~'(links-to (files (file-title "Beta Index" :exact t)))'~.
- ~linked-from~ :: Syntax: ~(linked-from any)~, ~(linked-from (headings EXPR))~, ~(linked-from (files EXPR))~.
  Targets: ~headings~, ~links~.
  Matches objects that have incoming links from the nested source. ~any~ means any incoming link.
  Example: ~'(linked-from (headings (property "CUSTOM_ID" "query-model" :inherit nil)))'~.

*** Link predicates

- ~link-type~ :: Syntax: ~(link-type TYPE...)~.
  Targets: ~links~.
  OR-matches stored link types.
  Example: ~'(links (link-type "file" "id"))'~.
- ~link-target~ :: Syntax: ~(link-target STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~links~.
  Matches stored raw target text with substring, regexp, or exact semantics.
  Example: ~'(links (link-target "notes.org" :exact t))'~.
- ~link-description~ :: Syntax: ~(link-description STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~links~.
  Matches stored raw description text.
  Example: ~'(links (link-description "Project.*" :regexp t))'~.
- ~has-description~ :: Syntax: ~(has-description)~.
  Targets: ~links~.
  Matches links with any stored description.
  Example: ~'(links (has-description))'~.
- ~status~ :: Syntax: ~(status STATUS...)~.
  Targets: ~links~.
  Matches persisted resolver state such as ~resolved~, ~broken~, ~unresolved~, ~ambiguous~, or ~unsupported~.
  Example: ~'(links (status "broken" "unresolved"))'~.
- ~source~ :: Syntax: ~(source any)~ or ~(source (headings EXPR))~.
  Targets: ~links~.
  Matches links by source heading relation. ~any~ means any heading source.
  Example: ~'(links (source (headings (tags "project"))))'~.
- ~target~ :: Syntax: ~(target any)~, ~(target (headings EXPR))~, ~(target (files EXPR))~.
  Targets: ~links~.
  Matches links by resolved target relation.
  Example: ~'(links (target (files (file-path "notes.org" :exact t))))'~.
- ~file-name~, ~file-path~, ~file-dir~, ~file-title~ :: Same syntax as above.
  Targets: ~links~.
  These filter links by their containing source file.
  Example: ~'(links (file-title "Projects" :exact t))'~.
- ~links-to~, ~linked-from~ :: Same syntax as above.
  Targets: ~links~.
  Relation predicates over link targets or incoming links.
  Example: ~'(links (links-to (headings (title "Beta Target" :exact t))))'~.

*** File predicates

- ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~file-modified~ :: Same syntax as above.
  Targets: ~files~.
  Direct file metadata predicates.
  Example: ~'(files (file-path ".*/projects/.*\\.org" :regexp t))'~.
- ~keyword~ :: Syntax: ~(keyword KEY [VALUE] :regexp t|nil)~.
  Targets: ~files~.
  Matches root/file keyword facts.
  Example: ~'(files (keyword "TITLE" "Proj.*" :regexp t))'~.
- ~property~ :: Syntax: ~(property KEY [VALUE] :regexp t|nil)~.
  Targets: ~files~.
  Matches direct root/file property facts only. ~:inherit~ is invalid in file queries.
  Example: ~'(files (property "CATEGORY" "work"))'~.
- ~tags~ / ~tags-all~ :: Same syntax as above, without ~:inherit~.
  Targets: ~files~.
  Matches tags stored on the synthetic file root heading. ~:match :all~ and ~:regexp~ are supported.
  Example: ~'(files (tags "project" "archive" :match :all))'~.
- ~has-link~ :: Syntax: ~(has-link)~ or ~(has-link (links EXPR))~.
  Targets: ~files~.
  Matches files by contained links, including preamble/root links.
  Example: ~'(files (has-link (links (status "broken"))))'~.

*** Unsupported or intentionally absent operators

- ~tags-regexp~ is not a supported public predicate. Use ~(tags ... :regexp t)~ instead.
- Query Model output options stay outside the query language itself. ~--output~ and ~--include~ are CLI options, not query forms.

** Root and File Matching Semantics

Synthetic root/file behavior matters most for heading queries:

- Every indexed file has a synthetic level-0 heading in storage.
- Every heading predicate is evaluated against the same heading-query domain: real headings plus the synthetic file/root object.
- When a heading query matches the root/file object, the JSON result is emitted as ~kind = "file"~, not ~kind = "heading"~.
- Matching file/root results expose ~level = 0~.
- This is why a heading query may legitimately return file nodes.

Important distinctions:

- ~title~ on ~headings~:
  - matches real headings
  - may also match the effective file/root title
  - returns a file node when the root/file object is the match
- ~file-title~:
  - filters by the containing file title
  - on ~headings~, still returns heading results unless the outer target is ~files~
- ~files~ target:
  - directly returns file nodes
  - never returns heading nodes

Examples:

#+begin_src shell
orgfdb query --json '(headings (title "Alpha Index" :exact t))'
orgfdb query --json '(headings (property "CATEGORY" "work"))'
orgfdb query --json '(headings (file-title "Alpha Index" :exact t))'
orgfdb query --json '(files (file-title "Alpha Index" :exact t))'
#+end_src

** Timestamp Semantics

Implemented date/time value forms:

- ISO-like date strings such as ~"2026-01-03"~
- ISO-like date-time strings such as ~"2026-01-03 09:15"~
- ~today~
- integer day offsets such as ~-7~, ~0~, or ~7~

Resolution and boundary rules:

- Relative values are resolved before SQL execution.
- The effective timezone is configured ~query.timezone~, or the current local system timezone when it is omitted.
- ~file-modified~ stores absolute Unix instants. Its date-only values describe a calendar day in the effective timezone, and offset-free datetimes are interpreted in that timezone before matching.
- ~file-modified~ accepts RFC 3339 datetimes with an explicit offset as absolute instants. Nonexistent or ambiguous offset-free local datetimes fail clearly; use an explicit offset for an ambiguous time.
- Org planning and generic timestamp values remain timezone-naive in Query Model v0. Explicit dates and datetimes are compared as written and are not shifted through ~query.timezone~; the timezone only chooses the calendar date for ~today~ and integer day offsets.
- Date-only ~:from~ is inclusive from the start of that day.
- Date-only ~:to~ includes the entire stated day.
- Date-only ~:on~ matches the entire stated day.
- Temporal values define intervals according to their written precision: a date is a complete day, a minute-precision datetime is a complete minute, and a second-precision datetime is a complete second.
- ~:from~ uses the inclusive beginning of its own value's interval. ~:to~ includes its own complete interval, implemented as an exclusive boundary at the next day, minute, or second. ~:on~ matches its value's complete interval.
- RFC 3339 datetimes with explicit offsets preserve the same minute or second precision as written.

Examples:

#+begin_src shell
orgfdb query --json '(scheduled :on today)'
orgfdb query --json '(deadline :to 7)'
orgfdb query --json '(ts-active :from "2026-01-01" :to "2026-12-31")'
orgfdb query --json '(scheduled :from "2026-01-03 14:00" :to "2026-01-03 15:00")'
orgfdb query --json '(planning :from -30 :to today)'
#+end_src

** Relation and Hierarchy Semantics

Public rules for nested relation predicates:

- The outer target determines the returned result kind.
- The nested query filters related rows only.
- Nested queries must use explicit target wrappers.
- Invalid nested targets are validation errors.

Implemented relation directions:

- ~parent~ :: Outer target ~headings~, nested target ~headings~, direction direct parent.
- ~children~ :: Outer target ~headings~, nested target ~headings~, direction direct child.
- ~ancestors~ :: Outer target ~headings~, nested target ~headings~, direction transitive upward.
- ~descendants~ :: Outer target ~headings~, nested target ~headings~, direction transitive downward.
- ~has-link~ :: Outer target ~headings~ or ~files~, nested target ~links~, direction contained link existence.
- ~links-to~ :: Outer target ~headings~ or ~links~, nested target ~headings~ or ~files~, direction outgoing target relation.
- ~linked-from~ :: Outer target ~headings~ or ~links~, nested target ~headings~, ~files~, or ~any~, direction incoming source relation.
- ~source~ :: Outer target ~links~, nested target ~headings~ or ~any~, direction source heading relation.
- ~target~ :: Outer target ~links~, nested target ~headings~, ~files~, or ~any~, direction resolved target relation.

Examples:

#+begin_src shell
orgfdb query --json '(headings (children (headings (todo "NEXT"))))'
orgfdb query --json '(headings (ancestors (headings (tags "project"))))'
orgfdb query --json '(headings (links-to (files (file-title "Beta Index" :exact t))))'
orgfdb query --json '(links (source (headings (title "Query Engine" :exact t))))'
orgfdb query --json '(links (target (files (file-path "notes.org" :exact t))))'
#+end_src

** Includes

Includes enrich output only. They never change which rows match.

- ~path~ :: Valid on all targets.
  Added field: ~node_path~ on result nodes.
  File roots appear as the first path entry.
- ~properties~ :: Valid on ~headings~ and ~files~.
  Added field: ~properties~.
  Raw stored property rows, preserving duplicates and the ~append~ flag.
- ~effective_properties~ :: Valid on ~headings~ and ~files~.
  Added field: ~effective_properties~.
  Resolved effective property values used by property matching.
- ~keywords~ :: Valid on ~headings~ and ~files~.
  Added field: ~keywords~.
  Root/file keyword facts. Heading queries read them through root context where applicable.
- ~links~ :: Valid on ~headings~ and ~files~.
  Added field: ~links~.
  Outgoing included-link objects.
- ~backlinks~ :: Valid on ~headings~ and ~files~.
  Added field: ~backlinks~.
  Incoming included-link objects.
- ~source~ :: Valid on ~links~.
  Added field: ~source~.
  Structured source file/heading context for the matched link.
- ~target~ :: Valid on ~links~.
  Added field: ~target~.
  Structured resolved target context where available.

Included-link objects expose:

- ~id~
- ~source_context~
- ~format~
- ~link_type~
- ~raw~
- ~raw_target~
- ~raw_description~
- ~link_path~
- ~search_option~
- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~
- ~resolution_status~
- ~resolution_diagnostic~
- ~location~
- ~source_path~
- ~source~

** Output Modes

- ~flat~ :: Valid on all targets.
  Returns matched objects only.
- ~outline~ :: Valid on all targets.
  Returns file-root trees. Unmatched ancestor context rows may appear for heading and link queries.

Outline specifics:

- ~headings~ outline:
  - emits file roots as top-level nodes
  - inserts ancestor headings as context where needed
  - sets ~matched = true~ only on matched headings or matched file roots
- ~links~ outline:
  - emits file roots as top-level nodes
  - groups links under the source heading or directly under the file root for level-0 links
  - inserts ancestor heading context when needed
- ~files~ outline:
  - returns matched file roots with ~children: []~
  - does not expand contained headings or links just because ~outline~ was requested

Ordering:

- The response ~includes~ list is normalized to unique sorted values.
- Flat results use deterministic DB/result-shaper ordering.
- Outline children are sorted deterministically by stored location and object type.

** Errors and Exit Codes

Exit codes:

- ~0~ :: success
- ~1~ :: query parse/validation/backend/config/database/output error
- ~2~ :: CLI usage error reported by Clap or missing required ~--json~

User-visible error categories include:

- parse errors such as malformed syntax
- validation errors such as unknown predicates, wrong arity, invalid options, invalid nested targets, or target/predicate mismatches
- backend capability errors such as ~has-text~ without persisted body-text capability
- date resolution errors such as invalid timezone or out-of-range relative offsets
- result-shaping integrity errors such as missing stored rows needed for enrichment
- ordinary DB read failures

Important expected messages:

- ~query currently only supports --json~
- ~unsupported operator: tags-regexp; use (tags ... :regexp t) instead~
- ~has-text requires body text to be available in the database~

* ~orgfdb search --json~

~orgfdb search --json EXPRESSION~ executes a raw SQLite FTS5 ~MATCH~ expression against the trusted derived ~=heading_fts= index and prints canonical heading/file match rows as JSON.

The command is read-only. It does not scan Org files, rebuild the index, repair stale search state, apply migrations, or mutate the database.

Supported options:

- ~--json~ :: required for the stable output mode
- ~--title~ :: restricts the search to the FTS ~=title= column
- ~--body~ :: restricts the search to the FTS ~=body= column
- ~--config PATH~ :: loads ~db_path~ and ~search.fts5_enabled~ before opening the database read-only

~--title~ and ~--body~ are mutually exclusive.

Examples:

#+begin_src shell
orgfdb search --json sqlite
orgfdb search --json --title '"sqlite phrase"'
orgfdb search --json --body 'phrase AND search'
orgfdb search --json 'title:(sqlite) OR body:(search)'
#+end_src

The output is a JSON array ordered deterministically by:

1. ~rank~ ascending
2. ~heading_id~ ascending

Each JSON object exposes these public fields:

- ~heading_id~
- ~path~
- ~title~
- ~line_number~
- ~byte_start~
- ~byte_end~
- ~rank~

Notes:

- ~EXPRESSION~ is raw backend-specific SQLite FTS5 syntax. Supported constructs follow the linked SQLite FTS5 implementation and may include terms, quoted phrases, prefixes, boolean operators, grouping, column filters, and ~NEAR~.
- ~search~ is a convenience command, not Query Model v0. It does not change ~(has-text ...)~ or other query semantics.
- Search matches only through the derived ~=heading_fts= index, but all returned title/path/location fields come from canonical ~=headings= and ~=files= rows.
- The command never reads ~=heading_fts.title= or ~=heading_fts.body= payload values from the contentless FTS table.
- The active config must leave ~search.fts5_enabled = true~. This is permission to use search, not proof that the database contains a trusted index.
- Existing databases built before persisted FTS trust metadata were introduced must be rebuilt once before ~search~ works. The command will instruct the user to run ~orgfdb rebuild~ when the trusted search metadata is missing or stale.
- ~--body~ requires a trusted FTS index that was rebuilt with body indexing enabled. Title-only trusted indexes still support default and ~--title~ searches.
- When ~--title~ or ~--body~ is used, explicit FTS column filters inside ~EXPRESSION~ are rejected so user input cannot broaden the selected scope.

* Link storage contract

Phase 3 stores raw link source facts, and later rebuild-time resolution may populate separate Phase 4 target fields. ~orgfdb links --json~ exposes both sets together without rebuilding, resolving on demand, or mutating the database. Root-attached links are part of the stored data model and remain visible in CLI output, including broken, ambiguous, unresolved, and unsupported rows.
