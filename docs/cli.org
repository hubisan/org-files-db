#+TITLE: CLI Reference
#+STARTUP: showall

This page documents the user-facing ~orgfdb~ commands that are stable enough to treat as repository-local reference material.

* Output format

~headings~, ~links~, ~status~, ~changes~, ~query~, and ~search~ emit JSON by default. ~--format json~ is the canonical explicit form and leaves room for future formats; ~--json~ remains a visible compatibility form. The three forms use the same renderer and produce byte-identical JSON. Supplying more than one format selector, including repeated ~--format~, is a CLI usage error with exit code ~2~.

Read-only database commands (~headings~, ~links~, ~status~, ~changes~, ~query~, and ~search~) require the existing database to use the current schema version. They never migrate an older database. An outdated schema is rejected before command-specific table access with an instruction to run an indexing command to migrate or rebuild the database.

#+begin_src shell
orgfdb query '(todo "NEXT")'
orgfdb query --json '(todo "NEXT")'
orgfdb query --format json '(todo "NEXT")'
#+end_src

* ~orgfdb rebuild~

~orgfdb rebuild --config PATH~ performs a complete rebuild from the configured files and directory roots.

Successful rebuilds persist deterministic identity evidence for every configured directory root in the same transaction as files, headings, links, FTS state, indexing context, and search trust metadata. The evidence contains the configured native logical path, canonical target path, Unix device and inode identity, and recursive mode. A later automatic full reconciliation refuses to continue when a previously committed root is missing, inaccessible, no longer a directory, or has been replaced at the same configured path.

Databases that already contain indexed files, use configured directory roots, and predate source-root evidence require one explicit adoption rebuild:

#+begin_src shell
orgfdb rebuild --config ./org-files-db.toml --accept-source-root-changes
#+end_src

Use ~--accept-source-root-changes~ only after verifying that the currently configured directory roots are the intended replacements. The option accepts their current identities for this manual rebuild, but it does not bypass stability checks while the rebuild runs and it does not imply ~--allow-empty~. If discovery finds no input files and existing indexed rows would be removed, ~--allow-empty~ is still required independently.

Normal rebuilds and watcher startup never accept changed root identities automatically. A root-identity rejection leaves the previously committed database and metadata unchanged.

* ~orgfdb watch~

~orgfdb watch --config PATH~ starts long-running watcher-driven indexing for the configured Org inputs. It is supported on Unix-like systems only.

Startup order is part of the command contract:

1. Load the configured indexing and schema options.
2. Open or initialize the configured SQLite database.
3. Derive and register configured roots, source parents, and canonical target watches from the indexer source universe.
4. Refresh those registrations with an overlapping hand-off.
5. Run full configured-source reconciliation, including committed configured-root identity validation.
6. Print ~watcher ready~ to stderr unless shutdown was already requested, then enter steady-state handling.

If a configured directory is missing, startup stops before readiness and reports the affected path together with the instruction to restore the directory or update the configuration. A reachable directory whose persisted identity changed is reported separately and requires an intentional manual rebuild with ~--accept-source-root-changes~.

The command writes no routine activity to stdout and does not emit a JSON event stream. Lifecycle messages are written to stderr:

- ~watcher ready~ after successful startup reconciliation;
- ~watcher stopping~ after ~SIGINT~ or ~SIGTERM~ is observed;
- ~watcher stopped~ after pending work has been flushed.

#+begin_src shell
orgfdb watch --config ./org-files-db.toml
#+end_src

~SIGINT~ and ~SIGTERM~ stop new event intake and invoke the controller's flush policy. A batch already pending at shutdown becomes immediately eligible without waiting for its debounce deadline. The command exits successfully only after that pending work completes. Fatal source, watch registration, configured-root identity, startup reconciliation, controller, or indexer execution failures are reported on stderr and return exit code ~1~. CLI usage errors continue to return exit code ~2~.

Backend uncertainty, including a native rescan request, a backend error, or overflow of the bounded 1,024-message input buffer, requests full configured-source reconciliation instead of guessing individual mutations. The callback stores only bounded translated messages; oversized path sets also become uncertainty. Before full reconciliation, the runtime validates retained old target identities and the newly derived targets, registers the new targets with an overlapping hand-off, and prepares a fresh indexer source-universe normalizer. Repeated overflow is represented by one bounded marker until the runtime consumes it.

The command does not daemonize itself, install a service, restart automatically, or support Windows service semantics.

* ~orgfdb headings~

~orgfdb headings~ prints stored heading rows from the SQLite database as JSON. It is a database inspection command: it reads persisted facts only and does not analyze the current contents of Org files.

The command is read-only. It does not scan Org files, rebuild files, resolve targets, or mutate the database.

The output is a JSON array ordered deterministically by:

1. ~file_path~
2. ~byte_start~
3. ~id~

Synthetic root rows are included by default, and ~--no-root~ excludes them. Root rows use the synthetic repository conventions: ~level = 0~, ~parent_id = null~, and they represent file/document scope rather than parser-level Org headings.

The JSON objects expose the heading fields used by the current CLI contract:

- ~id~
- ~file_id~
- ~file_path~
- ~parent_id~
- ~level~
- ~line_number~
- ~byte_start~
- ~byte_end~
- ~title~
- ~title_raw~
- ~todo_keyword~
- ~todo_type~
- ~priority~
- ~scheduled_raw~
- ~scheduled_ts~
- ~deadline_raw~
- ~deadline_ts~
- ~closed_raw~
- ~closed_ts~

For real headings, ~title~ is the cleaned semantic title. ~title_raw~ preserves the source title area after the headline stars, including TODO keywords, priorities, and statistics cookies, while still excluding trailing Org tags.
- ~archivedp~
- ~footnote_section_p~
- ~all_tags~

~--include-root~ is retained only as a compatibility no-op. The default output already includes root rows.

If you need the underlying configuration settings for the database path, source file selection, link protocols, TODO keywords, or search options, see [[./config.org][docs/config.org]].

* ~orgfdb links~

~orgfdb links~ prints stored link source facts plus stored resolution snapshot fields from the SQLite database as JSON. It is a database inspection command: it reads persisted facts only and does not analyze the current contents of Org files.

The command is read-only. It does not scan Org files, rebuild files, resolve targets, or mutate the database.

The output is a JSON array ordered deterministically by:

1. ~file_path~
2. ~byte_start~
3. ~id~

Root links are included. For root links, ~heading_level~ is ~0~ and ~heading_path~ is an empty array.

The JSON objects expose these public fields:

- ~file_id~
- ~file_path~
- ~heading_id~
- ~heading_path~
- ~heading_level~
- ~source_context~
- ~format~
- ~link_type~
- ~raw~
- ~raw_target~
- ~raw_description~
- ~path~
- ~search_option~
- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~
- ~resolution_status~
- ~resolution_diagnostic~
- ~byte_start~
- ~byte_end~
- ~line~

The output uses ~link_type~, not a legacy ~type~ field.

Notes:

- ~format~ identifies the source syntax: ~bracket~, ~angle~, or ~plain~.
- ~source_context~ records where the link came from in the indexed Org file, such as normal text or a drawer context.
- ~path~, ~search_option~, ~byte_start~, ~byte_end~, and ~line~ provide editor-jump data from the stored database facts.
- ~path_absolute~, ~target_file_id~, ~target_heading_id~, ~target_custom_id~, ~target_id~, ~resolution_status~, and ~resolution_diagnostic~ mirror the stored resolver-owned DB columns as-is and may be ~null~.
- ~resolution_status = null~ means no resolver pass has populated the row yet.
- ~resolution_status = resolved~, ~broken~, ~unresolved~, ~ambiguous~, and ~unsupported~ reflect the stored Phase 4 outcome.
- File-only links resolve to the target file's synthetic root heading, and file links to indexed files populate ~path_absolute~ and ~target_file_id~.
- Supported file search options are only ~::*Heading~ and ~::#custom-id~; unsupported examples include ~::42~, ~::/regexp/~, and dedicated targets such as ~::target~ or ~::<<target>>~.
- Org ~id:~ links resolve only against indexed non-root headings. External ~org-id-locations~ are not supported, so missing indexed IDs remain ~unresolved~ with ~id not found~.
- The command opens the existing database in read-only mode. If ~--config~ is provided, only the stored ~db_path~ is read from that config file.

* ~orgfdb status~

~orgfdb status~ returns the committed database identity and generation together with the canonical path of the configured SQLite database, without performing indexing or query planning.

#+begin_src shell
orgfdb status --config ./org-files-db.toml --format json
#+end_src

#+begin_src json
{
  "schema_version": 12,
  "database_path": "/home/user/notes/org-files-db.sqlite",
  "database_id": "74f470e2-0354-4ed8-b2e0-e0647e0c706a",
  "generation": 1842,
  "last_changed_at": "2026-08-05T00:42:10Z"
}
#+end_src

~database_path~ is the absolute canonical filesystem path of the database that was opened. Cached clients can use its directory to install file-notification watches for the SQLite main file, ~-wal~, and ~-shm~ files without duplicating config-path resolution.

The command opens the existing configured database read-only. It does not initialize a missing database, migrate an older schema, scan Org files, reconcile sources, resolve links, touch FTS, or update timestamps. An older database must first be opened by a normal indexing command so schema migration can run.

* ~orgfdb changes~

~orgfdb changes~ returns the committed affected-file delta after a cached generation.

#+begin_src shell
orgfdb changes \
  --config ./org-files-db.toml \
  --database-id 74f470e2-0354-4ed8-b2e0-e0647e0c706a \
  --since-generation 1840 \
  --format json
#+end_src

The JSON response contains ~from_generation~, ~to_generation~, ~oldest_available_generation~, ~cache_action~, ~complete~, ~reason~, ~upsert_files~, and ~deleted_files~ in addition to ~schema_version~ and ~database_id~.

~cache_action~ is:

- ~unchanged~ when the requested generation is current;
- ~patch~ when the complete interval is available as exact per-file actions;
- ~rebuild~ when the database identity changed, history is unavailable, or the interval contains full invalidation.

Stable rebuild reasons are ~database-id-changed~, ~history-unavailable~, and ~full-invalidation~. Paths are exact persisted canonical paths and are returned deterministically. A generation newer than the current database is an error.

The command is read-only and performs no query execution. See [[./design/index-generations-and-cached-views.org][Index Generations and Cached Query Views]] for transaction semantics, view patch safety, and the Emacs refresh algorithm.

* ~orgfdb query~

~orgfdb query QUERY~ parses Query Model v0 syntax, validates it against the current query contract, executes it against the existing SQLite database, and prints the shaped JSON response.

The command is strictly read-only. It does not scan Org files, rebuild files, resolve links on demand, apply migrations beyond opening the existing DB read-only, or mutate stored facts.

Execution uses the persisted query stack only:

- Query syntax is parsed by the Query Model v0 parser.
- Validation uses the Query Model v0 semantic validator plus backend capability checks against the opened SQLite database.
- Execution uses the persisted SQLite query layer.
- Output shaping uses the persisted result-enrichment layer.

The normative language contract remains [[./reference/query-model-v0.org][docs/reference/query-model-v0.org]]. This CLI page is the complete user-facing reference for the implemented ~orgfdb query~ command.

** Synopsis

#+begin_src shell
orgfdb query [OPTIONS] QUERY
#+end_src

~QUERY~ is a single Query Model v0 expression. In normal shells, quote the whole expression with single quotes and keep query strings inside it in double quotes.

#+begin_src shell
orgfdb query '(todo "NEXT")'
orgfdb query '(files (file-title "Projects" :exact t))'
orgfdb query '(links (status "broken"))'
#+end_src

Accepted options:

- ~--format FORMAT~ :: Accepted value: ~json~. Default: ~json~.
  This is the canonical explicit output selector.
- ~--json~ :: Compatibility form for ~--format json~.
  It may not be combined with ~--format~ or repeated.
- ~--output~ :: Accepted values: ~flat~, ~outline~.
  Default: ~flat~.
  Repeatable: no.
  Changes output shape only, never matching semantics.
- ~--include~ :: Accepted values: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~, ~source~, ~target~.
  Default: none.
  Repeatable: yes.
  Values may be comma-separated and/or supplied in repeated flags. Duplicates are removed before serialization.
- ~--config PATH~ :: Accepted value: filesystem path.
  Default: none.
  Repeatable: no.
  Loads ~db_path~ and query-time settings such as ~query.timezone~ before opening the DB read-only.

~--include~ validation:

- ~path~ is valid for all targets.
- ~properties~, ~effective_properties~, ~keywords~, ~links~, and ~backlinks~ are valid for ~headings~ and ~files~ output only.
- ~source~ and ~target~ are valid for ~links~ output only.
- Unknown include values are rejected by Clap with exit code ~2~.

** Restricting execution to affected files

~--restrict-files-json PATH_OR_DASH~ adds an owning-file restriction to a structural query. ~PATH_OR_DASH~ is a UTF-8 JSON file containing an array of exact persisted canonical paths, or ~-~ to read that array from standard input.

#+begin_src shell
printf '%s' '["/home/user/notes/a.org","/home/user/notes/b with spaces.org"]' |
  orgfdb query \
    --config ./org-files-db.toml \
    --restrict-files-json - \
    '(headings (not (done)))'
#+end_src

The restriction combines with the query as an additional AND condition without modifying the Query Model expression. It applies to heading, link, and file targets. Duplicate paths are ignored, an empty array returns no rows, and unknown paths return no rows.

This option exists for patching complete cached structural query views after ~orgfdb changes~. It does not make every query view patch-safe. Search views, truncated views, incoming-link or backlink-dependent queries, and cross-file result expansions require a complete rerun. Top-level JSON result rows continue to expose their owning canonical file path independently of displayed view columns.

** Query Grammar Overview

Complete supported top-level forms:

#+begin_src text
(headings EXPR?)
(links EXPR?)
(files EXPR?)

(and EXPR...)
(or EXPR...)
(not EXPR)

(predicate ARG... :option VALUE...)
#+end_src

Important public rules:

- Top-level heading shorthand is supported. Bare heading predicates such as ~(todo "NEXT")~ are equivalent to ~(headings (todo "NEXT"))~.
- Nested relation queries must always use an explicit target wrapper such as ~(links (status "broken"))~ or ~(files (file-path "notes.org"))~.
- Empty target wrappers are supported for implemented targets, for example ~(links)~ or ~(files)~.
- Boolean operators are ordinary query expressions, not predicates:
  - ~(and EXPR...)~ requires all children to match.
  - ~(or EXPR...)~ requires any child to match.
  - ~(not EXPR)~ negates exactly one child expression.
- Strings use double quotes.
- Integers are bare numeric values.
- Boolean options use ~t~ or ~nil~.
- Enum-like keyword values use symbols such as ~:all~ or ~:any~.
- Invalid syntax is a parse error with exit code ~1~.

Examples:

#+begin_src shell
orgfdb query '(and (todo "NEXT") (priority "A"))'
orgfdb query '(headings (not (tags "archive")))'
orgfdb query '(links (source (headings (title "Query Engine" :exact t))))'
orgfdb query '(files)'
#+end_src

** Targets

- ~headings~ ::
  - Returns matched real headings and, when the heading query domain includes file/root objects, those file/root matches as ~kind = "root"~.
  - Bare top-level shorthand: yes.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~.
- ~links~ ::
  - Returns matched links.
  - Bare top-level shorthand: no.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~source~, ~target~.
- ~files~ ::
  - Returns matched files.
  - Bare top-level shorthand: no.
  - Valid output modes: ~flat~, ~outline~.
  - Valid includes: ~path~, ~properties~, ~effective_properties~, ~keywords~, ~links~, ~backlinks~.

Target notes:

- Bare ~(headings)~ returns the complete heading-query domain: all real headings plus one file/root object per indexed file.
- ~headings~ root/file results are always serialized as ~kind = "root"~. The internal level-0 storage rows are never exposed as ~kind = "heading"~ results.
- In flat output, the file/root result sorts before headings from the same file.
- In outline output, the file/root result is the tree root for headings in that file.
- Predicates such as ~title~ may also match the synthetic root/file object when their documented root participation is enabled.
- File predicates on ~headings~ apply to both real headings and file/root objects: real headings inspect their containing file, and matching file/root objects are returned as ~kind = "root"~.
- ~links~ always return link objects. Nested source/target/file/headings relations affect matching only; they do not change the returned object kind.
- ~files~ return file objects and use the file root heading as the storage source for tags, keywords, properties, and file-level links.

** Predicate Option Index

The current public predicate options are:

- ~:exact~ :: 
  - Valid on: ~title~, ~link-target~, ~link-description~, ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~outline-sequence~.
  - Value type: ~t~ or ~nil~.
  - Default: ~nil~.
  - Usually requires exactly one text argument. ~outline-sequence~ applies it per path segment and allows multiple arguments.
- ~:regexp~ ::
  - Valid on: ~title~, ~has-text~, ~tags~, ~property~, ~keyword~, ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~outline-contains~, ~outline-sequence~, ~link-target~, ~link-description~.
  - Value type: ~t~ or ~nil~.
  - Default: ~nil~.
  - Meaning is predicate-specific. SQLite uses Rust regular expressions and matching is case-sensitive unless the pattern says otherwise.
- ~:match~ ::
  - Valid on: ~tags~.
  - Value type: ~:any~ or ~:all~.
  - Default: ~:any~.
  - ~(tags-all ...)~ is a parser alias for ~(tags ... :match :all)~.
- ~:inherit~ ::
  - Valid on: ~tags~, ~property~, ~keyword~ on ~headings~.
  - Value type: ~t~ or ~nil~.
  - Default: ~t~.
  - Invalid on file queries.
- ~:from~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Inclusive lower bound.
- ~:to~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Inclusive query-model upper bound. The complete interval implied by the value is included.
- ~:on~ ::
  - Valid on: ~file-modified~, ~ts~, ~ts-active~, ~ts-inactive~, ~deadline~, ~scheduled~, ~closed~, ~planning~.
  - Value type: date/time value.
  - Default: none.
  - Matches the given day or the given datetime, depending on the value form.

Options are validated per predicate. A supported option on one predicate does not imply support elsewhere.

** Complete Predicate Reference

*** Boolean expressions

- ~(and EXPR...)~ :: Valid on all targets.
  All child expressions must match.
  Example: ~'(and (todo "NEXT") (tags "project"))'~.
- ~(or EXPR...)~ :: Valid on all targets.
  Any child expression may match.
  Example: ~'(or (priority "A") (priority "B"))'~.
- ~(not EXPR)~ :: Valid on all targets.
  Negates exactly one child.
  Example: ~'(not (done))'~.

*** Heading predicates

- ~todo~ :: Syntax: ~(todo [KEYWORD...])~.
  Targets: ~headings~.
  No args means any heading with a TODO keyword. With args, matches any listed TODO keyword. Case-sensitive against stored keyword values.
  Example: ~'(todo "NEXT" "PLAN")'~.
- ~done~ :: Syntax: ~(done)~.
  Targets: ~headings~.
  Matches headings whose TODO type is ~closed~.
  Example: ~'(done)'~.
- ~title~ :: Syntax: ~(title STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~.
  Default is case-insensitive substring matching against normalized heading titles. Matching file/root titles return ~kind = "root"~ nodes.
  Example: ~'(title "Query Engine" :exact t)'~.
- ~has-text~ :: Syntax: ~(has-text STRING... :regexp t|nil)~.
  Targets: ~headings~.
  Matches persisted heading body text. Default is case-insensitive substring matching for all supplied terms. Requires persisted body text capability. With ~:regexp t~, each pattern is matched against the persisted body text using Rust regex syntax.
  Example: ~'(has-text "sqlite" "fts")'~.
- ~level~ :: Syntax: ~(level NUMBER)~, ~(level MIN MAX)~, ~(level COMPARATOR NUMBER)~.
  Targets: ~headings~.
  Matches heading levels. Comparator form uses ~<~, ~<=~, ~>~, or ~>=~.
  Example: ~'(level 1 2)'~.
- ~priority~ :: Syntax: ~(priority VALUE...)~ or ~(priority COMPARATOR VALUE)~.
  Targets: ~headings~.
  Multi-value form is OR. Comparator form supports ~<~, ~<=~, ~>~, and ~>=~ using semantic priority order: ~A > B > C~. Query-time ranks are ~A = 1~, ~B = 2~, and so on through ~Z = 26~; numeric values from ~0~ through ~64~ use their integer rank, so ~A~ and ~1~ match equivalently. The original source value remains stored and returned. Query Model v0 uses this fixed mapping and does not evaluate Emacs priority variables or file-local ~#+PRIORITIES~ declarations.
  Example: ~'(priority > "B")'~ matches ~A~ and ~1~.
- ~tags~ :: Syntax: ~(tags TAG... :inherit t|nil :regexp t|nil :match :any|:all)~.
  Targets: ~headings~, ~files~.
  Heading queries use effective tags by default, including inherited/root tags when present. File queries match tags stored on the file root heading. With ~:regexp t~, each pattern is matched against one effective tag value.
  Example: ~'(tags "project" "urgent" :match :all)'~.
- ~tags-all~ :: Syntax: ~(tags-all TAG... [same options as tags except :match])~.
  Targets: parser alias.
  Readability alias for ~(tags ... :match :all)~. It is normalized before validation.
  Example: ~'(tags-all "project" "urgent")'~.
- ~property~ :: Syntax: ~(property KEY [VALUE] :inherit t|nil :regexp t|nil)~.
  Targets: ~headings~, ~files~.
  With one argument, matches by property key existence. With two, matches key/value. Heading queries use effective properties by default; ~:inherit nil~ restricts to direct rows. File queries are always direct root/file property matches and reject ~:inherit~. With ~:regexp t~, the pattern is matched against the resolved effective property value.
  Local effective values use one source-independent rule for property drawer rows and file-level ~#+PROPERTY~ rows: the last non-append definition is the base value, and all append definitions for the same key are appended in source order even if they appear before or between non-append definitions.
  Compatibility note: this intentionally differs from Org for some repeated file-level ~#+PROPERTY~ sequences mixed with append rows. For example, orgfdb resolves
  ~#+PROPERTY: KEYWORD_RESET old~, ~#+PROPERTY: KEYWORD_RESET+ appended-before-reset~, ~#+PROPERTY: KEYWORD_RESET replacement~, ~#+PROPERTY: KEYWORD_RESET+ appended-after-reset~
  as ~replacement appended-before-reset appended-after-reset~, while Org may resolve the same file-level sequence as ~replacement appended-after-reset~.
  This incompatibility is deliberate so drawer properties and file-level keyword properties follow one uniform query-resolution rule. Raw ~properties~ output still preserves the original ~source~ and ~append~ metadata for each stored row.
  Example: ~'(property "CATEGORY" "work")'~.
- ~keyword~ :: Syntax: ~(keyword KEY [VALUE] :regexp t|nil :inherit t|nil)~.
  Targets: ~headings~, ~files~.
  Matches root/file keyword facts. Heading queries inherit keywords from the containing file by default; ~:inherit nil~ checks only the candidate heading. Because document keywords are currently stored on the synthetic file heading, local-only matching normally returns only the file result. File queries always match their root/file keywords and reject ~:inherit~. With ~:regexp t~, the pattern applies to the keyword value, not the keyword name.
  Example: ~'(keyword "AUTHOR" "Alice")'~.
- ~file-name~ :: Syntax: ~(file-name STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~files~.
  Matches the containing file name. On ~headings~, matching file/root objects are also returned as ~kind = "root"~.
  Example: ~'(file-name "notes.org" :exact t)'~.
- ~file-path~ :: Syntax: ~(file-path STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the containing file path. A value of ~~ or beginning with ~~/~ expands its leading ~~ from the process ~HOME~ environment variable before substring, exact, or regexp matching. Named-user forms such as ~~alice/~ are not supported. Expansion does not invoke a shell, resolve symlinks, canonicalize paths, or require them to exist; stored and returned paths remain unchanged. On ~headings~, matching file/root objects are also returned as ~kind = "root"~. On links this applies through the source file relation.
  Example: ~'(file-path "~/projects/notes.org" :exact t)'~.
- ~file-dir~ :: Syntax: ~(file-dir STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the containing directory path. A value of ~~ or beginning with ~~/~ expands its leading ~~ from the process ~HOME~ environment variable before substring, exact, or regexp matching. Named-user forms such as ~~alice/~ are not supported. Expansion does not invoke a shell, resolve symlinks, canonicalize paths, or require them to exist; stored and returned paths remain unchanged. On ~headings~, matching file/root objects are also returned as ~kind = "root"~. On links this applies through the source file relation.
  Example: ~'(file-dir "~/projects" :exact t)'~.
- ~file-title~ :: Syntax: ~(file-title STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~, ~links~, ~files~.
  Matches the effective file/root title. On ~headings~, this evaluates both real headings by containing file title and file/root objects themselves; it is different from ~title~, which can match real headings and, by default, the root object itself.
  Example: ~'(file-title "Projects" :exact t)'~.
- ~file-modified~ :: Syntax: ~(file-modified :from DATE :to DATE :on DATE)~.
  Targets: ~headings~, ~files~.
  Matches persisted file modification timestamps. On ~headings~, matching file/root objects are also returned as ~kind = "root"~. Relative dates such as ~today~ or integer day offsets are resolved before SQL execution.
  Example: ~'(file-modified :from -7 :to today)'~.
- ~outline-contains~ :: Syntax: ~(outline-contains STRING... :regexp t|nil)~.
  Targets: ~headings~.
  Matches headings whose complete outline path contains all supplied components somewhere in the path. The synthetic file/root title is the first component. With ~:regexp t~, each pattern is matched against individual outline components. No ~:exact~ option.
  Example: ~'(outline-contains "Project" "Query")'~.
- ~outline-sequence~ :: Syntax: ~(outline-sequence STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~headings~.
  Matches contiguous components of the complete outline path in order. The synthetic file/root title is the first component. With ~:exact t~, each supplied segment must exactly match the corresponding path component. With ~:regexp t~, each pattern is matched against the corresponding outline component.
  Example: ~'(outline-sequence "Projects" "Org database" :exact t)'~.
- ~ts~ :: Syntax: ~(ts :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches any stored timestamp row associated with the heading.
  Example: ~'(ts :on today)'~.
- ~ts-active~ :: Syntax: ~(ts-active :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Like ~ts~, but only active timestamps.
  Example: ~'(ts-active :from "2026-01-01" :to "2026-12-31")'~.
- ~ts-inactive~ :: Syntax: ~(ts-inactive :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Like ~ts~, but only inactive timestamps.
  Example: ~'(ts-inactive :from -30 :to today)'~.
- ~deadline~ :: Syntax: ~(deadline :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading deadline metadata.
  Example: ~'(deadline :to 7)'~.
- ~scheduled~ :: Syntax: ~(scheduled :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading scheduled metadata.
  Example: ~'(scheduled :on today)'~.
- ~closed~ :: Syntax: ~(closed :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches persisted heading closed metadata.
  Example: ~'(closed :from -7)'~.
- ~planning~ :: Syntax: ~(planning :from DATE :to DATE :on DATE)~.
  Targets: ~headings~.
  Matches any of ~scheduled~, ~deadline~, or ~closed~.
  Example: ~'(planning :from today :to 7)'~.
- ~parent~ :: Syntax: ~(parent)~ or ~(parent (headings EXPR))~.
  Targets: ~headings~.
  Checks exactly one level upward: the direct parent only. The direct parent is also an ancestor, but grandparents do not match. The synthetic root is the parent of top-level Org headings and has no parent itself.
  Example: ~'(parent (headings (level 0)))'~ matches top-level Org headings.
- ~children~ :: Syntax: ~(children)~ or ~(children (headings EXPR))~.
  Targets: ~headings~.
  Checks exactly one level downward: direct children only. Grandchildren do not match. Direct children are also descendants, and the synthetic root has top-level Org headings as children.
  Example: ~'(children (headings (todo "NEXT")))'~.
- ~ancestors~ :: Syntax: ~(ancestors)~ or ~(ancestors (headings EXPR))~.
  Targets: ~headings~.
  Checks one or more strict levels upward. It includes the direct parent and every higher ancestor, including the synthetic root for every real heading; a heading never matches itself.
  Example: ~'(ancestors (headings (level 0)))'~ matches every real heading in a file.
- ~descendants~ :: Syntax: ~(descendants)~ or ~(descendants (headings EXPR))~.
  Targets: ~headings~.
  Checks one or more strict levels downward. It includes direct children and deeper descendants; a heading never matches itself. A matching descendant makes every strict ancestor, including the synthetic root, eligible as an outer result.
  Example: ~'(descendants (headings (todo "WAITING")))'~.
- ~has-link~ :: Syntax: ~(has-link)~ or ~(has-link (links EXPR))~.
  Targets: ~headings~, ~files~.
  Zero-arg form matches objects containing any stored link. Nested form filters by contained links. File queries include preamble/root links.
  Example: ~'(has-link (links (link-type "file")))'~.
- ~links-to~ :: Syntax: ~(links-to (headings EXPR))~ or ~(links-to (files EXPR))~.
  Targets: ~headings~, ~links~.
  Matches objects that link to a target heading or file matching the nested query. The matched object is still the outer heading or link.
  Example: ~'(links-to (files (file-title "Beta Index" :exact t)))'~.
- ~linked-from~ :: Syntax: ~(linked-from any)~, ~(linked-from (headings EXPR))~, ~(linked-from (files EXPR))~.
  Targets: ~headings~, ~links~.
  Matches objects that have incoming links from the nested source. ~any~ means any incoming link.
  Example: ~'(linked-from (headings (property "CUSTOM_ID" "query-model" :inherit nil)))'~.

**** Hierarchy depth examples

The following single-file outline distinguishes direct from transitive relations:

#+begin_src org
,#+TITLE: hierarchy-example

,* Parent
,** Child
,*** Grandchild
#+end_src

- ~(parent (headings (title "Parent")))~ matches ~Child~, not ~Grandchild~; only the direct parent is checked.
- ~(children (headings (title "Grandchild")))~ matches ~Child~, not ~Parent~; only direct children are checked.
- ~(ancestors (headings (title "Parent")))~ matches both ~Child~ and ~Grandchild~ because it checks every strict ancestor.
- ~(descendants (headings (title "Grandchild")))~ matches both ~Child~ and ~Parent~ because it checks every strict descendant.

Relations never cross file boundaries. A heading never matches itself through ~ancestors~ or ~descendants~. ~(parent (headings (level 0)))~ matches all real top-level headings, while ~(ancestors (headings (level 0)))~ matches every real heading; a ~descendants~ query can return the synthetic root when a matching real heading is below it.

*** Link predicates

- ~link-type~ :: Syntax: ~(link-type TYPE...)~.
  Targets: ~links~.
  OR-matches stored link types.
  Example: ~'(links (link-type "file" "id"))'~.
- ~link-target~ :: Syntax: ~(link-target STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~links~.
  Matches stored raw target text with substring, regexp, or exact semantics.
  Example: ~'(links (link-target "notes.org" :exact t))'~.
- ~link-description~ :: Syntax: ~(link-description STRING... :regexp t|nil :exact t|nil)~.
  Targets: ~links~.
  Matches stored raw description text.
  Example: ~'(links (link-description "Project.*" :regexp t))'~.
- ~has-description~ :: Syntax: ~(has-description)~.
  Targets: ~links~.
  Matches links with any stored description.
  Example: ~'(links (has-description))'~.
- ~status~ :: Syntax: ~(status STATUS...)~.
  Targets: ~links~.
  Matches one or more persisted resolution statuses. Supported values are ~resolved~, ~broken~, ~unresolved~, ~ambiguous~, and ~unsupported~; a ~null~ status means no resolver pass has populated the row yet.
  Example: ~'(links (status "broken" "unresolved"))'~.

**** Link resolution statuses

- ~resolved~ :: Exactly one indexed target was found. Only resolved links can match structured ~(target (headings ...))~ or ~(target (files ...))~ queries.
- ~broken~ :: The link is expected to resolve to an indexed target, but no valid target exists.
- ~unresolved~ :: Resolution was not attempted or there was not enough information to resolve the link.
- ~ambiguous~ :: Multiple possible indexed targets were found and no unique target could be selected.
- ~unsupported~ :: The link type or target form is not supported by the resolver.

Use ~status~ to inspect each non-resolved outcome; structured ~target~ queries do not match ~broken~, ~unresolved~, ~ambiguous~, or ~unsupported~ links.

#+begin_src lisp
(links (status "resolved"))
(links (status "broken"))
(links (status "unresolved"))
(links (status "ambiguous"))
(links (status "unsupported"))
#+end_src

- ~source~ :: Syntax: ~(source :any)~, ~(source (headings EXPR))~, or ~(source (files EXPR))~.
  Targets: ~links~.
  Matches links by their indexed source location. Use a nested ~headings~ query for heading sources or a nested ~files~ query for containing source-file filters; ~:any~ means any indexed source.
  Example: ~'(links (source (files (file-name "linked-from.org" :exact t))))'~.
- ~target~ :: Syntax: ~(target :any)~, ~(target (headings EXPR))~, ~(target (files EXPR))~.
  Targets: ~links~.
  Matches links by resolved target relation; ~:any~ means any resolved indexed target.
  Example: ~'(links (target (files (file-path "notes.org" :exact t))))'~.
- ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~file-modified~ :: Not directly valid for ~links~.
  Filter link results by their containing source file with a nested ~files~ query, for example ~'(links (source (files (file-title "Projects" :exact t))))'~.
- ~links-to~, ~linked-from~ :: Not valid for ~links~; they target ~headings~ and ~files~ only.
  Use ~source~ to filter link origins and ~target~ to filter resolved link destinations when returning link objects.

*** File predicates

- ~file-name~, ~file-path~, ~file-dir~, ~file-title~, ~file-modified~ :: Same syntax as above.
  Targets: ~files~.
  Direct file metadata predicates.
  Example: ~'(files (file-path ".*/projects/.*\\.org" :regexp t))'~.
- ~keyword~ :: Syntax: ~(keyword KEY [VALUE] :regexp t|nil)~.
  Targets: ~files~.
  Matches root/file keyword facts.
  Example: ~'(files (keyword "TITLE" "Proj.*" :regexp t))'~.
- ~property~ :: Syntax: ~(property KEY [VALUE] :regexp t|nil)~.
  Targets: ~files~.
  Matches direct root/file property facts only. ~:inherit~ is invalid in file queries.
  Example: ~'(files (property "CATEGORY" "work"))'~.
- ~tags~ / ~tags-all~ :: Same syntax as above, without ~:inherit~.
  Targets: ~files~.
  Matches tags stored on the synthetic file root heading. ~:match :all~ and ~:regexp~ are supported.
  Example: ~'(files (tags "project" "archive" :match :all))'~.
- ~has-link~ :: Syntax: ~(has-link)~ or ~(has-link (links EXPR))~.
  Targets: ~files~.
  Matches files by contained links, including preamble/root links.
  Example: ~'(files (has-link (links (status "broken"))))'~.

** Root and File Matching Semantics

Synthetic root/file behavior matters most for heading queries:

- Every indexed file has a synthetic level-0 heading in storage.
- Every heading predicate is evaluated against the same heading-query domain: real headings plus the synthetic file/root object.
- When a heading query matches the root/file object, the JSON result is emitted as ~kind = "root"~, not ~kind = "heading"~.
- Matching file/root results expose ~level = 0~.
- This is why a heading query may legitimately return root nodes.

Important distinctions:

- ~title~ on ~headings~:
  - matches real headings
  - may also match the effective file/root title
  - returns a file node when the root/file object is the match
- ~file-title~:
  - filters by the containing file title
  - on ~headings~, still returns heading results unless the outer target is ~files~
- ~files~ target:
  - directly returns file nodes
  - never returns heading nodes

Examples:

#+begin_src shell
orgfdb query '(headings (title "Alpha Index" :exact t))'
orgfdb query '(headings (property "CATEGORY" "work"))'
orgfdb query '(headings (file-title "Alpha Index" :exact t))'
orgfdb query '(files (file-title "Alpha Index" :exact t))'
#+end_src

** Timestamp Semantics

Implemented date/time value forms:

- ISO-like date strings such as ~"2026-01-03"~
- ISO-like date-time strings such as ~"2026-01-03 09:15"~
- ~today~
- integer day offsets such as ~-7~, ~0~, or ~7~

Resolution and boundary rules:

- Relative values are resolved before SQL execution.
- The effective timezone is configured ~query.timezone~, or the current local system timezone when it is omitted.
- ~file-modified~ stores absolute Unix instants. Its date-only values describe a calendar day in the effective timezone, and offset-free datetimes are interpreted in that timezone before matching.
- ~file-modified~ accepts RFC 3339 datetimes with an explicit offset as absolute instants. Nonexistent or ambiguous offset-free local datetimes fail clearly; use an explicit offset for an ambiguous time.
- Org planning and generic timestamp values remain timezone-naive in Query Model v0. Explicit dates and datetimes are compared as written and are not shifted through ~query.timezone~; the timezone only chooses the calendar date for ~today~ and integer day offsets.
- Date-only ~:from~ is inclusive from the start of that day.
- Date-only ~:to~ includes the entire stated day.
- Date-only ~:on~ matches the entire stated day.
- Temporal values define intervals according to their written precision: a date is a complete day, a minute-precision datetime is a complete minute, and a second-precision datetime is a complete second.
- ~:from~ uses the inclusive beginning of its own value's interval. ~:to~ includes its own complete interval, implemented as an exclusive boundary at the next day, minute, or second. ~:on~ matches its value's complete interval.
- RFC 3339 datetimes with explicit offsets preserve the same minute or second precision as written.

Examples:

#+begin_src shell
orgfdb query '(scheduled :on today)'
orgfdb query '(deadline :to 7)'
orgfdb query '(ts-active :from "2026-01-01" :to "2026-12-31")'
orgfdb query '(scheduled :from "2026-01-03 14:00" :to "2026-01-03 15:00")'
orgfdb query '(planning :from -30 :to today)'
#+end_src

** Relation and Hierarchy Semantics

Public rules for nested relation predicates:

- The outer target determines the returned result kind.
- The nested query filters related rows only.
- Nested queries must use explicit target wrappers.
- Nested ~(headings ...)~ relation queries use the complete heading domain, including synthetic level-0 file/root objects. When an outer heading query returns one of those matches, it remains ~kind = "root"~.
- Invalid nested targets are validation errors.

Implemented relation directions:

- ~parent~ :: Outer target ~headings~, nested target ~headings~, direction direct parent.
- ~children~ :: Outer target ~headings~, nested target ~headings~, direction direct child.
- ~ancestors~ :: Outer target ~headings~, nested target ~headings~, direction transitive upward.
- ~descendants~ :: Outer target ~headings~, nested target ~headings~, direction transitive downward.
- ~has-link~ :: Outer target ~headings~ or ~files~, nested target ~links~, direction contained link existence.
- ~links-to~ :: Outer target ~headings~ or ~files~, nested target ~headings~ or ~files~, direction outgoing target relation.
- ~linked-from~ :: Outer target ~headings~ or ~files~, nested target ~headings~, ~files~, or ~any~, direction incoming source relation.
- ~source~ :: Outer target ~links~, nested target ~headings~, ~files~, or ~any~, direction source location relation.
- ~target~ :: Outer target ~links~, nested target ~headings~, ~files~, or ~any~, direction resolved target relation.

Examples:

#+begin_src shell
orgfdb query '(headings (children (headings (todo "NEXT"))))'
orgfdb query '(headings (ancestors (headings (tags "project"))))'
orgfdb query '(headings (links-to (files (file-title "Beta Index" :exact t))))'
orgfdb query '(links (source (headings (title "Query Engine" :exact t))))'
orgfdb query '(links (target (files (file-path "notes.org" :exact t))))'
#+end_src

** Output Modes

- ~flat~ :: Valid on all targets.
  Returns matched objects only.
- ~outline~ :: Valid on all targets.
  Returns file-root trees. Unmatched ancestor context rows may appear for heading and link queries.

Outline specifics:

- ~headings~ outline:
  - emits file roots as top-level nodes
  - inserts ancestor headings as context where needed
  - sets ~matched = true~ only on matched headings or matched file roots
- ~links~ outline:
  - emits file roots as top-level nodes
  - groups links under the source heading or directly under the file root for level-0 links
  - inserts ancestor heading context when needed
- ~files~ outline:
  - returns matched file roots with ~children: []~
  - does not expand contained headings or links just because ~outline~ was requested

Ordering:

- The response ~includes~ list is normalized to unique sorted values.
- Flat results use deterministic DB/result-shaper ordering.
- Outline children are sorted deterministically by stored location and object type.

* ~orgfdb search~

~orgfdb search EXPRESSION~ executes a raw SQLite FTS5 ~MATCH~ expression against the trusted derived ~=heading_fts= index and prints ranked canonical heading/root results as JSON.

The command is read-only. It does not scan Org files, rebuild the index, repair stale search state, apply migrations, or mutate the database.

** Search scope

Without a scope option, the expression searches both indexed columns:

- ~title~
- ~body~

Supported options:

- ~--format FORMAT~ :: Accepted value: ~json~. Default: ~json~.
  This is the canonical explicit output selector.
- ~--json~ :: Compatibility form for ~--format json~.
  It may not be combined with ~--format~ or repeated.
- ~--title~ :: Restricts the complete expression to the FTS ~=title= column.
- ~--body~ :: Restricts the complete expression to the FTS ~=body= column.
- ~--config PATH~ :: Loads ~db_path~ and ~search.fts5_enabled~ before opening the database read-only.

~--title~ and ~--body~ are mutually exclusive.

Examples:

#+begin_src shell
# Search title and body.
orgfdb search sqlite

# Search only the title column.
orgfdb search --title sqlite

# Search only the body column.
orgfdb search --body sqlite
#+end_src

Without ~--title~ or ~--body~, column filters may be placed directly in the FTS5 expression:

#+begin_src shell
# The title must contain sqlite.
orgfdb search 'title:sqlite'

# The body must contain alphaquartz.
orgfdb search 'body:alphaquartz'

# Both conditions must match the same result.
orgfdb search 'title:sqlite AND body:alphaquartz'

# Either condition may match.
orgfdb search 'title:sqlite OR body:alphaquartz'

# Search explicitly in either indexed column.
orgfdb search '{title body}:sqlite'
#+end_src

When ~--title~ or ~--body~ is used, explicit column filters inside ~EXPRESSION~ are rejected. This prevents the expression from broadening the scope selected by the command-line option.

** FTS5 expression syntax

~EXPRESSION~ uses SQLite FTS5 syntax. It is not a regular expression and does not use shell glob syntax.

*** Terms

A plain term searches for a complete token:

#+begin_src shell
orgfdb search 'sqlite'
orgfdb search 'title:sqlite'
#+end_src

A search for ~alpha~ does not normally match ~alphaquartz~, because these are different tokens.

Search is normally case-insensitive according to the configured FTS5 tokenizer:

#+begin_src shell
orgfdb search 'sqlite'
orgfdb search 'SQLITE'
#+end_src

Punctuation is handled by the tokenizer. Text such as ~alpha-quartz~, ~alpha/quartz~, or ~alpha.quartz~ may therefore be indexed as multiple tokens rather than as one literal string.

*** Prefixes

Append ~*~ to a token to match all tokens beginning with that prefix:

#+begin_src shell
orgfdb search 'alpha*'
orgfdb search 'body:alpha*'
orgfdb search 'title:sql* AND body:alpha*'
#+end_src

~alpha*~ may match tokens such as:

- ~alpha~
- ~alphabet~
- ~alphaquartz~
- ~alphanumeric~

The ~*~ operator matches only from the beginning of a token.

These are not supported as general wildcard or substring searches:

#+begin_src text
alpha.*
*quartz
*quartz*
alph?quartz
#+end_src

In particular:

- ~alpha.*~ is regular-expression syntax, not FTS5 syntax.
- ~*quartz~ cannot search by token suffix.
- ~*quartz*~ cannot search for an arbitrary substring.
- ~?~ is not a single-character wildcard.

Place the prefix operator outside quoted text. This is reliable:

#+begin_src text
alpha*
#+end_src

This may not behave as expected because the tokenizer can consume or discard the ~*~ inside the quoted string:

#+begin_src text
"alpha*"
#+end_src

*** Phrases

Use double quotes when tokens must occur consecutively and in the specified order:

#+begin_src shell
orgfdb search '"full text search"'
orgfdb search 'title:"sqlite database"'
orgfdb search 'body:"alpha quartz"'
#+end_src

The phrase:

#+begin_src text
"alpha quartz"
#+end_src

matches a consecutive ~alpha~ token followed immediately by a ~quartz~ token. It does not merely require both tokens to occur somewhere in the same text.

Phrase components can also be joined explicitly with ~+~:

#+begin_src shell
orgfdb search 'alpha + quartz'
orgfdb search 'alpha + quart*'
#+end_src

The second expression matches a phrase beginning with ~alpha~ followed by a token whose prefix is ~quart~.

*** Boolean operators

FTS5 supports the uppercase operators:

- ~AND~ :: Both expressions must match.
- ~OR~ :: At least one expression must match.
- ~NOT~ :: The left expression must match and the right expression must not match.

Examples:

#+begin_src shell
orgfdb search 'sqlite AND database'
orgfdb search 'sqlite OR postgres'
orgfdb search 'sqlite NOT deprecated'
orgfdb search 'title:sqlite AND body:alpha*'
orgfdb search '(sqlite OR database) AND body:index*'
#+end_src

The operator names must be uppercase to be interpreted as operators. Lowercase words such as ~and~ or ~or~ are ordinary search terms.

Whitespace between terms implies ~AND~:

#+begin_src text
sqlite database
#+end_src

is equivalent to:

#+begin_src text
sqlite AND database
#+end_src

Use parentheses whenever an expression combines ~AND~, ~OR~, and ~NOT~. FTS5 operator precedence is not identical to that of many programming languages.

For example:

#+begin_src text
(sqlite OR postgres) AND index
#+end_src

means that either ~sqlite~ or ~postgres~ must match, and ~index~ must also match.

By contrast:

#+begin_src text
sqlite OR postgres AND index
#+end_src

is interpreted according to FTS5 precedence and may not express the intended grouping.

*** Column filters

A column filter restricts a term, phrase, proximity expression, or grouped expression to an indexed column:

#+begin_src shell
orgfdb search 'title:sqlite'
orgfdb search 'body:"full text search"'
orgfdb search 'title:(sqlite OR database)'
orgfdb search 'body:(alpha* AND quartz)'
#+end_src

Use braces to search a set of columns:

#+begin_src shell
orgfdb search '{title body}:sqlite'
orgfdb search '{title body}:(sqlite AND index*)'
#+end_src

Because ~=heading_fts= contains only ~=title= and ~=body=, an unqualified expression already searches both:

#+begin_src shell
orgfdb search 'sqlite'
#+end_src

is normally preferable to:

#+begin_src shell
orgfdb search '{title body}:sqlite'
#+end_src

Use explicit column filters when different conditions must apply to different fields:

#+begin_src shell
orgfdb search 'title:sqlite AND body:alpha*'
#+end_src

*** Proximity with ~NEAR~

~NEAR~ requires phrases to occur within a limited token distance:

#+begin_src shell
orgfdb search 'NEAR(sqlite index)'
orgfdb search 'NEAR(sqlite index, 5)'
orgfdb search 'body:NEAR("query model" sqlite, 10)'
#+end_src

The optional number specifies the maximum allowed separation according to FTS5 token positions. When omitted, SQLite FTS5 uses its default distance.

~NEAR~ is useful when requiring both terms with ~AND~ would be too broad:

#+begin_src text
sqlite AND index
#+end_src

requires both terms somewhere in the indexed result, whereas:

#+begin_src text
NEAR(sqlite index, 5)
#+end_src

requires them to occur close to each other.

*** Combining constructs

FTS5 constructs can be combined:

#+begin_src shell
# Exact phrase in the title.
orgfdb search 'title:"sqlite database"'

# Title token plus body prefix.
orgfdb search 'title:sqlite AND body:alpha*'

# One of two title terms and a required body term.
orgfdb search 'title:(sqlite OR database) AND body:index'

# Phrase or prefix in either column.
orgfdb search '"full text search" OR alpha*'

# Nearby terms in the body, excluding deprecated results.
orgfdb search 'body:NEAR(sqlite index, 5) NOT body:deprecated'
#+end_src

Shell quoting is recommended so spaces, parentheses, ~*~, and quotation marks reach ~orgfdb~ unchanged:

#+begin_src shell
orgfdb search 'title:sqlite AND body:alpha*'
orgfdb search 'title:"full text search"'
#+end_src

** Indexed title semantics

The FTS ~=title= column contains source-oriented headline text:

- ~=headings.title_raw= when available
- otherwise the effective canonical ~=headings.title=

For real headings, ~title_raw~ may contain:

- the TODO keyword
- a priority cookie such as ~[#A]~
- the source title text
- a statistics cookie such as ~[2/5]~ or ~[50%]~

Trailing Org tags are excluded because they are not part of ~title_raw~.

For example:

#+begin_src org
,* NEXT [#A] Improve search documentation [2/5] :docs:
#+end_src

may be found through textual title searches for:

#+begin_src shell
orgfdb search --title NEXT
orgfdb search --title Improve
orgfdb search --title documentation
#+end_src

The trailing tag ~docs~ is not indexed as part of the FTS title merely because it occurs in the headline.

Priority and statistics cookies are tokenized by FTS5. Their punctuation should not be assumed to remain part of one searchable token. Exact structured semantics must use Query Model v0 predicates instead.

The distinction is intentional:

- ~search --title~ searches source-oriented FTS title text.
- Query Model v0 ~(title ...)~ matches the normalized semantic title.
- ~(todo ...)~, ~(priority ...)~, and ~(tags ...)~ provide exact structured matching.

** Output

The output is a JSON array ordered deterministically by:

1. ~rank~ ascending
2. canonical heading ~id~ ascending

Each JSON object is a canonical flat heading/root result plus ~rank~. It exposes:

- ~kind~ :: ~root~ for a synthetic level-0 file root, or ~heading~ for a real heading.
- ~matched~ :: Always ~true~.
- ~id~, ~file_id~, ~parent_id~, ~level~
- ~title~, ~title_raw~
- ~todo_keyword~, ~todo_type~, ~priority~
- ~scheduled_raw~, ~scheduled_ts~
- ~deadline_raw~, ~deadline_ts~
- ~closed_raw~, ~closed_ts~
- ~archivedp~, ~footnote_section_p~, ~all_tags~
- ~location~ :: ~file_path~, ~line~, ~byte_start~, and ~byte_end~.
- ~rank~ :: The only search-specific field.

~rank~ is an FTS5 relevance value. Lower values sort before higher values. Numeric rank values may change after rebuilding the index or changing indexed text, even when the public JSON shape remains unchanged.

** Behaviour and limitations

- ~EXPRESSION~ is passed as raw backend-specific SQLite FTS5 syntax.
- ~search~ is a convenience command, not part of Query Model v0.
- It does not change ~(has-text ...)~ or any other query semantics.
- Search matches only through the derived ~=heading_fts= index, including canonical level-0 file roots.
- Search retrieves only matching heading IDs and ranks from FTS.
- All public heading/root fields come from canonical ~=headings= and ~=files= rows.
- The command never reads ~=heading_fts.title= or ~=heading_fts.body= payload values from the contentless FTS table.
- TODO keywords, tags, priorities, and planning metadata are returned as canonical metadata but are not separate FTS columns.
- A textual FTS match is not equivalent to an exact structured metadata match.
- Use Query Model v0 predicates to combine body text with TODO, tag, property, keyword, timestamp, or other structured conditions.
- The active configuration must leave ~search.fts5_enabled = true~. This permits search but does not prove that the database contains a trusted index.
- Existing databases built before persisted FTS trust metadata, level-0 roots, or FTS contract version ~3~ must be rebuilt once before ~search~ works.
- When trusted search metadata is missing or stale, the command instructs the user to run ~orgfdb rebuild~.
- ~--body~ requires a trusted FTS index rebuilt with body indexing enabled.
- A trusted title-only index still supports default and ~--title~ searches, but its default search can match only indexed title content.
- Root titles are indexed in ~=title=.
- Root preamble text is indexed only in ~=body= when body indexing is enabled.
- Synthetic roots previously emitted as ~kind = "file"~ now emit ~kind = "root"~. Actual ~(files ...)~ results remain ~kind = "file"~.
