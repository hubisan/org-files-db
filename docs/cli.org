#+TITLE: CLI Reference
#+STARTUP: showall

This page documents the current user-facing ~orgfdb~ commands. It describes command syntax and command-specific behavior.

Read [[./reference/query-language.org][Structural Query Language]] for query predicates. Read [[./reference/query-json.org][Query JSON Contract]] for structural query response fields.

* General output rules

These read-only commands emit JSON by default:

- ~headings~
- ~links~
- ~status~
- ~changes~
- ~query~
- ~search~

The ~view register~, ~view show~, and ~view remove~ commands also emit JSON. These commands do not accept output-format options.

~view read~ emits the cached ~presentation-json~ payload directly. It does not accept an output-format option.

For read-only commands, use ~--format json~ as the explicit machine-readable form. ~--json~ is a compatibility form for the same output.

#+begin_src shell
orgfdb query '(headings)'
orgfdb query --json '(headings)'
orgfdb query --format json '(headings)'
#+end_src

Do not combine ~--json~ with ~--format~. Clap reports conflicting or invalid CLI syntax with exit code ~2~.

Current JSON output is pretty-printed and ends with a newline.

* Configuration selection

~rebuild~, ~watch~, and all ~view~ subcommands require ~--config PATH~.

Read-only commands accept an optional ~--config PATH~. If this option is absent, they use the default ~org-files-db.sqlite~ database path.

If ~--config PATH~ is present, relative paths in that file use the configuration file directory as their base.

Read [[./config.org][Configuration Reference]] for all supported configuration keys.

* Read-only database behavior

~headings~, ~links~, ~status~, ~changes~, ~query~, and ~search~ open an existing database in read-only mode.

These commands do not initialize a missing database. They also do not apply schema migrations.

A read-only command rejects a database whose schema version is not current. Run an indexing command to migrate or rebuild that database first.

* ~orgfdb rebuild~

~rebuild~ reconciles the complete configured source set and writes a complete index state.

** Synopsis

#+begin_src shell
orgfdb rebuild --config PATH [--allow-empty] [--accept-source-root-changes]
#+end_src

** Options

- ~--config PATH~ selects the required configuration file.
- ~--allow-empty~ permits an intentional empty-source rebuild that removes existing indexed rows.
- ~--accept-source-root-changes~ accepts current configured directory-root identities for this manual rebuild.

The two safety options are independent. ~--accept-source-root-changes~ does not imply ~--allow-empty~.

** Source-root identity

The index stores identity evidence for configured directory roots. This protects automatic reconciliation from an unexpected directory replacement.

A manual rebuild rejects a changed stored root identity by default. Inspect the configured root before you accept the new identity.

After you verify the replacement, run:

#+begin_src shell
orgfdb rebuild \
  --config ./org-files-db.toml \
  --accept-source-root-changes
#+end_src

A failed root-identity check leaves the previous committed database state unchanged.

** Empty-source protection

A normal rebuild stops if discovery finds no sources and the operation erases an existing index.

If an empty source set is intentional, run:

#+begin_src shell
orgfdb rebuild \
  --config ./org-files-db.toml \
  --allow-empty
#+end_src

Exclusions that intentionally remove all sources follow their documented exclusion semantics. Read [[./config.org][Configuration Reference]] for details.

* ~orgfdb watch~

~watch~ keeps the configured index current with filesystem notifications and incremental reconciliation.

** Synopsis

#+begin_src shell
orgfdb watch --config PATH
#+end_src

~watch~ is supported on Unix-like systems only. It runs in the foreground.

** Startup

The watcher loads configuration, prepares watches, and performs a configured-source reconciliation before it becomes ready.

After successful startup, it writes:

#+begin_example
watcher ready
#+end_example

to stderr.

A missing configured directory stops startup. A changed configured-root identity also stops automatic reconciliation.

Use a verified manual ~rebuild --accept-source-root-changes~ when a root replacement is intentional.

** Shutdown

~SIGINT~ and ~SIGTERM~ stop new event intake. The watcher flushes pending eligible work before exit.

Normal lifecycle messages use stderr:

- ~watcher ready~
- ~watcher stopping~
- ~watcher stopped~

Routine file activity does not produce a JSON event stream.

A clean shutdown also removes materialized presentation-view data for the current watcher session.

A later watcher session starts with an empty view registry and a new cache-session identity.

** Backend uncertainty

A watcher backend can report uncertainty instead of exact file changes. Buffer overflow can create the same condition.

In that case, the runtime requests full configured-source reconciliation. It does not guess individual mutations.

* ~orgfdb view~

~view~ manages named presentation view registrations in the active watcher session.

Emacs can register a small set of expensive views after it starts its watcher integration.

Registrations exist only in watcher memory. A new watcher session starts with an empty registry.

The watcher eagerly materializes cache-enabled registered views. A view read uses only the materialized cache and never starts query work.

** Control connection

The watcher owns the authoritative view registry.

Separate ~orgfdb view~ processes use a local Unix socket to reach the active watcher.

The watcher creates the socket before it prints ~watcher ready~.

The socket directory uses ~XDG_RUNTIME_DIR~ when that variable contains an absolute path.

If ~XDG_RUNTIME_DIR~ is unavailable, the control path uses the XDG cache directory.

The fallback is ~$HOME/.cache/orgfdb/control~ when ~XDG_CACHE_HOME~ is unavailable.

A clean watcher shutdown removes the control socket. A stale socket from an abnormal shutdown is replaced at the next watcher start.

A second watcher for the same database and control directory fails while the first watcher is active.

** Register or replace a view

#+begin_src shell
orgfdb view register \
  --config ./org-files-db.toml \
  --output flat \
  --include path,properties \
  --presentation-spec-json '{"columns":[{"name":"title"},{"name":"file-path"}]}' \
  agenda \
  '(headings (todo "NEXT"))'
#+end_src

A view definition contains:

- the view name
- the structural query
- the query output mode
- explicit query includes
- the effective query timezone
- whether the validated query depends on relative dates
- the presentation specification

Registration validates the query and presentation specification before it contacts the watcher.

The watcher normalizes explicit includes by sorting them and removing duplicates.

An identical registration returns ~unchanged~ and keeps its revision.

A new or changed registration starts an eager full cache rebuild.

Queries with ~today~ or integer day offsets also rebuild when their effective query date changes. The configured query timezone determines that date.

A date-only refresh keeps the current database generation unchanged. Fixed-date views do not rebuild only because the calendar date changes.

A changed definition returns ~replaced~ and receives a new revision.

A new definition returns ~registered~.

Each successful response also contains the watcher ~session_id~.

** Show a registered view

#+begin_src shell
orgfdb view show \
  --config ./org-files-db.toml \
  agenda
#+end_src

~show~ returns the current session ID, definition revision, and complete registered definition.

~show~ does not run the structural query. It also does not start presentation cache work.

** Read a materialized view

#+begin_src shell
orgfdb view read \
  --config ./org-files-db.toml \
  agenda
#+end_src

~read~ waits until the registered view cache matches the current database generation and view revision.

For relative-date views, the cache must also match the current effective query date.

The command does not start a rebuild. Registration and watcher database changes start rebuilds eagerly.

If a rebuild is active, ~read~ waits for the current target. If that rebuild fails, ~read~ returns an error.

The command never returns the previous stale payload as the current view.

After the cache is ready, ~read~ validates the cache envelope and streams the stored ~presentation-json~ payload to stdout.

** Remove a registered view

#+begin_src shell
orgfdb view remove \
  --config ./org-files-db.toml \
  agenda
#+end_src

~remove~ removes the named registration from the active watcher session.

The response contains ~removed: true~ when the view existed. A repeated removal returns ~removed: false~.

* ~orgfdb headings~

~headings~ prints stored heading rows for database inspection. It does not parse current Org source files.

** Synopsis

#+begin_src shell
orgfdb headings [--config PATH] [--no-root] [--format json | --json]
#+end_src

** Root rows

Synthetic level-0 file roots are included by default. Use ~--no-root~ to remove them from this inspection output.

~--include-root~ is a deprecated compatibility no-op. Root rows are already included by default.

Synthetic roots represent file scope. They are not parser-level Org headings.

** Output order

Rows use deterministic order by:

1. ~file_path~
2. ~byte_start~
3. ~id~

** JSON fields

Each object contains:

- ~id~
- ~file_id~
- ~file_path~
- ~parent_id~
- ~level~
- ~line_number~
- ~byte_start~
- ~byte_end~
- ~title~
- ~title_raw~
- ~todo_keyword~
- ~todo_type~
- ~priority~
- ~scheduled_raw~
- ~scheduled_ts~
- ~deadline_raw~
- ~deadline_ts~
- ~closed_raw~
- ~closed_ts~
- ~archivedp~
- ~footnote_section_p~
- ~all_tags~

For real headings, ~title~ contains the normalized semantic title. ~title_raw~ preserves the stored source title area without trailing Org tags.

* ~orgfdb links~

~links~ prints stored link facts and stored resolution fields. It does not resolve links on demand.

** Synopsis

#+begin_src shell
orgfdb links [--config PATH] [--format json | --json]
#+end_src

** Output order

Rows use deterministic order by:

1. ~file_path~
2. ~byte_start~
3. stored link identity

** JSON fields

Each object contains:

- ~file_id~
- ~file_path~
- ~heading_id~
- ~heading_path~
- ~heading_level~
- ~source_context~
- ~format~
- ~link_type~
- ~raw~
- ~raw_target~
- ~raw_description~
- ~path~
- ~search_option~
- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~
- ~resolution_status~
- ~resolution_diagnostic~
- ~byte_start~
- ~byte_end~
- ~line~

The public field is ~link_type~. There is no legacy ~type~ field in this output.

Root links use ~heading_level = 0~ and an empty ~heading_path~.

~resolution_status~ can be null if no resolver pass populated the row. Stored non-null states are ~resolved~, ~broken~, ~unresolved~, ~ambiguous~, and ~unsupported~.

The resolver supports file heading searches with ~::*Heading~ and ~::#custom-id~. Other file search forms are not resolved by the current implementation.

Org ~id:~ links resolve only against indexed non-root headings. External ~org-id-locations~ are not part of this resolver.

* ~orgfdb status~

~status~ returns the committed database identity, generation, and canonical database path.

** Synopsis

#+begin_src shell
orgfdb status [--config PATH] [--format json | --json]
#+end_src

Example response:

#+begin_src json
{
  "schema_version": 12,
  "database_path": "/home/user/notes/org-files-db.sqlite",
  "database_id": "74f470e2-0354-4ed8-b2e0-e0647e0c706a",
  "generation": 1842,
  "last_changed_at": "2026-08-05T00:42:10Z"
}
#+end_src

~database_path~ is the canonical path of the database that the command opened.

A successful no-op reconciliation does not advance ~generation~. It also does not update ~last_changed_at~.

Read [[./design/index-generations-and-changes.org][Index Generations and Changes]] for the consistency model.

* ~orgfdb changes~

~changes~ reports committed affected-file changes after a client generation.

** Synopsis

#+begin_src shell
orgfdb changes \
  --database-id ID \
  --since-generation N \
  [--config PATH] \
  [--format json | --json]
#+end_src

Example:

#+begin_src shell
orgfdb changes \
  --config ./org-files-db.toml \
  --database-id 74f470e2-0354-4ed8-b2e0-e0647e0c706a \
  --since-generation 1840 \
  --format json
#+end_src

The response contains:

- ~schema_version~
- ~database_id~
- ~from_generation~
- ~to_generation~
- ~oldest_available_generation~
- ~cache_action~
- ~complete~
- ~reason~
- ~upsert_files~
- ~deleted_files~

~cache_action~ has three values:

- ~unchanged~ means the requested generation is current.
- ~patch~ means the complete interval contains exact file actions and no full invalidation.
- ~rebuild~ means a client cannot apply that interval as an exact file patch.

Stable rebuild reasons are:

- ~database-id-changed~
- ~history-unavailable~
- ~full-invalidation~

A generation newer than the current generation is an error.

The command does not execute a structural query. Read [[./design/index-generations-and-changes.org][Index Generations and Changes]] for journal semantics.

* ~orgfdb query~

~query~ runs the structural query language against the existing SQLite database.

** Synopsis

#+begin_src shell
orgfdb query [OPTIONS] QUERY
#+end_src

Quote the complete query expression in normal shells:

#+begin_src shell
orgfdb query '(headings (not (done)))'
orgfdb query '(links (status "broken"))'
orgfdb query '(files (tags "project"))'
#+end_src

Read [[./reference/query-language.org][Structural Query Language]] for complete predicate syntax.

** Options

- ~--format json~ selects the stable query JSON format.
- ~--format presentation-json~ selects the query-only presentation format.
- ~--presentation-spec-json JSON~ supplies one ~PresentationSpec~ for presentation output.
- ~--json~ is a compatibility form for ~--format json~.
- ~--output flat|outline~ selects the result shape. The default is ~flat~.
- ~--include VALUE~ requests optional structured result data.
- ~--restrict-files-json PATH_OR_DASH~ restricts query ownership to exact persisted file paths.
- ~--config PATH~ selects database and query-time configuration.

~--presentation-spec-json~ is valid only with ~--format presentation-json~. The presentation format requires this option.

The CLI parses ~PresentationSpec~ before it runs the query. Rust rejects unknown presentation column names.

After query parsing, the CLI validates displayed columns and sort-only columns against the query target.

For example, ~link-target~ is valid for ~(links)~ but not for ~(headings)~. The same registry validates sort-only columns.

Singular row columns require their matching ~row_source~ value. Row sources are valid for heading and file query results.

Only outline-path columns accept the ~outline_path~ option object.

The registry records required query includes for every supported column. The CLI adds these includes before it runs the query.

Displayed columns, sort-only columns, and row sources can add required includes. Explicit ~--include~ values stay enabled.

For example, a hidden ~outline-path~ sort adds ~path~. An ~effective-properties~ row source adds ~effective_properties~.

The query command emits complete presentation responses for normal and expanded views.

The presentation path runs the query once. It expands rows, sorts them, calculates shared widths, truncates, pads, and assigns semantic roles.

The presentation query reads index state and query data from one database read transaction. The response identifies one database snapshot.

~presentation-json~ uses compact JSON and ends with one newline. Normal ~--format json~ keeps its existing pretty JSON serialization.

The supported row sources are ~tags~, ~effective-properties~, and ~keywords~. Empty row-source collections produce no rows.

Other commands do not accept ~presentation-json~ or ~--presentation-spec-json~.

Example request:

#+begin_src shell
orgfdb query \
  --format presentation-json \
  --presentation-spec-json '{"columns":[{"name":"title"}]}' \
  '(headings)'
#+end_src

Example keyword expansion:

#+begin_src shell
orgfdb query \
  --format presentation-json \
  --presentation-spec-json '{"columns":[{"name":"file-name"},{"name":"keyword-name"},{"name":"keyword-value"}],"row_source":{"kind":"keywords"}}' \
  '(files)'
#+end_src

The response contains:

- ~presentation_version~
- ~database_id~
- ~generation~
- ~results~
- ~schemas~
- ~rows~

~presentation_version~ is ~2~ for the current compact wire format.

~results~ stores each original query result once.

~schemas~ defines the positional row, row-context, and cell layouts.

Each row refers to one result through the ~result_index~ position defined by that schema.

Each cell preserves complete ~search_text~, final ~display_text~, and one optional semantic ~role~.

The wire format can encode equal display text as ~null~ and roles as indexes into the emitted role table.

Read [[./design/presentation.org][Presentation Output Design]] for the current ~PresentationSpec~ model.

~--include~ is repeatable. One flag can also contain comma-separated values.

Supported include values are:

- ~path~
- ~properties~
- ~effective_properties~
- ~keywords~
- ~links~
- ~backlinks~
- ~source~
- ~target~

The CLI accepts every listed include for every query target. Each include affects only result kinds that provide its data.

- ~path~ affects ~headings~, ~links~, and ~files~.
- ~properties~, ~effective_properties~, ~keywords~, ~links~, and ~backlinks~ affect ~headings~ and ~files~.
- ~source~ and ~target~ affect ~links~.

A non-applicable include remains listed in the response ~includes~ array but adds no field to that result kind.

Includes enrich output. They do not change which objects match.

Read [[./reference/query-json.org][Query JSON Contract]] for include-controlled fields.

** Output modes

~flat~ returns matched top-level result objects only.

~outline~ returns file-root trees. Heading and link queries can contain unmatched ancestor context nodes needed for hierarchy.

For ~files~, outline output returns matched file roots. It does not expand all contained headings or links.

The ~matched~ field distinguishes actual matches from outline context.

** Restrict files

~--restrict-files-json~ adds an owning-file restriction without changing the query expression.

The value is a path to a UTF-8 JSON array, or ~-~ for standard input.

#+begin_src shell
printf '%s' '["/home/user/notes/a.org","/home/user/notes/b.org"]' |
  orgfdb query \
    --config ./org-files-db.toml \
    --restrict-files-json - \
    '(headings (not (done)))'
#+end_src

Duplicate paths are removed. An empty array returns no rows. Unknown paths also return no rows.

The restriction applies to ~headings~, ~links~, and ~files~ by owning indexed file.

This option can support file-based client refresh work. It does not prove that every higher-level cached view is safe to patch.

* ~orgfdb search~

~search~ runs a raw SQLite FTS5 ~MATCH~ expression against the trusted derived heading index.

Search is separate from the structural query language.

** Synopsis

#+begin_src shell
orgfdb search [--title | --body] [--config PATH] [--format json | --json] EXPRESSION
#+end_src

The expression must not be empty.

Without ~--title~ or ~--body~, search uses both indexed FTS columns.

- ~--title~ restricts the complete expression to the FTS ~title~ column.
- ~--body~ restricts the complete expression to the FTS ~body~ column.

The two scope options conflict.

If one scope option is active, the expression cannot contain its own explicit FTS column filter.

** Search requirements

Search requires all of these conditions:

- the active configuration has ~search.fts5_enabled = true~
- the opened SQLite build supports FTS5
- the database contains current trusted FTS metadata
- the trusted FTS table has the expected schema

~--body~ also requires a trusted index built with body text.

Run ~orgfdb rebuild~ after you change relevant search configuration or when search reports stale FTS state.

** FTS5 examples

Search for one token:

#+begin_src shell
orgfdb search 'sqlite'
#+end_src

Search a token prefix:

#+begin_src shell
orgfdb search 'sql*'
#+end_src

Search a phrase:

#+begin_src shell
orgfdb search '"full text search"'
#+end_src

Combine terms:

#+begin_src shell
orgfdb search 'sqlite AND database'
orgfdb search 'sqlite OR postgres'
orgfdb search 'sqlite NOT deprecated'
#+end_src

Use explicit column filters only without ~--title~ or ~--body~:

#+begin_src shell
orgfdb search 'title:sqlite'
orgfdb search 'body:index*'
orgfdb search 'title:sqlite AND body:index*'
#+end_src

FTS5 tokenization controls punctuation and case behavior. This command does not implement a regular-expression language.

Prefix ~*~ works from the start of a token. It does not provide general suffix or substring wildcard matching.

For advanced FTS5 syntax, use SQLite FTS5 ~MATCH~ syntax supported by the linked SQLite library.

** Search output

Each search row uses the canonical heading/root result shape and adds ~rank~.

~kind~ is ~heading~ for real headings and ~root~ for synthetic file roots.

Search returns normalized structural heading fields. It does not return structural query includes.

* Exit codes

~orgfdb~ uses these main exit-code classes:

- ~0~ means success.
- ~1~ means a runtime, data, query, database, serialization, or indexing error.
- ~2~ means a CLI usage error.

Query parse and validation errors use exit code ~1~. Invalid Clap arguments use exit code ~2~.
