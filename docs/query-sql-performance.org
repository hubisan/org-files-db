#+TITLE: Query SQL Performance
#+STARTUP: showall

* Purpose

This document records the SQL performance work for structural query execution and result enrichment.

The uncached presentation benchmark showed that query execution dominates latency for large result sets.

The SQL work keeps public query semantics and normal JSON output unchanged.

* Round 1 baseline and result

The first uncached presentation benchmark measured these database-query medians at ~50'000~ original results.

| Workload | Original median |
|----------+-----------------|
| ~headings.normal~ | about ~798 ms~ |
| ~headings.tags~ | about ~824 ms~ |
| ~headings.effective-properties~ | about ~1.25 s~ |
| ~files.keywords~ | about ~1.04 s~ |

Those measurements used fixed ~900~-ID enrichment chunks.

Round 1 replaced the fixed chunk size with the runtime SQLite variable limit. It also removed broad reloads after simple flat queries.

The local round 1 benchmark reported ~SQLITE_LIMIT_VARIABLE_NUMBER = 32766~ and these ~50'000~-result medians.

| Workload | Round 1 median | SQL statements |
|----------+----------------+----------------|
| ~headings.normal~ | ~354.2 ms~ | 5 |
| ~headings.tags~ | ~352.1 ms~ | 5 |
| ~headings.properties~ | ~481.1 ms~ | 7 |
| ~headings.effective-properties~ | ~492.2 ms~ | 7 |
| ~headings.path~ | ~846.0 ms~ | 11 |
| ~files.normal~ | ~179.3 ms~ | 5 |
| ~files.keywords~ | ~361.2 ms~ | 7 |

The common presentation workloads improved by about ~56%~ to ~65%~ against the original database-query baseline.

The round 1 lookup microbenchmark also compared five ways to load ~150'000~ effective-property rows for ~50'000~ heading IDs.

| Strategy | Median |
|----------+--------|
| ~query-derived-join~ | ~23.7 ms~ |
| ~json-each-relation~ | ~39.5 ms~ |
| ~runtime-limit-in~ | ~58.0 ms~ |
| ~temporary-id-relation~ | ~74.7 ms~ |
| ~cte-values~ | ~102.9 ms~ |

The query-derived join won at every measured result size.

A temporary relation lost the single-lookup test because the test included relation setup cost. Round 2 adds a reuse benchmark across several enrichment stages.

* Round 1 SQL changes

** Runtime variable limit

Large ID lists use the connection value of ~SQLITE_LIMIT_VARIABLE_NUMBER~.

The code derives the available parameter capacity from that runtime limit.

A connection with a smaller configured limit uses smaller chunks automatically.

File-restriction inserts also use the runtime parameter capacity.

** Direct flat shaping

Flat heading rows already contain heading scalars, file paths, locations, and effective tags.

Flat file rows contain file scalars and the synthetic-root fields required by public results.

Flat link rows contain link scalars, source locations, and file paths.

Round 1 shapes simple flat rows directly and avoids broad file and heading reloads.

** Query joins and ordering

Top-level heading queries always join ~files~ because public heading rows contain the file path.

They join the synthetic root only when a predicate uses root data.

Nested relations add file and root joins only when their predicates require those aliases.

Global SQL sorting was removed where Rust can restore the same public order with small grouped sorts.

* Round 2 architecture

Round 2 targets the remaining SQLite to Rust to SQLite ID round trips.

The production query executor now keeps the compiled matched SQL relation beside the normal matched rows.

This relation metadata stays internal. Public query rows and public JSON output keep their existing shapes.

The production execute-and-shape path passes the internal relation to result shaping.

Standalone shaping from caller-supplied ~QueryRows~ keeps the existing ID-based fallback loaders.

** Query snapshot

Public query execution now starts one deferred read transaction when the caller has no active transaction.

All match and enrichment statements for that call use the same SQLite snapshot.

An existing caller transaction remains authoritative and is not nested.

An error rolls back the transaction that the query call created.

** Heading tags

Base heading execution still returns effective tags as part of each heading row.

The tag loader no longer sends matched heading IDs back through a dynamic ~IN (...)~ list.

It wraps the exact compiled heading query as a ~matched~ CTE and joins ~effective_tags~ to that relation.

Tag order remains stored-position order after a small Rust sort per heading.

** Direct metadata enrichment

The production direct-flat path uses query-derived relations for:

- direct properties
- effective properties
- keywords
- file-root tags
- ~outline_path~ validation

Each relation uses the exact compiled match query and its original bound parameters.

Rust keeps the existing property, keyword, and tag ordering after collection.

A relation loader skips heading or root branches when the matched result has no rows from that branch.

The old runtime-limit ID loaders remain available for data sets that originate in Rust.

** Path enrichment

Flat heading path output no longer loads every heading from each matched file.

A query-derived recursive CTE starts with the matched headings and follows only required parent rows.

A separate query-derived join loads the containing file and synthetic root for each matched heading.

The recursive path query validates ~outline_path~ rows for matched headings and required ancestors.

The current missing-row and malformed-JSON errors remain unchanged.

Flat file path output needs only the matched file and its synthetic-root data.

Complex link, backlink, source, target, and outline contexts keep the broader enrichment path.

Those contexts can introduce file-wide relations and one-to-many fan-out. They remain on the safe fallback without new benchmark evidence.

** Avoid join fan-out

Round 2 does not combine unrelated one-to-many relations into one large result query.

Tags, properties, keywords, and links remain separate enrichment relations.

This avoids multiplication such as ~tag_count * property_count~ for one heading.

* Round 2 strategy benchmark

Benchmark output schema version ~2~ keeps the round 1 lookup comparison and adds relation-reuse measurements.

The reuse benchmark compares:

- repeated query-derived joins
- one shared TEMP result relation reused by several loaders

It uses both a simple match relation and a more selective complex match relation.

The simple relation matches level-1 headings.

The complex relation also requires the ~project~ effective tag and the ~GROUP=group0~ effective property.

Each relation has two workloads.

- The single workload loads effective properties.
- The multi workload loads effective properties, effective tags, direct properties, and ~outline_path~ rows.

The shared TEMP timing includes relation reset and population on every sample.

The repeated-derived timing includes re-evaluation of the matched relation for every loader.

Both strategies run inside one deferred transaction so they use one stable database snapshot.

This comparison shows whether one reusable relation amortizes its setup cost across several enrichments.

* ID transport fallback

Round 1 showed that ~json_each~ beats large dynamic ~IN (...)~ lists on the benchmark system.

The production fallback still uses runtime-limit ~IN (...)~ chunks.

This path works without a project requirement for SQLite JSON table functions.

Round 2 keeps ~json_each~ in the benchmark for IDs that genuinely originate in Rust.

A later change can use it when measurements justify the extra serialization and SQLite JSON parsing.

* Query plan audit

Benchmark output schema version ~2~ also records ~EXPLAIN QUERY PLAN~ details from the real compiled query SQL.

The audit covers representative queries for:

- heading level
- heading title
- file path
- direct tags
- effective tags
- direct properties
- effective properties
- keywords
- parent hierarchy
- link source
- link target
- scheduled time
- file restriction

The level-1 benchmark intentionally matches a large fraction of the heading table. A table scan can be the correct plan for this broad case.

Exact normalized heading titles can use ~idx_headings_title_lower~.

Exact normalized file paths can use ~idx_files_path_lower~.

Direct tag and property lookups have dedicated indexes.

Effective tag and property predicates use their existing materialized projections.

Parent, link source, link target, and planning timestamp predicates have dedicated indexes.

The benchmark records the actual plan details so local results can expose unexpected scans or temporary B-trees.

Round 2 adds no persistent index before those plans and timings provide evidence.

* Existing materialized projections

The schema already stores several expensive derived relations.

- ~effective_properties~ stores resolved property values.
- ~effective_tags~ stores inherited tag order.
- ~outline_path~ stores structural outline paths.
- Optional FTS stores indexed title and body search data.

Round 2 adds no persistent materialized table.

The current bottleneck is access to matched relations, not recomputation of these existing projections.

A new persistent projection needs measured benefit that exceeds rebuild, update, storage, and schema costs.

* Production profiling

Production SQL statements contain internal benchmark comments with a stage name and parameter count.

The measurement binary enables SQLite profiling only for one separate profile run per workload.

Latency samples run without the profile callback.

The profile records actual statement counts, bound parameter counts, and SQLite-reported statement durations.

The SQLite profile callback has coarse timing resolution on the benchmark system.

Complete workload timings and dedicated relation-strategy timings remain the authoritative latency measurements.

* Run the round 2 SQL benchmark

Build the release benchmark binary.

#+begin_src sh
cargo build --release --bin orgfdb-query-sql-benchmark
#+end_src

The SQL benchmark reuses compatible corpus databases when they exist.

It creates the work directory and missing corpus databases when required.

The first run can spend significant time preparing the ~50'000~-result database.

Use a persistent work directory when repeated benchmark runs need database reuse.

#+begin_src sh
target/release/orgfdb-query-sql-benchmark \
  --rows 100,1000,10000,50000 \
  --warmups 1 \
  --iterations 3 \
  --work-dir /tmp/orgfdb-presentation-benchmark-work \
  --output /tmp/orgfdb-query-sql-benchmark-round2-v1.json
#+end_src

Use a new output path for each benchmark run.

* Current design decision

Round 2 uses query-derived relations in the common production direct-flat path.

The implementation keeps runtime-limit ~IN (...)~ as the safe fallback for Rust-originated ID sets.

The path fast path loads only matched headings, containing files, roots, and required ancestors.

No new persistent index or materialized table has enough round 2 evidence yet.

The local round 2 benchmark supplies the final evidence for the relation-reuse decision.
