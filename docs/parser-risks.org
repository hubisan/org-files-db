#+TITLE: Parser Risks
#+STARTUP: showall

This document tracks parser-backend and parser-contract risks for ~org-files-db~.

The project keeps ~Orgize~ isolated behind ~src/parser/orgize_adapter.rs~ so parser-specific instability, compatibility gaps, and project-owned normalization decisions stay visible and replaceable. This register is the central place to record those risks, the current containment strategy, and the next decision for each item.

* Scope and Status

This register covers parser backend behavior and parser-contract risks. It does not serve as a general indexer, query, CLI, or database risk register unless a risk is directly caused by parser output or parser-model decisions.

- Current parser backend: ~Orgize~
- Current Orgize crate version: ~0.10.0-alpha.10~
- Current adapter boundary: ~src/parser/orgize_adapter.rs~
- Emacs Org-mode is used as a reference oracle for tricky semantics when that helps confirm parser behavior.
- Unsafe Emacs Lisp and diary expressions must never be evaluated.

Status labels used in this file:

- ~accepted contract~: current behavior is accepted for now, even if it is surprising, because it matches Org / Emacs semantics or is otherwise good enough for the current phase
- ~backend extraction gap~: the parser backend does not currently expose the data the project needs in the desired shape
- ~contract gap~: the project parser model or normalization contract is not complete yet
- ~planned model gap~: the architecture already requires the behavior or shape, but the model has not been implemented yet
- ~open decision~: a project-owned parser contract decision is still unresolved

Decision labels used in this file:

- ~accept~
- ~work around locally~
- ~report upstream~
- ~replace later~

* Risk Register

** Phase 3 link scanner cross-checks

- Risk: Raw ~Orgize~ link nodes and Emacs ~org-element~ link elements do not define the Phase 3 link scanner contract, so backend/reference-parser differences must stay documented as evidence rather than silently becoming product behavior.
- Current status: ~accepted contract~
- Fixture set:
  - [[file:../tests/data/parser/links/plain-and-bracket-links/fixture.org][plain-and-bracket-links fixture]]
  - [[file:../tests/orgize_adapter.rs][orgize_adapter link tests]]
  - [[file:../src/parser/link_scanner.rs][link_scanner tests]]
- Comparison method:
  - Use the project scanner contract and its focused tests as the source of truth.
  - Cross-check raw ~Orgize~ link-node extraction on a small representative content set covering bracket, angle, plain, drawer/property-drawer, permissive-description, and multi-line cases.
  - Cross-check representative plain-link boundary and path-end cases plus drawer / ignored-region behavior with Emacs ~org-element-parse-buffer~.
- Expected matches:
  - Emacs matched the accepted plain-link boundary cases already encoded in the scanner tests: links are accepted after ~!~, ~"~, ~_~, and ~Prefix:~, but not after ~'~, ~$~, ~%~, or mid-word text.
  - Emacs matched the accepted plain-link path-end cases already encoded in the scanner tests: balanced ~<...>~, ~(...)~, and ~[...]~ suffixes remain part of the plain link; deterministic trailing punctuation is trimmed; trailing ~/~ and ~-~ remain part of the link.
  - Emacs and the scanner both excluded links inside representative ignored regions such as inline code/verbatim and source blocks.
- Expected mismatches:
  - Raw ~Orgize~ link nodes covered only bracket links in the representative mixed-link probe. The same probe produced no raw ~Orgize~ link nodes for angle links, plain links, property-drawer links, or normal-drawer links. This is an accepted backend extraction gap; the project scanner contract wins.
  - Emacs exposed angle links, plain links, property-drawer links, and normal-drawer links in the representative probe. Phase 3 accepts that behavior only where it matches the documented scanner contract; it does not make the project depend on Emacs internals.
  - Emacs accepted the representative multi-line bracket example as a link, while the Phase 3 scanner deliberately rejects links that would need to cross a newline. This remains a local Phase 3 policy choice, not an Orgize bug.
  - In the whitespace-terminated plain-link example, Emacs link element spans currently include the following separator space in ~:end~, while the scanner stores the final accepted link span without trailing whitespace. The scanner byte-span contract wins.
  - Raw ~Orgize~ link nodes did not surface the representative permissive bracket-description or multi-line bracket cases in the validation probes. This is consistent with keeping the project scanner contract independent from ~Orgize~ link-node details.
- Unexpected mismatches:
  - None found in the chosen fixture set.
- Why it matters: Phase 3 needs stable source-fact extraction even when the backend parser and the Emacs reference parser disagree or expose different link subsets. The project must preserve scanner-owned behavior for storage and later CLI output.
- Current decision: ~accept~ the current scanner contract as independent from raw ~Orgize~ and Emacs link extraction details, while keeping cross-check notes explicit.
- Workaround / containment:
  - Keep link extraction project-owned in ~src/parser/link_scanner.rs~ and use ~Orgize~ only for structural context and ignored-region annotation in ~src/parser/orgize_adapter.rs~.
  - Keep representative boundary/end semantics covered by focused scanner tests and note any future Emacs comparison changes before changing the scanner.
  - Treat property-drawer and normal-drawer link inclusion as project-owned indexing policy, not as an upstream parser bug.
- Fixtures / tests:
  - [[file:../tests/data/parser/links/plain-and-bracket-links/fixture.org][plain-and-bracket-links fixture]]
  - [[file:../tests/orgize_adapter.rs][orgize_adapter link tests]]
  - [[file:../src/parser/link_scanner.rs][link_scanner tests]]
  - [[file:../.project/tasks/archive/2026-06-30--extract-plain-links-with-configurable-protocols.org][plain-link boundary review task]]
- Upstream issue candidates:
  - Existing references remain the relevant context for the observed raw ~Orgize~ extraction gaps:
    - https://github.com/PoiScript/orgize/issues/88
    - https://github.com/PoiScript/orgize/issues/91
  - No new upstream issue was opened from this validation pass because the chosen repro set did not reveal a new general parser bug beyond the already-known gap pattern.
- Follow-up: Re-run this validation only when the scanner contract changes, when ~Orgize~ is upgraded, or when a new link-format decision would otherwise rely on backend/reference-parser behavior rather than the documented project contract.

** Multi-line planning behavior

- Risk: Multi-line planning immediately below a heading does not retain every planning field in the current reviewed example.
- Current status: ~accepted contract~
- Observed behavior: In the reviewed example with separate ~SCHEDULED~, ~DEADLINE~, and ~CLOSED~ lines, Emacs ~org-element-parse-buffer~ currently keeps only ~SCHEDULED~ in the planning node. The current adapter follows that same effective behavior for the active fixture.
- Why it matters: This looks like a parser bug at first glance, but treating it as an Orgize defect would be misleading if the current Org / Emacs parse tree behaves the same way. The project needs to distinguish compatibility semantics from real backend regressions.
- Current decision: ~accept~ for now as parser semantics / compatibility behavior, not as a confirmed Orgize bug.
- Workaround / containment: Keep the current expectation explicit in the regression fixture and document the semantic surprise here so later planning-field work does not “fix” it accidentally.
- Fixtures / tests:
  - [[file:../tests/data/parser/headings/nested-planning-lines/fixture.org][nested-planning-lines fixture]]
  - [[file:../tests/data/parser/headings/nested-planning-lines/expected.txt][nested-planning-lines expectation]]
  - [[file:../.project/tasks/archive/2026-06-16--evaluate-minimal-orgize-adapter.org][Evaluate minimal Orgize adapter]]
- Follow-up: Re-check this item only if upstream Org / Emacs semantics or Orgize behavior changes, or if the project adopts a documented normalization layer that intentionally differs from raw parser behavior.

** Plain links

- Risk: Plain links such as ~https://www.example.com~ are not yet exposed through the project parser model and appear weaker in the current Orgize-backed path than bracketed or file-style links.
- Current status: ~backend extraction gap~
- Observed behavior: The active link fixture is currently preparatory only. The parser model does not yet expose links, and the earlier adapter evaluation noted that plain links need explicit regression coverage because Orgize appears not to surface them like bracket/file links.
- Why it matters: Link extraction is part of the intended project scope. If plain links are missing or inconsistent, later DB import and query behavior will silently under-report document structure.
- Current decision: ~work around locally~ once the link model is implemented, unless upstream fixes make the workaround unnecessary.
- Workaround / containment: Keep a dedicated parser fixture ready before link extraction work begins. Treat plain links as a known gap rather than assuming current backend behavior is sufficient.
- Fixtures / tests:
  - [[file:../tests/data/parser/links/plain-and-bracket-links/fixture.org][plain-and-bracket-links fixture]]
  - [[file:../tests/data/parser/links/plain-and-bracket-links/expected.txt][plain-and-bracket-links expectation]]
  - [[file:../.project/tasks/archive/2026-06-16--evaluate-minimal-orgize-adapter.org][Evaluate minimal Orgize adapter]]
- Follow-up: When the project introduces a ~ParsedLink~ model, decide whether Orgize is sufficient with adapter-local supplementation or whether a narrower upstream issue is warranted.

** Org in-buffer TODO keyword handling

- Risk: TODO keyword normalization must stay aligned with Org in-buffer declarations while keeping file-local TODO sources out of scope.
- Current status: ~accepted contract~
- Observed behavior: The current parser and indexer honor in-buffer ~#+TODO:/#+SEQ_TODO:/#+TYP_TODO:~ declarations first, then fall back to config defaults. 
- Why it matters: TODO interpretation is a core parser contract. If precedence drifts, heading state, DB import, and later queries will disagree with Org-mode semantics for customized files.
- Current decision: ~accept~ this precedence as the project contract and keep file-local TODO behavior out of scope.
- Workaround / containment: Keep the precedence explicit in parser, indexer, and CLI contract tests so later work does not reintroduce file-local TODO sources by accident.
- Fixtures / tests:
  - [[file:../tests/data/parser/todo-keywords/custom-sequence/fixture.org][custom-sequence fixture]]

  - [[file:../.project/tasks/todo.org][Architecture decisions in todo.org]]
- Follow-up: Revisit only if the project intentionally adds a new file-local TODO source or changes the precedence contract.

** File-scope / synthetic level 0 heading

- Risk: The project architecture requires a synthetic level 0 heading for file-scope data, but the current parser output does not model it yet.
- Current status: ~planned model gap~
- Observed behavior: File-level keywords can already be stored in metadata, but pre-heading content, file tags, category, file-level TODO declarations, and future file-level links are not yet represented through the synthetic level 0 heading described in the architecture decisions.
- Why it matters: File-level scope is a deliberate project contract, not an optional convenience. Without it, file-wide data has no consistent structural home and later import/query layers will need ad hoc exceptions.
- Current decision: ~work around locally~ only through temporary metadata storage; full resolution requires implementing the planned model.
- Workaround / containment: Keep file-level metadata in ~ParsedDocumentMetadata~ where available and maintain explicit fixtures that describe the missing level 0 behavior.
- Fixtures / tests:
  - [[file:../tests/data/parser/file-scope/file-keywords-and-preamble/fixture.org][file-keywords-and-preamble fixture]]
  - [[file:../tests/data/parser/file-scope/file-keywords-and-preamble/expected.txt][file-keywords-and-preamble expectation]]
  - [[file:../.project/tasks/todo.org][Architecture decisions in todo.org]]
- Follow-up: Implement the synthetic level 0 heading and move file-level properties, tags, TODO declarations, links, and pre-heading text into that contract.

** Byte offset reliability

- Risk: UTF-8 byte offsets are the chosen editor-jump coordinates, but coverage is still too narrow to treat them as fully trustworthy across parser edge cases.
- Current status: ~open decision~
- Observed behavior: The adapter currently computes byte offsets and line numbers for headings, and existing heading tests verify that offsets are present and ordered. Broader edge cases such as file-scope content, links, body spans, and future level 0 nodes are not yet covered.
- Why it matters: Editor integration depends on correct byte offsets. Incorrect offsets would break jump-to-source behavior even if the rest of the parsed data looks plausible.
- Current decision: ~accept~ the current approach of UTF-8 byte offsets as the primary coordinate system, but treat coverage as incomplete.
- Workaround / containment: Keep byte offsets as the canonical contract and add explicit regression coverage whenever new parser structures are introduced.
- Fixtures / tests:
  - [[file:../tests/orgize_adapter.rs][Orgize adapter tests]]
  - [[file:../tests/data/parser/headings/basic-heading/fixture.org][basic-heading fixture]]
  - [[file:../tests/data/parser/priorities/todo-priority-tags/fixture.org][todo-priority-tags fixture]]
- Follow-up: Extend coverage to file-scope nodes, body extraction, links, and any future parser structures that will be used for editor navigation.

** Body extraction boundaries

- Risk: The parser contract does not yet define where a heading body starts and ends, especially whether child subtrees are excluded from parent body text.
- Current status: ~open decision~
- Observed behavior: The current internal model does not yet expose heading body content, and no active fixture defines the exact boundary semantics the project wants.
- Why it matters: Body extraction directly affects DB import, search indexing, and user-visible search results. A vague or shifting body contract will create inconsistent behavior across indexing and query layers.
- Current decision: ~accept~ that this is still an unresolved parser-contract decision and do not infer behavior from partial backend output yet.
- Workaround / containment: Delay body extraction implementation until the boundary rules are explicitly documented and covered by fixtures.
- Fixtures / tests:
  - no dedicated active body fixture yet
  - parser fixture structure already reserves body-oriented expansion via [[file:../tests/data/parser/README.org][tests/data/parser/README.org]]
  - [[file:../tests/data/parser/body/README.org][body fixture placeholder]]
  - [[file:../.project/tasks/todo.org][Architecture decisions in todo.org]]
- Follow-up: Add dedicated body fixtures before implementing body extraction, including parent/child subtree cases and file-scope preamble behavior.

** FTS5 parser-adjacent assumptions

- Risk: Later FTS5 behavior depends on parser decisions about title and body extraction, but those parser-side assumptions are not fully settled yet.
- Current status: ~open decision~
- Observed behavior: The project already decided that FTS5 is optional and that body indexing is separately configurable, but parser-side body and file-scope semantics are still incomplete.
- Why it matters: Search behavior should not accidentally define the parser contract. Parser output must be stable enough that later indexing logic can consume it consistently whether FTS5 is enabled or disabled.
- Current decision: ~accept~ the current separation of concerns and keep this register limited to parser-adjacent assumptions rather than broader query/indexer behavior.
- Workaround / containment: Treat FTS5 concerns here only when they depend on parser output shape such as title/body availability, not as a general search-feature backlog.
- Fixtures / tests:
  - [[file:../.project/tasks/todo.org][Architecture decisions in todo.org]]
  - future body and file-scope fixtures will be the primary evidence
- Follow-up: Revisit this entry when body extraction and level 0/file-scope modeling are implemented so the parser-side contract for indexing input becomes explicit.

* Decision Rules

- Accept behavior as the current contract when it matches documented Org / Emacs semantics closely enough for the current project phase, even if it is surprising.
- Add an adapter-local workaround when the project needs behavior that the backend does not expose reliably, but the gap can be contained inside ~src/parser/orgize_adapter.rs~ without leaking backend-specific types or rules.
- Report upstream when the backend behavior appears incorrect relative to Org / Emacs semantics and a small reproducible fixture exists.
- Consider backend replacement later when multiple important parser gaps accumulate, adapter-local workarounds become complex or brittle, or the backend API proves too unstable for the intended parser contract.

* Maintenance

- Every new parser regression fixture marked as risky, unsupported, or deliberately unsupported should either reference an existing entry here or trigger a new entry.
- When adapter behavior changes in a risk-relevant way, update both the fixture expectations and this file in the same task.
- When a risk is resolved, keep the historical context short but update the entry so future work does not re-open the same uncertainty accidentally.
- Do not create a second parser-risk document elsewhere in the repository. Extend this file instead.
