#+TITLE: Planned Presentation Output Design
#+STARTUP: showall

* Status

This document describes planned presentation work and the implemented presentation data models.

The ~query~ command accepts ~presentation-json~ as a query-specific output format. It also accepts ~PresentationSpec~ through ~--presentation-spec-json~.

The response wire model now exists in Rust. The query command does not emit this response yet.

A valid presentation request still reports that presentation output is unavailable.

The current ~orgfdb query --format json~ contract stays unchanged. Presentation output remains a separate opt-in representation.

* Goal

Move expensive UI-independent presentation work from Emacs to Rust. Keep the Emacs client small and theme-aware.

The design targets predefined structural query views such as ~(headings)~. Free-text search is outside this design.

The design does not use Child Emacs or ~async.el~ for presentation preparation.

* Command boundary

Presentation remains part of ~orgfdb query~. It does not become a second query command.

The query command now accepts ~--format presentation-json~. Other commands continue to accept JSON output only.

The current staged command shape is:

#+begin_src shell
orgfdb query \
  --format presentation-json \
  --presentation-spec-json '...' \
  '(headings)'
#+end_src

~--presentation-spec-json~ accepts the complete specification as one JSON value. Normal JSON output rejects this option.

* PresentationSpec

One ~PresentationSpec~ owns the UI-independent presentation configuration.

The implemented top-level model contains:

#+begin_example
PresentationSpec
  columns
  sort
  row_source
#+end_example

~columns~ is required and must contain at least one column. ~sort~ defaults to an empty list. ~row_source~ defaults to ~null~.

A column uses this shape:

#+begin_src json
{
  "name": "outline-path",
  "width": {"mode": "max", "value": 80},
  "truncate": {"position": "right", "marker": "…"},
  "outline_path": {
    "separator": " » ",
    "include_root": false,
    "include_match": true
  }
}
#+end_src

The column name must be one of the public names in the Rust presentation registry. Unknown names are rejected during JSON parsing.

~width~ defaults to ~{"mode":"auto"}~. The initial width modes are:

- ~auto~ without ~value~
- ~max~ with a positive ~value~
- ~fixed~ with a positive ~value~

This object can add another width mode later without changing the surrounding column model.

~truncate~ is optional. If present, ~position~ defaults to ~right~ and ~marker~ defaults to ~…~.

The supported truncation positions are:

- ~left~
- ~middle~
- ~right~

~outline_path~ is optional. If present, it uses these defaults:

- ~separator~: ~ » ~
- ~include_root~: ~false~
- ~include_match~: ~true~

A sort rule uses this shape:

#+begin_src json
{"column": "title", "direction": "asc"}
#+end_src

~direction~ defaults to ~asc~. The supported values are ~asc~ and ~desc~.

A non-null ~row_source~ uses this shape:

#+begin_src json
{"kind": "tags"}
#+end_src

The model recognizes these row-source kinds:

- ~tags~
- ~effective-properties~
- ~keywords~

The object leaves room for source-specific options later. This stage only parses these row-source values.

The later row-expansion work defines their execution.

The parser rejects unknown fields and unknown enum values. It also rejects empty column lists, empty names, and invalid width shapes.

* Supported columns

Rust is the authoritative definition of public presentation columns. Presentation does not use arbitrary JSON field lookup as its public column API.

Each supported column defines:

- valid result contexts
- required query includes
- one value source for later extraction
- one semantic-role rule
- valid column options
- an optional required row source

Sort-only columns use the same registry as displayed columns.

The ~heading~ context supports:

- ~title~
- ~todo-keyword~
- ~todo-type~
- ~priority~
- ~outline-path~
- ~tags~
- ~scheduled-raw~
- ~deadline-raw~
- ~closed-raw~
- ~file-title~
- ~file-name~
- ~file-path~
- ~line-number~

The ~file~ context supports:

- ~file-title~
- ~file-name~
- ~file-path~
- ~tags~
- ~line-number~

The ~link~ context supports:

- ~link-type~
- ~link-target~
- ~link-description~
- ~resolution-status~
- ~source-outline-path~
- ~target-outline-path~
- ~file-name~
- ~file-path~
- ~line-number~

The registry also reserves a ~search~ context for later client work. It supports:

- ~title~
- ~outline-path~
- ~file-name~
- ~file-path~
- ~line-number~
- ~rank~

The current presentation CLI is query-only, so it cannot select the ~search~ context yet.

The registry reserves these row-expansion columns:

- ~tag~ for ~row_source.kind = tags~
- ~property-name~ and ~property-value~ for ~row_source.kind = effective-properties~
- ~keyword-name~ and ~keyword-value~ for ~row_source.kind = keywords~

The row-expansion implementation is still planned. The parser already rejects a singular row column without its required row source.

Only ~outline-path~, ~source-outline-path~, and ~target-outline-path~ accept the ~outline_path~ option object.

The registry also records query include requirements:

- ~outline-path~ in the ~heading~ context requires ~path~.
- ~file-title~ in the ~heading~ context requires ~path~.
- ~source-outline-path~ requires ~path~.
- ~target-outline-path~ requires ~target~.
- ~property-name~ and ~property-value~ require ~effective_properties~.
- ~keyword-name~ and ~keyword-value~ require ~keywords~.

The other initial columns need no additional query include.

This stage only derives those requirements. A later task combines inferred includes with explicit query includes during query execution.

* Semantic roles

Rust defines semantic roles without concrete client styling.

The initial roles are:

- ~heading~
- ~title~
- ~todo~
- ~done~
- ~priority~
- ~tag~
- ~date~
- ~file-name~
- ~file-path~
- ~keyword-name~
- ~keyword-value~
- ~property-name~
- ~property-value~

The complete ~outline-path~, ~source-outline-path~, and ~target-outline-path~ value uses the ~heading~ role.

The ~todo-keyword~ column uses ~todo~ for ~todo_type = open~ and ~done~ for ~todo_type = closed~.

A missing or unknown TODO type produces no semantic role. Columns without a useful display distinction also have no role.

Link-specific columns have no special role in the initial registry. A later change can add one when a distinct display meaning exists.

Rust does not encode heading levels, Emacs face names, colors, font sizes, or theme data.

The cell wire model stores one optional role per cell. It has no role ranges and no separate outline-separator role.

* Results, rows, and cells

The presentation response separates query results from presentation rows. The Rust wire model uses ~presentation_version = 1~.

The response contains:

#+begin_example
presentation_version
database_id
generation
results
rows
#+end_example

~database_id~ and ~generation~ identify the database snapshot. ~results~ stores each original ~QueryResultNode~ once.

Each row contains:

#+begin_example
result_index
row_context
cells
#+end_example

~result_index~ points into the top-level ~results~ array. Row order does not change result identity.

Normal rows use ~row_context = null~. The wire model also defines structured contexts for later row expansion.

A tag context has this JSON shape:

#+begin_src json
{"kind":"tag","value":"project"}
#+end_src

An effective-property context has this JSON shape:

#+begin_src json
{"kind":"effective-property","name":"OWNER","value":"Daniel"}
#+end_src

A keyword context has this JSON shape:

#+begin_src json
{"kind":"keyword","name":"TITLE","value":"Notes"}
#+end_src

This task defines these shapes only. It does not execute row expansion.

Each cell contains:

#+begin_example
search_text
display_text
role
#+end_example

~search_text~ contains the complete logical value. Later truncation and padding do not replace this value.

~display_text~ contains the final visible value. The later formatting stage produces this text.

~role~ contains one semantic presentation role or ~null~. Cells contain no role ranges or other rich-text metadata.

Rows do not duplicate complete result objects. Several rows can reference the same ~result_index~.

* Planned pipeline

Rust performs this pipeline:

#+begin_example
query
  -> original results
  -> row expansion
  -> cell value extraction
  -> sort keys
  -> sort
  -> shared column widths
  -> truncation
  -> padding
  -> semantic roles
  -> presentation rows
#+end_example

Emacs receives prepared rows and performs only Emacs-specific work.

* Row expansion

The data model includes ~row_source~ from the start. Initial implementation can use only normal one-row-per-result behavior.

Later row sources are:

- ~tags~
- ~effective-properties~
- ~keywords~

One result can then create several rows. Each row keeps the same ~result_index~ and gets a structured ~row_context~.

Example tag context:

#+begin_example
kind = tag
value = project
#+end_example

Example effective-property context:

#+begin_example
kind = effective-property
name = OWNER
value = Daniel
#+end_example

Example keyword context:

#+begin_example
kind = keyword
name = TITLE
value = Example
#+end_example

Only one row source can be active for one presentation. The design does not create Cartesian products between row sources.

Empty source collections produce no presentation rows.

* Includes and data requirements

Rust derives includes required by displayed columns, sort columns, and row source.

A caller can also request explicit includes for other client needs. Rust combines explicit includes with presentation-derived includes.

This keeps Emacs actions outside ~PresentationSpec~. For example, an Emacs action can request ~target~ data without displaying a target column.

Rust does not know Emacs action function names.

One query invocation must provide all declared data requirements. The client does not run one follow-up query per selected result.

* Emacs boundary

Emacs maps semantic roles to real faces. The mapping belongs to ~org-files-db.el~, not to ~org-files-db.toml~.

A planned mapping can distinguish roles such as ~heading~, ~title~, ~file-path~, and keyword roles. The Emacs client also keeps completion line height based on the ~default~ face.

Emacs builds lightweight completion candidates from prepared rows. A selected row resolves through ~result_index~ to the original result for actions.

Emacs does not recalculate values, sorting, widths, truncation, padding, or outline paths.

* JSON and streaming

The first implementation uses compact JSON. It does not use JSONL or streaming.

Sorting and shared width calculation require the complete row set before final display rows are ready. Streaming adds complexity before measurements show a need.

* Cache policy

The first implementation has no presentation cache.

Benchmarks must measure the uncached Rust path before a cache design is selected. Measurements must separate Rust work, serialization, transfer, JSON parsing, and Emacs candidate construction.

If the uncached path is fast enough, no presentation cache is added.

Existing ~database_id~, ~generation~, ~changes~, and ~cache_action~ keep their current meanings. The presentation design does not overload them.

If measurements later justify a cache, the cache design must follow the measured bottleneck.

* Compatibility

The following command remains the compatibility interface for existing structural-query clients:

#+begin_src shell
orgfdb query --format json '(headings)'
#+end_src

Presentation output is opt-in. It does not change existing JSON result fields, include semantics, output modes, or query matching.
