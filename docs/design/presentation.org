#+TITLE: Presentation Output Design
#+STARTUP: showall

* Status

The initial Rust presentation pipeline is implemented for normal and expanded row output.

The ~query~ command accepts ~presentation-json~ as a query-specific output format. It also accepts ~PresentationSpec~ through ~--presentation-spec-json~.

Rust now performs value extraction, sorting, shared layout, semantic role selection, and compact response serialization.

The current ~orgfdb query --format json~ contract stays unchanged. Presentation output remains a separate opt-in representation.

JSONL, streaming, and presentation caching remain separate later work.

* Goal

Move expensive UI-independent presentation work from Emacs to Rust. Keep the Emacs client small and theme-aware.

The design targets predefined structural query views such as ~(headings)~. Free-text search is outside this design.

The design does not use Child Emacs or ~async.el~ for presentation preparation.

* Command boundary

Presentation remains part of ~orgfdb query~. It does not become a second query command.

The query command now accepts ~--format presentation-json~. Other commands continue to accept JSON output only.

A presentation request uses this command shape:

#+begin_src shell
orgfdb query \
  --format presentation-json \
  --presentation-spec-json '...' \
  '(headings)'
#+end_src

~--presentation-spec-json~ accepts the complete specification as one JSON value. Normal JSON output rejects this option.

* PresentationSpec

One ~PresentationSpec~ owns the UI-independent presentation configuration.

The implemented top-level model contains:

#+begin_example
PresentationSpec
  columns
  sort
  row_source
#+end_example

~columns~ is required and must contain at least one column. ~sort~ defaults to an empty list. ~row_source~ defaults to ~null~.

A column uses this shape:

#+begin_src json
{
  "name": "outline-path",
  "width": {"mode": "max", "value": 80},
  "truncate": {"position": "right", "marker": "…"},
  "outline_path": {
    "separator": " » ",
    "include_root": false,
    "include_match": true
  }
}
#+end_src

The column name must be one of the public names in the Rust presentation registry. Unknown names are rejected during JSON parsing.

~width~ defaults to ~{"mode":"auto"}~. The initial width modes are:

- ~auto~ without ~value~
- ~max~ with a positive ~value~
- ~fixed~ with a positive ~value~

This object can add another width mode later without changing the surrounding column model.

Rust uses right truncation with ~…~ when a width constraint truncates text by default.

The optional ~truncate~ object overrides this behavior. Its ~position~ defaults to ~right~ and its ~marker~ defaults to ~…~.

The supported truncation positions are:

- ~left~
- ~middle~
- ~right~

An empty marker performs hard truncation. The marker counts inside the configured column width.

If the marker is wider than the column, Rust truncates the marker to the column width.

Width values count Unicode scalar values, not UTF-8 bytes. Percentage widths are not part of the initial model.

~outline_path~ is optional. If present, it uses these defaults:

- ~separator~: ~ » ~
- ~include_root~: ~false~
- ~include_match~: ~true~

A sort rule uses this shape:

#+begin_src json
{"column": "title", "direction": "asc"}
#+end_src

~direction~ defaults to ~asc~. The supported values are ~asc~ and ~desc~.

A non-null ~row_source~ uses this shape:

#+begin_src json
{"kind": "tags"}
#+end_src

The model recognizes these row-source kinds:

- ~tags~
- ~effective-properties~
- ~keywords~

The object leaves room for source-specific options later. The presentation pipeline executes these row sources.

The parser rejects unknown fields and unknown enum values. It also rejects empty column lists, empty names, and invalid width shapes.

* Supported columns

Rust is the authoritative definition of public presentation columns. Presentation does not use arbitrary JSON field lookup as its public column API.

Each supported column defines:

- valid result contexts
- required query includes
- one value source
- one semantic-role rule
- valid column options
- an optional required row source

Sort-only columns use the same registry as displayed columns.

The ~heading~ context supports:

- ~title~
- ~todo-keyword~
- ~todo-type~
- ~priority~
- ~outline-path~
- ~tags~
- ~scheduled-raw~
- ~deadline-raw~
- ~closed-raw~
- ~file-title~
- ~file-name~
- ~file-path~
- ~line-number~

The ~file~ context supports:

- ~file-title~
- ~file-name~
- ~file-path~
- ~tags~
- ~line-number~

The ~link~ context supports:

- ~link-type~
- ~link-target~
- ~link-description~
- ~resolution-status~
- ~source-outline-path~
- ~target-outline-path~
- ~file-name~
- ~file-path~
- ~line-number~

The registry also reserves a ~search~ context for later client work. It supports:

- ~title~
- ~outline-path~
- ~file-name~
- ~file-path~
- ~line-number~
- ~rank~

The current presentation CLI is query-only, so it cannot select the ~search~ context yet.

The registry supports these row-expansion columns:

- ~tag~ for ~row_source.kind = tags~
- ~property-name~ and ~property-value~ for ~row_source.kind = effective-properties~
- ~keyword-name~ and ~keyword-value~ for ~row_source.kind = keywords~

A singular row column is valid only with its required row source.

Only ~outline-path~, ~source-outline-path~, and ~target-outline-path~ accept the ~outline_path~ option object.

The registry also records query include requirements:

- ~outline-path~ in the ~heading~ context requires ~path~.
- ~file-title~ in the ~heading~ context requires ~path~.
- ~source-outline-path~ requires ~path~.
- ~target-outline-path~ requires ~target~.
- ~property-name~ and ~property-value~ require ~effective_properties~.
- ~keyword-name~ and ~keyword-value~ require ~keywords~.

The other initial columns need no additional query include.

Row sources can also require data. ~effective-properties~ requires ~effective_properties~, and ~keywords~ requires ~keywords~.

The query command combines explicit includes with presentation includes before one query execution. Duplicate includes do not cause duplicate result data.

* Value extraction and include inference

Rust now extracts presentation values from structured query results. The presentation registry selects one extractor for each public column.

The extraction layer keeps useful value types until later presentation stages. Text lists keep their source order. Line numbers stay numeric.

Outline values keep their components and separator. The extractor applies ~include_root~ and ~include_match~ before it creates the logical outline value.

The initial structural extraction rules include these examples:

- ~title~ uses the heading or synthetic-root title.
- ~tags~ uses effective heading tags or file tags.
- ~file-title~ uses the source file title. Heading results get this title from ~path~ data.
- ~file-name~ and ~file-path~ use the owning result location.
- ~link-target~ uses the authored ~raw_target~ value.
- ~link-description~ uses ~raw_description~.
- ~source-outline-path~ uses structured source path data.
- ~target-outline-path~ uses the structured resolved target.

Optional values can be missing without causing an error. A missing required include field produces a presentation extraction error.

Reserved row columns read their value from ~row_context~. The row-expansion stage creates this context from structured query data.

The ~rank~ value remains reserved for search results. Structural query presentation does not create search result objects.

Clients can still request extra includes for actions or other client needs. Rust combines these explicit includes with presentation requirements.

* Sorting

Rust now sorts presentation rows with logical values from the public column registry.

Rust extracts sort values for each row once before sorting. Hidden sort columns use the same registry and extraction rules as displayed columns.

Sort rules run in their declared order. Each rule supports ~asc~ or ~desc~.

If a sort column is also displayed, its column options define the extracted value. A hidden outline sort uses default outline options.

Sorting uses typed logical values:

- text uses case-sensitive lexicographic order
- integers use numeric order
- text lists compare their elements in order
- outlines compare their components in order

The rendered outline separator does not affect outline ordering.

Missing values sort after present values for both directions.

Rows with equal sort keys keep their incoming row order. This rule also works when several rows reference one result.

Sorting changes only row order. The top-level ~results~ array and each ~result_index~ keep their original identity.

Free-text search remains outside the presentation sorting stage.

* Widths, truncation, and padding

Rust prepares final display cells after row sorting.

The layout stage first extracts every displayed value. It then calculates one shared width for each column across the complete row set.

The width modes use these rules:

- ~auto~ uses the largest complete value width.
- ~max N~ uses the smaller value between the largest width and ~N~.
- ~fixed N~ always uses ~N~.

Rust truncates values that exceed the shared width. It then adds spaces on the right until each cell reaches that width.

Left truncation keeps the end of the value. Right truncation keeps the start of the value.

Middle truncation keeps both ends. If the remaining content width is odd, the start receives the extra character.

Width calculation and truncation use Unicode scalar values. This keeps UTF-8 boundaries valid and makes the behavior deterministic.

The layout stage does not use terminal-specific or Emacs-specific width tables.

Each cell keeps its complete logical value in ~search_text~. Only ~display_text~ contains truncation and padding.

* Semantic roles

Rust defines semantic roles without concrete client styling.

The initial roles are:

- ~heading~
- ~title~
- ~todo~
- ~done~
- ~priority~
- ~tag~
- ~date~
- ~file-name~
- ~file-path~
- ~keyword-name~
- ~keyword-value~
- ~property-name~
- ~property-value~

The complete ~outline-path~, ~source-outline-path~, and ~target-outline-path~ value uses the ~heading~ role.

The ~todo-keyword~ column uses ~todo~ for ~todo_type = open~ and ~done~ for ~todo_type = closed~.

A missing or unknown TODO type produces no semantic role. Columns without a useful display distinction also have no role.

Link-specific columns have no special role in the initial registry. A later change can add one when a distinct display meaning exists.

Rust does not encode heading levels, Emacs face names, colors, font sizes, or theme data.

The cell wire model stores one optional role per cell. It has no role ranges and no separate outline-separator role.

* Results, rows, and cells

The presentation response separates query results from presentation rows.

~presentation-json~ uses ~presentation_version = 2~.

The response contains:

#+begin_example
presentation_version
database_id
generation
results
schemas
rows
#+end_example

~database_id~ and ~generation~ identify the database snapshot.

~results~ stores each original ~QueryResultNode~ once.

Version 2 keeps the original query-result object representation inside ~results~.

The compact positional rules apply only to presentation rows, row contexts, and cells.

The ~schemas~ object defines every positional field once per payload:

#+begin_src json
{
  "row_fields": ["result_index", "row_context", "cells"],
  "cell_fields": ["search_text", "display_text", "role"],
  "row_context_shapes": {
    "tag": ["kind", "value"],
    "effective-property": ["kind", "name", "value"],
    "keyword": ["kind", "name", "value"]
  },
  "display_text_null": "same-as-search_text",
  "role_encoding": "null-or-index-into-role_values",
  "role_values": [
    "heading",
    "title",
    "todo",
    "done",
    "priority",
    "tag",
    "date",
    "file-name",
    "file-path",
    "keyword-name",
    "keyword-value",
    "property-name",
    "property-value"
  ]
}
#+end_src

Each row is a three-value array that follows ~row_fields~:

#+begin_src json
[0, null, [["Task", null, 1]]]
#+end_src

Index 0 is ~result_index~.

It points into the top-level ~results~ array.

Index 1 is ~row_context~.

Normal rows use ~null~.

Expanded rows use one positional context from ~row_context_shapes~.

A tag context has this shape:

#+begin_src json
["tag", "project"]
#+end_src

An effective-property context has this shape:

#+begin_src json
["effective-property", "OWNER", "Daniel"]
#+end_src

A keyword context has this shape:

#+begin_src json
["keyword", "TITLE", "Notes"]
#+end_src

Index 2 is the cell array.

Each cell is a three-value array that follows ~cell_fields~.

Cell index 0 is ~search_text~.

It contains the complete logical value.

Cell index 1 is ~display_text~.

It contains the final visible value after truncation and padding.

If ~display_text~ equals ~search_text~, the wire value at index 1 is ~null~.

This ~null~ value means exactly ~display_text == search_text~.

The cell always keeps three positions, so the omission never shifts ~role~.

Cell index 2 is ~role~.

It is either ~null~ or an integer index into ~role_values~.

The role indexes are stable in version 2:

- 0: ~heading~
- 1: ~title~
- 2: ~todo~
- 3: ~done~
- 4: ~priority~
- 5: ~tag~
- 6: ~date~
- 7: ~file-name~
- 8: ~file-path~
- 9: ~keyword-name~
- 10: ~keyword-value~
- 11: ~property-name~
- 12: ~property-value~

Rows do not duplicate complete result objects.

Several rows can reference the same ~result_index~.

The positional field order and role indexes are part of the version 2 wire contract.

An incompatible positional change requires a new ~presentation_version~.

New compatible top-level metadata can be added without changing existing positional meanings.

These compact rules apply only to ~presentation-json~.

Normal ~orgfdb query --format json~ keeps its existing object contract.

* Initial pipeline

Rust performs this pipeline for normal and expanded presentation rows:

#+begin_example
query
  -> original results
  -> row expansion
  -> cell value extraction
  -> sort keys
  -> sort
  -> shared column widths
  -> truncation
  -> padding
  -> semantic roles
  -> presentation-json
#+end_example

Without ~row_source~, each result creates one row with ~row_context = null~.

With ~row_source~, one result can create zero or more rows with the same ~result_index~.

The presentation query reads ~database_id~, ~generation~, and query data inside one read transaction. This keeps the response tied to one database snapshot.

Emacs receives prepared rows and performs only Emacs-specific work.

* Row expansion

The presentation pipeline supports these row sources for heading and file results:

- ~tags~
- ~effective-properties~
- ~keywords~

One result can create several rows. Each expanded row keeps the same ~result_index~ and gets one structured ~row_context~.

Example tag context:

#+begin_example
kind = tag
value = project
#+end_example

Example effective-property context:

#+begin_example
kind = effective-property
name = OWNER
value = Daniel
#+end_example

Example keyword context:

#+begin_example
kind = keyword
name = TITLE
value = Example
#+end_example

Only one row source can be active for one presentation. The pipeline does not create Cartesian products.

Empty source collections produce no presentation rows. Normal columns repeat for every expanded row.

The pipeline preserves source order when the query result defines it. Keyword expansion also preserves duplicate keyword entries.

A keyword without a value uses an empty string in ~row_context~ and ~keyword-value~. The original query result stays unchanged.

* Includes and data requirements

Rust derives includes required by displayed columns, sort columns, and row source.

A caller can also request explicit includes for other client needs. Rust combines explicit includes with presentation-derived includes.

This keeps Emacs actions outside ~PresentationSpec~. For example, an Emacs action can request ~target~ data without displaying a target column.

Rust does not know Emacs action function names.

One query invocation must provide all declared data requirements. The client does not run one follow-up query per selected result.

* Emacs boundary

Emacs maps semantic roles to real faces. The mapping belongs to ~org-files-db.el~, not to ~org-files-db.toml~.

A planned mapping can distinguish roles such as ~heading~, ~title~, ~file-path~, and keyword roles. The Emacs client also keeps completion line height based on the ~default~ face.

Emacs builds lightweight completion candidates from prepared rows. A selected row resolves through ~result_index~ to the original result for actions.

Emacs does not recalculate values, sorting, widths, truncation, padding, or outline paths.

* JSON and streaming

The current ~presentation-json~ output uses compact JSON and ends with one newline. It does not use JSONL or streaming.

Sorting and shared width calculation require the complete row set before final display rows are ready. Streaming adds complexity before measurements show a need.

* Cache policy

The first implementation has no presentation cache.

Benchmarks must measure the uncached Rust path before a cache design is selected. Measurements must separate Rust work, serialization, transfer, JSON parsing, and Emacs candidate construction.

The Rust-side benchmark harness is documented in [[../presentation-performance.org][Presentation Performance Benchmark]].

If the uncached path is fast enough, no presentation cache is added.

Existing ~database_id~, ~generation~, ~changes~, and ~cache_action~ keep their current meanings. The presentation design does not overload them.

If measurements later justify a cache, the cache design must follow the measured bottleneck.

* Compatibility

The following command remains the compatibility interface for existing structural-query clients:

#+begin_src shell
orgfdb query --format json '(headings)'
#+end_src

Presentation output is opt-in. It does not change existing JSON result fields, include semantics, output modes, or query matching.

~presentation-json~ version 2 is an intentional wire-format change from version 1.

Clients must read ~presentation_version~ and use the emitted ~schemas~ object for positional rows and cells.
