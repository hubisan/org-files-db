#+TITLE: Parser Semantics and Risks
#+STARTUP: showall

This document records current parser boundaries that need careful regression coverage. It does not describe obsolete parser gaps as current behavior.

* Parser boundary

~OrgizeAdapter~ is the production parse entry. Since #103 it builds every structural fact from the own line scanner (~src/parser/structure_scanner.rs~, see [[./line-scanner.org][Line Scanner]]) and the raw-line helpers in ~src/parser/title.rs~, ~properties.rs~ and ~timestamp_raw.rs~. Since #105 the inline objects (timestamps, inline code ranges, title markup and link description normalization) come from own code in ~src/parser/inline_scanner.rs~, and the ~orgize~ dependency is gone. The type keeps its name for the public API. The register below lists the deviations of the former Orgize backend and what became of each.

The public parser model includes:

- document keywords and title metadata
- one synthetic level-0 file root
- real headings
- heading body text
- TODO state and priority
- direct tags and properties
- planning and generic timestamps
- Org links
- byte positions and line numbers

The indexer converts these parser values into normalized database facts.

* Reference behavior

Emacs Org mode is the semantic reference for difficult Org syntax. Tests use focused fixtures for behavior that can differ across parser implementations.

The project does not run arbitrary Emacs Lisp to parse indexed files. It also does not evaluate diary expressions.

When backend behavior is incomplete, keep project-specific handling inside the parser boundary where practical.

* Synthetic file root

The parser creates one synthetic level-0 heading for each file.

This root stores file-scope data such as:

- pre-heading body text
- file tags
- file-level properties
- document keyword context
- file-root links

Real Org headings start at level 1. Top-level Org headings use the synthetic root as their parent.

This model gives file-scope data one structural location throughout the index and query layers.

* TODO keyword precedence

In-buffer ~#+TODO~, ~#+SEQ_TODO~, and ~#+TYP_TODO~ declarations take precedence over configured defaults.

If a file has no supported in-buffer declaration, the parser uses the configured default open and closed keyword sets.

Keep this precedence covered by parser and indexer tests. A change affects heading state and structural query results.

* Link scanning

The project scans links through ~src/parser/link_scanner.rs~, not through a parser backend's link nodes.

The scanner handles bracket, angle, and configured plain-link forms. It records exact source byte ranges and authored link text.

The adapter also assigns structural source context, from scanner regions. Examples include heading text, property drawers, ordinary drawers, and verse, quote, center and justify blocks.

Link scanning skips keyword lines (also affiliated ones), planning lines, comment and fixed-width runs, the whole range of src, example, export and comment blocks, and inline code, verbatim, inline source and snippets. Org parses no objects there (verse and dynamic block content is parsed, so it is scanned).

Keep ignored ranges and structural context synchronized with parser changes. A mismatch can create false links or miss authored links.

Configured plain-link protocols also affect parsing semantics. A protocol configuration change therefore belongs to the indexing semantic context.

* Property parsing

The scanner finds the property drawer and ~parsed_property_from_raw_line~ reads its rows.

A drawer only counts as the property drawer when it is the first element of its section, optionally after a planning line (also an empty one, ~SCHEDULED: garbage~); in the file-level section it may only be preceded by comment lines, not even blank lines. Drawers after body text or inside blocks are ordinary drawers and create no properties.

Every row between ~:PROPERTIES:~ and ~:END:~ must be a property (~:KEY:~ with a key of non-blank characters, alone or followed by a blank and a value). Otherwise Org reads a generic drawer and ~org-entry-get~ finds no properties, and so does the scanner. A key is the token up to its last colon.

Rows keep source type, append semantics, and line numbers. Keep duplicate and append cases covered by tests.

File-level ~#+PROPERTY~ and ~#+CATEGORY~ values use the project property model as separate source facts.

* Timestamp parsing

Planning timestamps come from the scanner's planning line, read as raw text by ~planning_timestamps~ (~src/parser/timestamp_raw.rs~) like ~org-element-planning-parser~: every ~SCHEDULED:~, ~DEADLINE:~ and ~CLOSED:~ in the line (Org searches the whole line, so text between entries is ignored), each followed directly, after spaces or tabs, by a timestamp. A timestamp is a diary sexp ~<%%(SEXP)>~ or ~<~ or ~[~, an ISO date, optional text after a space, and a closing bracket on the same line (~org-ts-regexp-both~), optionally joined to a second one by ~--~ (a range, ~<a>--[b]~ counts). A keyword without a timestamp gives no entry, and the line still is a planning line. The planning line holds no other timestamps or links.

Body and title timestamps are read by the inline scanner (~src/parser/inline_scanner.rs~, see [[./line-scanner.org][Line Scanner]] and the register, R23) as ~org-element~ reads them: any text after the ISO date up to the first ~]~ or ~>~ of the line makes a timestamp (so a repeater with an unknown unit or a ~.+1m/2m~ deadline part does), a range needs ~--~ and a second timestamp, and a timestamp inside code, verbatim, a link, a table.el table and the like is no timestamp. Repeater and warning modifiers, explicit time and the bounds of all timestamps, planning or body, come from the raw text (~timestamp_raw.rs~); for a range Org takes the first repeater and the first warning of the whole value.

Do not remove the raw handling only because common timestamp fixtures pass. Keep the targeted regression cases first.

* Timezone limitation

Stored Org planning and generic timestamps are timezone-naive.

The parser normalizes date and time components without a document timezone. The project does not model Org timestamp timezones at this layer.

Structural query configuration can apply a timezone to relative query values. That query-time rule does not change stored Org timestamp semantics.

Read [[../reference/query-language.org][Structural Query Language]] for query-time date rules.

* Diary timestamps

Org diary timestamps can be recognized as timestamp syntax. The project does not evaluate diary expressions.

A diary value therefore cannot become a computed calendar instant through arbitrary Lisp evaluation.

Keep this boundary explicit. Indexing untrusted Org files must not execute source expressions.

* Body extraction

Heading body text excludes child subtrees. The synthetic root body represents file preamble text before the first real heading.

Metadata at the start of a heading does not become normal body text when parser rules identify it as structural metadata: the planning line, the property drawer and top-level keyword lines (also affiliated ones), each with the blank lines after it. A generic drawer, such as a property drawer with a row that is no property, stays in the body.

Body persistence is controlled by ~search.index_body_text~. Parser extraction and persistence are separate concerns.

Body boundary changes affect ~has-text~ queries and FTS body search. Keep parent, child, empty-body, and metadata fixtures covered.

* Byte positions

Parser positions use UTF-8 byte offsets into the captured source bytes. Line numbers are additional navigation information.

The indexer parses the same byte sequence that it hashes. This keeps stored positions tied to the captured file snapshot.

Every new source-bearing parser structure needs byte-range regression coverage. Links, bodies, headings, and timestamps already depend on these positions.

* Title normalization

The parser stores normalized semantic titles and raw source title text separately where the model supports both values.

TODO keywords, priority cookies, trailing tags, and Org inline markup can affect normalized heading titles.

A trailing tag block is stripped from the title when it matches Org's tag rule: a colon, one or more Unicode alphanumerics or ~_@#%:~, and a closing colon, after a space or tab. Empty segments count, so ~* T ::a::~ and ~* T :a::b:~ have title ~T~ like in Org, while ~::~ and ~: :~ stay title text. Org reports the empty segments as empty tags; orgfdb stores only the non-empty ones.

The TODO keyword and the priority cookie are read only directly at the start of the title (keyword first, then cookie), as in Org: ~* foo [#A] x~ has no priority, and a cookie after ~COMMENT~ is title text. A line feed may be preceded by a CR; the CR is not part of the headline, so tags and keywords of CRLF files work like those of LF files (Emacs normally decodes CRLF files too; the oracle reads files as ~utf-8-unix~ and therefore has no CRLF fixture).

Keep normalization tests tied to the same source ranges used for links and heading metadata. Parser changes must not shift unrelated byte coordinates.

* Intentional differences

These differences from Emacs are deliberate (#80). Each is classified c in ~scripts/emacs-oracle-known.json~.

| Difference | Emacs | orgfdb | Cat | DB relevance |
|-
| Lowercase or mixed-case planning keywords (~scheduled:~, ~Deadline:~) | planning line, but the timestamp is filed under ~:closed~ | planning line, each timestamp filed under its own keyword | c | Low: Org quirk |
| ~file+sys:~, ~file+emacs:~ | type ~file~ | type kept whole, resolved like ~file:~ | c | Medium: filter by ~link_type~ |
| Unregistered scheme in a bracket link | fuzzy | typed | c | Low |
| Links in property drawer values | none | ~source_context = property_drawer~ | c | Low |
| Numeric priority ~[#10]~ | no priority | priority ~10~ | c | Low |
| Bare ~* TODO~ | plain title in org-element, TODO in ~org-entry-get~ | TODO | c | Low |

Tag blocks with empty segments (~::a::~) follow Org for the title and differ only in that empty tags are dropped; the oracle harness ignores empty tags.

Reasons:

- *Planning keyword case*: Org 9.6 matches the planning line case-insensitively, but ~org-element--get-time-properties~ then compares the keyword with case-sensitive ~equal~, so every keyword other than ~SCHEDULED:~ and ~DEADLINE:~ in upper case, including lowercase ~scheduled:~ and ~deadline:~, lands in ~:closed~. The ~planning~ element itself is empty. orgfdb follows the line detection and maps each keyword by name instead of copying the misfiling. Emacs keeps only the last entry on the line; orgfdb keeps one per keyword.
- *Unknown link types*: ~[[unknown:thing]]~ is typed ~unknown~ because users filter by scheme and Org treats unregistered schemes as fuzzy only because it does not know the protocol (~links.custom_protocols~ in ~docs/config.org~).
- *Numeric priorities*: ~[#10]~ is stored as priority ~10~ because priorities are plain strings in the schema and multi-digit cookies are used in practice.
- *~file+sys:~, ~file+emacs:~*: the full scheme stays the link type so the application stays visible; the resolver treats them like ~file:~.
- *Links in property values*: they are indexed with ~source_context = property_drawer~ so backlink queries see them and can tell them apart from body links.
- *Bare ~* TODO~*: the heading is a TODO state because Org's outline and agenda regexps treat it so; only ~org-element~ needs trailing text.

* Emacs reference comparison

~scripts/emacs-oracle.py~ compares the indexed facts of a file with what Emacs Org mode reports through ~org-element-parse-buffer~. It is a local check only. CI does not run it because Emacs is not installed there.

Requirements: Emacs with Org (tested with Emacs 29.3 and Org 9.6.15), Python 3, and a built ~orgfdb~ binary. The runner finds ~target/release/orgfdb~ or ~target/debug/orgfdb~. Set ~ORGFDB_BIN~ or ~EMACS~ to override.

#+begin_src sh
scripts/emacs-oracle.py compare                       # all parser and oracle fixtures
scripts/emacs-oracle.py compare path/to/file.org      # one file
scripts/emacs-oracle.py emacs path/to/file.org        # Emacs facts as JSON
scripts/emacs-oracle.py orgfdb path/to/file.org       # orgfdb facts as JSON
#+end_src

The default run covers every ~tests/data/parser/**/fixture.org~ and every file in ~tests/data/emacs-oracle/~. The oracle fixtures are small files for planning lines, link kinds, TODO defaults and custom sequences, tags, priorities, COMMENT and archived headings, property drawer placement, and (~structure.org~) the scanner rules: block and drawer ends, dynamic blocks, affiliated keywords, garbage planning lines and generic drawers. After a parser change also run it on the docs (~scripts/emacs-oracle.py compare docs/*.org docs/*/*.org *.org~); both runs must report no unclassified difference.

~scripts/emacs-org-dump.el~ only parses. It disables file-local and directory-local variables, never follows links, evaluates no diary expressions or Babel blocks, and refuses files with ~#+SETUPFILE~. Do not weaken these settings, per the parser validation rule in ~AGENTS.md~.

Compared facts per heading: level, raw title, TODO keyword and type, priority, direct tags, archived flag, direct properties, SCHEDULED, DEADLINE and CLOSED raw text, and links (type, path, search option, format, description, source text). File level: keywords, FILETAGS, TODO keyword set, file properties and preamble links.

Harness normalizations, which are not differences:

- ~title_raw~ keeps the TODO keyword, priority cookie and COMMENT (~docs/cli.org~), so the harness strips them before comparing with Emacs ~:raw-value~.
- Property keys and keyword names are upper-cased. Emacs always reports a synthetic ~CATEGORY~ from the file name, so it counts only when declared.
- TODO keywords compare as a set. Emacs orders them per sequence and repeats duplicates.
- Direct tags compare sorted, because the ~tags~ table keeps no order.
- An empty keyword value compares equal to NULL.

Unclassified differences make the script exit with status 1. Classified ones live in ~scripts/emacs-oracle-known.json~. Categories: a is an orgfdb bug, b is a deviation of the former Orgize backend that the adapter did not correct, c is an intentional model difference. No a or b rows remain, and with Orgize gone no b row can come back.

Remaining differences (last run: 16 differences, all intentional model differences, see the next section):

Everything else in the fixtures matched, including planning lines with repeaters, warnings and ranges, ~id:~, ~file:~, custom-id and plain links, default TODO behavior, archived and COMMENT headings, and FILETAGS.

* Register

Each entry records one known deviation of the former Orgize backend or a project workaround. The Orgize strategy was tracked in #41. Stage 2 (#103) replaced most Orgize calls with the scanner and raw-line helpers, stage 3 (#105) replaced the rest with the inline scanner and removed the dependency; every entry is marked *Resolved* and kept short as history. Orgize 0.10.0-alpha was the parser backend until then; it had no upstream release since June 2024. Test names refer to ~tests/orgize_adapter.rs~ unless noted. Org behavior was verified against Emacs 29.3 / Org 9.6.15 where an entry says so.

** R1 Link nodes unused, own link scanner

- Repro:
  #+begin_src org
  ,* Task
  See [[file:a b.org::*Heading][text]], <file:x.org> and https://example.org/x.
  #+end_src
- Orgize (history): exposed link nodes for bracket links only and did not cover angle or configurable plain links, nor the project source-context model.
- Org: bracket, angle and plain links are all link objects, plain links depending on ~org-link-types~.
- Workaround: ~scan_links~ and ~LinkScanner::scan~ in ~src/parser/link_scanner.rs~, called from ~parse_document_core~ in ~src/parser/orgize_adapter.rs~ with ignored ranges and source contexts from scanner regions.
- Type rule: a bracket target is ~TYPE:PATH~ only when the prefix has no dot or is a configured protocol, so ~[[test.org::Heading]]~ is ~fuzzy~ with the whole target as path, as in Org (verified against Emacs 29.3 / Org 9.6.15). Unregistered dotless prefixes such as ~unknown:thing~ stay typed (a c row, #80).
- Test: ~orgize_adapter_collects_project_owned_links_including_plain_file_splits~, ~dotted_prefix_is_not_a_link_type_unless_configured~, plus the unit tests in ~src/parser/link_scanner.rs~.
- Tracked in #41. Stays: the link scanner is project code.

** R2 Bracket-link placeholders in titles

- Repro:
  #+begin_src org
  ,* TODO Read [[https://example.org][the [docs]]] now
  #+end_src
- Orgize (history): its title nodes did not match the project's link ranges.
- Org: the link is one object inside the title.
- Resolved (#105): the inline scanner reads the title text itself and steps over a bracket link with the extent of ~bracket_link_at~ in ~src/parser/link_scanner.rs~, so no tokens go in and out of the title. The link renders as its description or its decoded target.
- Test: ~orgize_adapter_recovers_fragmented_bracket_link_titles_and_timestamps~, ~titles_show_their_visible_text~ (~src/parser/inline_scanner_tests.rs~, expectations from Emacs).
- Tracked in #41.

** R3 Link descriptions re-rendered via sentinel parse

- Repro:
  #+begin_src org
  ,* [[https://example.org][*bold* description]]
  #+end_src
- Org: the description is parsed as inline objects and displayed without markup.
- Resolved (#105): the description is the contents of the link object and is lexed in the same pass, with the object restrictions Org has for link descriptions (no links, timestamps or footnotes) and rendered without markup. The sentinel re-parse is gone.
- Test: ~orgize_adapter_renders_recovered_link_descriptions_like_inline_titles~.
- Tracked in #41.

** R4 Titles normalized by synthetic parse

- Repro:
  #+begin_src org
  ,* [#A] *Important* task [1/2]
  #+end_src
- Org: the title excludes the cookie and keeps inline objects; the displayed title drops markup characters and the statistics cookie.
- Resolved (#105): ~split_headline_title~ (~src/parser/title.rs~) cuts keyword and priority cookie from the raw title, then ~normalize_title_text~ in ~src/parser/inline_scanner.rs~ lexes the rest and renders it: markers of bold, italic, underline, code and verbatim dropped, statistics cookies removed, links replaced. Titles without one of ~* / _ = ~ ~ [~ skip the lexer. No synthetic headline is parsed, so no keyword or tag is read from the title text and nothing pairs with a sentinel. Org's emphasis rules apply in full: a closing mark may stand before ~-~, ~\~, ~[~, ~"~, ~}~ and more, which Orgize did not accept.
- Test: ~orgize_adapter_only_re_normalizes_todo_titles_with_link_placeholders~, ~orgize_adapter_removes_priority_and_statistics_cookies_from_titles~, ~titles_show_their_visible_text~.
- Tracked in #41.

** R5 Title re-read from the raw source line

- Test: ~orgize_adapter_keeps_invalid_tag_block_in_title~, ~orgize_adapter_strips_valid_org_tag_characters~.

- Resolved (#103): ~split_headline_title~ reads the priority from the raw title. Multi-digit cookies such as ~[#10]~ stay priorities (project extension, #80), and ~* TODO [#10] x~ now drops the cookie from the title like ~* [#10] x~.

** R11 Timestamp modifiers parsed from raw text

- Repro:

  ,* Task
  SCHEDULED: <2024-11-20 Wed .+1w -2d>
  #+end_src
- Orgize: repeater and warning nodes are incomplete for some combinations and units.

- Resolved (#105): ~parse_timestamp_modifiers_from_raw~ in ~src/parser/timestamp_raw.rs~ reads the modifiers of planning and body timestamps alike (~body_timestamp~); the fallback to Orgize nodes is gone.

** R12 Explicit time and range type from raw text

- Repro:
  #+begin_src org
  ,* Task
  <2024-11-20 Wed 10:00-11:00> and <2024-11-20 Wed>--<2024-11-22 Fri>
  #+end_src
- Orgize: cannot always tell an explicit time or a time range from a date range.
- Org: ~HH:MM-HH:MM~ is a time range, ~--~ a date range.
- Resolved (#105): body timestamps use ~normalize_raw_timestamp_bounds~ and ~raw_timestamp_has_explicit_time~ like planning ones. A range like ~[2024-04-01 Mon]--[2024-04-02 Tue 10:00]~ now starts at midnight of its first date (Org: ~:hour-start~ is nil); Orgize used the time of the second one. Approximation that remains for both kinds: a time is read only from a blank-separated ~HH:MM~ or ~HH:MM-HH:MM~ token, so ~10:00--11:00~ and ~10:00am~ make a timestamp without explicit time (Org's ~org-parse-time-string~ searches the string).
- Test: ~orgize_adapter_collects_ranges_repeaters_and_body_timestamps~, ~timestamps/inline-objects~.
- Tracked in #41.

** R13 Generic drawer named PROPERTIES

- Resolved (#103): the scanner decides. The property drawer is the first element of its section (after planning, also empty planning, or after comment lines only at file level, not even blank lines), and every row must be a property; otherwise it is a generic drawer without properties (Org: ~org-get-property-block~ uses ~org-property-drawer-re~). Indentation is free; values are trimmed of spaces and tabs; duplicate keys stay as separate rows (Org: the first drawer definition wins; ~effective_properties~ follows that). The resolver trims ~id:~ and ~#custom-id~ link targets of spaces and tabs before matching, which accepts slightly more than Org.
- Test: ~property_drawer_placement_matches_org~, ~property_drawer_rows_match_org~, ~property_key_is_the_token_up_to_its_last_colon~ (tables checked against Emacs 29.3 / Org 9.6.15), ~tests/data/parser/properties/planning-garbage-and-generic-drawers~.

** R14 Empty property rows recovered line by line

- Resolved (#103): rows are read line by line from the drawer (~parsed_property_from_raw_line~), so ~:EMPTY:~ is a property with an empty value.
- Test: ~orgize_adapter_falls_back_to_empty_property_drawer_rows_omitted_by_orgize~, ~orgize_adapter_preserves_empty_and_trailing_space_property_rows_across_multiple_headings~.

** R17 ParseConfig ignores in-buffer #+TODO

- Repro:
  #+begin_src org
  ,#+TODO: NEXT | FINISHED
  ,* NEXT Task
  #+end_src
- Resolved (#103): in-buffer declarations come from the scanner's keywords (~parsed_keywords~, ~resolve_todo_keywords_from_keywords~ in ~src/todo_keywords.rs~), and Orgize no longer reads keywords at all.
- Org: in-buffer declarations override the defaults. Spec syntax: ~split_todo_keyword_spec~ in ~src/todo_keywords.rs~ mirrors ~org-set-regexps-and-options~ (Org 9.6.15): the name is the text before the first ~(~ when the spec ends with ~)~, the fast key is the character right after ~(~ unless it is ~!~, ~@~ or ~/~, and log settings are ignored. Specs without a trailing ~)~ are literal names. Org assigns automatic fast keys to keywords without an explicit one; the project stores only explicit keys.

** R18 Diary timestamps in planning lines

- Resolved (#103): ~SCHEDULED: <%%(diary-float t 42)> DEADLINE: <2026-03-20 Fri>~ is a planning line read from the raw text (Org: ~:scheduled~ is the diary timestamp, the drawer below is the property drawer; only the ~<%%(SEXP)>~ form counts, never evaluated). Diary values are stored as raw ~scheduled_raw~ with no parsed date. A planning line with no valid entry (~SCHEDULED: <%%(x) y>~, ~SCHEDULED: [%%(x)]~) is still an empty planning element: it is no body text.
- Test: ~diary_planning_lines_match_org~, ~orgize_adapter_only_populates_shortcuts_when_parser_exposes_planning~, ~orgize_adapter_excludes_structured_metadata_from_body_text~; fixtures ~timestamps/planning-timestamp~ and ~body/structured-metadata-exclusion~.

** R19 Deep headline nesting recursion

- Repro: a file with many thousands of nested headings, ~*~ repeated to a very high level.
- Orgize (history): parsing built the headline tree recursively and overflowed the stack (an abort) at roughly 400 to 500 levels on a 2 MiB debug-build thread.
- Resolved (#103, #105): the scanner is iterative and the inline scanner nests at most 48 levels, so no depth needs a limit for stack safety. ~MAX_HEADING_LEVEL~ (100) stays a product rule (#44), which now only protects against pathological files, and counts ~^\*+ ~ lines only; Org reads a ~*~ line inside a block as a headline, so such a line counts, while ~**<TAB>x~ is text and never does.
- Test: ~orgize_adapter_parses_max_heading_depth_on_small_stack~, ~orgize_adapter_rejects_headings_deeper_than_limit_without_overflow~ and ~heading_depth_limit_counts_headline_lines_only~ in ~tests/orgize_adapter.rs~.
- Tracked in #41 and #44.

* Risk handling rules

Use these rules when a parser difference appears:

- Accept the behavior if it matches the documented project contract.
- Add a local fallback if the gap is small and contained.
- Add a focused fixture before broadening a workaround.
- Check the behavior against Emacs Org (~scripts/emacs-oracle.py~, ~emacs --batch -Q~) before choosing it.

* Maintenance

Update this document when a parser boundary changes in a way that affects indexed facts.

Keep historical implementation details in task archives or version control. Do not present resolved gaps as current limitations.

Add or update fixtures in the same task as a parser-contract change.
