#+TITLE: Index Generations and Cached Query Views
#+STARTUP: showall

This document defines the persistent index-state and affected-file contract used by external clients such as ~org-files-db.el~. It describes committed database state. It does not describe source files that have changed but have not yet been indexed successfully.

* Public consistency model

Every database has a persistent ~database_id~ and a monotonic ~generation~.

#+begin_example
equal database_id and equal generation
→ same known committed query-visible state

equal database_id and newer generation
→ committed query-visible state changed

different database_id
→ different or recreated database; rebuild cached views
#+end_example

~last_changed_at~ is an RFC 3339 UTC timestamp written only when the generation advances. It is not the time of the most recent indexing attempt. A successful no-op reconciliation therefore leaves both ~generation~ and ~last_changed_at~ unchanged.

The generation is advanced in the same SQLite transaction as files, headings, links, derived resolution fields, FTS maintenance, indexing context, and the affected-file journal. A reader observes either the previous committed generation or the new complete generation. A failed or rolled-back transaction publishes neither index rows nor generation rows.

One committed logical batch advances the generation once, regardless of the number of files in that batch. Raw filesystem events, debounce cycles, queries, searches, status reads, WAL checkpoints, and other SQLite maintenance do not advance it.

* Persistent schema

Schema version 12 adds three tables:

- ~index_state~ contains the singleton database identity, current generation, and ~last_changed_at~.
- ~index_generations~ contains one committed batch row per generation and its ~full_invalidation~ flag.
- ~index_generation_files~ contains the final ~upsert~ or ~delete~ action for each affected canonical path in a generation.

A new empty database starts at generation 0 with no generation journal rows. The first successful full rebuild advances it to generation 1 and publishes full invalidation.

A populated database migrated from an earlier schema receives a new database identity, generation 1, and a generation-1 full-invalidation row. Existing indexed data is retained. A client that previously cached the older database cannot safely associate it with the new identity and must rebuild its views.

Ordinary rebuilds preserve ~database_id~. Recreating the SQLite database file creates a new identity.

* Affected-file journal

The journal records all files whose persisted query-visible state changed, not only files whose source text changed.

Public actions are:

- ~upsert~: remove cached rows owned by this path and rerun a patch-safe query for the path.
- ~delete~: remove cached rows owned by this path and do not query it again.

A rename is represented as an old-path ~delete~ plus a new-path ~upsert~. Deleted paths remain in the journal after their ~files~ rows have been removed.

When link resolution changes for links stored in an otherwise unchanged source file, that source file is recorded as ~upsert~. For example, deleting a target can produce one target-path ~delete~ and several source-path ~upsert~ actions when their outgoing links become broken.

The changes reader collapses several generations into one final action per path. Paths are returned in deterministic order.

No automatic retention is applied in this version. The read contract nevertheless exposes ~oldest_available_generation~. If a later retention policy removes history older than the requested generation, the client receives ~cache_action = rebuild~ with reason ~history-unavailable~.

* Full invalidation

A generation uses ~full_invalidation = true~ when an exact affected-file set is not available or is not worth deriving safely.

The current implementation uses full invalidation for:

- every successful full rebuild;
- migration of a populated pre-version-12 database;
- incremental plans whose persisted indexing-context invalidation cannot be represented safely as a file delta.

A full-invalidation generation may omit individual file rows. When any generation in the requested range has this flag, ~orgfdb changes~ returns ~cache_action = rebuild~ and reason ~full-invalidation~.

* Read-only commands

** Status

#+begin_src shell
orgfdb status --config ./org-files-db.toml --format json
#+end_src

The response is:

#+begin_src json
{
  "schema_version": 12,
  "database_path": "/home/user/notes/org-files-db.sqlite",
  "database_id": "74f470e2-0354-4ed8-b2e0-e0647e0c706a",
  "generation": 1842,
  "last_changed_at": "2026-08-05T00:42:10Z"
}
#+end_src

~database_path~ is the absolute canonical path of the database that was actually opened. External cache clients should use this value for SQLite file-notification setup rather than reimplementing config-path resolution.

The command opens the configured database read-only. It performs no discovery, reconciliation, query planning, FTS work, migration, or timestamp update. A database whose schema predates index state must first be opened by an indexing command so the normal migration can run.

** Changes since a generation

#+begin_src shell
orgfdb changes \
  --config ./org-files-db.toml \
  --database-id 74f470e2-0354-4ed8-b2e0-e0647e0c706a \
  --since-generation 1840 \
  --format json
#+end_src

A patch response is:

#+begin_src json
{
  "schema_version": 12,
  "database_id": "74f470e2-0354-4ed8-b2e0-e0647e0c706a",
  "from_generation": 1840,
  "to_generation": 1843,
  "oldest_available_generation": 0,
  "cache_action": "patch",
  "complete": true,
  "reason": null,
  "upsert_files": [
    "/home/user/notes/project.org"
  ],
  "deleted_files": [
    "/home/user/notes/old.org"
  ]
}
#+end_src

~cache_action~ has these meanings:

- ~unchanged~: the requested generation equals the current generation.
- ~patch~: the complete requested journal interval is available and contains no full invalidation.
- ~rebuild~: the database identity changed, history is unavailable, or the interval contains full invalidation.

Stable ~reason~ values are ~database-id-changed~, ~history-unavailable~, and ~full-invalidation~. A database-ID mismatch is an expected cache transition and returns a normal JSON rebuild response. A requested generation newer than the current database is an invalid request and returns a non-zero command error.

~complete = false~ means the exact requested history cannot be supplied, as with a changed identity or unavailable history. ~complete = true~ with ~cache_action = rebuild~ means the history is complete but deliberately contains full invalidation.

* File-restricted structural queries

A patch-safe cached query view can rerun the same structural query for only the ~upsert_files~ paths:

#+begin_src shell
orgfdb query \
  --config ./org-files-db.toml \
  --restrict-files-json /tmp/affected-files.json \
  '(headings (not (done)))'
#+end_src

The JSON file contains one array of exact persisted canonical paths:

#+begin_src json
[
  "/home/user/notes/a.org",
  "/home/user/notes/b with spaces.org"
]
#+end_src

Use ~--restrict-files-json -~ to read the array from standard input. An empty array returns an empty result set. Duplicate paths are ignored. Unknown paths return no rows.

The restriction is an additional owning-file condition. It does not rewrite or weaken the user query. It applies to headings, links, files, and synthetic root rows, and existing sorting and JSON result shapes remain unchanged.

Every machine-readable structural result already exposes its owning canonical path:

- file rows expose ~path~ and ~location.file_path~;
- heading and root rows expose ~location.file_path~;
- link rows expose ~location.file_path~.

A displayed column configuration does not remove this ownership field from the JSON contract.

* Saved-view cache algorithm

A cached Emacs view remains one complete result set. It stores at least:

#+begin_example
database_id
generation
normalized saved-view definition
complete result rows
owning file path for every top-level result row
saved deterministic sort definition
#+end_example

For a patch-safe structural query view:

1. Call ~orgfdb changes~ with the cached database identity and generation.
2. Keep the cache when ~cache_action = unchanged~.
3. Rerun the complete view when ~cache_action = rebuild~.
4. For ~cache_action = patch~:
   - remove cached rows owned by every path in ~upsert_files~ and ~deleted_files~;
   - rerun the same query restricted to ~upsert_files~;
   - merge the returned rows;
   - reapply the saved deterministic sort;
   - record ~to_generation~.

This is a partial replacement of one complete view cache, not one cache per file.

* When a view is patch-safe

File-based patching is correct only when all of these conditions hold:

- the cache contains the complete result set;
- every top-level result row has one owning indexed file;
- the view has no limit, offset, top-N, or other truncation;
- result membership and rendered row data are local to the owning file for the relevant mutation;
- the client can reproduce deterministic sorting after the merge.

A full rerun is required for:

- every ~search~ view, because FTS ranking can depend on corpus-wide statistics;
- limited, offset, top-N, or otherwise truncated query views;
- global aggregates or corpus-wide ranking;
- queries whose membership depends on facts owned by other files, such as incoming-link or backlink predicates;
- result expansions that embed data owned by other files, such as backlinks or resolved target details;
- any view whose patch safety the client cannot prove.

The ~patch~ action means that the database supplied an exact affected-file journal. It does not assert that every possible saved query definition is safe to patch. ~org-files-db.el~ makes that view-level decision from the saved view definition.

* Refresh races

Separate CLI processes do not share one long-lived SQLite read transaction. A safe client refresh is:

1. Read changes up to generation N.
2. Patch or rebuild the view.
3. Read status or changes again.
4. Publish the refreshed cache only if the database is still at generation N.
5. Otherwise continue from N or repeat the refresh.

This generation check is the consistency boundary. A concurrent writer never exposes a new generation with partially committed index or journal data.

* SQLite file notifications

Clients may monitor the directory containing the canonical ~database_path~ reported by ~orgfdb status~ for activity on the main database, WAL, or SHM files. Those events are wake-up signals only. Modification times, file sizes, WAL writes, SHM writes, and filesystem events do not establish a logical index change.

After any wake-up, read ~orgfdb status~ or ~orgfdb changes~. The database identity and generation are authoritative.
