#+TITLE: Incremental Indexing
#+STARTUP: showall

This document describes the current source and reconciliation contract. It focuses on rules that protect the committed SQLite state.

* Source identity

~org-files-db~ supports Linux and other Unix-like systems, including macOS. Windows is not supported.

The indexer identifies a source by canonical Unix target-path bytes. It stores those bytes in a versioned identity format.

Configured aliases and symlink paths can point to the same source. Canonical identity deduplicates those aliases.

The database also stores a display path. UTF-8 paths stay unchanged. Other Unix paths use reversible ~path-bytes:~ encoding.

Legacy rows can have ~identity = NULL~. Reconciliation upgrades such a row after discovery observes its canonical Unix path.

Hard links remain separate sources because their canonical paths differ. A rename is represented as one deletion and one creation.

* Discovery

Explicit ~files~ entries can use any file extension. Directory roots collect regular files with a case-insensitive ~.org~ extension.

Hidden files and directories use the normal discovery rules. File and directory symlinks are followed.

Cycle detection prevents recursive directory loops inside one configured root. Overlapping roots can traverse the same target through different logical paths.

Discovery keeps this logical provenance until exclusion rules finish. Canonical identity performs final deduplication.

Read [[../config.org][Configuration Reference]] for user-facing discovery and exclusion rules.

* Missing sources and discovery errors

A missing explicit file is an absent configured source. This state lets later reconciliation remove its old indexed row safely.

A missing configured directory is an error. Traversal, metadata, or canonicalization errors also stop discovery.

The indexer does not convert these discovery errors into deletions.

Global exclusions apply to every logical discovery path. A matching global rule removes the physical source from all configured aliases.

Root-local exclusions apply only to their own ~[[dirs]]~ entry. Directory matches can prune recursive traversal.

Link resolution uses the same eligible source universe. An excluded target is outside that universe.

* Configured-root identity

A successful full reconciliation stores identity evidence for each configured directory root in ~db_metadata~.

Each record includes:

- the configured logical path
- the canonical target path
- Unix device and inode identity
- recursive mode

Explicit files and discovered subdirectories do not receive this persistent root evidence.

Automatic full reconciliation compares retained roots with their last committed identities. A changed retained root stops the operation before file deletions.

The check detects missing roots, inaccessible roots, changed target paths, and changed native identities.

A manual rebuild can accept an intentional root replacement with ~--accept-source-root-changes~. This flag does not imply ~--allow-empty~.

The indexer repeats root checks during long full operations. A mismatch rejects the operation and rolls back its write transaction.

* Stable file preparation

The indexer prepares source files before a write transaction. One prepared value represents one captured file snapshot.

Preparation reads one byte sequence. It computes SHA-256 and parses that same byte sequence.

The indexer compares modification time and size before and after the read. A mismatch causes one complete retry.

A second mismatch fails the preparation of that one file (see "Failed sources").

The prepared snapshot keeps:

- canonical identity
- modification time
- file size
- content hash
- parsed document data
- parser diagnostics
- resolved TODO keyword configuration

Later incremental application rechecks stale-sensitive evidence before mutation. A known stale preparation is never committed as current.

* Indexing context

A successful rebuild stores deterministic indexing-context fingerprints in ~db_metadata~.

The context has three parts:

- semantic parsing and indexing rules
- source-universe rules
- derived search rules

The semantic part includes parser behavior, TODO defaults, link protocols, and body-text persistence.

The source-universe part includes configured paths, recursion, exclusions, and path bases.

The derived search part includes FTS policy, body indexing, and SQLite FTS5 capability.

Incremental planning compares the stored context with the current context. An incompatible context can require wider reconciliation or a full rebuild.

The semantic fingerprint includes ~PARSER_INDEXER_CONTRACT_VERSION~ (~src/indexing_context.rs~). Any change to parser or indexer output for unchanged input must bump it, so existing databases reparse all files on the next incremental or watch run. The guard test ~tests/parser_contract_guard.rs~ hashes the parsed output of every fixture under ~tests/data/parser~ and compares it, together with the version, against ~tests/data/parser/CONTRACT~. When it fails, bump the version and update that file.

~query.timezone~ is query-only configuration. It does not invalidate indexed source facts.

* Change planning

Change planning is read-only. It checks database context before it discovers or reads actionable files.

An actionable plan compares stored source identities with current discovered identities.

The plan can classify files as:

- unchanged
- metadata-only
- created
- modified
- deleted
- failed

The normal unchanged path compares ~mtime_ns~ and file size. Other cases can capture one stable byte snapshot and compare its content hash.

Deletion requires successful discovery of the relevant source universe. A failed current source does not become a deletion by accident.

Existing plan entries keep the expected database row identity. Transactional application rechecks that identity before mutation.

** Failed sources

One unreadable or unparsable source file must not fail the whole rebuild or stop the watcher. A file whose preparation fails is skipped. Failures are a read error, invalid UTF-8, an unstable snapshot, or a parse error such as heading depth above 100.

- Invalid UTF-8 is never decoded lossily, because byte offsets must match the file. The file is skipped.
- A rebuild does not index a skipped file. The rebuild commits all other files.
- Incremental and watcher application leaves the last good rows of a skipped file untouched. It does not delete them and does not record the new hash or modification time, so the next run retries the file.
- A skipped file still counts as a current source for the stale-plan identity check. It is not a deletion candidate.
- Each skipped file prints ~warning: <path>: skipped: <cause>~ to stderr. The commands still exit with code ~0~; see ~docs/cli.org~.
- A failure that a retry can resolve without the file changing (unstable snapshot, file vanished or interrupted read) is marked transient. The watcher applies the rest of the batch, then requeues the whole batch with backoff (see "Watcher execution").

* Transactional application

The indexer applies one accepted plan inside a controlled SQLite transaction.

The transaction updates canonical file facts and dependent rows. Foreign keys remove obsolete dependent data when a file row is replaced or deleted.

The same transaction updates link resolution and derived search state when the plan requires those operations. Link resolution is scoped: it re-resolves links owned by created, modified or metadata-updated files, links that were never resolved, and file or id links that have no target file (for example after the target was deleted), point at an affected file, or name an id defined in an affected file. Same-file links and unsupported links only depend on their own file and are kept. A plan with index invalidations takes the full pass. Scoped resolution must equal a full pass on the same database; a test compares both after title, id, custom id, create and delete edits.

The transaction also updates persistent generation state. A failed transaction leaves the previous committed state intact.

* Effective properties and tags

Raw property rows remain stored with source information. The index also materializes resolved effective property values.

Schema version 10 introduced the ~effective_properties~ projection. Query matching reads this projection instead of rebuilding inherited values recursively.

Raw direct tags remain canonical facts. Schema version 11 introduced ordered, deduplicated ~effective_tags~ for each heading.

File ~FILETAGS~ participate in normal tag inheritance. The public ~all_tags~ query field uses this projection.

* Watcher candidate batching

The watcher treats filesystem notifications as hints. Event kinds do not select database mutations directly.

Normal file events contribute candidate paths. Directory topology changes and backend uncertainty request full configured-source reconciliation.

Incomplete rename information, overflow, dropped events, and rescan requests also request full reconciliation.

Candidate paths pass through the current source-universe rules. Unrelated paths and normal SQLite sidecar activity are ignored.

One normalized batch retains at most 1,024 distinct candidates. A larger batch becomes one full-reconciliation request.

A full-reconciliation request supersedes path candidates in the same batch.

* Watcher execution

The watcher controller uses a default debounce interval of 250 milliseconds. Relevant input resets the pending deadline.

The controller stores bounded normalized work, not an unbounded raw event queue.

Only one reconciliation runs at a time. Events that arrive during execution remain pending for the next run.

A failed execution remains eligible for a later retry through the controller state.

The runtime classifies execution errors. Transient errors requeue the batch and the watcher keeps running:

- SQLite ~BUSY~ and ~LOCKED~
- an IO ~NotFound~ or ~Interrupted~ failure for a file that vanished or was interrupted while it was indexed
- an unstable file snapshot

Retries use exponential backoff: 1 s, doubling, capped at 30 s, without a retry limit. New input merges into the pending batch but does not shorten the backoff. Each retry writes the attempt, the delay and the cause to stderr. A successful execution resets the backoff. During shutdown the pending batch is attempted once without waiting; a transient failure then ends the watcher.

All other errors stay fatal. This includes an unavailable or replaced watch root, discovery and source-root errors, stale or rejected plans, and all other database and parse-setup errors. The runtime terminates before any deletion caused by an unavailable root.

Shutdown stops new event intake and flushes work that the controller already accepted.

* Filesystem observation

The ~notify~ crate observes configured inputs. Source eligibility and database decisions remain in the indexer.

Configured directories keep their recursive mode. Parent watches help detect replacement of configured roots.

Explicit files also use parent observation. This supports editor save patterns that replace a file.

The translated event buffer is bounded. Overflow collapses to one uncertainty state and requests full reconciliation.

A mutating event with no usable path also requests conservative reconciliation.

* Watcher startup and recovery

The watcher installs and refreshes registrations before its initial full reconciliation completes.

It keeps bounded overlap state during registration replacement. This reduces the risk of lost events during the hand-off.

A changed registered root identity stops the runtime before database mutation. Backend uncertainty also refreshes registrations.

The runtime returns fatal source, registration, channel, indexer, and plan errors to its caller. It does not restart itself silently.

Read [[../cli.org][CLI Reference]] for the user-facing ~watch~ lifecycle.

* Generations and affected files

Full and incremental writes use the same persistent generation contract.

A transaction that changes query-visible state advances the database generation once. A no-op reconciliation leaves it unchanged.

The same transaction records affected owning files when an exact file delta is available.

Full rebuilds and broad invalidations can publish a full invalidation instead of an unsafe partial delta.

Read [[./index-generations-and-changes.org][Index Generations and Changes]] for the public consistency and delta contract.
