#+TITLE: Incremental Indexing Source-Set Contract
#+STARTUP: showall

* Source identity

org-files-db supports Linux and Unix-like systems, including macOS. Windows is unsupported. The indexer identifies a source by its canonical Unix target-path bytes, encoded as a version-tagged byte sequence. This identity is stable across configured aliases and symlink paths. The database also keeps a human-facing display path: UTF-8 paths are stored unchanged, while non-UTF-8 paths use reversible percent-escaped bytes with the ~path-bytes:~ prefix.

Legacy databases have only a TEXT path and retain ~identity = NULL~ after the version-8 migration. The original native bytes cannot be reconstructed safely. A successful rebuild or future reconciliation upgrades the row only after discovery observes its canonical Unix path.

Hard links are separate sources because their canonical paths are distinct. A rename is therefore represented as deletion plus creation until a later task adds explicit rename correlation.

* Discovery policy

- Explicit configured files are regular-file overrides and may have any extension.
- Directory roots collect regular files with an ASCII case-insensitive ~.org~ extension.
- Hidden entries are not special.
- File and directory symlinks are followed. Directory cycles and repeated traversal are prevented within each configured root; directory targets outside the configured root remain eligible.
- Overlapping roots may traverse the same physical directory independently so later root-local exclusions can use the correct logical provenance. The resulting files are still globally deduplicated by canonical identity.

* Failure policy

A missing explicit file becomes an absent configured source so a later change planner can remove its persisted state without trying to canonicalize a missing leaf. A missing configured directory root, or any traversal/stat/canonicalization error other than an explicit missing file, is a hard discovery failure. Such a failure must not be interpreted as deletion.

Configured exclusions are evaluated before the final source set and link-resolution universe are built. The universe retains explicit inclusions plus one scope for every configured directory root, including its logical-to-canonical directory provenance and local rules. Global file exclusions are evaluated for every logical discovery provenance and remove a matched physical identity everywhere; directory-local exclusions apply only to their own logical root. Link resolution asks this same universe, so an excluded target is outside the indexed universe rather than missing within it. Directory matches prune recursive traversal. An explicit file matched by a global rule is ignored before stat or canonicalization, even if it is missing. Home-relative patterns are expanded once during configuration loading and use that stable basis thereafter. A source set made empty solely by valid exclusions, including a pruned tree, is an intentional rebuild input; genuinely empty input retains the full-rebuild safety guard.

* Per-file preparation

Before any database transaction, rebuild prepares each discovered file into an owned value containing the canonical identity, resolved TODO keywords, normalized document, diagnostics, and DB-ready metadata. Preparation reads the source bytes once per attempt, computes a lowercase hexadecimal SHA-256 hash over those exact bytes, and decodes and parses that same byte sequence.

Preparation compares mtime nanoseconds and size before and after the read. A mismatch retries the complete preparation once; a second mismatch fails with file-path context and opens no write transaction. The resulting mtime, size, and content hash are the snapshot evidence retained for later change planning. A prepared value represents its captured source snapshot: before a later incremental mutation, the caller must revalidate that evidence. A known-stale value must be retried or rejected and must not be committed as current.

Full rebuild prepares every file before its all-or-nothing write transaction and assigns ~indexed_at~ only while writing each prepared file. It does not claim a filesystem-wide atomic snapshot; a file may still change after preparation and before the transaction. Later incremental application must perform the documented stale-preparation revalidation.

* Indexing context and invalidation

Every successful rebuild writes a version and deterministic SHA-256 fingerprint for three indexing-context components to ~db_metadata~ in the same transaction as indexed facts, link resolution, and search trust metadata. Full rebuild does not compare the previous context and remains the recovery path for missing, malformed, or unsupported metadata. Later incremental planning treats such metadata as untrusted and requires a full rebuild.

- The semantic component covers the parser/indexer contract, configured default TODO keywords in their declared order, the effective plain-link protocol set, and body-text persistence. A mismatch requires reparsing all indexed files. Changing body-text persistence also requires a derived-search rebuild; direction-specific optimisation is deferred. Selective reparsing would require separately persisted per-file dependency evidence.
- The source-universe component covers resolved logical Unix paths for explicit files and configured directory roots, recursion, global exclusions, root-local exclusions, and the stable configuration/home bases used by discovery. Set-like inputs are sorted and deduplicated. A mismatch requires source-universe and link reconciliation.
- The derived-search component covers the FTS policy, FTS schema contract, body-index policy, and the persisted/current SQLite FTS5 capability. A mismatch requires rebuilding derived search state.

The comparison API returns ~Compatible~, ~FullRebuildRequired~, or a combinable set of ~ReparseAllFiles~, ~ReconcileSourceUniverseAndLinks~, and ~RebuildDerivedSearch~ actions. Missing keys, unsupported contract versions, invalid fingerprint text, and non-TEXT SQLite metadata values are all fail-safe ~FullRebuildRequired~ results; only actual SQLite access failures are returned as errors. Query-only settings, including ~query.timezone~, are excluded and do not invalidate source facts.

Fingerprint inputs use a tagged, length-prefixed binary encoding. Strings, booleans, enum-like values, lists, and native Unix path bytes are encoded without lossy path conversion. Source paths are the resolved logical configuration paths rather than only canonical targets, so root provenance and exclusion semantics remain visible to future reconciliation.

* Change planning

Change planning is read-only. It first checks the configured FTS5 capability and the persisted indexing context. Missing, malformed, or unsupported context metadata, and malformed populated stored file identities, produce a terminal ~FullRebuildRequired~ result without discovery, source reads, parsing, or actionable file changes.

An actionable plan compares valid stored identities with successfully discovered canonical identities. It reports unchanged, metadata-only, created, modified, deleted, and failed files in native Unix identity-byte order. Existing entries carry the expected ~files.id~ selected by identity (or the exact UTF-8 legacy display-path fallback); created entries have no existing row ID. Later transactional application must verify that this row and identity still match rather than repeating an ambiguous path lookup. A row is deleted only when discovery completed successfully and its identity was not observed in the eligible current source set. A missing explicit logical path is never deleted directly by display path, and a current file that later fails stat, capture, UTF-8 decoding, or parsing remains observed rather than becoming deleted.

The normal unchanged fast path compares ~mtime_ns~ and ~size~. Forced verification, changed metadata, and non-comparable stored hashes capture one stable byte snapshot. Once captured, its own metadata is authoritative: equal hash and equal captured metadata is unchanged, while equal hash and changed captured metadata is metadata-only. Hashes are stored only as ~sha256:<64 lowercase hexadecimal characters>~. NULL, legacy bare hashes, unknown prefixes, uppercase text, malformed text, and non-TEXT SQLite hash values are non-comparable; they cause modified-file preparation so a later application can upgrade the stored representation. Malformed, unsupported, or non-BLOB populated identities, and unusable path, mtime, or size values, require a full rebuild. Metadata-only files retain captured snapshot evidence without decoding or parsing. Reparse-all invalidation overrides the fast path, while derived-search-only invalidation does not parse unchanged sources.

* Transactional application

Only a failure-free planned result can be converted into a single-use actionable change set. The mutation boundary rejects terminal, failed, malformed, and stale plans without committing a partial result. Before application it verifies source snapshots; inside one immediate SQLite transaction it verifies the expected file-row baseline before updating metadata, replacing file-owned facts, or deleting a file. Replacement preserves the file row while dependent surrogate IDs are deliberately recreated. FTS, search capability metadata, link resolution, and indexing context are reconciled once before commit. The database records the validated source snapshots for that change set; it does not claim an atomic snapshot shared with the filesystem.

~properties~ are canonical source facts. Schema version 10 materializes their visible per-heading values in the mandatory ~effective_properties~ projection during the same transaction. The projection is rebuilt deterministically from property rows and the stored heading tree, including root-level ~#+PROPERTY~ and ~#+CATEGORY~ facts; ordinary keywords remain keywords. Property inheritance never crosses a file boundary.

~tags~ are canonical direct tag facts. Schema version 11 materializes the ordered, deduplicated tag set visible at each heading in ~effective_tags~ during the same transaction. Root ~FILETAGS~ participate in normal inheritance, metadata-only changes leave the projection unchanged, and replacement or deletion removes stale rows through the controlled file transaction and foreign-key cascades. The public ~all_tags~ array is built from this normalized projection; ~headings.all_tags_json~ no longer exists.

* Watcher candidate batching

The backend-independent watcher layer accepts raw path-bearing event hints plus explicit backend-uncertainty signals. Create, modify, remove, metadata, and other event kinds do not select database operations. A complete rename contributes both reported paths; an incomplete rename, backend overflow, dropped-event indication, rescan request, or equivalent uncertainty requests full configured-source reconciliation.

Candidate paths are normalized through the Phase 6 source universe captured from discovery. Existing paths use their canonical Unix target identity. Missing or renamed-away paths reuse retained logical-to-canonical source mappings, including explicit files and symlinked sources, without requiring the leaf to remain present. Explicit configured files remain eligible with any extension; directory roots accept only case-insensitive ~.org~ paths and retain their recursive, non-recursive, global-exclusion, and root-local-exclusion semantics.

Equivalent path hints are deduplicated by the version-tagged native Unix file identity and emitted in that identity order. A reconciliation request supersedes all path candidates in the batch. An empty or fully irrelevant batch produces an empty candidate set and performs no indexing work by itself.

* Watcher execution controller

The watcher execution controller uses a monotonic caller-provided timestamp and a default debounce interval of 250 milliseconds. Each relevant input resets the pending deadline. The interval is an internal setting so later CLI integration can expose or replace it without changing batching semantics. Tests advance timestamps directly and do not sleep.

Pending inputs are stored only as their normalized result, not as an unbounded raw event queue. Candidate batches merge by native Unix file identity, while a full reconciliation request supersedes all candidates. Once the deadline is reached, the controller starts exactly one execution and dispatches either bounded candidate reconciliation or complete configured-source reconciliation through the Phase 6 handoff.

An active execution blocks a second execution but does not block collection of the next pending batch. Inputs accepted while Phase 6 is running remain pending for a later execution. A failed execution is returned to the pending state and merged with later work; its retry becomes eligible after one debounce interval, avoiding both silent event loss and an immediate tight retry loop. Phase 6 errors retain their path context, and Phase 6 plan rejections are reported as watcher execution failures.

Shutdown uses a flush policy. The controller stops accepting new inputs, allows an active execution to finish, and makes any pending batch immediately eligible without waiting for its debounce deadline. Shutdown is complete only when no active or pending batch remains.
