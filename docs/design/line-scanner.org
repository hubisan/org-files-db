#+TITLE: Line Scanner
#+STARTUP: showall

This document describes the own Org scanner that replaced Orgize in three stages (#41). Stage 1 (#101) added the line scanner next to the adapter. Stage 2 (#103) built the production parse path, ~OrgizeAdapter~ in ~src/parser/orgize_adapter.rs~, from the scanner: every structural fact comes from it. Stage 3 (#105, done) reads the inline objects with own code in ~src/parser/inline_scanner.rs~ and removed the ~orgize~ dependency.

* Goal and scope

Orgize was replaced because its node model deviates from Org in many small places (see the register in [[./parser-risks.org][Parser Risks]]) and because its recursive tree limits heading depth. The replacement is deliberately not a full Org parser. It reproduces what Emacs Org 9.6 reports for the facts the index stores (checked with Emacs 29.3, and by ~scripts/emacs-oracle.py~). Where the scanner and the former Orgize-based adapter disagreed, the scanner follows Emacs.

The scanner has two stages. Both work on byte offsets into the UTF-8 source and are iterative, so nesting depth never grows the call stack.

- Stage A, ~src/parser/line_lexer.rs~: a pure classifier for one line.
- Stage B, ~src/parser/structure_scanner.rs~: an automaton over the classified lines that builds the structural model.

Timestamps, links, title parsing and property rows stay in their existing helpers (see the section on helpers).

* Stage A: line classes

Stage A never looks at neighbouring lines. A line ends at ~\n~; a ~\r~ right before it is not part of the text. Blanks are spaces and tabs. Classes are tried in this order, the first match wins.

| Class | Rule | Notes |
|-
| ~Headline~ | ~^\*+ ~ (one or more stars and a space) | Level is the star count. A bare ~*~, ~*\t~ and ~**x~ are text, verified with ~org-element-parse-buffer~. #101 proposed ~^\*+[ \t]~ and ~^\*+$~; Emacs disagrees, and Orgize agrees with Emacs here. |
| ~Empty~ | only blanks | |
| ~Comment~ | blanks, ~#~, then a space or the line end | |
| ~BlockBegin~ | blanks, ~#+begin_~ (any case), at least one non-blank name character | Arguments after the name are free text. The name is the maximal non-blank run (~#+begin_x:~ has the name ~x:~). |
| ~BlockEnd~ | blanks, ~#+end_~ (any case), name, blanks only | ~#+end_x q~ is text. |
| ~DynBlockBegin~ | blanks, ~#+begin:~ (any case), optional blanks, at least one non-blank name character | The start of a dynamic block (~#+BEGIN: clocktable :scope file~). Without a name (~#+BEGIN:~) the line is a keyword. |
| ~Keyword~ | blanks, ~#+~, a non-empty key without blanks or colon, ~:~, optional blanks, value | ~#+KEY:value~ is a keyword; ~#+a b: c~, ~#+: x~ and ~#+key~ are text. Block and dynamic block lines are tried first. |
| ~Planning~ | blanks, then ~SCHEDULED:~, ~DEADLINE:~ or ~CLOSED:~ in any case | Nothing after the keyword is needed; ~CLOSED:~ alone is a planning line. ~SCHEDULEDX:~ is not. |
| ~Drawer~ | blanks, ~:NAME:~, blanks | NAME is one or more Unicode alphanumerics, ~_~ or ~-~. Stage B decides between a drawer and a property row. |
| ~DrawerEnd~ | blanks, ~:END:~ (any case), blanks | |
| ~FixedWidth~ | blanks, ~:~, then a space or the line end | |
| ~Text~ | everything else | ~::~, ~:::~, ~:a b:~ and ~:x:y:~ are text. |

The class list is shorter than the sketch in ~old-files/docs/lexer-design.org~ on purpose. Clock lines, table rules and formulas do not affect the facts the scanner must reproduce. Keyword names keep the case of the source; the model exposes ranges instead of copies.

* Stage B: structure automaton

** Section position and containers

The automaton keeps two things. The section position decides whether a planning line or a property drawer is still allowed. A stack of open containers decides how far a search for an end line may look.

| Position | Meaning |
|-
| ~FileStart~ | before the first headline, only comment lines seen so far |
| ~AfterHeadline~ | the line directly after a headline |
| ~AfterPlanning~ | the line directly after the planning line |
| ~Body~ | everything else |

The diagram is in [[./line-scanner.svg][line-scanner.svg]] (source: ~line-scanner.dot~, render with ~dot -Tsvg docs/design/line-scanner.dot -o docs/design/line-scanner.svg~).

** Rules, each checked against Emacs

- *Headlines always end the section.* The search limit for any end line is the next headline line. A headline-looking line inside a src, example or quote block or inside a drawer is a headline, and the block or drawer is then unclosed (Emacs: ~* not~ inside ~#+begin_example~ is a headline). Only a block that is closed before the next headline is a block.
- *Unclosed blocks and drawers are text.* A begin line without a matching end before the limit is a paragraph line; the lines after it are classified as if it were not there. A search that found nothing is remembered per name and limit, so a run of unclosed begins stays linear.
- *Blocks end at the first matching end line.* The name is compared case-insensitively. A non-matching ~#+end_~ line inside is content. Nested blocks of different names are not tracked for the outer block: ~#+begin_quote~, ~#+begin_src~, ~#+end_quote~, ~#+end_src~ is a quote block with an unclosed src block inside.
- *Raw and greater blocks.* ~src~, ~example~, ~export~, ~comment~ and ~verse~ contents are raw: nothing inside is structure. ~quote~, ~center~ and every other name (special blocks such as ~justify~) contain parsed content. The content of a greater block is scanned with its end line as the limit, so a drawer that starts inside and ends outside is unclosed.
- *Drawers end at the first ~:END:~ line* (any case), searched up to the limit. A drawer cannot nest because the first ~:END:~ line always ends the outer one. A ~:END:~ line outside a drawer starts a drawer named END when another ~:END:~ follows (Emacs reports ~drawer name=END~ for that). Drawer names may hold hyphens and non-ASCII letters (Emacs: ~drawer name=my-drawer~, ~name=äö~).
- *Dynamic blocks* start at ~#+BEGIN: name~ and end at the first ~#+END:~ or ~#+END~ line (any case, blanks around) before the limit. Their content is parsed like a drawer's, so the begin and end lines are no keywords. An unclosed begin line is text, and a stray ~#+END:~ is a keyword (Emacs: ~#+BEGIN: x~ / ~#+END:~ gives no keyword element, ~#+END:~ alone gives ~END~).
- *Planning* only on the line directly after a headline. A second planning line, a blank line or a comment line in between makes it text.
- *Property drawer* only when ~:PROPERTIES:~ is the first element of its section, optionally after the planning line. At file level only comment lines may precede it, not even blank lines, keywords or planning lines. The name is matched in any case, because ~org-entry-get~ reads ~:properties:~ while ~org-element~ reports a generic drawer; the adapter follows ~org-entry-get~, like the Emacs oracle.
- *Property drawers with other rows.* ~org-element~ builds a property drawer, and ~org-get-property-block~ finds one, only when every row between ~:PROPERTIES:~ and ~:END:~ is a property: ~:KEY:~ with a key of non-blank characters, alone or followed by a blank and a value (~org-property-re~; ~:a b: c~ and ~:ID:x~ are no rows). Otherwise Emacs reads a generic drawer, parses its content (comments, blocks, keywords) and ~org-entry-get~ returns no property of it. The scanner does the same: such a drawer is a drawer region without rows. A key is the token up to its last colon (~:a:b: c~ has the key ~a:b~).
- *Affiliated keywords.* ~#+NAME:~, ~#+CAPTION:~, ~#+HEADER:~, ~#+RESULTS:~, ~#+ATTR_x:~ and the other Org affiliated keywords belong to the next element when a non-empty line follows inside the same container. They are then no document keywords (the output lists them in ~affiliated~), and the element range starts at the first of them. A comment line after them is part of a paragraph, not a comment. Without a following element (a blank line, a headline or the end of the file after the whole chain of them) they are plain keywords (Emacs: ~#+NAME: n~ before ~#+TITLE: t~ gives only ~TITLE~; ~#+NAME: x~ before a blank line gives ~NAME~).
- *Comments and fixed-width lines* form one region per run of consecutive lines.
- *Line endings.* CRLF is handled in the lexer. A lone ~\r~ is part of the text.
- *Depth.* The scanner returns an error for a headline deeper than ~MAX_HEADING_LEVEL~ (100, #44), which the adapter reports as a parse error naming level and line. Only ~^\*+ ~ lines count, wherever they stand, since Org reads a ~*~ line inside a block as a headline; ~**\tx~ is text and never counts. The scanner is iterative and does not need the limit for stack safety; it stays a product rule.

** Output model

~scan_structure~ returns a ~Structure~ with these parts.

- ~headings~: level, parent index, line number, headline range, subtree range (up to the next heading of the same or a lower level), section range (up to the next heading of any level), optional planning line, optional property drawer.
- ~file_properties~: the property drawer of the file-level section.
- ~keywords~: key, value and line ranges of keyword lines outside raw blocks, with a flag for lines outside any block or drawer (body text leaves those out). ~affiliated~ lists the affiliated keyword lines the same way.
- ~regions~: blocks (name, range, content range), dynamic blocks, generic drawers, comment runs and fixed-width runs, ordered by start. Ranges end after the terminator of the last line; Emacs also includes blank lines after an element in its range, the scanner does not.

The synthetic level-0 file root is not part of the scanner output. The adapter builds it from the file-level facts.

* What the adapter takes from the scanner

~OrgizeAdapter::parse_document_core~ builds the document in this order.

- Heading tree, levels, parents, line numbers, subtree ranges (~byte_start~ and ~byte_end~) and the depth error: ~headings~.
- Document keywords and the combined title: ~keywords~ (~parsed_keywords~). In-buffer ~#+TODO~, ~#+SEQ_TODO~ and ~#+TYP_TODO~ resolution in ~src/todo_keywords.rs~ uses the same keywords, so no second parse runs.
- Planning timestamps: the planning line, read by ~planning_timestamps~ in ~src/parser/timestamp_raw.rs~ like ~org-element-planning-parser~ (every keyword in the line, its timestamp directly after it, a ~--~ range is one timestamp).
- Property rows of headings and of the file: the property drawers.
- Title, TODO keyword, priority and tags: the raw headline line, split by ~split_headline_title~ and the other helpers in ~src/parser/title.rs~ (keyword and priority only directly at the start, tags from the last tag block, a CR before the line feed is no part of the line).
- Body text: the section range without the planning line, the property drawer and the top-level keyword lines, each with the blank lines after it (Org's ~:post-blank~).
- Link scanning: ignored ranges are keyword and affiliated lines, planning lines, comment and fixed-width runs, and the whole range of src, example, export and comment blocks; source contexts come from drawer, verse, quote, center and justify regions, property drawers and headline titles.

* Inline objects (stage 3)

~src/parser/inline_scanner.rs~ reads what lies between the structure: timestamps and inline code, verbatim, inline source and export snippets (~scan_inline~), and the visible text of titles (~normalize_title_text~). It follows ~org-element~ (Org 9.6.15, checked with Emacs 29.3) the way the line scanner does: a unit of text is lexed forward and an object that starts earlier hides what lies inside it.

Units. The body text comes from ~blanked_body_text~, a copy of the source with the same byte offsets in which everything the scanner knows as structure is blanked and every other structural-looking line is defused (unclosed begin lines, stray end lines, ~*~ followed by a tab). ~body_units~ cuts it into the texts in which Org parses objects:

- paragraphs, which end at a blank line, a list item, a table row or rule, a horizontal rule, a footnote definition (~[fn:x]~ at the line start), a LaTeX environment with its end line, a clock line, or at a line that leaves the list item that holds the paragraph (indentation, tabs count to the next multiple of 8);
- the text of a list item behind its bullet, counter and checkbox, and the tag of a description item (~- tag :: text~, for ~-~, ~+~ and ~*~ bullets only, at the last ~ ::~ of the line), each as a text of its own;
- table cells (between the bars, blanks trimmed; a rule row has none), and no text at all in a table.el table (a full rule line, then lines that start with ~|~ or ~+~, ending in a rule, with more than one rule);
- the content of a verse block as one text, blank lines included;
- a clock line, in which only the timestamps count (Emacs keeps them in the ~:value~ of the clock element, so ~org-element-map~ does not list them; orgfdb has always stored them as body timestamps);
- a headline title: the text behind the TODO keyword, the priority cookie and the word ~COMMENT~ up to the tags, as Org parses it.

Objects. ~Lexer~ tries an object at every character that can start one, in the order of ~org-element--object-lex~, and steps over what it finds: emphasis (bold, italic, underline, strike-through, code, verbatim) with the hard-coded rules of ~org-element--parse-generic-emphasis~ (opening after a space, ~-~, ~(~, ~'~, ~"~, ~{~ or a line start and before a non-space; closing after a non-space and before a space or one of ~-.,;:!?'")}\[~; any number of lines, because ~org-element~ 9.6 has no limit, unlike ~org-emphasis-regexp-components~ that only fontification uses; "space" is what the Org syntax table calls whitespace, which includes NBSP and the Unicode spaces), subscripts and superscripts, bracket, angle and plain links, timestamps, statistics cookies, inline footnotes, export snippets, macros, targets and radio targets, inline source blocks, entities (by the list of ~org-entities~ in ~src/parser/inline_entities.rs~) and LaTeX fragments. Containers parse their contents with the restrictions of ~org-element-object-restrictions~: a link description has no links, timestamps or footnotes, a table cell no inline source and no cookie, a radio target only emphasis, code and the like. A timestamp is ~org-element--timestamp-regexp~ (any text after the date up to the first ~]~ or ~>~ of the line, so ~<2024-04-01 Mon +1x>~ and ~<2024-04-01 Mon .+1m/2m>~ are timestamps), its raw value is read as ~org-element-timestamp-parser~ does, and range type, times, bounds and modifiers come from ~timestamp_raw.rs~ like for planning timestamps. Not read: citations, inline babel calls, line breaks and other object parsing inside a macro or latex fragment. A plain or angle link uses the configured protocols and ~org-link-plain-re~ / ~org-link-angle-re~ of Org 9.6; a bracket link uses the extent of ~link_scanner~ so that both agree.

Facts. Code, verbatim, inline source and snippet ranges are the ranges link scanning skips; other objects that swallow text (macros, LaTeX fragments) are not, as before. The adapter drops a timestamp that lies inside a bracket link of the scanner. Nesting is capped at 48 levels and every forward search is an indexed lookup or bounded by the object, so hostile input cannot overflow the stack or make a scan quadratic.

Titles. ~normalize_title_text~ renders the lexed title: the markers of bold, italic, underline, code and verbatim are dropped, statistics cookies removed, a bracket link replaced by its rendered description or its decoded target; strike-through, sub- and superscripts and inline footnotes keep their markers and render their contents; everything else stays as written. Leading and trailing spaces and tabs go. Titles without one of ~* / _ = ~ [~ skip the lexer.

* What stays in helpers

The scanner only finds lines. It reuses these modules and adds no second implementation.

- ~properties.rs~: property rows (~parsed_property_from_raw_line~), file keyword properties and tags.
- ~title.rs~: headline title, tags, TODO keyword and priority from the raw headline line.
- ~timestamp_raw.rs~: planning entries and timestamp values from the planning line.
- ~link_scanner.rs~: links, fed with the ignored ranges above.
- ~line_index.rs~: line numbers for byte offsets.

* Regression corpus

~src/parser/corpus_tests.rs~ replaced the stage 1 differential test, because the adapter is the scanner now. It feeds every ~tests/data/parser/**/fixture.org~, every file in ~tests/data/emacs-oracle/~, every ~docs/**/*.org~, ~README.org~, ~CHANGELOG.org~, about 120 hand-written adversarial inputs and 1500 deterministic random line sequences (~ADAPTER_CORPUS_CASES~ for more) through the adapter in a debug build. Every input must parse without a panic (or fail with the depth error), keep every heading, body, timestamp and link range on the source, and leave no structural line in the text the inline scanner reads. What Emacs decides is checked against Emacs: the parser fixtures in ~tests/data/parser/~ and ~tests/data/emacs-oracle/structure.org~ run in ~scripts/emacs-oracle.py~, and the parser contract guard (~tests/parser_contract_guard.rs~) pins their output.

* Resolved differences from Orgize

The stage 1 differential test allowed these adapter deviations from Emacs. The adapter now follows Emacs on each (verified with ~emacs --batch -Q~, ~org-element-parse-buffer~ and ~org-entry-get~). The parser contract version is 9 since #105.

- A planning keyword line without a timestamp (~SCHEDULED: garbage~, ~CLOSED:~) is an empty planning element (Emacs: planning L2-2, property-drawer L3-5), so the property drawer after it counts and the line is not body text.
- A block ends at the first matching end line, names compare without case (Emacs: src-block L2-5 across a non-matching ~#+end_example~; src-block L2-3 for ~#+begin_SRC~ ... ~#+End_src~).
- ~:my-drawer:~ and ~:äö:~ are drawers (Emacs: ~drawer name=my-drawer~, ~name=äö~).
- A drawer after ~#+NAME:~ starts at the keyword (Emacs: drawer L2-5).
- ~#+NAME:~ before a keyword, a comment, a stray end line or an unclosed block is no keyword element (Emacs: keyword TITLE, paragraph).
- A quote, center or special block without content is a block (Emacs: quote-block L1-2).
- Found on the way, with the same evidence: a property drawer with a row that is no property has no properties; a planning line holds every keyword in it; ~#+BEGIN: name~ ... ~#+END:~ is a dynamic block; priority cookies count only at the start of the title or directly after the keyword (~* foo [#A] x~ has no priority); ~* TODO [#10] x~ drops the cookie from the title like ~* [#10] x~; ~#+TITLE: t <2024-01-01>~ is a title; the tags of a CRLF headline are read.

* Staging plan

- Stage 1 (#101): lexer, scanner, differential test, this document.
- Stage 2 (#103, done): the production path is built from the scanner, Orgize is reduced to the inline seam, the differential test became the regression corpus, and every allowed deviation follows Emacs.
- Stage 3 (#105, done): own inline scanning replaces the three inline uses (timestamp nodes and inline code ranges, title normalization, timestamp conversion) and the dependency is removed. ~MAX_HEADING_LEVEL~ (100) is unchanged: the scanners need no limit for stack safety, so it only protects against pathological files and stays a product rule until the owner decides.

* Open questions

- Lists, tables, footnote definitions and LaTeX environments (~\begin{x}~ to ~\end{x}~) are modeled for inline objects only (see above). Emacs hides raw lines inside LaTeX environments and tables from block and drawer detection; the corpus found no such case. Model them when a corpus file needs it.
- Keyword lines inside a list item count as top-level for body text, because the scanner does not track indentation.
