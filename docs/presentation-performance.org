#+TITLE: Presentation Performance Benchmark
#+STARTUP: showall

* Purpose

This benchmark measures the complete uncached Rust presentation path.

It measures the sequential implementation before presentation cache or parallel optimization work.

The benchmark uses synthetic structural queries with 100, 1,000, 10,000, and 50,000 query results by default.

It also measures expanded rows from tags, effective properties, and keywords.

The payload analyzer measures how the current ~presentation-json~ wire format uses bytes.

* Status

The benchmark harness is implemented in ~orgfdb-presentation-benchmark~.

A local release benchmark completed on Linux x86_64 with eight available CPUs.

The run used one warmup and three measured iterations for each workload.

The payload analyzer is implemented in ~orgfdb-presentation-payload-analysis~.

The analyzer follows the active production ~presentation-json~ wire format.

The payload-size task uses analyzer schema version 2 for the compact version 2 wire format.

* Benchmark corpus

Each target result uses one small Org file and one level-1 heading.

Each heading contains three tags and two local properties.

Each file also contains two non-title document keywords.

The corpus generator uses deterministic names and values.

The JSON output records the corpus fingerprint for each result size.

The benchmark queries return exactly the requested number of original results.

Expanded workloads can produce more presentation rows than original query results.

* Workloads

The benchmark runs these workloads for every configured result size:

- ~headings.narrow~ uses one displayed title cell per heading result.
- ~headings.normal~ uses four displayed cells per heading result.
- ~headings.wide~ uses eleven displayed heading cells without row expansion.
- ~headings.tags~ expands effective heading tags.
- ~headings.effective-properties~ expands effective heading properties.
- ~files.keywords~ expands file keywords.

Each workload uses sorting and shared column widths.

The specifications also exercise fixed widths, maximum widths, truncation, and hidden sort columns.

The output records the original result count and the final presentation row count.

* Measured stages

The internal benchmark uses the production query and presentation code.

It records these timing distributions:

- database query execution
- row expansion
- sort-key creation
- sorting
- displayed-value extraction
- shared width calculation
- truncation, padding, and final row formatting
- complete presentation preparation
- compact JSON serialization
- query, presentation, and serialization together

The truncation stage also creates the final ~display_text~ strings.

These operations share one production loop and are measured together.

The benchmark excludes input cloning from isolated stage timers.

It prepares cloned stage input before each measured sample.

* Process measurements

The benchmark records one process-startup probe with ~orgfdb --help~.

This value includes process creation, CLI parsing, and help generation.

It does not include database or presentation work.

Each total CLI sample starts a fresh ~orgfdb~ process and runs the complete ~presentation-json~ query.

The runner captures stdout through a pipe.

Total CLI time therefore includes payload transfer into the benchmark process.

The output records the exact stdout payload size in bytes.

* Run the timing benchmark

Build both release binaries first.

#+begin_src sh
cargo build --release --bin orgfdb --bin orgfdb-presentation-benchmark
#+end_src

Run a short smoke benchmark before the full measurement.

#+begin_src sh
target/release/orgfdb-presentation-benchmark \
  --orgfdb target/release/orgfdb \
  --rows 100,1000 \
  --warmups 1 \
  --iterations 2 \
  --work-dir /tmp/orgfdb-presentation-smoke-work \
  --output /tmp/orgfdb-presentation-smoke.json
#+end_src

Use new work and output paths for a full benchmark.

#+begin_src sh
target/release/orgfdb-presentation-benchmark \
  --orgfdb target/release/orgfdb \
  --rows 100,1000,10000,50000 \
  --warmups 1 \
  --iterations 3 \
  --work-dir /tmp/orgfdb-presentation-benchmark-work \
  --output /tmp/orgfdb-presentation-benchmark.json
#+end_src

Keep the machine under normal low-load conditions during the measurement.

* Timing benchmark output

The benchmark writes one JSON document.

Each timing contains ~min_ns~, ~median_ns~, ~p95_ns~, ~max_ns~, and the sample count.

Each size record also contains corpus generation time, rebuild time, database size, and a corpus fingerprint.

Setup time is reproducibility evidence.

It is not part of the presentation latency totals.

The protocol record states that the benchmark uses no presentation cache and no presentation parallelism.

* Timing baseline

The completed local run shows that database query execution dominates normal presentation work at large result sizes.

The process-startup median is about 1.72 ms.

At 50,000 original results, the timing run produced these payloads:

| Workload | Results | Rows | CLI payload bytes |
|----------+---------+------+-------------------|
| ~headings.normal~ | 50,000 | 50,000 | 47,300,127 |
| ~headings.tags~ | 50,000 | 150,000 | 74,677,907 |
| ~headings.effective-properties~ | 50,000 | 150,000 | 87,347,199 |
| ~files.keywords~ | 50,000 | 150,000 | 94,425,521 |

The normal workload scales from 93,456 bytes at 100 results to 47,300,127 bytes at 50,000 results.

* Payload analysis

The payload analyzer reuses databases from an existing timing benchmark work directory.

It does not rebuild the corpus or modify the database.

** Run the payload analyzer

Build the analyzer after the timing benchmark work directory exists.

#+begin_src sh
cargo build --release --bin orgfdb-presentation-payload-analysis
#+end_src

Run the analyzer for the same result sizes.

#+begin_src sh
target/release/orgfdb-presentation-payload-analysis \
  --rows 100,1000,10000,50000 \
  --work-dir /tmp/orgfdb-presentation-benchmark-work \
  --output /tmp/orgfdb-presentation-payload-analysis.json
#+end_src

Use a new output path for each analysis run.

** Analysis behavior

The analyzer executes each existing workload once for each requested result size.

It serializes the same production ~PresentationResponse~ that the CLI uses.

The analyzer records ~compact_json_bytes~ without the final newline.

It also records ~cli_payload_bytes~, which adds the one-byte CLI newline.

** Payload sections

The byte sections form an exact hierarchy.

#+begin_example
compact_json_bytes
  = response_metadata_bytes
  + results_bytes
  + rows_bytes

rows_bytes
  = row_metadata_bytes
  + row_context_bytes
  + cells_bytes

cells_bytes
  = cell_structure_bytes
  + search_text_bytes
  + display_text_bytes
  + semantic_role_bytes
#+end_example

~results_bytes~ and ~rows_bytes~ are the serialized values of the two top-level fields.

~response_metadata_bytes~ contains the remaining top-level JSON data and syntax.

~row_context_bytes~ contains the serialized ~row_context~ values, including ~null~.

~cells_bytes~ contains every serialized cells array.

The cell value counters measure the encoded wire values.

For presentation version 2, ~display_text_bytes~ includes the ~null~ sentinel when the display value equals ~search_text~.

~cell_structure_bytes~ contains the remaining cell-array syntax and separators.

** Field-name and syntax overhead

The analyzer counts serialized object-key bytes separately.

The field-name counters include the quotes around each object key.

The analyzer also counts JSON braces, brackets, commas, and colons outside strings.

~structural_overhead.combined_bytes~ adds these field-name and syntax counts.

This value does not include quotes or escaping that belong to scalar string values.

** Repeated values

The repetition counters identify exact repeated values.

~search_display_equal_cells~ counts cells where ~search_text~ and ~display_text~ are identical.

~search_display_duplicate_bytes~ counts one serialized copy of each identical value.

~display_is_padded_search_cells~ counts cells where ~display_text~ only adds right-side spaces.

~padded_search_repeated_content_bytes~ counts the repeated serialized search content in those padded cells.

Row-context counters compare context scalar values with cell ~search_text~ values in the same row.

Result counters compare cell ~search_text~ values with exact scalar values in the referenced original result.

Result number values use their JSON decimal text for this comparison.

JSON ~null~ values do not match presentation text.

The repetition counters can overlap.

Do not add their byte counts as one possible saving value.

** Averages

The analyzer records these averages:

- serialized ~results~ bytes per original result
- serialized ~rows~ bytes per presentation row
- serialized cell bytes per cell
- total compact payload bytes per original result

Repeated object structure is the largest common wire cost.

* Compact wire candidate benchmark

The payload-size task compared five representations on identical in-memory ~PresentationResponse~ values.

The candidate run used 100 and 50,000 original results.

Every candidate passed semantic equality checks for metadata, results, rows, contexts, cells, display text, and roles.

The selected representation uses:

- positional row arrays with one shared row schema
- positional row-context arrays with explicit shared shapes
- positional cell arrays with one shared cell schema
- ~display_text = null~ when ~display_text == search_text~
- integer role indexes with one shared ~role_values~ table

At 50,000 results, the selected representation changes payload size as follows:

| Workload | Version 1 bytes | Selected bytes | Reduction |
|----------+-----------------+----------------+-----------|
| ~headings.narrow~ | 36,000,126 | 31,500,618 | 12.50 % |
| ~headings.normal~ | 47,800,126 | 35,400,618 | 25.94 % |
| ~headings.wide~ | 76,233,458 | 49,067,286 | 35.64 % |
| ~headings.tags~ | 75,177,906 | 44,478,398 | 40.84 % |
| ~headings.effective-properties~ | 87,847,198 | 56,156,785 | 36.07 % |
| ~files.keywords~ | 95,925,520 | 63,026,012 | 34.30 % |

The null display sentinel adds another 0.55 MB to 3.70 MB reduction beyond positional arrays at 50,000 results.

Role indexes add another 0.30 MB to 5.40 MB reduction beyond the display-null representation.

The selected representation also serializes faster than version 1 for every 50,000-result workload in this run.

Median serialization time changes as follows:

| Workload | Version 1 | Selected |
|----------+-----------+----------|
| ~headings.narrow~ | 52.58 ms | 32.05 ms |
| ~headings.normal~ | 48.10 ms | 37.48 ms |
| ~headings.wide~ | 106.04 ms | 56.72 ms |
| ~headings.tags~ | 87.61 ms | 55.58 ms |
| ~headings.effective-properties~ | 98.95 ms | 82.13 ms |
| ~files.keywords~ | 95.19 ms | 70.90 ms |

The 100-result workloads also have smaller payloads and no serialization regression with the selected representation.

These results select the positional display-null role-index representation for ~presentation-json~ version 2.

The original query-result objects remain unchanged inside the top-level ~results~ array.

The compact rules apply only to presentation rows, row contexts, cells, and roles.

The temporary candidate benchmark is removed after this selection.

** Remaining result-object overhead

The version 2 payload keeps each original query result as an object.

At 50,000 results, these objects still contain 13.4 MB to 16.3 MB of field-name bytes.

The client uses these complete results for actions through ~result_index~.

A compact result representation needs explicit schemas for file, heading, and link results.

It also needs rules for nested path, property, keyword, link, source, target, and child data.

That change adds a second result-decoding contract and requires another wire-format version.

Version 2 keeps these objects unchanged to keep the action boundary simple.

A separate payload task can benchmark result-object compaction if the extra contract is acceptable.


* Parallelism evaluation baseline

The final ~presentation-json~ version 2 production run is the sequential baseline for the parallelism task.

The baseline already measures all relevant presentation stages on 100, 1,000, 10,000, and 50,000 original results.

At 50,000 original results, expanded workloads create 150,000 presentation rows.

Their median isolated sorting time is:

| Workload | Rows | Sorting |
|----------+------+---------|
| ~headings.tags~ | 150,000 | 219.10 ms |
| ~headings.effective-properties~ | 150,000 | 301.79 ms |
| ~files.keywords~ | 150,000 | 264.35 ms |

The wide non-expanded workload creates 50,000 rows and 550,000 cells.

Its median value extraction time is 51.87 ms.

Its median truncation, padding, and row formatting time is 64.53 ms.

These measurements identify CPU-bound work before the project adds a parallel dependency.

The first parallel experiment uses Rayon 1.12.0 through the optional ~presentation-parallel-benchmark~ feature.

The production ~PresentationSpec::build_response~ path stays sequential during this experiment.

The experiment compares:

- sequential and parallel sort-key creation
- sequential and parallel sorting
- sequential and parallel value extraction with deterministic width reduction
- sequential and parallel final row formatting
- complete sequential presentation processing
- complete processing with parallel sort work only
- complete processing with parallel layout work only
- complete processing with all measured candidate stages in parallel

The experiment forces the parallel candidates at every requested result size.

This exposes coordination overhead at 100 and 1,000 results before a production threshold is selected.

Every parallel candidate must produce the exact same ~PresentationResponse~ as the sequential baseline.

SQLite query loading stays sequential and outside the candidate timing.

Complete CLI timing remains a final production gate after the benchmark selects a strategy and threshold.


* Parallel candidate v1 results

The first candidate benchmark runs on 14 available CPUs with 14 Rayon worker threads.

It forces parallel work at every requested size to expose coordination overhead.

All parallel responses equal the sequential response.

At 100 and 1,000 results, forced parallel work loses clearly.

At 10,000 results, ~headings.wide~ is the only strong complete-pipeline winner.

Its layout-only candidate changes complete presentation time by -44.6 %.

At 50,000 results, the complete candidates change as follows:

| Workload | Sort only | Layout only | All parallel |
|----------+-----------+-------------+--------------|
| ~headings.narrow~ | -25.6 % | +13.1 % | +5.1 % |
| ~headings.normal~ | +17.1 % | -10.8 % | -12.7 % |
| ~headings.wide~ | +11.4 % | -40.7 % | -33.0 % |
| ~headings.tags~ | -3.7 % | +4.9 % | -4.4 % |
| ~headings.effective-properties~ | -2.2 % | +11.4 % | -4.1 % |
| ~files.keywords~ | -16.3 % | -4.4 % | -23.5 % |

The stage data explains why one global mode is not suitable.

At 50,000 results, parallel value extraction improves every workload except ~headings.narrow~.

Parallel formatting strongly improves ~headings.normal~ and ~headings.wide~, but it loses for expanded tag and effective-property rows.

Parallel sorting strongly improves the isolated 150,000-row expanded sorting stage.

The second candidate benchmark therefore tests one selective strategy.

The strategy uses these thresholds:

- parallel sort at 100,000 presentation rows
- parallel extraction at 200,000 cells
- parallel extraction at 100,000 cells when the presentation has at least 8 columns
- parallel formatting only for one-row-per-result presentations that meet an extraction threshold

These thresholds keep small workloads sequential.

They also keep expanded-row formatting sequential when v1 shows a loss.

The v2 benchmark measures extraction-only and formatting-only totals in addition to the previous candidates.

Production remains sequential until this selective candidate passes the complete-presentation benchmark.
