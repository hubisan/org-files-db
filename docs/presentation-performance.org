#+TITLE: Presentation Performance Benchmarks
#+STARTUP: showall

* Purpose

The presentation benchmark code was removed in #114 and lives in git history before that change. This page keeps the measurements that explain completed design decisions.

The benchmarks used the final production presentation and cache implementations at the time of measurement.

Historical A/B implementations did not remain executable only to reproduce old comparisons.

* Benchmark classification

| Component | Former purpose |
|-----------+----------------|
| ~orgfdb-presentation-benchmark~ | Regression benchmark for query, presentation, serialization, payload size, and full CLI latency. |
| ~orgfdb-presentation-payload-analysis~ | Diagnostic that attributed production ~presentation-json~ bytes to results, rows, cells, roles, and repeated values. |
| ~orgfdb-presentation-cache-benchmark~ | Production-path diagnostic for view rebuild readiness, cache-hit CLI latency, and the uncached reference on one host. |
| ~orgfdb-presentation-parallel-benchmark~ | Completed A/B benchmark; the paired sequential-versus-parallel experiment selected the production thresholds. |
| ~orgfdb-query-sql-benchmark~ | Query diagnostic benchmark; see ~docs/query-sql-performance.org~. |

All of these were removed in #114.

* Shared deterministic corpus

The timing, payload, cache, and query SQL benchmarks can reuse the same deterministic corpus shape.

Each target result uses one small Org file and one level-1 heading.

Each heading contains three tags and two local properties.

Each file contains two non-title document keywords.

The corpus generator uses deterministic names and values.

The timing benchmark records a corpus fingerprint for each result size.

The default timing sizes are 100, 1,000, 10,000, and 50,000 query results.

The cache benchmark defaults to 50,000 query results.

* Shared workloads

The production presentation benchmarks use these workloads:

- ~headings.narrow~ displays one title cell per heading result.
- ~headings.normal~ displays four cells per heading result.
- ~headings.wide~ displays eleven cells per heading result.
- ~headings.tags~ expands effective heading tags.
- ~headings.effective-properties~ expands effective heading properties.
- ~files.keywords~ expands file keywords.

The specifications exercise sorting, hidden sort columns, widths, truncation, and row expansion.

The cache benchmark keeps four representative large workloads:

- ~headings.wide~
- ~headings.tags~
- ~headings.effective-properties~
- ~files.keywords~

* Regression benchmark

** Production presentation timing

~orgfdb-presentation-benchmark~ is the primary long-term presentation regression benchmark.

It uses the active production ~PresentationSpec::build_response~ strategy.

It does not force rejected sequential or parallel alternatives.

It measures these stages:

- database query execution
- row expansion
- sort-key creation
- sorting
- value extraction
- width calculation
- truncation, padding, and row formatting
- complete presentation processing
- compact JSON serialization
- query, presentation, and serialization together
- full fresh-process CLI latency
- process startup
- presentation payload size

The benchmark records the active production parallel strategy for each workload.

The current output schema version is 3.

The benchmark protects the production query-to-presentation path from large performance regressions.

It also protects representative expanded-row and wide-layout workloads.

** Timing output

Each timing contains ~min_ns~, ~median_ns~, ~p95_ns~, ~max_ns~, and the sample count.

Each size record contains corpus generation time, rebuild time, database size, and the corpus fingerprint.

Setup time is reproducibility evidence.

It is not part of the presentation latency totals.

Fresh CLI samples capture stdout through a pipe.

The CLI measurement therefore includes payload transfer into the benchmark process.

* Diagnostic benchmarks

** Presentation payload analysis

~orgfdb-presentation-payload-analysis~ is a reusable wire-format diagnostic.

It reads databases from an existing timing benchmark work directory.

It executes each workload once for each requested result size.

It serializes the active production ~PresentationResponse~.

The current analyzer output schema version is 2.

The analyzer records these main byte groups:

- response metadata
- original ~results~
- presentation rows
- row metadata
- row context
- cell structure
- ~search_text~
- ~display_text~
- semantic roles
- JSON field names and syntax

It also records exact repetition counters and per-result, per-row, and per-cell averages.

Use this diagnostic when payload size changes unexpectedly.

Use it before a future wire-format change that needs byte attribution.

** Production presentation cache benchmark

~orgfdb-presentation-cache-benchmark~ measures the production registered-view cache path.

The benchmark starts a real ~orgfdb watch~ process for each corpus size.

It uses the production view control protocol and production rebuild workers.

It uses the production cache store and ~orgfdb view read~ for cache hits.

The benchmark uses private XDG runtime and cache directories below its work directory.

It does not write benchmark cache data to the normal user cache directory.

The current cache benchmark output schema version is 2.

For each workload, the benchmark records:

- initial registration-to-ready time
- full rebuild-to-ready timing for new view revisions
- fresh-process ~orgfdb view read~ latency
- fresh-process uncached ~presentation-json~ latency
- payload size

Before each timed rebuild sample, the benchmark removes the current view registration.

The timer starts when the benchmark registers the same definition with a new revision.

The sample ends when the production control protocol reports the new cache ready.

This operation uses the normal complete rebuild and atomic cache publication path.

The timer does not include removal, file notification, or database update cost.

Production tests cover generation replacement, obsolete worker termination, and bounded rebuild coordination.

The benchmark no longer duplicates those behaviors with alternative benchmark-only worker implementations.

Every cache-hit sample must equal the uncached production presentation payload byte for byte.

* Historical measurements from completed design decisions

The following sections explain current architecture choices. None of the benchmark executables exist any more.

** Compact presentation wire selection

The payload task compared several row and cell representations on identical in-memory responses.

The selected version 2 representation uses positional rows, contexts, and cells.

It also uses a shared role table and a null display sentinel for equal text.

At 50,000 results, the final production payload changed as follows:

| Workload | Version 1 bytes | Version 2 bytes | Reduction |
|----------+-----------------+-----------------+-----------|
| ~headings.narrow~ | 36,000,126 | 31,600,618 | 12.22 % |
| ~headings.normal~ | 47,800,126 | 35,500,618 | 25.73 % |
| ~headings.wide~ | 76,233,458 | 49,267,286 | 35.37 % |
| ~headings.tags~ | 75,177,906 | 44,578,398 | 40.70 % |
| ~headings.effective-properties~ | 87,847,198 | 56,256,785 | 35.96 % |
| ~files.keywords~ | 95,925,520 | 63,326,012 | 33.98 % |

Median JSON serialization time also decreased for every 50,000-result workload.

| Workload | Version 1 | Version 2 | Change |
|----------+-----------+-----------+--------|
| ~headings.narrow~ | 68.44 ms | 51.09 ms | -25.4 % |
| ~headings.normal~ | 71.58 ms | 42.15 ms | -41.1 % |
| ~headings.wide~ | 103.75 ms | 43.86 ms | -57.7 % |
| ~headings.tags~ | 127.65 ms | 71.96 ms | -43.6 % |
| ~headings.effective-properties~ | 140.45 ms | 87.48 ms | -37.7 % |
| ~files.keywords~ | 181.41 ms | 80.59 ms | -55.6 % |

These results selected ~presentation-json~ version 2.

The normal ~orgfdb query --format json~ contract did not change.

The temporary representation A/B benchmark was removed after the decision.

The payload analyzer followed the selected production representation.

** Selective Rayon parallelism

The parallelism task first tested forced parallel stages at several result sizes.

Small forced parallel workloads lost because coordination cost exceeded the saved CPU work.

A corrected paired v3 benchmark compared the same candidate path with alternating sample order.

The selected strategy changed complete presentation time as follows on the measured 8-CPU Linux host:

| Workload | Results | Presentation rows | Selective change |
|----------+---------+-------------------+------------------|
| ~headings.wide~ | 10,000 | 10,000 | -39.2 % |
| ~headings.normal~ | 50,000 | 50,000 | -18.2 % |
| ~headings.wide~ | 50,000 | 50,000 | -39.8 % |
| ~headings.tags~ | 50,000 | 150,000 | -14.9 % |
| ~headings.effective-properties~ | 50,000 | 150,000 | -8.6 % |
| ~files.keywords~ | 50,000 | 150,000 | -11.2 % |

The selected production rules are:

- Parallel sorting starts at 150,000 presentation rows.
- Parallel layout applies only to one-row-per-result presentations.
- Layout parallelism starts at 200,000 cells.
- A layout with at least 8 columns starts at 100,000 cells.
- Expanded-row extraction and formatting stay sequential.
- SQLite query execution stays sequential.
- Row expansion and width resolution stay sequential.
- JSON serialization stays sequential.

The production v4 validation confirmed that the selected dispatch reached the normal build path.

| Workload | Results | Rows | Parallel work | Presentation median | CLI median |
|----------+---------+------+---------------+---------------------+------------|
| ~headings.wide~ | 10,000 | 10,000 | extraction and formatting | 20.21 ms | 128.27 ms |
| ~headings.narrow~ | 50,000 | 50,000 | none | 44.70 ms | 460.64 ms |
| ~headings.normal~ | 50,000 | 50,000 | extraction and formatting | 61.11 ms | 546.88 ms |
| ~headings.wide~ | 50,000 | 50,000 | extraction and formatting | 110.97 ms | 657.29 ms |
| ~headings.tags~ | 50,000 | 150,000 | sorting | 254.35 ms | 778.15 ms |
| ~headings.effective-properties~ | 50,000 | 150,000 | sorting | 342.21 ms | 1,023.84 ms |
| ~files.keywords~ | 50,000 | 150,000 | sorting | 263.37 ms | 903.03 ms |

The former ~presentation-parallel-benchmark~ feature and binary only supported this completed A/B decision.

They were removed from the benchmark infrastructure.

The normal timing benchmark records the current production strategy instead.

** Eager registered-view cache selection

The original cache validation used a benchmark-only cache worker before production cache code existed.

It compared sequential and parallel rebuild groups and tested obsolete worker termination.

At 50,000 results, the validation measured these single-view costs:

| Workload | Payload | Uncached CLI median | Rebuild + persist median | Cache-hit median | Hit reduction |
|----------+---------+---------------------+--------------------------+------------------+---------------|
| ~headings.wide~ | 48.61 MiB | 667.10 ms | 536.73 ms | 49.42 ms | -92.6 % |
| ~headings.tags~ | 43.32 MiB | 796.03 ms | 660.92 ms | 44.57 ms | -94.4 % |
| ~headings.effective-properties~ | 54.46 MiB | 1,025.24 ms | 901.85 ms | 53.63 ms | -94.8 % |
| ~files.keywords~ | 62.82 MiB | 888.26 ms | 746.45 ms | 60.15 ms | -93.2 % |

The validation also showed clear wall-time gains from concurrent rebuild workers.

| Views | Sequential median | Parallel unbounded median | Parallel budgeted median | Unbounded peak RSS | Budgeted peak RSS |
|-------+-------------------+---------------------------+--------------------------+--------------------+-------------------|
| 1 | 581.12 ms | 529.00 ms | 546.93 ms | 203.02 MiB | 202.93 MiB |
| 3 | 2,198.72 ms | 1,088.42 ms | 1,460.27 ms | 535.45 MiB | 570.88 MiB |
| 5 | 3,833.55 ms | 1,465.69 ms | 1,432.10 ms | 1,085.49 MiB | 1,044.61 MiB |
| 10 | 7,025.47 ms | 4,721.05 ms | 3,827.00 ms | 2,245.45 MiB | 1,929.29 MiB |

Ten large workers used too much memory for the default operating target on that host.

This evidence supported bounded concurrent rebuild workers.

The obsolete-generation experiment also confirmed that a terminated old worker did not publish its old generation.

The replacement generation then rebuilt successfully.

These measurements supported the eager registered-view cache architecture and separate rebuild worker processes.

The pre-production cache simulator no longer represents the final implementation.

Its worker modes, rebuild-group comparisons, and cancellation experiment are removed from executable benchmark code.

The cache benchmark measured the real production cache path.

* Raw benchmark results

Raw timing JSON files normally stay outside version control.

Keep a raw result when a future task needs durable evidence for an architecture decision.

Record the host, build profile, CPU availability, command, and corpus fingerprint with timing evidence.
