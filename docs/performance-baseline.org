#+TITLE: SQLite Query Performance Baseline
#+STARTUP: showall

* Purpose

The benchmark measures structural queries and production FTS5 search. It also records historical index-tuning evidence.

The benchmark does not change authoritative schema decisions, query semantics, or CI limits.

Schema version 10 materialized effective properties. Schema version 11 materialized effective tags. Schema version 12 added index generations and affected-file journaling.

These projections avoid repeated query-time reconstruction of inherited metadata.

* Run

Use an optimized release build. Use new, untracked paths for the work directory and JSON output.

#+begin_src sh
cargo run --release --bin orgfdb-benchmark -- \
  --files 1000 --seed 1 --warmups 5 --iterations 30 \
  --work-dir /tmp/orgfdb-benchmark-work \
  --output /tmp/orgfdb-benchmark.json
#+end_src

The corpus generator is deterministic for the same version, file count, and seed.

Its manifest records:

- file count
- expected heading count
- expected link count
- seed
- generation duration
- SHA-256 fingerprint

The corpus includes several outline shapes and indexed Org features. These include TODO states, tags, properties, timestamps, links, and search text.

The workload matrix measures direct and inherited tag matching separately. Inherited tag queries use the materialized ~effective_tags~ projection.

The runner writes benchmark JSON only to the requested output path. It does not modify source fixtures or documentation.

* Measurement protocol

Workloads have stable IDs and a stable execution order.

Structural query workloads use the production parser, validator, compiler, executor, and result shaper.

FTS title and body workloads use the production search path. An unavailable FTS feature becomes a structured skip.

The runner does not replace unavailable FTS with ~LIKE~ or regular-expression queries.

After rebuild, the runner closes the writer connection. Each workload group opens a fresh read-only connection for one cold-connection sample.

The runner then opens another read-only connection for warm-up and measured samples.

By default, it uses five warm-ups and thirty measured executions.

A fresh connection is only a cold connection. It does not prove that operating-system or storage caches are cold.

Run separate experiments if you need operating-system cache measurements.

* Recorded output

Each workload records important execution evidence, including:

- query expression
- production path
- output mode
- compiled SQL
- deterministic parameters
- result count
- cold-connection sample
- warmed timing distributions
- ~EXPLAIN QUERY PLAN~ output

The environment record includes build and SQLite information. It also records relevant command arguments and available platform details.

For each database variant, the output records database and WAL size evidence around the standard checkpoint.

The normal baseline does not run ~VACUUM~.

Keep machine-specific benchmark JSON untracked. Repository documentation must not present one machine as a universal timing baseline.

* SQLite linkage and dbstat

The project enables the ~rusqlite~ ~functions~ feature. It does not enable bundled SQLite.

On Unix-like systems, the build therefore uses an external SQLite library from the normal build environment.

The Rust process and the system ~sqlite3~ command can use different SQLite libraries. Equal version numbers do not prove equal binaries.

The benchmark records the runtime SQLite version and compile options from its own linked library.

It also tests ~sqlite_compileoption_used('ENABLE_DBSTAT_VTAB')~ and queries ~dbstat~ directly.

If ~dbstat~ is unavailable, the benchmark records a structured capability skip. Missing ~dbstat~ does not fail the benchmark.

When available, ~dbstat~ supplies per-index page, allocated-byte, and payload-byte evidence.

Storage evidence alone does not prove query benefit. Use query plans, timing distributions, rebuild measurements, and incremental measurements together.

On Linux, inspect linked libraries and ~dbstat~ capability with:

#+begin_src sh
ldd target/release/orgfdb-benchmark | grep -i sqlite
ldd "$(command -v sqlite3)" | grep -i sqlite
pkg-config --variable=libdir sqlite3
sqlite3 ':memory:' "SELECT sqlite_compileoption_used('ENABLE_DBSTAT_VTAB');"
sqlite3 ':memory:' 'SELECT count(*) FROM dbstat;'
#+end_src

* Historical index-tuning profiles

The runner can reconstruct the historical schema-version-8 index set for index-profile measurements.

Each profile uses a fresh database through the normal production path. Only the measured index set differs from the current schema.

All compared profiles use the same corpus, workload order, warm-ups, iterations, SQLite build, and application pragmas.

The runner rejects a profile comparison if result counts differ from its matching baseline variant.

The profile run does not use ~ANALYZE~, ~VACUUM~, or benchmark-only pragmas.

* Historical measured decision

The index decision used this command:

#+begin_src sh
cargo run --release --bin orgfdb-benchmark -- \
  --output .tmp/orgfdb-index-profiles-1000-fixed.json \
  --work-dir .tmp/orgfdb-index-profiles-1000-fixed-work \
  --files 1000 \
  --seed 1 \
  --warmups 5 \
  --iterations 30
#+end_src

The corpus contained 1,000 files, 5,675 headings, and 1,091 links.

The run used Linux x86_64, eight available CPUs, and SQLite 3.40.1.

FTS-disabled, title-only FTS, and body-enabled FTS variants completed. All 24 profile variants kept semantic equivalence after the incremental sequence.

The linked SQLite library did not provide ~dbstat~. The run therefore kept the structured capability skip instead of per-index page evidence.

| Candidate | Evidence | Storage delta | Decision |
|-----------+----------+---------------+----------|
| Add ~LOWER(files.path)~ | Exact case-insensitive ~file-path~ used ~idx_files_path_lower~. Warmed median latency improved by about 65-66 percent. | +164 KiB | Accept |
| Add ~LOWER(headings.title)~ | Exact title lookups used ~idx_headings_title_lower~. The file-title workload improved by about 68-70 percent. | +136 KiB | Accept |
| Add ~links(resolution_status)~ | The planner used the index. Timings had no stable gain, and incremental application became about 5-9 percent slower. | +24 KiB | Reject |
| Remove ~idx_tags_heading~ | The primary-key index on ~(heading_id, tag)~ already covers heading-first access. | -36 KiB | Accept |
| Remove ~idx_keywords_heading~ | The unique index on ~(heading_id, keyword, line_number)~ already covers heading-first access. | -16 KiB | Accept |
| Remove ~idx_timestamp_repeaters_timestamp_id~ | The ~UNIQUE~ constraint on ~timestamp_id~ already creates an equivalent index. | -16 KiB | Accept |
| Combined candidate | The combined profile also contained the rejected link-status index. | +256 KiB from version 8 | Reject as measured |

The accepted subset has an estimated net database-size increase of 232 KiB on this corpus.

The exact accepted subset was not measured as one profile. The combined profile also contained the rejected resolution-status index.

The accepted decision produced schema version 9. It added:

#+begin_src sql
CREATE INDEX idx_files_path_lower ON files(LOWER(path));
CREATE INDEX idx_headings_title_lower ON headings(LOWER(title));
#+end_src

It removed ~idx_tags_heading~, ~idx_keywords_heading~, and ~idx_timestamp_repeaters_timestamp_id~.

It did not add a resolution-status index.

Later schema versions did not change this historical index decision.

The schema-version-9 run also exposed slow inherited property resolution. One effective-value query took several seconds on the 1,000-file corpus.

Schema version 10 replaced that recursive query-time work with the materialized ~effective_properties~ projection.

A new benchmark can measure current property and effective-tag performance without changing the historical index-tuning record.
