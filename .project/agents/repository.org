* Parser validation with Emacs

Emacs is available and should be used as a reference oracle for Org-mode parser semantics when useful.

For parser tasks:

- Prefer Orgize as the implementation parser.
- Compare tricky Org syntax behavior with Emacs Org-mode, especially via ~org-element-parse-buffer~.
- Use Emacs output to validate expectations for planning lines, timestamps, special properties, tags, drawers, and agenda-relevant behavior.
- If Orgize and Emacs disagree, document the difference in the active task file before choosing behavior.
- Do not evaluate unsafe Emacs Lisp from project files.
- Do not evaluate diary expressions or arbitrary ~.dir-locals.el~ forms unless a task explicitly defines a safe, data-only subset.

* Preferred checks

Before setting a task to ~REVIEW~, run:

- ~make ci~

If not all checks can be run, explain why in the task file.

* Documentation maintenance

Keep repository documentation updated as part of the same task that changes behavior.

- CLI changes should update ~docs/cli.org~.
- Config changes should update ~docs/config.org~.
- Parser or indexing behavior changes should update the relevant files in ~docs/~.
- README claims should be updated when they become outdated.
- Do not duplicate full documentation in this file; use this file only as a repository instruction.
