* Planning

** Problem summary

Property drawers containing empty-value rows such as ~:KEY:~, ~:KEY+:~, ~:KEY: ~, and ~:KEY+: ~ were not indexed consistently. Some cases were omitted entirely, which meant ~--include properties~ returned no raw rows and property predicates could not match the affected headings after rebuild.

** Goals

- Preserve empty drawer rows as raw property rows with empty-string values.
- Keep the existing property indexing pipeline and storage schema.
- Avoid duplicate raw rows when Orgize already exposes a node-property line.

** Non-goals

- No schema migration.
- No change to effective property resolution semantics.
- No special-casing in query hydration or result shaping.

** Architecture

- Use Orgize's direct property-drawer node when available for normal drawers.
- Fall back to parsing raw ~PROPERTIES~ drawer lines only when Orgize omits some empty property rows.
- Deduplicate fallback rows by source line number so one source row still yields one stored property row.

** Execution plan

- Extend property-drawer discovery to support both normal Orgize property drawers and generic ~PROPERTIES~ drawers.
- Add narrow raw-line fallback parsing for property drawer content.
- Cover both parser-only and rebuild/query regressions with tests.
- Run the repo-preferred checks before moving the task to ~REVIEW~.

** Risks & assumptions

- Orgize can expose different syntax shapes for visually similar empty property rows, so fallback parsing must remain restricted to actual ~PROPERTIES~ drawers.
- The existing property contract already treats empty stored components as empty strings, so no public API changes are required.
