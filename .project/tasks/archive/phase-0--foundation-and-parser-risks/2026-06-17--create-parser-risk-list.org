* Planning

** Problem summary

The parser work now has active regression fixtures, an Orgize-backed adapter, and several documented behavior gaps. These risks are currently spread across ~todo.org~, archived task files, fixture comments, and adapter tests. The project needs one durable document that records parser-backend and parser-contract risks in a form that can drive future implementation decisions without re-discovering the same context.

** Goals

- Create ~docs/design/parser-risks.org~ as the single central parser-risk register.
- Cover both current Orgize-specific observations and project-owned parser contract gaps.
- Cross-link each risk to active evidence where available, especially regression fixtures and earlier task notes.
- Make the later ~Document parser risks~ backlog item effectively a maintenance/follow-up concern instead of a separate documentation effort.

** Non-goals

- No parser implementation changes.
- No adapter behavior changes.
- No DB, query, CLI, or FTS feature changes beyond documenting parser-adjacent assumptions.
- No general pipeline risk register; scope stays at parser backend and parser contract level.

** Architecture

The document should reflect the existing architecture decision that Orgize is isolated behind ~src/parser/orgize_adapter.rs~ and that the rest of the system depends on project-owned parser types. The risk register therefore needs to distinguish:

- backend extraction gaps or unstable Orgize behavior
- parser-contract gaps in the project's own internal model
- compatibility semantics that currently match Emacs/Org behavior and should not be mislabeled as backend bugs

Planned structure for ~docs/design/parser-risks.org~:

- ~#+TITLE: Parser Risks~
- short purpose statement explaining why the adapter boundary exists and why the register is maintained
- ~* Scope and Status~
  - current backend: Orgize
  - current crate version from ~Cargo.toml~: ~0.10.0-alpha.10~
  - meaning of risk states and decisions
- ~* Risk Register~
  - one subsection per risk with the same fields:
    - ~Risk~
    - ~Current status~
    - ~Observed behavior~
    - ~Why it matters~
    - ~Current decision~
    - ~Workaround / containment~
    - ~Fixtures / tests~
    - ~Follow-up~
- ~* Decision Rules~
  - when to accept behavior as current contract
  - when to add an adapter-local workaround
  - when to report upstream
  - when to consider backend replacement
- ~* Maintenance~
  - how new risky fixtures feed the register
  - when fixture expectation changes must update the risk document
