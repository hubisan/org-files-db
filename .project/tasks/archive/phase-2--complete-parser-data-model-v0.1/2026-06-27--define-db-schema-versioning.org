- User request: implement the BUILD for explicit SQLite schema versioning around ~PRAGMA user_version~.
- Scope copied from ~todo.org~:
  - Define the current schema version as the single source of truth in code.
  - Read and validate on-disk ~user_version~ during DB open/init.
  - Treat ~user_version = 0~ explicitly as missing/unversioned and migrate/init to current.
  - Fail closed on future/newer DB versions.
  - Write ~user_version~ only after successful schema application/migration.
  - Add focused tests and concise developer documentation.

* Planning

** Problem summary
DB schema versioning currently exists only implicitly. ~src/db.rs~ writes ~user_version~ before schema application, and the open/init path does not explicitly reject future DB versions.

** Goals
- Make schema versioning explicit and testable around SQLite ~PRAGMA user_version~.
- Define a single code-level current schema version constant.
- Reject newer on-disk schema versions clearly.
- Preserve current legacy migration behavior for supported older or unversioned DBs.

** Non-goals
- Do not introduce a separate migration framework.
- Do not change unrelated parser, CLI, indexer, or config behavior.
- Do not use ~.project/manual-tests~ for validation.

** Architecture
- Keep the source of truth in ~src/db/schema.rs~ alongside ~SchemaDefinition~.
- Keep open/init orchestration in ~src/db.rs~ with small helper functions for version read, validation, and write.
- Reuse the existing schema-application path for supported older/unversioned databases.

** Execution plan
1. Add ~CURRENT_SCHEMA_VERSION~ and wire ~SchemaDefinition::default()~ to it.
2. Update DB initialization to read, validate, apply, then set ~user_version~ only on success.
3. Add regression tests for fresh/current/unversioned/future/failing initialization cases.
4. Document the versioning policy in ~README.org~ and run ~make ci~.

** Risks & assumptions
- With the current schema version still at ~1~, the only supported older on-disk state is effectively ~0~ / unversioned legacy databases.
- Existing migration helpers remain the compatibility path and do not need separate version-step dispatch yet.
