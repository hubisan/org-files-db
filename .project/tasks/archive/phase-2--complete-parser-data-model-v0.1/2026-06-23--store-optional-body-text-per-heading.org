** BUILD Store optional body text per heading

Goal:
Store the body text that belongs directly to each heading in ~heading_bodies~, controlled by the existing ~search.index_body_text~ configuration.

This feature is optional because body text can consume significant database space. When ~search.index_body_text = false~, body text should not be written to ~heading_bodies~ and should not be indexed into FTS.

Context:
The schema already has a dedicated ~heading_bodies~ table so body text can stay out of the compact ~headings~ table.

Existing config:

#+begin_src toml
  [search]
  fts5_enabled = false
  index_body_text = false
#+end_src

Design decision:
- ~heading_bodies~ stores body text only when ~search.index_body_text = true~.
- ~heading_bodies~ is the source for optional body FTS indexing.
- Heading title indexing and body indexing must remain separate.
- Body text is inserted into ~heading_fts~ only when both ~search.fts5_enabled = true~ and ~search.index_body_text = true~.
- If ~search.index_body_text = false~, no body rows should be written and FTS body content should remain empty or omitted according to the existing FTS design.

Body ownership rules:
- Each regular heading owns only the body content in its own section.
- Body text must exclude child heading subtrees.
- Body text must exclude the heading line itself.
- File-level text before the first regular heading belongs to the synthetic level 0 heading.
- If there is no body text for a heading, either omit the ~heading_bodies~ row or insert an empty string consistently; prefer omitting empty rows unless existing DB writer conventions require otherwise.
- Body byte ranges should be stored as ~body_byte_start~ and ~body_byte_end~ when available.
- Byte ranges must use UTF-8 byte offsets in the original file content.
- If exact byte ranges are not available from the parser, document the limitation and keep the columns ~NULL~ rather than guessing.

Preferred table:

#+begin_src sql
  CREATE TABLE IF NOT EXISTS heading_bodies (
      heading_id          INTEGER PRIMARY KEY,
      body_text           TEXT NOT NULL,
      body_byte_start     INTEGER,
      body_byte_end       INTEGER,
      FOREIGN KEY (heading_id)
          REFERENCES headings(id)
          ON DELETE CASCADE
  );
#+end_src

* Planning

** Problem summary
- The schema and cleanup path already know about ~heading_bodies~, but the parser model and indexer pipeline do not currently carry heading body content through to persistence.
- The current FTS path always inserts empty body strings via ~body_for_fts()~, so enabling ~index_body_text~ has no effect today.
** Goals
- Extract section-local body text for the synthetic level 0 heading and regular headings.
- Persist ~heading_bodies~ only when ~search.index_body_text = true~.
- Feed body text into ~heading_fts~ only when both FTS and body indexing are enabled.
** Non-goals
- No redesign of heading/title/tag/property/timestamp parsing.
- No query/search feature work.
- No unconditional storage of body text when body indexing is disabled.
** Architecture
- Use Orgize ~Document::section()~ for file-level pre-heading content and ~Headline::section()~ for per-heading section content.
- Extend ~ParsedHeading~ with optional body text and byte-range fields rather than adding a separate parser result structure.
- Keep body extraction tied to the parser's existing structural view instead of introducing a second raw-text scanner.
** Execution plan
- Extend the parser model and Orgize adapter to populate optional body fields from section nodes.
- Add DB writer support for ~heading_bodies~ rows and teach the indexer to write them only when enabled.
- Replace the current empty-body FTS placeholder with gated body content from parsed headings.
- Add focused parser fixture/unit coverage plus indexer regressions for disabled/enabled body storage and subtree exclusion.
** Risks & assumptions
- Orgize section text may include planning lines and property drawers for regular headings; that behavior will be documented in tests rather than normalized away in this task.
- Level 0 body text may include file-level keyword lines when they are part of the document section; tests will assert the required inclusion of pre-heading content without overconstraining unrelated section details.

- None blocking after inspecting Orgize's ~section()~ API.
