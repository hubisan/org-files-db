** BUILD Parse properties drawer and file-level properties

Goal:
Extract direct Org properties from property drawers and file-level property declarations, store them as queryable property rows, and attach buffer-level properties to the synthetic level 0 heading.

This task stores direct property definitions only. It does not materialize inherited or effective properties.

* Planning

** Problem summary
The parser currently extracts only heading-local drawer properties and models them as inherited-capable rows without source, append, or per-property line information. File-level ~#+PROPERTY~ and ~#+CATEGORY~ lines are only represented as raw keywords when they occur in the zeroth section, buffer-level property drawers are not attached to the synthetic level 0 heading, and the database schema still deduplicates property rows through a uniqueness constraint.

** Goals
- Represent direct properties uniformly across regular headings and the synthetic level 0 heading.
- Parse direct properties from heading drawers, buffer-level drawers, ~#+PROPERTY~, and ~#+CATEGORY~.
- Preserve duplicate direct property definitions as separate rows.
- Normalize keys by uppercasing only and encode the trailing ~+~ as ~append = true~.
- Keep raw keyword storage separate from normalized property rows.
- Update the DB schema and migration path so direct property rows are not deduplicated.

** Non-goals
- No inherited or effective property resolution.
- No overwrite or append-value computation.
- No malformed drawer recovery beyond what Orgize exposes structurally.
- No unrelated keyword-to-property conversions.

** Architecture
Orgize remains the only syntax authority. The adapter translates Orgize property drawers, node-property nodes, and relevant keyword nodes into project-owned ~ParsedProperty~ rows. The parser output carries source, append, and line metadata. The indexer writes every parsed property row, including level 0 rows, into the ~properties~ table while still storing ~#+PROPERTY~ and ~#+CATEGORY~ as raw keyword rows in ~keywords~.

** Execution plan
- Extend the parser property model with source, append, optional value, and line metadata.
- Update the Orgize adapter to collect heading and document property drawers without collapsing duplicates.
- Add a full-buffer collection path for special keywords so ~PROPERTY~ and ~CATEGORY~ raw keyword rows are captured anywhere in the file alongside the existing TODO-keyword handling.
- Parse property-like keyword values into level 0 ~ParsedProperty~ rows.
- Update indexer and DB writer plumbing for the new property shape.
- Rebuild the ~properties~ table schema to replace ~inherited~ with ~append~ and remove uniqueness on direct rows.
- Extend parser fixtures, adapter tests, DB tests, and indexer tests for the new property behaviors.

** Risks & assumptions
- Orgize and Emacs differ for some pre-heading drawer cases and empty property forms; implementation follows Orgize and any observed mismatch should be documented here.
- Existing legacy databases may already contain rows using the old ~inherited~ column; migration must preserve them as direct rows with ~append = 0~.
- Empty properties exposed by Orgize as valid node properties should be stored as empty strings, not ~NULL~.

- None at implementation start.

* Results

** Approach
- Reworked the parser property model from inherited/local placeholders to direct property facts with ~source~, ~append~, optional ~value~, and per-property ~line_number~.
- Kept Orgize as the syntax authority:
  - heading drawers are read from ~headline.properties()~ and iterated via ~node_properties()~
  - buffer-level drawers are read from ~document.properties()~
  - malformed drawers that Orgize does not expose as property drawers remain ignored
- Added a full-buffer keyword collection path for ~TODO~, ~SEQ_TODO~, ~TYP_TODO~, ~PROPERTY~, and ~CATEGORY~ so raw keyword rows and derived file-level property rows are captured wherever these lines occur.
- Updated the DB schema and migration path so direct property rows are no longer deduplicated and the append operator is stored explicitly.
- Verified the main parser-semantics discrepancy observed during implementation and chose Orgize behavior as required:
  - Emacs ~org-element~ exposed the pre-heading ~:PROPERTIES:~ block differently from Orgize in the exploratory check
  - Orgize provides the intended buffer-level property access through ~document.properties()~, so the implementation follows Orgize for this task
- Stored Orgize-exposed empty property values as empty strings.
