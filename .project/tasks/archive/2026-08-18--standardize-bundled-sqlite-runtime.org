Start this task before further SQLite query optimization work.

Query benchmark results are not fully comparable unless the SQLite runtime is known.

The current build normally uses the system SQLite library.

Different Linux distributions, WSL environments, and machines can therefore use different SQLite versions and build configurations even when the Rust source is identical.

Goal: make the SQLite runtime part of every query performance result and determine whether a newer SQLite runtime materially changes current production query performance.

Do not change the production SQLite linking strategy only to complete this task.

In particular, do not switch permanently to bundled SQLite without separate evidence that it provides all SQLite functionality required by orgfdb.

** Phase 1 - Record SQLite runtime information

Extend ~orgfdb-query-sql-benchmark~ so every benchmark output records the SQLite runtime used for that run.

Record at least:

- ~sqlite_version()~
- ~sqlite_source_id()~
- relevant SQLite compile options
- whether the benchmark is using the normal system-linked build or an explicitly selected comparison build

Keep this information in the benchmark environment metadata.

Do not require manual notes outside the benchmark JSON to determine which SQLite runtime produced a result.

If the existing general benchmark already records useful SQLite runtime information, reuse the same representation where practical.

Keep the benchmark schema explicit when new environment fields are added.

** Phase 2 - Verify required SQLite capabilities

Before comparing an alternative SQLite build, identify the SQLite capabilities required by the current orgfdb implementation and test suite.

Do not assume that a default bundled SQLite configuration provides everything orgfdb requires.

Verify the comparison runtime against the required:

- SQLite functions
- extensions or compile-time capabilities
- limits used by orgfdb
- query behavior required by the current implementation

A comparison runtime is valid only if it can run the relevant orgfdb tests and query workloads correctly.

Do not weaken orgfdb functionality only to make an alternative SQLite build work.

** Phase 3 - Compare runtimes

Compare the normal current SQLite runtime with a recent controlled SQLite runtime.

Use the same:

- orgfdb source
- release build profile
- benchmark corpus
- benchmark parameters
- machine and operating environment

Change only the SQLite runtime or build configuration required for the comparison.

The comparison may use bundled SQLite or another controlled linking method.

The task does not prescribe the mechanism.

If bundled SQLite lacks required functionality, use another comparison method or record that limitation.

Run representative query workloads including:

- normal headings
- headings with properties
- headings with effective properties
- headings with path
- representative expensive predicate queries
- representative file queries

Measure complete query latency.

Also compare query plans when the runtime changes them.

Do not retain a SQLite runtime change only because an isolated SQL operation improves.

Require useful production-level evidence.

If the newer SQLite runtime gives no material benefit, keep the current linking strategy.

If it gives a material benefit, document the result and create a separate implementation decision before changing the production linking strategy.

Do not combine that production packaging decision with this investigation.

Update ~docs/query-sql-performance.org~ with:

- SQLite runtime metadata requirements
- compared SQLite versions

- the final decision

* Planning

** Decision update

The project will use bundled SQLite instead of selecting a SQLite runtime from the host system.

Keep benchmark schema version ~13~ and its runtime probes.

Remove the system-versus-controlled-runtime experiment from this task.

The attempted comparison did not load the requested SQLite ~3.53.4~ library.

** Problem summary

A system-linked SQLite runtime makes builds depend on the host distribution.

This dependency makes query performance and SQLite capabilities less reproducible across machines.

Bundled SQLite can pin the runtime through ~rusqlite~ and ~libsqlite3-sys~.

The project must first update ~rusqlite~ to a suitable current release.

The bundled build must also provide every SQLite capability that orgfdb requires.

** Goals

- Keep the schema version ~13~ SQLite runtime metadata.
- Update ~rusqlite~ and ~libsqlite3-sys~ to a suitable current stable combination.
- Enable bundled SQLite for normal orgfdb builds.
- Record the actual bundled SQLite version and source ID.
- Verify required SQLite capabilities against the bundled runtime.
- Establish a new bundled query performance baseline.

** Non-goals

- Do not compare system SQLite against bundled SQLite as a packaging decision.
- Do not maintain a custom external SQLite shared library.
- Do not update unrelated Rust dependencies in this task.
- Do not change query compilation, indexes, relation reuse, enrichment, or result shaping.

* Results

** Implemented bundled runtime selection

The dependency now selects ~rusqlite 0.40.2~ with ~default-features = false~.

The enabled features are ~bundled~, ~functions~, ~limits~, and ~trace~.

This keeps the existing required rusqlite features and excludes unrelated new defaults.

~Cargo.lock~ now selects ~libsqlite3-sys 0.38.2~.

The stable bundle contains SQLite ~3.53.2~.

SQLite ~3.53.4~ is newer upstream.

This task does not vendor a custom SQLite source to follow the upstream patch release.

The schema version ~13~ runtime identity remains authoritative after the build.

** Required API migration

~rusqlite 0.40.2~ deprecates the old ~Connection::profile~ interface.

The query SQL benchmark now uses ~trace_v2~ with ~SQLITE_TRACE_PROFILE~ only.

The existing stage marker and duration aggregation stay unchanged.

Normal query execution does not enable the trace callback.

The updated limits API returns ~Result<i32>~ from ~limit~ and ~set_limit~.

The runtime variable-limit helper now handles that result explicitly.

Tests restore changed limits only after the calls succeed.

SQLite integer values now decode through signed integer types before conversion to ~usize~ or ~u64~.

This applies to benchmark counts and database page metrics.

orgfdb already enables foreign keys explicitly when it opens normal database connections.

** Bundled performance baseline

The primary complete-query medians at 50000 results are:

| Workload | System SQLite 3.45.1 | Bundled SQLite 3.53.2 | Change |
|----------+----------------------+-----------------------+--------|
| headings.normal | 209.481 ms | 189.553 ms | -9.5% |
| headings.tags | 244.509 ms | 188.439 ms | -22.9% |
| headings.properties | 408.382 ms | 298.967 ms | -26.8% |
| headings.effective-properties | 314.415 ms | 273.617 ms | -13.0% |
| headings.path | 411.178 ms | 390.317 ms | -5.1% |
| files.normal | 120.974 ms | 134.772 ms | +11.4% |
| files.keywords | 263.100 ms | 251.132 ms | -4.5% |

All seven 10000-result primary workloads improve.

Six of seven 50000-result primary workloads improve.

The 50000-result ~files.normal~ median regresses by about ~11.4%~.

Its separate direct-phase profile moves in the opposite direction.

Bundled SQLite reduces its matched SQL execution, enrichment SQL execution, row decoding, and final result shaping in that profile.

The current evidence therefore does not identify a bundled SQLite operation that causes the complete-query increase.

A focused 50000-result repeat with more timing samples is required before this task moves to ~REVIEW~.

The small-result differences are mixed.

The largest absolute increase at 1000 results is about ~2.23 ms~.

** Variable-limit result

The bundled limit of ~32766~ exercises the existing runtime chunking.

At 50000 results, ~headings.path~ uses six direct-profile statements instead of four.

Its maximum bound-parameter count drops from ~50000~ to ~32766~.

The complete-query median still improves by about ~5.1%~.
