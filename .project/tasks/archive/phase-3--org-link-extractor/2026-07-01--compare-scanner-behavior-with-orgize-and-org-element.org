Goal:

- Validate accepted Phase 3 link scanner behavior against Orgize and Emacs ~org-element~ where useful.
- Document expected mismatches.
- Identify unexpected mismatches that need tests or follow-up tasks.
- Keep the project scanner contract independent from Orgize and Emacs internals.

Contract:

- The project scanner contract remains the source of truth.
- Orgize may be used for structural context where reliable.
- Orgize link nodes are optional cross-checks, not the contract.
- Emacs ~org-element~ may be used as a reference for selected ambiguous cases, especially plain-link boundary and path-end behavior.
- If Orgize detects a link that the scanner intentionally does not support, the scanner contract wins.
- If the scanner detects a supported link that Orgize misses, the scanner contract wins.
- If Emacs ~org-element~ differs from the scanner in an accepted Phase 3 case, document the mismatch and decide whether the scanner contract needs clarification.
- Phase 3 does not block on upstream Orgize fixes.
- General Orgize parser correctness issues may be reported upstream with minimal reproducible examples.
- Project-specific indexing behavior stays local.
- A friendly Orgize fork remains a last resort only.

Known mismatch candidates:

- Plain links may appear as plain text in Orgize because plain-link recognition depends on known link types.
- Angle-link support may be incomplete, absent, or different in Orgize.
- Property drawer links may not appear as Orgize link nodes even though they work as links in normal Org usage.
- Normal drawer behavior may differ between parser references and project indexing policy.
- Permissive bracket description parsing may differ.
- Multi-line link behavior may differ and remains unsupported by the project scanner.
- Unsupported forms such as radio targets and link abbreviations remain deliberate project decisions.
- Plain-link boundary and path-end behavior should be compared against Emacs ~org-element-parse-buffer~ for representative ambiguous cases.

Relevant Orgize issues to reference in project notes:

- https://github.com/PoiScript/orgize/issues/88
- https://github.com/PoiScript/orgize/issues/91

** Test results
- Emacs matched the accepted plain-link boundary and path-end cases already captured by the focused scanner tests.
- Emacs exposed angle links, plain links, property-drawer links, and normal-drawer links in the representative probe, while still excluding links in the representative ignored regions such as inline code/verbatim and source blocks.
- Emacs accepted the representative multi-line bracket example and its element span for the whitespace-terminated plain-link case included the following separator space, both of which are now documented as intentional scanner-contract differences.
- The raw `Orgize` probe surfaced only bracket links in the representative mixed-link content and did not surface angle links, plain links, property-drawer links, normal-drawer links, or the representative permissive-description / multi-line bracket probes as raw link nodes.
- No unexpected mismatch was found in the chosen fixture set, so no new follow-up task or new upstream issue was required.
