Goal:

- Document the property-resolution behavior already implemented by orgfdb.
- Clearly describe the intentional incompatibility with Org for repeated file-level ~#+PROPERTY~ definitions mixed with append definitions.
- Do not change query execution, property resolution, indexing, storage, or result hydration.

Current behavior:

- Property drawer rows and file-level ~#+PROPERTY~ rows use the same effective-value resolution.
- For one normalized key at one location:
  - the last non-append definition is the base value
  - all append definitions are appended in source order
- Append definitions participate regardless of whether they occur before, between, or after non-append definitions.
- This behavior is already implemented and must remain unchanged in this task.

Uniform orgfdb example:

#+begin_src org
:TEST: old
:TEST+: append 1
:TEST: new
:TEST+: append 2
#+end_src

orgfdb resolves this as:

#+begin_src text
new append 1 append 2
#+end_src

File-level equivalent:

#+begin_src org
,#+PROPERTY: KEYWORD_RESET old
,#+PROPERTY: KEYWORD_RESET+ appended-before-reset
,#+PROPERTY: KEYWORD_RESET replacement
,#+PROPERTY: KEYWORD_RESET+ appended-after-reset
#+end_src

orgfdb resolves this as:

#+begin_src text
replacement appended-before-reset appended-after-reset
#+end_src

Intentional Org incompatibility:

- Org may resolve the file-level example as:

#+begin_src text
replacement appended-after-reset
#+end_src

- orgfdb intentionally retains ~appended-before-reset~.
- orgfdb applies one source-independent resolution rule to:
  - property drawer rows
  - file-level ~#+PROPERTY~ rows

Rationale:

- Query semantics depend on logical property rows rather than their source representation.
- Drawer and keyword properties behave consistently.
- Consumers do not need to know whether a property originated from a drawer or a keyword.
- Raw property records continue to expose their original ~source~ and ~append~ values.
- Exact Org compatibility for this edge case would require source-specific resolver behavior and would change existing query results.

Inheritance:

- ~:inherit nil~ resolves only rows stored directly on the candidate.
- ~:inherit t~ additionally considers inherited property values.
- The documented local resolution rule remains the same in both cases.
- A local non-append value is the local base.
- Append-only local rows may extend an inherited base according to the existing implemented inheritance semantics.

Documentation changes:

- Update ~docs/reference/query-model-v0.org~.
- Update ~docs/cli.org~.
- Add a clearly labelled compatibility note.
- Document the existing uniform rule.
- Include:
  - one property-drawer example
  - one equivalent file-level keyword example
  - the orgfdb result
  - the differing Org result
  - the rationale for the deliberate incompatibility

Suggested contract text:

#+begin_src org
- orgfdb uses one source-independent resolution rule for property drawer rows and file-level ~#+PROPERTY~ rows.
- At one location, the last non-append definition is the effective base value.
- All append definitions for the same normalized key are appended to that base in source order.
- Append definitions participate regardless of whether they occur before, between, or after non-append definitions.
- This behavior intentionally differs from Org for some repeated file-level ~#+PROPERTY~ sequences.
- Raw property rows remain available with their original source and append metadata.
#+end_src
