* Planning

** Problem summary

The view registry exists only in the watcher process.

Materialized presentation data must survive separate ~orgfdb~ CLI processes in the same watcher session.

The storage layer must reject stale or unrelated cache files before a caller reads the payload.

** Goals

- Add a persistent cache store for one current payload per registered view.
- Keep each watcher session in a separate cache namespace.
- Use an explicit cache format version.
- Store validity metadata before the raw presentation payload.
- Validate the session, database, generation, view definition, and presentation wire version.
- Publish replacement payloads with an atomic rename.
- Keep cache reads compatible with direct payload streaming.
- Report a soft size warning at about ~250 MB~.

** Non-goals

- Do not start cache rebuilds.
- Do not add watcher rebuild coordination.

- Do not add a public materialized-view read command.

- Do not keep historical cache generations.
- Do not add a configurable cache directory.

** Architecture

Use ~${XDG_CACHE_HOME}/orgfdb~ when ~XDG_CACHE_HOME~ is an absolute path.

Otherwise use ~$HOME/.cache/orgfdb~.

Store presentation views below a dedicated ~presentation-views~ directory.

Hash the watcher session identity for the session directory name.

Hash the view name for the current cache file name.

Each cache file contains a small binary prefix, a JSON metadata header, and the raw presentation JSON payload.

The metadata header contains an independent cache format version.

The raw payload remains unchanged, so a later reader can stream it without JSON reserialization.

The metadata header records:

- watcher session identity
- database identity
- database generation
- view name
- view registry revision
- view-definition SHA-256 identity
- presentation wire version
- payload byte count

Write a replacement cache to a unique temporary file in the same directory.

Close the temporary file before the atomic rename to the current cache path.

Do not call ~fsync~ because this cache is disposable session data.

A reader validates the complete metadata header before it exposes the payload.

A reader also validates the stored payload length against the file size.

* Results

** Approach

The new cache store keeps each watcher session in a hashed directory below the XDG cache root.

Each view name maps to one hashed current cache file. A new generation or view revision replaces that same file.

The cache envelope uses format version ~1~. It stores a small JSON header before the unchanged presentation JSON payload.

The header records all current validity inputs except the later relative-date validity value. That value belongs to its separate follow-up task.

The view-definition identity is a SHA-256 digest of the normalized registered definition.

The writer creates a private temporary file in the same directory. It closes the file before an atomic rename publishes it.

The reader validates the complete header and payload length before it returns a streaming reader. It does not parse or reserialize the presentation payload.

The cache format version is separate from ~PRESENTATION_VERSION~. A separate producer version is not necessary for this session-local cache.

A watcher restart creates a new session identity. This already prevents reuse across a producer restart.

Payloads of at least ~250 MiB~ emit a soft warning. The cache has no hard size limit.

The storage API is not connected to rebuild workers in this task. A temporary ~dead_code~ allowance keeps this staged internal API lint-clean until the next task connects it.
