Use this cache model:

- Emacs registers a small set of named presentation views through the CLI.
- View registration is valid only for the current Emacs and watcher session.
- View registrations do not persist across watcher restarts.
- A view contains a fixed query and presentation specification.
- The specification includes columns, sorting, row layout, and other presentation inputs.
- A view produces the presentation output that Emacs needs.
- The cache stores the complete materialized presentation output.
- The cache uses persistent local storage across separate ~orgfdb~ query processes.
- Each registered view has only one current cache.
- The normal unrestricted ~orgfdb query~ interface remains unchanged.
- Add a separate ~orgfdb view~ interface in a later implementation task.

The expected lifecycle is:

- Emacs registers a cache-enabled view.
- Registration starts the initial full cache build.
- The watcher keeps the registered view current.
- Each successful database change makes the current view cache stale.
- The watcher starts a full rebuild after the database update.
- The watcher does not wait for view rebuilds before it processes more file changes.
- Rebuild different registered views in parallel.
- Do not patch cached views from individual changed files.
- Do not reuse cached results across database generations.
- Do not keep historical cache generations.

Handle consecutive database changes as one current target.

If a newer database generation appears during a rebuild, stop or discard the obsolete rebuild.

Start a new rebuild for the newest generation.

Do not publish an obsolete intermediate generation.

A view request must return data for the current valid generation.

Do not return the previous stale cache while a rebuild runs.

If the current rebuild fails, return an error for that view.

A view request must never start a rebuild.

** Risks & assumptions

The benchmark worker process is diagnostic code, not the future public ~orgfdb view~ command.

A worker startup adds a small process cost that the existing benchmark already measures separately.

Parallel full rebuilds can contend for SQLite reads, CPU, memory, and disk writes.

A 10-view test can use substantial memory because each worker owns a complete presentation response.

The benchmark must report failures instead of adding a production limit from one machine result.

A relative-date view can change while the database generation stays constant.

The later implementation must include the effective query date in validity for queries with relative date operands.

** Test results

A valid cache hit takes 44.57 ms to 60.15 ms median for the four large workloads.

The corresponding uncached CLI requests take 667.10 ms to 1,025.24 ms median.

The cache hit reduces measured read latency by 92.6 % to 94.8 %.

A full rebuild plus persistence takes 536.73 ms to 901.85 ms median.

One read after each database change already amortizes the measured eager rebuild cost.

The rebuild plus one hit is 6.8 % to 12.1 % faster than one uncached read.

Representative cache files use 43.32 MiB to 62.82 MiB per view.

One rebuild worker uses 203.02 MiB to 267.48 MiB peak RSS.

Three concurrent large workers complete in 1,088.42 ms with 535.45 MiB peak aggregate RSS in the unbounded mode.

Five budgeted workers complete in 1,432.10 ms with 1,044.61 MiB peak aggregate RSS.

Ten budgeted workers complete in 3,827.00 ms with 1,929.29 MiB peak aggregate RSS.

Ten large concurrent rebuilds are not a suitable default target on this 8-CPU host.

Use bounded concurrent rebuild workers and queue excess registered views.

The obsolete-worker experiment terminates the old worker in 13.42 ms.

The obsolete generation never becomes current.

The replacement generation rebuild completes in 839.70 ms.

Separate worker processes therefore provide a simple cancellation boundary.

The cache model remains practical and has no measured design blocker.

** Design conclusions

Proceed with the eager cache for explicit session-local presentation views.

Use complete materialized presentation JSON payloads as cache values.

Use an XDG cache location with one namespace for each watcher session.

Use a separate cache format version in addition to the presentation wire version.

Cache validity must include the active session, ~database_id~, ~generation~, view identity, and both format versions.

For relative-date queries, cache validity must also include the effective query date.

The watcher must rebuild these views when the effective query date changes.

This date-triggered rebuild does not change ~generation~ or ~changes~ semantics.

Use separate rebuild worker processes.

Run different view rebuilds concurrently, but keep a bounded active-worker count.

Do not publish obsolete worker output.

A view request waits for the current cache and returns an error after a rebuild failure.

Do not add incremental per-file cache updates or cross-generation reuse.

Do not add a hard cache-size limit.

A warning near ~250 MB~ for one view can remain a soft operational guard.
