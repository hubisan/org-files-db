* Planning

** Problem summary

The query model already validates ~(has-text ...)~ and the indexer already persists canonical heading body text, but the SQLite backend still rejects the predicate during SQL compilation. That leaves a contract gap where the capability exists in validation metadata and database storage, yet execution cannot match against persisted heading bodies.

** Goals

- Implement ~(has-text ...)~ for heading queries using persisted ~heading_bodies.body_text~.
- Keep matching independent from FTS5 and raw Org file access.
- Preserve clear capability errors when body text is unavailable.
- Add focused tests for SQL compilation, execution semantics, and bound parameters.

** Non-goals

- No FTS5 query syntax or tokenizer behavior.
- No regexp support beyond existing explicit rejection.
- No changes to parser or indexing semantics for what counts as heading body text.

** Architecture

- Compile ~(has-text ...)~ to correlated ~EXISTS~ subqueries against ~heading_bodies~ keyed by the current heading id.
- Reuse the backend's existing case-insensitive substring matching strategy via ~LOWER(...)~ and ~INSTR(..., LOWER(?)) > 0~.
- Keep one correlated ~EXISTS~ per term so multiple terms naturally mean AND on the same heading body.
- Leave capability gating in validation and execute-time checks unchanged.

** Execution plan

- Add SQLite compilation support for heading-target ~(has-text ...)~.
- Extend compiler and execution tests around bound parameters, AND semantics, case behavior, empty bodies, and no-match cases.
- Update query-model and CLI docs where they still describe backend support as unavailable.
- Run focused tests, then ~cargo test --all-targets --all-features~, then ~make ci~.

** Risks & assumptions

- Root/file pseudo-heading rows should not match because they have no ~heading_bodies~ row; the base heading scope filter should keep normal heading semantics intact.
- Existing validation should already prevent zero-arity and unsupported regexp queries, but compilation still needs defensive handling consistent with other text predicates.

* Results

** Approach

- Added SQLite compilation support for ~(has-text ...)~ on heading queries using correlated ~EXISTS~ subqueries against ~heading_bodies~.
- Reused the backend's current case-insensitive substring semantics via ~LOWER(...)~ and ~INSTR(..., LOWER(?)) > 0~, with one bound parameter per search term and AND semantics across terms.
- Seeded persisted heading-body fixtures in the SQLite query tests so execution coverage exercises available capability, missing rows, and empty-body rows without touching parser or indexer behavior.
- Updated CLI docs with a direct ~has-text~ example against the persisted query layer.
- Tightened the shared SQLite body-text capability check so it now requires all of: existing ~db_metadata~, existing ~heading_bodies~, and a persisted ~body_text_available~ value of exactly ~"1"~.
- Reused that complete capability check for both validation-option loading and the execute-time backend guard, so inconsistent reduced schemas are classified as unavailable capability instead of surfacing raw ~no such table: heading_bodies~ errors.
- Added reduced-schema regression coverage for missing ~db_metadata~, missing ~heading_bodies~, missing metadata row, explicit ~"0"~, and the valid ~heading_bodies + "1"~ case.
