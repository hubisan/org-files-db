Goal:

- Implement ~:with-time~ filtering using persisted explicit-time facts.
- Apply the same semantics consistently to planning and generic timestamp predicates.

Rules:

- ~:with-time t~ matches only Org timestamps containing an explicit time.
- ~:with-time nil~ matches only date-only Org timestamps.
- Omitting ~:with-time~ matches both forms.
- Explicit midnight counts as containing an explicit time.
- Filtering must use persisted explicit-time facts.
- Filtering must not infer explicit-time presence from encoded timestamp values.
- A backend without explicit-time facts must return a clear unsupported-backend error.
- All user-provided query values must continue to use bound SQL parameters.

Acceptance criteria:

- ~:with-time t~ matches timestamps containing an explicit hour and minute.
- ~:with-time t~ matches explicit midnight timestamps.
- ~:with-time t~ does not match date-only timestamps.
- ~:with-time nil~ matches date-only timestamps.
- ~:with-time nil~ does not match timestamps containing an explicit time.
- Omitting ~:with-time~ matches both date-only and timed timestamps.
- Planning predicates support ~:with-time~.
- Generic ~ts~, ~ts-active~, and ~ts-inactive~ predicates support ~:with-time~.
- Date-only timestamps and explicit midnight timestamps are distinguished correctly.
- Missing explicit-time backend capabilities produce a clear unsupported-backend error.
- The query model documentation describes the implemented semantics.
- Query SQL continues to use bound parameters for user-provided values.

* Planning

** Problem summary

The SQLite query backend still rejects ~:with-time~ for planning and generic timestamp predicates even though explicit-time facts are already persisted.

** Goals

- Compile ~:with-time~ into SQLite filters using only persisted ~has_time~ columns.
- Preserve existing date-bound semantics and bound SQL parameters.
- Fail clearly on schemas that do not expose the required explicit-time columns.

** Non-goals

- No schema, parser, or indexer changes.
- No inference from raw timestamp strings or encoded timestamp values.

** Architecture

- Extend timestamp predicate SQL compilation to add optional ~has_time = 1|0~ constraints.
- Add execute-time schema capability checks before SQLite compilation/execution when a query uses ~:with-time~.
- Add focused backend tests using seeded in-memory SQLite fixtures.

* Results

** Approach

- Added execute-time backend capability checks that inspect ~headings~ and ~timestamps~ columns before compiling or executing any query that uses ~:with-time~.
- Extended SQLite timestamp predicate compilation to emit persisted explicit-time filters using the relevant ~*_has_time~ or ~timestamps.has_time~ column while preserving bound parameters for date inputs.
- Added focused SQLite compilation and execution tests for planning predicates, generic timestamp predicates, composed date-bound queries, and reduced-schema capability failures.
- Updated the query model reference to document explicit-time semantics, unknown persisted facts, and unsupported-backend behavior.
