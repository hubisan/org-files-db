- Continue task: *BUILD [#B] Complete date-only and datetime query-bound semantics*
- Goal:
  - Define and implement consistent semantics for date-only and datetime arguments used with ~:on~, ~:from~, and ~:to~.
  - Keep query bounds consistent with the timezone-naive representation of indexed Org timestamps.
- Key rules:
  - Date-only ~:on~ matches the complete specified calendar day.
  - Date-only ~:from~ is inclusive start-of-day.
  - Date-only ~:to~ includes the complete day via exclusive next-day boundary.
  - Datetime arguments preserve explicit hour and minute and are not converted between timezones.

* Planning

** Problem summary

The current SQLite query layer already approximates separate date-only and datetime bound behavior, but the semantics are not explicitly documented and the edge cases are not covered by targeted tests.

** Goals

- Make the date-only and datetime bound semantics explicit in code-adjacent documentation.
- Keep query execution aligned with the parser's timezone-naive timestamp encoding.
- Add regression tests for date-only and datetime ~:on~, ~:from~, and ~:to~ behavior, including edge boundaries.

** Non-goals

- No schema change.
- No ~:with-time~ backend support yet.
- No conversion of stored Org timestamps between timezones.

** Architecture

- Reuse the existing resolved date-string flow.
- Keep SQL generation on bound parameters.
- Clarify semantics in the Query Model reference and prove them through SQLite query tests.

** Execution plan

- Review and, if needed, tighten SQL bound generation for date-only vs datetime values.
- Add tests for whole-day inclusion, explicit datetime preservation, midnight datetimes, month/year boundaries, and DST-adjacent dates.
- Update reference docs and task results.

** Risks & assumptions

- SQLite datetime parsing must stay aligned with the parser's timezone-naive timestamp encoding.
- Datetime upper-bound semantics must remain consistent with persisted minute-precision timestamps.
