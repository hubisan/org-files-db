* Planning

** Problem summary

The repository already provides optional contentless FTS5 indexing through ~heading_fts~, but there is no public CLI command that uses that derived index directly. The new ~search~ command must expose backend-specific FTS5 search as a read-only convenience feature without changing Query Model semantics, relying on contentless payload reads, or trusting stale on-disk FTS state.

** Goals

- Add a JSON-only ~orgfdb search~ command for raw SQLite FTS5 ~MATCH~ expressions.
- Return canonical heading/file metadata joined from ~headings~ and ~files~, never from FTS payload columns.
- Enforce explicit title/body scope options without allowing user expressions to broaden the selected scope.
- Require current config opt-in plus trusted persisted FTS metadata and structural compatibility checks.
- Keep the command strictly read-only and require one successful rebuild before pre-metadata databases become searchable.

** Non-goals

- No change to ~(has-text ...)~ or Query Model v0.
- No snippets, highlighting, pagination, result limits, or text-mode output.
- No fallback search path, no implicit rebuild, no repair, and no incremental FTS maintenance changes.
- No graph mutation, link repair, or Org-file scanning during search.

** Architecture

- Add ~search~ as a new CLI subcommand with required ~--json~, optional ~--config~, mutually exclusive ~--title/~--body~, and a single required raw FTS5 expression argument.
- Reuse the existing read-only DB open helper and the existing runtime SQLite FTS5 capability probe.
- Persist explicit FTS trust metadata in ~db_metadata~:
  - ~fts_available~
  - ~fts_body_indexed~
  - ~fts_schema_version~
- Write that metadata transactionally during rebuild:
  - successful FTS-enabled rebuild => trusted metadata for the current schema contract
  - successful FTS-disabled rebuild => explicit untrusted metadata
  - failed rebuild => rollback leaves prior state unchanged
- Implement search trust checks using persisted metadata first, then structural checks:
  - ~heading_fts~ existence
  - virtual-table/FTS5 identity
  - logical columns ~= title, body~
  - contentless layout
  - ~unicode61~ tokenizer where inspectable
- Compile search SQL against ~heading_fts MATCH ?~ joined to canonical ~headings~ and ~files~, with ~headings.level > 0~, ~bm25(heading_fts)~, and deterministic ~rank ASC, heading_id ASC~ ordering.
- Reject scoped expressions containing explicit FTS column-filter syntax when ~--title~ or ~--body~ is selected, then compile the enforced scope as a fixed outer FTS expression.

** Execution plan

- Extend rebuild-time metadata writes and document the persisted FTS trust contract.
- Add read-only search execution, trust inspection, scoped-expression validation, result mapping, and search-specific error handling.
- Add CLI parsing, JSON output, and regression coverage for trusted search, malformed expressions, scope bypass attempts, read-only guarantees, and pre-metadata databases.
- Update CLI/config/README documentation and record implementation plus checks in this task file.

** Risks & assumptions

- Scoped-expression validation intentionally fails closed on ambiguous unquoted ~:~ usage when a fixed scope is requested.
- FTS5 syntax and rank values remain backend-specific and may vary across SQLite builds.
- Read-only FTS5 probing is assumed to work on the opened connection and will be covered by tests through the search path.

* Results

** Approach
- Added a new read-only ~orgfdb search --json~ CLI command that executes raw SQLite FTS5 ~MATCH~ expressions against trusted ~=heading_fts= state and returns a top-level JSON array of canonical heading/file match rows.
- Reused the existing read-only DB open helper and runtime FTS5 probe, then added a dedicated search trust contract on top of persisted ~db_metadata~ keys:
  - ~fts_available~
  - ~fts_body_indexed~
  - ~fts_schema_version~
- Search now requires:
  - active ~search.fts5_enabled = true~ in the current config
  - runtime SQLite FTS5 support on the opened connection
  - exact trusted persisted FTS metadata from a successful rebuild
  - structural compatibility of the current ~=heading_fts= table
- Rebuild now writes the FTS trust metadata transactionally:
  - successful FTS-enabled rebuild => trusted current search index
  - successful FTS-disabled rebuild => explicitly untrusted/stale-on-disk FTS state
  - failed rebuild => rollback leaves prior metadata untouched
- Scope enforcement is fail-closed:
  - default scope allows raw backend-specific column filters
  - ~--title~ and ~--body~ reject explicit unquoted column-filter syntax in the user expression and then compile a fixed outer column scope
- Search result fields come only from canonical ~=headings= and ~=files=~ rows, never from contentless FTS payload columns, with defensive ~headings.level > 0~ filtering and deterministic ~bm25(heading_fts), heading_id~ ordering.
- Existing databases without the new trusted FTS metadata are rejected as untrusted and must be rebuilt once before ~search~ works.
- Follow-up fix: extracted rebuild-time search trust metadata persistence into a shared helper so empty successful rebuilds and non-empty successful rebuilds write the same ~=fts_available= / =fts_body_indexed= / =fts_schema_version=~ contract.
- Added a regression proving that a zero-input successful FTS-enabled rebuild on an otherwise empty database leaves ~=heading_fts= trusted and allows ~orgfdb search --json~ to return an empty JSON array instead of rejecting the database as untrusted.
