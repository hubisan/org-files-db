** DONE Allow synthetic roots in nested heading relation queries

Task file: [[file:2026-07-21--allow-synthetic-roots-in-nested-heading-relation-queries.org][Allow Synthetic Roots in Nested Heading Relation Queries]]

Goal:

- Make nested ~headings~ queries inside hierarchy predicates use the same root-inclusive heading semantics as top-level heading queries.
- Allow ~parent~ and ~ancestors~ to match the synthetic file/root heading.
- Preserve the existing root behaviour of ~children~ and ~descendants~.
- Add complete regression coverage for all four hierarchy predicates.

Affected predicates:

- ~parent~
- ~children~
- ~ancestors~
- ~descendants~

Current storage model:

- Each indexed file has one synthetic heading with:
  - ~level = 0~
  - ~parent_id = NULL~
- Every real top-level Org heading stores the synthetic root ID as its ~parent_id~.
- The ~outline_path~ table includes:
  - the synthetic root at ~depth = 0~
  - every real heading below it
- The persisted hierarchy therefore already models the root correctly.
- No index or schema change is required.

Current compiler problem:

- Top-level ~headings~ queries are executed in two parts:
  - real headings with ~level > 0~
  - synthetic root/file results with ~level = 0~
- A nested ~headings~ query inside a relation is compiled with a normal ~RealHeading~ scope only.
- The nested scope therefore receives this implicit base filter:

#+begin_src sql
nested_heading.level > 0
#+end_src

- A query such as:

#+begin_src lisp
(parent
  (headings
    (level 0)))
#+end_src

is effectively compiled with contradictory conditions:

#+begin_src sql
nested_heading.level > 0
AND nested_heading.level = 0
#+end_src

- The same problem affects:

#+begin_src lisp
(ancestors
  (headings
    (level 0)))
#+end_src

- Consequently, the synthetic root cannot currently satisfy any nested ~headings~ query.

Required semantics:

- A nested ~headings~ target must represent the complete heading domain:
  - synthetic level-0 roots
  - real headings with level greater than zero
- It must not silently imply ~level > 0~.
- Explicit predicates determine whether roots or real headings match.

Examples:

#+begin_src lisp
(parent
  (headings
    (level 0)))
#+end_src

matches every real top-level heading because its direct parent is the synthetic root.

#+begin_src lisp
(ancestors
  (headings
    (level 0)))
#+end_src

matches every real heading because the synthetic root is an ancestor of every real heading in that file.

#+begin_src lisp
(children
  (headings
    (todo "TODO")))
#+end_src

matches every heading, including a synthetic root, that has a direct child satisfying the nested query.

#+begin_src lisp
(descendants
  (headings
    (todo "TODO")))
#+end_src

matches every heading, including a synthetic root, that has a matching descendant at any depth.

Root relation rules:

- The synthetic root:
  - has no parent
  - has no ancestors
  - may have direct children
  - may have descendants
- A real top-level heading:
  - has the synthetic root as its direct parent
  - has the synthetic root as an ancestor
- A nested real heading:
  - has its direct real parent
  - has all real ancestors plus the synthetic root as ancestors
- A heading is never its own:
  - parent
  - child
  - ancestor
  - descendant

Required implementation direction:

- Do not change persisted ~parent_id~ or ~outline_path~ data.
- Do not special-case only ~(level 0)~.
- Fix the nested heading target domain itself.
- Introduce an explicit heading-scope mode for nested relation queries that includes both root and real heading rows.

For example, distinguish:

#+begin_src rust
enum HeadingMatchKind {
    RealHeading,
    RootFile,
    AllHeadings,
}
#+end_src

or use an equivalent design.

- For an ~AllHeadings~ nested scope:
  - do not add an implicit level filter
  - allow the nested Predicate to match either level 0 or level > 0
- Keep the existing split output handling for top-level heading results if needed.
- Nested relation matching does not need to produce result rows; it only needs a root-inclusive relational domain.
- Ensure nested predicates such as ~title~, ~tags~, ~property~, ~keyword~, ~level~, and boolean combinations retain their normal heading semantics.
- Avoid compiling the nested query twice unless required by the existing architecture.

Review the current helper:

#+begin_src rust
let nested_scope = aliases.next_scope(QueryTarget::Headings);
#+end_src

- This currently creates a ~RealHeading~ scope.
- Replace it with a root-inclusive nested heading scope for hierarchy relations.

~parent~:

- Keep the direct relation:

#+begin_src sql
nested.id = current.parent_id
#+end_src

- Allow ~nested.id~ to refer to a level-0 root.
- Do not reject the outer synthetic root through relation matching alone; it naturally has ~parent_id = NULL~ and therefore cannot match.
- The existing explicit outer-root false handling may remain, but it should be reviewed for redundancy and consistency.

~ancestors~:

- Continue using strict ancestor ordering.
- Include depth 0 in the possible nested ancestor rows.
- The current root entry in ~outline_path~ must be eligible to satisfy the nested query.
- Do not include the candidate itself.

~children~:

- Preserve current direct-child semantics.
- The synthetic root may be returned as the outer result when one of its top-level headings matches.
- A level-0 row cannot be a child of another heading because its ~parent_id~ is ~NULL~.

~descendants~:

- Preserve strict descendant semantics at any depth.
- The synthetic root may be returned as the outer result.
- Every matching descendant contributes all strict ancestors up to and including the file root.
- Do not exclude the root from outer results.

* Planning

** Problem summary

Nested ~headings~ queries used by ~parent~, ~ancestors~, ~children~, and ~descendants~ currently receive the ~RealHeading~ scope's implicit ~level > 0~ filter. This prevents the persisted synthetic level-0 root from satisfying a nested relation query even though the stored ~parent_id~ and ~outline_path~ hierarchy already represents it correctly.

** Goals

- Make nested heading relation targets root-inclusive without changing top-level result shaping.
- Let ~parent (headings (level 0))~ match top-level real headings and ~ancestors (headings (level 0))~ match every real heading in the file.
- Preserve strict/direct hierarchy semantics and current outer-root behavior: roots cannot match ~parent~ or ~ancestors~, but can match ~children~ and ~descendants~.
- Document the root-inclusive nested-query contract and add regression coverage.

** Non-goals

- No schema, indexing, migration, parser, or link-resolution changes.
- No changes to non-hierarchy relation predicates or output kinds/order.

** Architecture

- Extend the SQLite heading match-kind model with an explicit all-headings mode whose base filter is absent; keep the existing real-heading and root-file modes for top-level heading result compilation.
- Add an alias-allocator helper for an all-headings nested scope and use it only when compiling hierarchy relation nested targets.
- Continue using the existing direct ~parent_id~ predicates and strict ~outline_path~ depth/materialized-path predicates. Retain the root-false guard for outer ~parent~ and ~ancestors~ candidates.

** Execution plan

1. Update ~src/query/sqlite.rs~ so a nested hierarchy target compiles against all headings in its file, allowing both level-0 roots and real headings to satisfy its predicates without an injected level restriction.
2. Extend focused SQLite execution tests with a branched hierarchy fixture. Cover root matching through nested ~level~, title, boolean, TODO, and tag predicates; direct-child vs transitive-descendant behavior; root outer candidates for ~children~ and ~descendants~; branch isolation; and self-exclusion.
3. Add a compiler-level regression assertion that the all-headings nested scope emits no implicit ~level > 0~ condition. Keep existing real-heading nested-relation behavior covered.
4. Update ~docs/cli.org~ and ~docs/reference/query-model-v0.org~ to state that nested hierarchy ~headings~ queries include roots, clarify root parent/ancestor/child/descendant rules, and add the required parent, ancestors, and root-descendant examples.
5. Run focused query tests, then ~make ci~. Record results and move the task through the normal BUILD/REVIEW workflow.

** Risks & assumptions

- Assumption: one level-0 root row per file and its existing depth-0 outline entry remain invariant.
- The all-headings mode is restricted to nested hierarchy matching so it does not alter top-level SQL result splitting or unrelated relation semantics.
- Root/file rows continue to serialize as ~kind = "file"~ when returned by outer heading queries.
