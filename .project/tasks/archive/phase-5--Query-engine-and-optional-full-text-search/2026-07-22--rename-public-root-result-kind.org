Goal:

- Represent synthetic level-0 roots consistently as ~kind = "root"~ in every public output.
- Reserve ~kind = "file"~ for actual file result objects.
- Keep ~kind = "heading"~ for real Org headings with ~level > 0~.

Public semantics:

- ~root~ means the synthetic level-0 heading associated with an indexed file.
- ~heading~ means a real Org heading with ~level > 0~.
- ~file~ means an actual file-domain result returned by a ~(files ...)~ query.
- A root remains internally backed by its canonical heading row and retains its canonical ~heading_id~ where that field is exposed.

Scope:

- Audit every public JSON serializer and result type that can expose a synthetic root.
- Update Query Model heading results.
- Update hierarchy relation results.
- Update link-related heading relation results.
- Update already serialized synthetic roots in included links, backlinks, source, and target objects where they appear.
- Update ~orgfdb search --json~ results.
- Update flat and outline output shapes.
- Update any diagnostics, snapshots, fixtures, examples, and helper types containing public result kinds.
- Do not rename internal database tables or foreign keys merely because roots are stored as heading rows.

Compatibility:

- Treat this as an intentional breaking API change.
- Do not emit both ~file~ and ~root~ aliases.
- Do not infer ~kind~ from presentation context; derive it from the canonical result domain and heading level.
- Do not add a root object where the current public shape intentionally omits one.
- File-query results must remain ~kind = "file"~.
- Synthetic level-0 results must never be emitted as ~kind = "file"~ or ~kind = "heading"~.

Implementation rules:

- Centralize public kind derivation where possible:
  - file-domain result -> ~file~
  - heading row with ~level = 0~ -> ~root~
  - heading row with ~level > 0~ -> ~heading~
- Avoid separate serializer-specific mappings that can drift.
- Preserve all existing IDs, paths, titles, locations, levels, and relation semantics.
- Do not change matching semantics or database schema.

Regression tests:

- A top-level ~(headings)~ query serializes the synthetic root as ~kind = "root"~.
- A real heading serializes as ~kind = "heading"~.
- A ~(files ...)~ result serializes as ~kind = "file"~.
- Parent, children, ancestors, and descendants serialize matched roots as ~root~.
- Link ~source~ and ~target~ expansions serialize root objects as ~root~.
- ~links-to~ and ~linked-from~ results serialize level-0 matches as ~root~.
- Preamble-related results preserve their existing source shape; no root object is added where one is currently omitted.
- FTS root-title and preamble matches serialize as ~kind = "root"~.
- Flat and outline outputs use the same kind semantics.
- No public snapshot or JSON fixture still expects ~kind = "file"~ for a level-0 heading.
- Actual file-domain results remain ~kind = "file"~.

Documentation:

- Update ~docs/reference/query-model-v0.org~.
- Update ~docs/cli.org~.
- Document the distinction between ~root~, ~heading~, and ~file~.
- Update all JSON examples containing synthetic roots.
- Add a breaking-change note for consumers of the JSON API.

Acceptance criteria:

- Every public synthetic level-0 result uses ~kind = "root"~.
- ~kind = "file"~ appears only for actual file-domain results.
- ~kind = "heading"~ appears only for real headings.
- No matching, identity, location, or relation behaviour changes.
- ~make ci~ passes.
