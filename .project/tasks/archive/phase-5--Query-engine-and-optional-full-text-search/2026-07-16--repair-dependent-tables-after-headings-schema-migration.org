- Task file: [[file:archive/2026-07-16--repair-dependent-tables-after-headings-schema-migration.org]]

Goal:

- Fix the legacy ~headings~ migration so that tables referencing ~headings~ keep valid foreign keys and indexed data remains internally consistent.
- Prevent successful database opening or rebuilding from leaving populated ~headings~ rows with empty dependent tables.
- Restore query execution after a ~headings~ schema migration.

Observed failure:

- Query commands fail with errors such as:

#+begin_src text
missing stored heading row for id 31
#+end_src

- The affected database contains rows in ~headings~, but tables such as ~outline_path~ and ~links~ are empty.
- The dumped schema contains foreign keys that still reference the removed table ~headings_legacy~.
- Additional affected tables include at least:
  - ~keywords~
  - ~properties~
  - ~tags~
  - ~timestamps~
  - ~heading_bodies~
  - ~links~
  - ~outline_path~

Root cause:

- ~migrate_legacy_headings_table~ currently renames ~headings~:

#+begin_src sql
ALTER TABLE headings RENAME TO headings_legacy;
#+end_src

- SQLite updates foreign keys in dependent tables so that they reference ~headings_legacy~.
- The migration then creates the new ~headings~ table and drops ~headings_legacy~.
- Dependent tables are not recreated, so their foreign keys continue to reference the removed legacy table.
- Dropping the legacy heading table can also remove dependent rows through cascading foreign keys.
- The query result loader uses an ~INNER JOIN~ from ~headings~ to ~outline_path~, so missing outline rows make existing headings appear unavailable.

Implementation requirements:

- Perform the ~headings~ migration without leaving any foreign key that references ~headings_legacy~.
- Recreate every table whose schema references ~headings~ as part of the same migration.
- Preserve canonical source data where safe and practical.
- Treat derived/cache data such as ~outline_path~ and FTS rows as rebuildable.
- Ensure migration and schema repair run transactionally.
- Do not leave a partially migrated database if any migration step fails.
- Do not rely on disabling foreign-key enforcement as the only fix.
- Ensure the final schema matches the current definitions in ~sql/schema.sql~.
- Decide explicitly whether dependent rows are:
  - copied during migration, or
  - discarded and regenerated through a mandatory rebuild.
- If a rebuild is required after migration, enforce or perform it rather than allowing queries against an incomplete database.
- Ensure the migration also repairs already affected databases whose tables currently reference ~headings_legacy~.

Suggested approach:

- Detect foreign keys whose target table is ~headings_legacy~ using ~PRAGMA foreign_key_list~.
- Create replacement versions of all affected dependent tables with foreign keys targeting ~headings~.
- Copy source-of-truth rows using stable heading IDs where applicable.
- Rebuild derived tables after the canonical rows have been restored.
- Drop the broken table versions only after their replacement tables are ready.
- Run ~PRAGMA foreign_key_check~ before committing.
- Consider increasing the schema version so already opened broken databases receive the repair migration.

Query robustness:

- Improve the current error so that a missing ~outline_path~ row is distinguishable from a missing ~headings~ row.
- The query layer should report an integrity error such as:

#+begin_src text
missing outline_path row for stored heading id 31
#+end_src

- This clearer error is diagnostic only and must not replace fixing the migration.

Acceptance criteria:

- After migrating an older database, no foreign key references ~headings_legacy~.
- ~PRAGMA foreign_key_check~ returns no rows.
- Every stored heading has exactly one ~outline_path~ row.
- Query commands no longer fail with ~missing stored heading row~ after migration and rebuild.
- Existing links, tags, properties, timestamps, bodies, and keywords are preserved or deterministically regenerated according to the documented migration strategy.
- A full rebuild after migration populates ~outline_path~ and ~links~ correctly.
- Existing already-broken databases are repaired automatically or rejected with a clear recovery message.
- The migration is atomic.
- FTS-disabled databases migrate successfully.
- FTS-enabled databases migrate successfully and recreate consistent FTS rows.
- ~make ci~ passes.

* Planning

** Problem summary

- ~migrate_legacy_headings_table~ renames ~headings~ to ~headings_legacy~, creates the new table, copies rows, and drops the legacy table.
- SQLite rewrites dependent foreign keys to reference ~headings_legacy~ during the rename.
- Dependent tables are not rebuilt as part of that migration, so dropping ~headings_legacy~ can cascade-delete their rows and leaves broken FK targets behind.
- Query shaping currently loads headings through an ~INNER JOIN~ on ~outline_path~, so missing derived rows are reported misleadingly as missing stored heading rows.

** Goals

- Repair the legacy ~headings~ migration so dependent tables are rebuilt transactionally alongside ~headings~.
- Preserve canonical dependent rows during the real migration path where the source data still exists.
- Repair already-affected databases by rebuilding structural tables and FK definitions so query execution no longer fails because of broken ~outline_path~ / FK state.
- Improve the query-shaping error so missing ~outline_path~ rows are reported distinctly.

** Non-goals

- No Query Model syntax changes.
- No changes to ~has-text~ semantics.
- No incremental FTS maintenance changes beyond keeping trust state safe when a headings repair invalidates derived search state.

** Architecture

- Add a dedicated schema-repair path for tables that reference ~headings~:
  - canonical tables: ~keywords~, ~properties~, ~tags~, ~timestamps~, ~heading_bodies~, ~links~
  - derived table: ~outline_path~
- When ~headings~ itself needs migration:
  - rename ~headings~ to ~headings_legacy~
  - rename dependent tables to temporary repair tables before dropping the legacy headings table
  - recreate current schema objects
  - copy canonical rows forward
  - rebuild ~outline_path~ from canonical ~headings~
- When an already-openable database still contains FK targets pointing at ~headings_legacy~, run the same dependent-table repair without re-migrating ~headings~.
- Invalidate trusted FTS metadata when a headings-dependent repair runs, because ~heading_fts~ is derived and full-rebuild-owned.
- Change query heading loading from ~INNER JOIN outline_path~ to ~LEFT JOIN~, then raise a dedicated missing-~outline_path~ shape error when canonical headings exist but the derived row does not.

** Execution plan

- Update the task index entry to ~BUILD~ and link this task file.
- Implement the dependent-table repair helpers in ~src/db/schema.rs~.
- Rebuild ~outline_path~ from canonical ~headings~ during repair.
- Invalidate trusted FTS metadata after a headings-dependent repair.
- Tighten query-shape diagnostics for missing ~outline_path~ rows.
- Add migration regressions for:
  - a real legacy headings migration with populated dependent tables
  - an already-affected database with FK targets pointing at ~headings_legacy~
- Run formatting and relevant Rust / CI checks.

** Risks & assumptions

- Already-affected databases may have permanently lost canonical dependent rows before this fix; those rows cannot be reconstructed during open without rereading Org files.
- Rebuilding ~outline_path~ from canonical headings is sufficient to restore the main heading-query failure mode.
- Search trust should be invalidated on repair rather than attempting a partial FTS rebuild during schema open.

** Open questions

- None. Proceed with the smallest repair that preserves existing data when still available and makes prior damage explicit/safe.
