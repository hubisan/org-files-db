Reject outdated database schemas on read-only query opens while preserving writable migration behaviour.

* Planning

** Problem summary

Read-only database opens reject future schema versions but currently permit older versions. Because read-only commands cannot migrate, an outdated database can proceed until a later table or column access fails with a lower-level SQLite error.

** Goals

- Reject schema versions older than the required schema during read-only opens.
- Keep future-version rejection unchanged.
- Keep writable migration behaviour unchanged.
- Return an actionable error that tells the user to run an indexing command.
- Verify the read-only query path fails before query execution and does not modify the database.

** Non-goals

- Do not migrate during read-only access.
- Do not change schema definitions or migrations.
- Do not change query SQL or query semantics.

** Architecture

Keep the existing shared future-version validation used by writable initialization. Add an additional outdated-version check only in the read-only open path and represent it with a dedicated ~DbError~ variant.

** Execution plan

1. Add an outdated read-only schema error variant and display message.
2. Validate the lower bound in ~open_existing_database_read_only_with_schema~ after the existing future-version check.
3. Add focused database/CLI regression coverage for an older read-only schema and unchanged on-disk version.
4. Document that read-only CLI commands require the current database schema.

** Risks & assumptions

- A database with only ~PRAGMA user_version~ changed is sufficient to verify version gating independently of structural migration details.
- Existing writable migration tests cover the requirement that older writable opens remain supported.

Added a read-only-only lower-bound schema check after the existing future-version validation.
