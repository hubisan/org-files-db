** BUILD Parse Org timestamps and planning fields

Goal:
Parse Org timestamps from parser-owned Orgize or Org-compatible timestamp structures and store them in both direct heading shortcut fields and rich timestamp tables.

Merged from:
- Parse planning lines
- Parse rich timestamps

Acceptance criteria:
- Parser model can represent timestamp role, raw value, normalized start/end timestamps, activity type, range type, byte ranges, line number, and modifiers.
- Planning data is represented in the parser model.
- DB schema supports direct planning shortcut fields on ~headings~:
  - ~scheduled_raw~
  - ~scheduled_ts~
  - ~deadline_raw~
  - ~deadline_ts~
  - ~closed_raw~
  - ~closed_ts~
- Planning timestamps are mirrored into ~timestamps~ with role ~scheduled~, ~deadline~, or ~closed~.
- General entry timestamps are stored in ~timestamps~ with role ~body~ or ~NULL~.
- Raw Org timestamp text is preserved exactly from the timestamp node or parser raw value.
- ~*_ts~ fields are UTC Unix timestamp seconds.
- Date-only timestamps normalize to ~00:00:00~ UTC.
- Date-time timestamps normalize to the given ~HH:MM~ in UTC.
- Time/date ranges populate ~start_ts~ and ~end_ts~ where the parser exposes enough structure.
- Diary expressions are stored as raw timestamps with type ~diary~, but never evaluated.
- JSON output includes heading planning shortcut fields.
- Tests cover scheduled, deadline, closed, one-line planning, active timestamps, inactive timestamps, date ranges, time ranges, repeaters, diary expressions, and multiple body timestamps belonging to one heading.

* Planning

** Problem summary
The repository currently implements only direct heading planning shortcut fields. ~ParsedPlanning~ stores raw and normalized values per keyword, the Orgize adapter extracts heading planning only, and the DB layer persists ~scheduled_*~, ~deadline_*~, and ~closed_*~ on ~headings~. There is no project-owned rich timestamp model, no timestamp rows, no modifier rows, and no parser-to-indexer path for non-planning timestamps.

The merged task needs one coherent model that keeps Orgize as the structural source of truth while exposing project-owned timestamp and planning data to the indexer, DB, and JSON layers. The task also needs to preserve the important ownership rule: only parser-owned heading planning data populates the heading shortcut fields.

** Goals
- Introduce project-owned timestamp models for rich parser output.
- Keep Orgize-specific AST handling and timestamp extraction in ~src/parser/orgize_adapter.rs~.
- Preserve direct heading planning shortcut fields for fast heading queries.
- Insert rich timestamp rows for planning and non-planning timestamp occurrences.
- Preserve exact raw timestamp text and parser-owned byte/line metadata.
- Preserve diary expressions as raw values without evaluation.
- Store repeaters and warning modifiers in a dedicated modifier table if available.
- Cover edge cases around duplicate planning keywords, planning-looking body text, and diary planning.

** Non-goals
- No diary expression execution.
- No regex-based recovery of planning semantics from body text.
- No Orgize types outside the adapter boundary.
- No agenda engine or recurrence expansion.
- No unrelated refactors beyond parser, indexer, DB, fixtures, and task docs needed for this scope.

** Architecture
The adapter remains the parser boundary:

#+begin_src text
Orgize AST / parser accessors / byte ranges
  -> src/parser/orgize_adapter.rs
  -> ParsedHeading / ParsedPlanning / ParsedTimestamp
  -> indexer
  -> DB writer
  -> DB reader / JSON output
#+end_src

Design rules:
- Orgize parser timestamp structures are the source of truth for type, ranges, and modifiers.
- Heading shortcut fields are derived from parser-owned ~ParsedPlanning~ only.
- Planning timestamps also become timestamp rows with role ~scheduled~, ~deadline~, or ~closed~.
- Generic title/body timestamps become timestamp rows with role ~body~ or ~NULL~.
- If the parser exposes duplicate values for the same planning keyword, last value wins for shortcut fields.
- Paragraph or body lines that merely look like planning must not populate heading shortcut fields unless the parser surfaces them as heading planning data.

Planned parser model shape:

#+begin_src rust
pub struct ParsedPlanning {
    pub scheduled: Option<ParsedTimestamp>,
    pub deadline: Option<ParsedTimestamp>,
    pub closed: Option<ParsedTimestamp>,
}

pub struct ParsedTimestamp {
    pub role: Option<ParsedTimestampRole>,
    pub raw_value: String,
    pub timestamp_type: ParsedTimestampType,
    pub range_type: ParsedTimestampRangeType,
    pub start_ts: Option<i64>,
    pub end_ts: Option<i64>,
    pub byte_start: i64,
    pub byte_end: i64,
    pub line_number: Option<i64>,
    pub modifiers: Vec<ParsedTimestampModifier>,
}
#+end_src

Shortcut field derivation stays straightforward:

#+begin_src text
scheduled_raw = planning.scheduled.raw_value
scheduled_ts  = planning.scheduled.start_ts
deadline_raw  = planning.deadline.raw_value
deadline_ts   = planning.deadline.start_ts
closed_raw    = planning.closed.raw_value
closed_ts     = planning.closed.start_ts
#+end_src

* Results

** Approach
- Kept the legacy table name ~timestamp_repeaters~ but corrected its row shape to match Org/Emacs timestamp properties directly: one row per timestamp with explicit repeater and warning columns.
- Extended parser-owned timestamp modifiers to carry the repeater deadline pair exposed by Org/Emacs: ~:repeater-deadline-value~ and ~:repeater-deadline-unit~.
- Changed the DB mapping so parsed repeater and warning modifiers for the same timestamp are merged into one ~timestamp_repeaters~ row instead of being split across generic modifier rows.
- Added focused adapter fallback only for the unsupported ~+1w/2d~ planning form because the current Orgize version does not parse that timestamp as a planning node. This keeps the broader timestamp/planning design unchanged while preserving the required modifier data.
- Added a compatibility migration that rebuilds ~timestamp_repeaters~ into the explicit per-timestamp shape and folds both earlier layouts into it:
  - the oldest legacy ~deadline_value~ / ~deadline_unit~ table
  - the intermediate generic ~kind~ / ~type~ / ~value~ / ~unit~ row model
