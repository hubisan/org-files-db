Analyze the current ~presentation-json~ payload before changing the public wire format.

Measure response sections, repeated field names, repeated values, and average bytes for the existing benchmark workloads.

* Planning

** Problem summary

The first presentation benchmark produced payloads from about 47 MB through 94 MB at 50,000 original results.

The project needs exact payload attribution before it changes the wire format.

** Goals

- Reuse the existing benchmark corpus and database files.
- Measure the top-level ~results~ and ~rows~ components.
- Split row bytes into metadata, row context, and cells.
- Split cell bytes into structure, search text, display text, and semantic roles.
- Count repeated JSON field-name bytes.
- Estimate structural JSON overhead.
- Measure repeated values between results, row contexts, and cells.
- Measure search content repeated by display padding.
- Record average bytes per result, row, and cell.
- Keep the public ~presentation-json~ contract unchanged.

** Non-goals

- Do not change the public presentation wire format.
- Do not add compression.
- Do not add JSONL or streaming.
- Do not add a presentation cache.
- Do not add parallel execution.
- Do not rebuild the benchmark corpus for payload analysis.

** Architecture

Add a measurement-only payload analyzer beside the existing presentation benchmark code.

The analyzer reads databases from an existing benchmark work directory.

It runs each existing workload once through the production query and presentation pipeline.

It serializes the current ~PresentationResponse~ without changing that type.

The analyzer reports hierarchical byte sections so their totals remain exact.

It also scans serialized JSON for field-name and syntax overhead.

Exact scalar matches identify repeated values between original results and presentation cells.

** Execution plan

1. Add payload-analysis result types to the benchmark module.
2. Add a payload analyzer for existing benchmark work directories.
3. Add exact byte accounting for response, row, and cell sections.
4. Add field-name and JSON syntax accounting.
5. Add repeated-value counters.
6. Add a dedicated payload-analysis binary.
7. Add unit tests for accounting invariants and repetition detection.
8. Document the local analysis command and output fields.
9. Archive the completed benchmark task.

** Risks & assumptions

- The detailed analysis requires the existing benchmark work directory.
- The analysis does not include the final stdout newline in section totals.
- ~cli_payload_bytes~ adds the one-byte newline used by the CLI.
- Result-to-cell repetition counts exact scalar matches only.
- Repetition counters are indicators and are not additive savings estimates.
