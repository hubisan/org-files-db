Benchmark the complete uncached Rust presentation path before cache or parallel optimization work.

* Planning

** Problem summary

The complete sequential presentation pipeline now exists.

The project needs a reproducible baseline before it evaluates parallel execution or presentation caching.

** Goals

- Add a dedicated presentation benchmark runner.
- Generate deterministic result sizes from 100 through 50,000 results.
- Measure normal and expanded-row workloads.
- Measure useful production stages separately.
- Measure compact JSON serialization and payload size.
- Measure a process-startup floor.
- Measure total CLI elapsed time with a fresh process.
- Keep the benchmark sequential and uncached.

** Non-goals

- Do not add a presentation cache.
- Do not add parallel execution.
- Do not change presentation semantics.
- Do not change the normal query JSON contract.
- Do not benchmark Emacs in this task.

** Architecture

Add ~orgfdb-presentation-benchmark~ as a measurement-only binary.

Use the production query parser, validator, result shaper, presentation registry, row expansion, sorting, layout, and serializer.

Factor existing presentation stages only where the benchmark needs a real production boundary.

Keep stage helpers internal to the crate.

Use one synthetic file per requested original result. Use one level-1 heading per file.

Measure expanded rows through tags, effective properties, and file keywords.

Measure total CLI time by starting the release ~orgfdb~ binary and capturing its stdout.

Use ~orgfdb --help~ as a repeatable process-startup probe.

** Review fix: SQLite variable limit

The first 50,000-result run exposed the SQLite variable limit in query enrichment.

Large result sets passed every file or heading ID through one ~IN (...)~ clause.

The fix uses chunks of 900 IDs for enrichment queries.

The same chunk limit now applies to:

- files
- heading-to-file lookup
- headings
- effective tags
- properties
- effective properties
- keywords
- links and backlinks

This change keeps the query result contract unchanged.

The benchmark can now reach large result sets without one SQL variable per result.

** Local benchmark result

The release benchmark completed on Linux x86_64 with eight available CPUs.

The run used one warmup and three measured iterations.

At 50,000 original results, normal heading presentation took about 1.20 seconds of median CLI time.

The expanded workloads produced 150,000 presentation rows.

Their median CLI times ranged from about 1.54 seconds through 2.16 seconds.

The process-startup median was about 1.72 ms.

The 50,000-result payload sizes ranged from 47,300,127 bytes through 94,425,521 bytes.

These payload sizes require analysis before parallel or cache work.
