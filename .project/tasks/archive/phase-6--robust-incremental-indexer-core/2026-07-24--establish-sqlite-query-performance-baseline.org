Establish a reproducible SQLite query-performance baseline without changing indexes.

** DONE Establish SQLite query-performance baseline

- Task file: [[file:archive/2026-07-24--establish-sqlite-query-performance-baseline.org]]

Goal: Measure whether the current schema and existing indexes are fast enough for the intended Query Model v0 workload before changing indexes.

Note:

- The project is query-oriented, but a separate data warehouse is unnecessary unless measurements demonstrate a real bottleneck.
- This task measures and documents existing behaviour. It does not change persistent indexes.

Acceptance criteria:

- A reproducible benchmark corpus defines file count, heading count, hierarchy shape, tags, properties, timestamps, links, body-text volume, and representative selectivity.
- The corpus includes both shallow and wide outlines and deep hierarchical outlines.
- Common queries are generated through the real Query Model v0 compiler where possible rather than only handwritten SQL.
- Workloads include TODO predicates, tags, properties, links and link status, planning and timestamps, file predicates, outline ancestors, descendants and subtrees, and representative result shaping.
- FTS query performance is measured when FTS5 is enabled.
- FTS measurements include title-only and body-enabled databases.
- Materialized-path subtree queries are measured for shallow, wide, and deep outlines.
- ~EXPLAIN QUERY PLAN~ output is recorded for representative queries.
- Query plans are related to the indexes already present in ~sql/schema.sql~.
- Measurements distinguish warm and cold behaviour where practical.
- Measurements report result counts and use repeated runs.
- SQLite version, build capabilities, relevant pragmas, hardware assumptions, and command configuration are documented.
- Baseline database size is recorded.
- Existing index size and rebuild/write cost are recorded so read performance is not evaluated in isolation.
- Commands, corpus generation, raw results, summaries, and limitations are documented reproducibly.
- No index is added or removed merely because it appears theoretically useful.

* Results

** Approach

- Added the =orgfdb-benchmark= release runner with explicit corpus, seed, iteration, new work-directory, and new output-path arguments.
- Added a deterministic versioned corpus with path groups, shallow/wide and deep outlines, TODOs, tags, properties, planning and generic timestamps, repeaters, resolved/broken links, and controlled search tokens.
- Added stable Query Model v0 workload IDs covering selective/non-selective TODO, tag, property, file, link, timestamp, hierarchy, flat, and outline paths. FTS title/body workloads use the production search implementation and emit structured skips when unavailable or disabled.
- Closed the rebuild connection before measurement. Each workload records one fresh-connection end-to-end sample, then warm-ups and samples on a separate reused read-only connection.
- Recorded generation/rebuild durations, SQLite version and compile options, capability, pragma, environment, query-plan, and database/WAL/checkpoint evidence.

** Changed files

- ~src/benchmark.rs~ and ~src/bin/orgfdb-benchmark.rs~ provide the generator, runner, output contract, and focused contract tests.
- ~src/cli.rs~ exposes the existing production search execution against a supplied connection for the runner while retaining early CLI input validation.
- ~docs/performance-baseline.org~ documents the protocol and intentionally local JSON artifacts.
