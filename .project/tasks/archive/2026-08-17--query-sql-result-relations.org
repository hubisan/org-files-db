Goal: Remove avoidable SQL work after a query matches a large result set.

The first SQL optimization round removed the fixed ~900~ parameter chunks.

It also reduced unnecessary enrichment work and uses the SQLite runtime variable limit.

The remaining main pattern is now:

#+begin_example
SQLite matches result IDs
  -> Rust collects result IDs
  -> Rust sends the same IDs back to SQLite
  -> SQLite loads enrichment data
#+end_example

Avoid this round trip where SQLite can keep the result relation and join against it directly.

Keep Rust post-processing when it is simpler or faster after SQLite returns the required data.

** Goals

- Remove the large-ID round trip from heading tag loading.

** Architecture

Add an internal execution result that carries the compiled matched SQL relation with the normal query rows.

The public row-only execution functions keep their existing API and discard the internal relation metadata.

The production execute-and-shape path passes the matched relation to result shaping.

Direct-flat metadata loaders join against the compiled matched relation instead of sending matched IDs back through large ~IN (...)~ clauses.

Heading tag loading uses the same compiled heading relation.

The direct-flat path validates ~outline_path~ through the matched relation and keeps the current corruption errors.

The flat heading path reuses the matched query relation instead of loading all headings from matched files.

A recursive query-derived ancestor loader fetches only missing ancestors required to construct paths.

Fallback shaping from caller-supplied ~QueryRows~ keeps the existing ID-based loaders.
