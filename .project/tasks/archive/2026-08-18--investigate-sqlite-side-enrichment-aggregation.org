* Planning

** Problem summary

Large heading queries transfer one SQLite row for every effective tag.

The benchmark corpus has three effective tags for each level-1 heading.

A ~50'000~-heading query therefore transfers about ~150'000~ tag rows before Rust builds ~50'000~ final tag collections.

Rust also groups the rows, sorts them by stored position, and serializes each tag vector to JSON.

The flat result shaper then parses that JSON into the public ~Vec<String>~.

** Goals

- Measure the current heading-tag row transfer with the bundled SQLite runtime.
- Compare one isolated SQLite aggregation candidate with the current production path.
- Require exact public result equality before timing the candidate.
- Record SQLite execution, row decoding, Rust grouping, local sorting, final shaping, and complete latency.
- Record tag text payload bytes where the trace can measure them directly.
- Keep only a candidate that improves complete query latency at ~50'000~ results without a material small-workload regression.

** Non-goals

- Do not change predicate compilation.
- Do not change shared TEMP relation selection.
- Do not move final presentation formatting into SQLite.
- Do not change properties, effective properties, or keywords before the heading-tag result justifies more work.

** Architecture

Keep the current row-per-tag loader as the production strategy during measurement.

Add an internal benchmark-only strategy selector for heading-tag enrichment.

The candidate uses SQLite ~json_group_array(tag ORDER BY position)~ and returns one JSON value for each heading that has tags.

The candidate writes this JSON value directly into ~HeadingQueryRow.all_tags_json~.

This avoids a new JSON decode and encode round trip in the enrichment loader.

The existing final result shaper remains the only JSON decoder for heading tags.

Headings without tags keep the existing ~[]~ value and do not require an aggregate row.

** Risks & assumptions

SQLite aggregation can reduce row decoding while increasing SQLite work.

JSON aggregation increases the text bytes for tag values because it adds JSON syntax.

The candidate remains useful only if fewer SQLite rows and less Rust work offset that cost.

The bundled SQLite runtime provides JSON aggregate functions and ordered aggregate arguments.

* Results

** Approach

Tested heading tags first, as required by the task gate.

The candidate used SQLite ~json_group_array(tag ORDER BY position)~ and returned one aggregate row per heading.

The baseline kept the current row-per-tag enrichment.

The paired benchmark required exact public ~QueryResponse~ equality before timing either strategy.

Production execution stayed on row-per-tag during the investigation.

After the benchmark rejected the candidate, the temporary strategy selector and schema version ~14~ measurement code were removed.

The normal query SQL benchmark therefore stays on schema version ~13~.

** Benchmark result

The bundled SQLite runtime was ~3.53.2~ with ~MAX_VARIABLE_NUMBER=32766~.

The benchmark used ~2~ warmups and ~7~ iterations for ~100~, ~1'000~, and ~50'000~ result workloads.

| Results | Row-per-tag median | JSON aggregate median | Complete latency change | Tag rows | Aggregate tag rows | Tag payload | Aggregate payload |
|---------+--------------------+-----------------------+-------------------------+----------+--------------------+-------------+-------------------|
| 100 | 0.715 ms | 0.757 ms | +6.0% | 300 | 100 | 1.9 KB | 2.9 KB |
| 1'000 | 4.532 ms | 4.616 ms | +1.8% | 3'000 | 1'000 | 19 KB | 29 KB |
| 50'000 | 261.575 ms | 261.046 ms | -0.2% | 150'000 | 50'000 | 950 KB | 1.45 MB |

At ~50'000~ results, total SQLite-to-Rust rows fall from ~250'000~ to ~150'000~.

The candidate therefore reduces total transferred rows by ~40%~ and tag rows by about ~67%~.

The lower row count does not produce a meaningful complete-query improvement.

For the ~50'000~-result tag step, the phase profile reports these costs.

| Phase | Row-per-tag | JSON aggregate |
|-------+-------------+----------------|
| SQLite execution | 45.574 ms | 78.150 ms |
| SQLite row decoding | 26.893 ms | 8.186 ms |
| Rust grouping | 10.469 ms | 8.483 ms |
| Rust local sorting | 11.251 ms | 0 ms |
| Total | 94.187 ms | 94.818 ms |

SQLite aggregation adds enough execution cost to offset the lower decoding, grouping, and sorting work.

The JSON representation also increases tag payload bytes because it adds aggregate JSON syntax.

** Decision

Reject SQLite-side JSON aggregation for heading tags.

Keep the existing row-per-tag production enrichment.

The ~50'000~-result complete-query gain is about ~0.2%~, which is too small to justify more SQL and strategy complexity.

The candidate is also slower at the two measured small result sizes.

Do not investigate properties, effective properties, or file keywords in this task.

The task explicitly requires the first heading-tag result to justify further aggregation work, and this result does not meet that gate.

This is a successful no-production-change result, not a cancelled investigation.
