* Planning

** Problem summary

The crate currently exports every top-level module from =src/lib.rs=, and =src/db.rs= re-exports a broad set of helpers, row structs, and writer input types. The integration tests only exercise the parser-facing API plus =todo_keywords::resolve_todo_keywords=, so much of the DB and indexer surface appears public by convenience rather than by an explicit support decision.

** Goals

- Identify the current de facto public library surface.
- Separate parser-facing items that are actively exercised from DB/indexer helpers that look internal.
- Produce a narrow BUILD scope that reduces accidental API exposure without changing behavior or requiring broad test migration.

** Non-goals

- Do not redesign the library API.
- Do not change CLI, parser, indexer, or DB behavior.
- Do not privatize the parser model surface in this pass.
- Do not perform top-level module restructuring unless a change is trivially safe and clearly unused.

** Architecture

- Treat =parser= as the only clearly exercised external library surface for now, because all integration tests import parser traits, parser model types, =OrgizeAdapter=, and parser diagnostics through =org_files_db::parser=.
- Treat =todo_keywords::resolve_todo_keywords= as externally exercised for now because an integration test imports it directly.
- Treat most =db= row structs, writer input structs, read-only open helpers, and schema-specific constructor helpers as internal implementation details unless README or tests show a stronger support signal.
- Keep =src/lib.rs= module exports unchanged in the first narrowing pass unless an entire module is obviously unused externally and can be hidden without touching tests.

** Execution plan

1. In the BUILD, inventory the =db= re-exports and classify each item as parser-facing, CLI-only, test-only, or genuinely reusable library API.
2. Narrow the DB surface first:
   - make =open_existing_database_read_only= and =open_existing_database_read_only_with_schema= =pub(crate)= if they are only used by =cli= and internal tests
   - make =HeadingListRow= and possibly =DbReader= =pub(crate)= if they are only used by =cli=, =indexer= tests, and DB unit tests
   - make writer row/input structs =pub(crate)= when they are only consumed by =indexer=, =cli= unit tests, and DB unit tests
3. Review =cli= helpers:
   - keep =cli::run= public for the binary entry point
   - consider making =run_with_args= and =rebuild= private or =pub(crate)= if they are not needed outside the crate
4. Review =indexer= conservatively:
   - only narrow =Indexer=, =RebuildReport=, =IndexedFile=, and =IndexerError= if no integration tests, docs, or public callers depend on them
   - if this looks semantically larger than the DB-only cleanup, defer indexer narrowing to a follow-up
5. Leave =parser= exports and =todo_keywords::resolve_todo_keywords= unchanged in this pass to avoid moving integration tests or creating test-only shims.
6. Run =make ci= and adjust any unit tests that need to move inside their owning modules after visibility is reduced.

** Risks & assumptions

- Narrowing visibility is an API-contract change even if behavior is unchanged, so the BUILD should stay intentionally small.
- Because integration tests live outside the crate boundary, any parser-surface narrowing would require either test migration or test-only support helpers; that is broader than this task needs.
- =SchemaDefinition= and =CURRENT_SCHEMA_VERSION= are mentioned in =README.org=, which is weak evidence of intentional support. The BUILD should avoid narrowing them unless there is a strong reason.
- Top-level modules like =config=, =dir_locals=, and =query= are not used by integration tests, but hiding them from =src/lib.rs= is a broader contract decision than narrowing obvious DB internals.

** Open questions

- Whether =Indexer= should remain public for future embedding use, even though current tests and docs do not establish it as supported API.
- Whether =Config= should be treated as intentionally public because it represents a stable file format contract, or left unchanged simply to avoid unrelated churn.

** Proposed checks

- Inspect visibility errors after narrowing and move any affected helper tests from integration tests to unit tests only if strictly necessary.
- Run =make ci=.
