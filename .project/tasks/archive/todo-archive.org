** DONE [2026-06-23 Tue 20:17] Fix PROPERTY and CATEGORY normalization to use whole-file keyword scan

[[./phase-2--complete-parser-data-model-v0.1/2026-06-23--fix-property-and-category-normalization-to-use-whole-file-keyword-scan.org]]

Goal: Ensure that normalized property rows created from ~#+PROPERTY~ and ~#+CATEGORY~ are based on keyword lines from the whole Org document, not only on keywords before the first regular heading.

Context: Org keyword lines can appear later in the buffer and still be recognized by Org-mode. The raw keyword parser/indexer stores keyword rows on the synthetic level 0 heading. Property normalization for ~#+PROPERTY~ and ~#+CATEGORY~ must use the same parsed keyword source, but this task must not change TODO keyword semantics.

Important regression context: A previous attempt changed the central keyword collection path too broadly and caused ~todo_keywords~ insertion to fail with a uniqueness error. This task must avoid that regression.

Do not change:

- Do not change normalized ~TODO~, ~SEQ_TODO~, or ~TYP_TODO~ behavior.
- Do not remove existing TODO keyword deduplication or merge logic.
- Do not change the ~todo_keywords~ schema.
- Do not change the uniqueness behavior of ~todo_keywords~.
- Do not modify manual SQLite database files.
- Do not modify task tracking files such as ~.project/tasks/todo.org~, except for moving this task through the workflow if explicitly required by the project process.
- Do not implement a second independent raw-text scanner if a parsed keyword list already exists.
- Do not compute effective or inherited property values in this task.

Problem:

#+begin_src org
  ,#+PROPERTY: var before

  ,* First heading

  ,#+PROPERTY: var after
  ,#+CATEGORY: later-category

  ,* Second heading
#+end_src

Expected parser/indexer behavior:

- Both ~#+PROPERTY~ rows are stored as raw keyword rows.
- The later ~#+CATEGORY~ row is stored as a raw keyword row.
- Both ~#+PROPERTY~ rows also create normalized rows in ~properties~ with ~source = property_keyword~.
- The ~#+CATEGORY~ row also creates a normalized row in ~properties~ with ~source = category_keyword~.
- All normalized rows are attached to the synthetic level 0 heading.
- No normalized row is attached directly to ~First heading~ or ~Second heading~.

Scope:

- Reuse the existing parsed keyword collection used for raw keyword insertion, if available.
- If the existing parser has special whole-buffer keyword logic for ~TODO~, ~SEQ_TODO~, ~TYP_TODO~, ~PROPERTY~, or ~CATEGORY~, preserve it unless a test proves it is wrong.
- Do not replace the central keyword collector with a broad ~syntax().descendants().filter_map(Keyword::cast)~ implementation unless all existing keyword/TODO tests still pass and no duplicate ~todo_keywords~ rows are produced.
- Do not limit ~#+PROPERTY~ or ~#+CATEGORY~ normalization to the preamble before the first regular heading.
- Preserve duplicate raw keyword rows.
- Preserve duplicate normalized property rows.
- Preserve source order through ~line_number~ and/or insertion order.
- Keep keyword rows and property rows separate.
- Store ~#+PROPERTY~ and ~#+CATEGORY~ twice: once as raw ~keywords~ rows and once as normalized ~properties~ rows.
- Attach normalized ~property_keyword~ and ~category_keyword~ rows only to the synthetic level 0 heading.
- Do not attach normalized keyword-derived property rows to surrounding regular headings.

Normalization rules:

- ~#+PROPERTY: key value~ creates a row in ~properties~ with key ~KEY~, value ~value~, source ~property_keyword~, append = 0, and heading_id = synthetic level 0 heading.
- ~#+PROPERTY: key+ value~ creates a row in ~properties~ with key ~KEY~, value ~value~, source ~property_keyword~, append = 1, and heading_id = synthetic level 0 heading.
- ~#+CATEGORY: value~ creates a row in ~properties~ with key ~CATEGORY~, value ~value~, source ~category_keyword~, append = 0, and heading_id = synthetic level 0 heading.
- The trailing ~+~ append marker is not part of the stored key.
- Property keys are normalized consistently with the existing property implementation.

* DONE Phase 3: Org link extractor
:PROPERTIES:
:VISIBILITY: folded
:END:

** Goal of this phase
:PROPERTIES:
:VISIBILITY: folded
:END:

Extract Org links as raw source facts and store them in SQLite without depending on Orgize's link support being complete. Link resolution to files, headings, IDs, CUSTOM_IDs, org-id-locations, dedicated targets, or relationship graphs belongs to later phases.

Core rules:

- Store source facts only.
- Do not resolve link targets in Phase 3.
- Do not execute action-like links such as ~shell:~ or ~elisp:~.
- Keep raw link text and byte ranges as the source of truth.
- Use Orgize for document structure where useful, but do not rely on Orgize as the source of link-token truth.
- Implement a project-owned raw-text scanner for link tokens.
- Bracket links and angle links are syntax-driven.
- Plain links are protocol-list-driven.
- Bracket links, angle links, and configured plain links are the supported Phase 3 link formats.
- Radio targets are not supported.
- Link abbreviations are not supported.
- Relationship markers in descriptions are not supported.
- Multi-line bracket and angle links are not supported.
- Dedicated targets such as ~<<target>>~ are not stored as link facts.
- Links outside regular headings attach to the synthetic level-0/root heading.
- Links should always have a ~heading_id~; missing root attachment is an indexing invariant violation.
- User-facing CLI output must expose enough source location data for editor jumps.

** Phase 3 link extraction contract
:PROPERTIES:
:CUSTOM_ID: phase3-link-contract
:VISIBILITY: folded
:END:

This is the contract that implementation, tests, storage, rebuild, and CLI tasks must follow.

*** Source-fact contract

- Link extraction is source-fact extraction only.
- No link target resolution happens in Phase 3.
- Raw source text and byte ranges are the source of truth.
- Link targets are never executed, evaluated, shell-expanded, or used as SQL/code.
- All link fields must be written through parameterized SQL statements.
- Raw link content must not be interpolated into SQL strings.

*** Supported formats

Supported ~format~ values:

- ~bracket~
- ~angle~
- ~plain~

Dedicated targets are not represented as a ~format~ value.

*** Bracket links

Supported:

- ~[[target]]~
- ~[[target][description]]~

Rules:

- If bracket syntax is valid, extract the link.
- Explicit typed targets store the prefix before the first ~:~ as ~link_type~.
- Unknown explicit types are preserved as their ASCII-lowercase prefix.
- The target part is stricter than the description part.
- The description part is permissive.
- In the description part, arbitrary characters may appear, including unescaped ~[~ and ~]~.
- Nested-looking bracket sequences in descriptions are allowed.
- A bracket link closes only at the first valid same-line ~]]~ delimiter.
- Multi-line bracket links are not supported.
- If a bracket link would require crossing a newline to close, treat it as not-a-link and continue scanning.

Minimal classification for targets without explicit type:

- ~[[#custom-id]]~ => ~link_type = custom-id~
- ~[[*Heading]]~ => ~link_type = fuzzy~
- ~[[dedicated]]~ => ~link_type = fuzzy~

Implicit file bracket links:

- Classify as file-like only when the target starts with:
  - ~./~
  - ~../~
  - ~/~
  - ~/~ 
- ~[[notes.org]]~ remains fuzzy, not file.

Examples:

#+begin_src org
  [[target]]
  [[target][description]]
  [[file:notes.org]]
  [[./notes.org]]
  [[../notes.org]]
  [[~/notes.org]]
  [[/tmp/notes.org]]
  [[#custom-id]]
  [[*Heading]]
  [[dedicated]]
  [[unknown:foo]]
  [[shell:ls]]
#+end_src

*** Angle links

Supported:

- ~<type:path>~

Rules:

- Angle links are syntax-driven.
- The type is the substring before the first ~:~.
- The type does not need to be predefined.
- Unknown explicit types are preserved as their ASCII-lowercase prefix.
- The closing ~>~ must be on the same line.
- Spaces inside the path are allowed.
- If an angle link would require crossing a newline to close, treat it as not-a-link and continue scanning.
- Angle links are extracted by the project scanner, regardless of whether Orgize exposes them.

Examples:

#+begin_src org
  <https://example.com/some path with spaces>
  <file:~/code/main.c::255>
  <jira:ABC-123>
  <unknown:foo>
  <shell:ls *.org>
#+end_src

*** Plain links

Supported:

- ~type:path~

Rules:

- Plain links are protocol-list-driven.
- Plain links are extracted only when ~type~ is enabled through the plain-link protocol configuration.
- Orgize plain-link support is not part of the contract.
- The project config controls the protocol list; Emacs Org's built-in protocol list is not the project protocol contract.
- Plain-link boundary and path-end behavior should follow Emacs Org's ~org-link-plain-re~ behavior where feasible.
- Ambiguous plain-link boundary, quote, delimiter, and trailing-punctuation cases must be checked against Emacs ~org-element-parse-buffer~ before changing scanner behavior.
- The project scanner remains the implementation contract, but any deliberate deviation from observed Org behavior must be documented explicitly with fixture examples.
- Plain links do not contain whitespace.
- Plain links may contain punctuation and balanced delimiter groups only where Org's plain-link grammar accepts them.
- Deterministic trailing punctuation is not part of the stored link span.
- The stored ~raw~, ~byte_start~, and ~byte_end~ refer to the final accepted link span.

Plain-link left-boundary policy:

- A plain link may start at the beginning of a line.
- A plain link may start after whitespace.
- A plain link may start after punctuation when Org's plain-link grammar accepts a word boundary before the protocol.
- A plain link must not start in the middle of a word.
- Single-quoted plain links are treated as not-a-link in Phase 3, matching observed Org behavior.
- This is a plain-link boundary rule, not an ignored-region rule.

Plain-link path/end policy:

- Plain links stop at whitespace.
- Plain links may include delimiter-like groups such as ~(...)~, ~[...]~, and ~<...>~ when Org's plain-link grammar accepts them as balanced groups.
- A plain link may end with a non-punctuation, non-whitespace character.
- A plain link may end with ~/~.
- A plain link may end with ~-~.
- A plain link may end with an Org-accepted balanced delimiter group.
- Other deterministic trailing punctuation is trimmed from the stored link span.

Trimmed trailing punctuation for plain links:

- ~.~
- ~,~
- ~;~
- ~:~
- ~!~
- ~?~
- ~)~
- ~]~
- ~}~

The stored ~raw~, ~byte_start~, and ~byte_end~ refer to the final accepted and trimmed link span.

Examples:

#+begin_src org
https://example.org
file:notes.org
id:abc123
mailto:person@example.org
jira:ABC-123

!https://www.example.com
"https://www.example.com
$https://www.example.com
%https://www.example.com
'https://www.example.com
xhttps://www.example.com

https://example.org/path with text after whitespace

Expected plain-link boundary and end behavior:

- ~https://example.org~ stores ~https://example.org~.
- ~file:notes.org~ stores ~file:notes.org~.
- ~id:abc123~ stores ~id:abc123~.
- ~mailto:person@example.org~ stores ~mailto:person@example.org~.
- ~jira:ABC-123~ stores ~jira:ABC-123~ only when ~jira~ is configured.
- ~!https://www.example.com~ stores ~https://www.example.com~.
- ~"https://www.example.com~ stores ~https://www.example.com~.
- ~$https://www.example.com~ stores no plain link, matching observed Org behavior.
- ~%https://www.example.com~ stores no plain link, matching observed Org behavior.
- ~'https://www.example.com~ stores no plain link, matching observed Org behavior.
- ~xhttps://www.example.com~ stores no plain link because the protocol starts in the middle of a word.
- ~https://example.org/path with text after whitespace~ stores ~https://example.org/path~.
- ~https://example.org/path<balanced-suffix>~ stores ~https://example.org/path<balanced-suffix>~, matching Org plain-link behavior.
- ~https://example.org/path.~ stores ~https://example.org/path~.
- ~https://example.org/path/~ stores ~https://example.org/path/~.
- ~https://example.org/path-~ stores ~https://example.org/path-~.

Reference notes:

- Emacs Org parses plain links through ~org-link-plain-re~ in ~org-element-link-parser~.
- The important boundary component is Org's word-boundary assertion before the configured protocol.
- The exact set of accepted prefix characters is syntax-table and parser-context dependent, so the contract should not maintain a complete hand-written prefix-character list.
- Representative examples must be kept in tests and fixtures instead.

Config semantics:

- Missing ~plain_protocols~ uses the default list.
- ~plain_protocols = []~ disables the default plain-link protocols only.
- ~custom_protocols~ remains active even when ~plain_protocols = []~.
- Effective plain-link protocols are ~plain_protocols + custom_protocols~.
- Protocol matching is ASCII-case-insensitive for extraction.
- Stored ~link_type~ is ASCII-lowercase.
- Duplicate protocols after lowercase normalization are ignored.
- To disable all plain-link extraction, set both:
  - ~plain_protocols = []~
  - ~custom_protocols = []~
- ~custom_protocols~ affects plain-link detection only.
- ~custom_protocols~ does not affect bracket links.
- ~custom_protocols~ does not affect angle links.
- Bracket links and angle links do not require their protocol/type to be listed in config.
- Bracket links with unknown explicit types are still extracted.
- Angle links with unknown explicit types are still extracted.
- This intentionally allows the project scanner to extract more raw source facts than Org/Emacs may visually highlight when a custom link type is not registered.
- Action-like protocols such as ~shell~ and ~elisp~ are not enabled by default for plain links.
- Action-like protocols may be enabled for plain-link extraction explicitly through ~plain_protocols~ or ~custom_protocols~.
- Action-like protocols may still be stored when they occur in bracket or angle syntax.
- Action-like protocols are never executed.

Default plain-link protocol rationale:

- The default list follows Org's common built-in external link types where plain-link extraction is useful as a raw source fact.
- ~file+sys~ and ~file+emacs~ are included as file-like variants.
- ~ftp~ is included for compatibility with Org's plain-link recognition behavior.
- ~shell~ and ~elisp~ are intentionally excluded from default plain-link extraction because they are action-like.
- Bracket and angle syntax can still store ~shell~ and ~elisp~ as raw source facts because explicit delimiters make the author's intent clearer.

*** Search option splitting

- Resolve bracket same-file ~CUSTOM_ID~ links.
- Resolve file-context ~CUSTOM_ID~ search options.
- Resolve ~ID~ links within the indexed ID universe.
- Match ~CUSTOM_ID~ and ~ID~ lookup values using Org-compatible normalization:
  - trim leading and trailing whitespace
  - compare case-insensitively
- Whenever a target resolves to a heading, set both ~target_file_id~ and ~target_heading_id~.
- Preserve raw link source fields.

Scope:

- Same-file ~CUSTOM_ID~ links:
  - ~[[#foo]]~
  - ~[[#foo][Description]]~
- File-context ~CUSTOM_ID~ links:
  - ~[[file:other.org::#foo]]~
  - ~[[file:other.org::#foo][Description]]~
  - ~[[./other.org::#foo]]~
  - ~[[../other.org::#foo]]~
  - ~<file:other.org::#foo>~
  - plain ~file:other.org::#foo~ when extracted by configured plain-link protocols
- Org ID links:
  - ~id:foo~
  - ~[[id:foo]]~
  - ~[[id:foo][Description]]~
  - ~<id:foo>~
  - plain ~id:foo~ when extracted by configured plain-link protocols

Important parser model:

- Same-file ~[[#foo]]~ may be classified as ~link_type = fuzzy~.
- It is still a ~CUSTOM_ID~ target when:
  - ~link_type = fuzzy~
  - ~path~ starts with exactly one leading ~#~
- This is analogous to same-file star heading links:
  - ~[[*foo]]~ resolves by heading title in the source file.
  - ~[[#foo]]~ resolves by ~CUSTOM_ID~ in the source file.
- File-context ~CUSTOM_ID~ links are file links with:
  - ~link_type = file~
  - ~search_option~ beginning with exactly one leading ~#~
- Bare angle or plain ~#foo~ is not a supported CUSTOM_ID link form.
- Angle and plain CUSTOM_ID links require an explicit ~file:...::#foo~ form.

Shared lookup rules:

- Match against indexed heading properties:
  - ~properties.key~
  - ~properties.value~
- Match property keys exactly:
  - ~CUSTOM_ID~
  - ~ID~
- Normalize property target values before lookup.
- Compare property values case-insensitively.
- Do not fuzzy-match property values.
- Do not normalize internal whitespace.
- Exclude synthetic root headings from property-target lookup.
- Do not rely on unspecified SQL row order.
- Define document order using stored heading order, such as ~byte_start~ or the existing heading-order field.
- Raw link source fields must remain unchanged.

Property target normalization:

- Apply only to ~CUSTOM_ID~ and ~ID~ lookup values.
- For ~CUSTOM_ID~:
  - remove exactly one leading ~#~
  - trim leading and trailing whitespace from the remaining value
  - use the normalized value for property lookup
  - store the normalized value in ~target_custom_id~
  - compare case-insensitively against stored ~CUSTOM_ID~ property values
- For ~ID~:
  - use the parsed ID target value from the existing link fields
  - trim leading and trailing whitespace from the value
  - use the normalized value for property lookup
  - store the normalized value in ~target_id~
  - compare case-insensitively against stored ~ID~ property values
- Do not lowercase the stored raw link fields.
- Do not mutate:
  - ~raw~
  - ~raw_target~
  - ~raw_description~
  - ~path~
  - ~search_option~
- Do not normalize internal whitespace:
  - ~" Foo Bar "~ becomes ~"Foo Bar"~
  - ~"Foo  Bar"~ remains ~"Foo  Bar"~

Duplicate target policy:

- Duplicate ~CUSTOM_ID~ targets follow observed Org behavior.
- If multiple matching ~CUSTOM_ID~ properties exist in the active search scope:
  - select the first matching heading in document order
  - set ~target_file_id~ to the matched heading's file
  - set ~target_heading_id~ to the first matching heading
  - set ~resolution_status = resolved~
  - set ~resolution_diagnostic = NULL~
- Duplicate ~ID~ targets are data errors.
- If multiple indexed headings have the same ~ID~ after case-insensitive matching:
  - do not choose a target
  - set ~target_file_id = NULL~
  - set ~target_heading_id = NULL~
  - set ~target_id~ to the normalized requested ID
  - set ~resolution_status = ambiguous~
  - set ~resolution_diagnostic = duplicate id~

Diagnostics policy:

- Successful resolutions use:
  - ~resolution_diagnostic = NULL~
- Missing same-file or file-context ~CUSTOM_ID~ uses:
  - ~resolution_status = broken~
  - ~resolution_diagnostic = custom id not found~
- Missing ~ID~ uses:
  - ~resolution_status = unresolved~
  - ~resolution_diagnostic = id not found~
- Duplicate ~ID~ uses:
  - ~resolution_status = ambiguous~
  - ~resolution_diagnostic = duplicate id~

Out of scope:

- Do not support bare angle ~<#foo>~ as a CUSTOM_ID link.
- Do not support bare plain ~#foo~ as a CUSTOM_ID link.
- Do not resolve ~attachment:~ links.
- Do not resolve regexp search options.
- Do not resolve line-number search options.
- Do not resolve dedicated targets.
- Do not resolve non-star and non-~#~ fuzzy links.
- Do not change file heading-title search option behavior.
- Do not change same-file star fuzzy heading resolution.
- Do not change file-only synthetic root heading behavior.
- Do not scan files outside the indexed DB.
- Do not use Emacs ~org-id-locations~.
- Do not add a DB schema migration.

Implementation notes:

- Prefer a shared helper for property target normalization.
- Keep property key matching exact.
- Implement case-insensitive value comparison deterministically.
- Either:
  - query candidate properties in scope ordered by heading document order and compare normalized values in Rust
  - or use deterministic SQL case-insensitive comparison with explicit ~ORDER BY headings.byte_start, headings.id~
- Preserve deterministic first-match behavior for ~CUSTOM_ID~.
- Preserve strict ambiguous behavior for duplicate ~ID~.
- Keep raw DB link fields unchanged.

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.

- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.

- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

*** Incremental and watcher-like workloads

Measured examples included:

- metadata-only update
- one modified file
- one created file
- one deleted file
- mixed create, modify, and delete change set

Results:

- Metadata-only and delete operations contained no parse work.
- Single-file create and modify operations spent far below 1% of their end-to-end time in parsing.
- The mixed three-file change set also spent far below 1% in parsing.
- Discovery, planning, SQLite application, and derived-state maintenance dominated these operations.
- Starting or coordinating parser workers for these batches would likely cost more than the parsing work being parallelized.

Conclusion:

- Watcher execution must remain sequential.
- Small reconciliation batches must remain sequential.
- Parallel parsing would provide no meaningful benefit for normal incremental operation.

** DONE Decide whether parallel parsing and preparation are justified

Decision:

- Parallel parsing and preparation are not justified by the measurements.
- The sequential Phase 6 path remains the production implementation.
- Phase 8 closes without adding parallel execution.

Theoretical upper bound:

- At 1,000 files, only approximately ~0.084–0.086 s~ of an approximately ~0.80 s~ rebuild is parallelizable.
- With eight perfectly utilized workers and zero scheduling overhead, the mathematical maximum saving would be approximately ~0.073–0.076 s~.
- This corresponds to an ideal end-to-end improvement of only approximately ~9%~.
- Unlimited perfect parallelism could not remove more than the measured parse share of approximately ~10–11%~.

Realistic expectation:

- Worker scheduling, result collection, deterministic reordering, synchronization, memory allocation, and uneven file sizes would reduce the theoretical benefit.
- A realistic 1,000-file saving was estimated at approximately ~0.04–0.065 s~.
- The rebuild would likely improve only from approximately ~0.80 s~ to approximately ~0.74–0.76 s~.
- This difference is measurable but not operationally significant.

10,000-file projection:

- No 10,000-file benchmark was executed.
- A projection from the measured corpora suggests a complete rebuild of approximately ~8–9.5 s~ for files of similar average size and structure.
- The parallelizable parse portion would be approximately ~0.8–0.9 s~.
- A realistic eight-worker saving would likely be approximately ~0.4–0.65 s~.
- This projection is not treated as measured acceptance evidence.
- Even at this scale, the expected saving does not justify adding permanent concurrency complexity before a real user workload demonstrates a higher parse share or unacceptable rebuild latency.

Complexity considered:

- Define complete owned parse-job inputs.
- Define complete owned preparation-result values.
- Ensure parser configuration and all worker inputs are immutable and ~Send~ compatible.
- Add a bounded worker scheduler or dependency.
- Restore results to deterministic change-plan order.
- Preserve deterministic error ordering regardless of worker completion order.
- Aggregate worker failures without allowing partial application.
- Bound queued prepared data and resulting memory growth.
- Preserve a sequential fallback.
- Define worker-count and activation-threshold configuration.
- Test worker counts, completion-order variations, cancellation, rollback, error ordering, FTS state, link state, indexing metadata, and source-universe fingerprints.
- Maintain concurrency-specific code indefinitely despite the small expected gain.

Final rationale:

- The likely benefit is a few percent of end-to-end rebuild time.
- The dominant stage cannot be parallelized within the accepted Phase 8 scope.
- Normal watcher and incremental workloads would not benefit.
- The implementation would add substantially more complexity than the user-visible performance improvement warrants.
- Avoiding the feature keeps the indexer simpler, deterministic, easier to test, and easier to maintain.

** Reconsideration criteria

Reopen parallel parsing only if at least one of the following becomes true:

- Measurements from a real production corpus show that ~parse_and_prepare~ is a substantially larger share of end-to-end rebuild time.
- Full rebuild latency becomes operationally disruptive.
- Individual Org files become substantially larger or more parser-heavy than the benchmark corpus.
- A future architecture change removes or significantly reduces the serial ordered-application bottleneck.
- A simpler concurrency implementation becomes available without compromising deterministic ordering, rollback, memory bounds, or maintainability.

Until then, the measured sequential implementation is considered sufficient.
