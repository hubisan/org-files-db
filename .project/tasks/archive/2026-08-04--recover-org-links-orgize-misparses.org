Goal: Correctly recognize, index, resolve, render, and update valid Org links in cases where Orgize does not produce a correct ~LINK~ syntax node or classifies parts of the link as unrelated Org syntax.

Implement one isolated compatibility layer in the ~orgfdb~ Orgize adapter.

The rest of the application must consume one normalized link representation without needing to know whether a link was:

- parsed natively by Orgize
- recovered by the compatibility scanner

Do not spread Orgize-specific workarounds throughout:

- indexing
- heading extraction
- database writing
- link resolution
- query output
- rename handling
- source rewriting

** Known Orgize parsing failures

Orgize currently fails to recognize some valid links whose descriptions contain square brackets.

Example:

#+begin_src org
[[https://medium.com/@Graphling/intro-to-brazilian-jiu-jitsu-modeling-language-bjjml-9dd689ddd048][Intro to Brazilian Jiu-Jitsu Modeling Language [BJJML] | by Graphling | Medium]]
#+end_src

Expected description:

#+begin_example
Intro to Brazilian Jiu-Jitsu Modeling Language [BJJML] | by Graphling | Medium
#+end_example

Orgize may expose the complete source as plain ~TEXT~ rather than as a ~LINK~ node.

Links whose descriptions begin with inactive timestamps are also affected:

#+begin_src org
[[file:../notes/gesundheit/leiden/leiden.org::#3b8e6503-ec59-463b-8f86-66a07d356afc][[2026-03-21 Sa] (circa) Rechte Ferse bei Bouldern angeschlagen]]

[[file:../notes/gesundheit/leiden/2022-12-operation-nasenscheidenwand.org][[2022-12-13 Di] Operation Nasenscheidenwand & Nebenhöhlen]]

[[file:../notes/gesundheit/leiden/leiden.org::#f22e2595-302b-4263-85d5-0394a16ac405][[2026-03-21 Sa] Schmerzen Fuss unten vorne]]
#+end_src

Orgize may expose these as a sequence such as:

#+begin_example
TEXT
TIMESTAMP_INACTIVE
TEXT
#+end_example

instead of one complete link.

Orgize also misclassifies links at the beginning of list items when their target contains ~::~:

#+begin_src org
- [[test.org::Heading]]
- [[test.org::#1]]
#+end_src

The beginning of the link may be interpreted as a descriptive-list tag because of the ~::~ inside the target.

This ordinary paragraph form is recognized correctly and must remain correct:

#+begin_src org
Parsed as link: [[test.org::Heading]]
#+end_src

** Org target escaping rules

The compatibility scanner must follow Org link-target escaping rules.

In the link target, escaping is required for:

- every literal ~[~
- every literal ~]~
- every backslash immediately preceding ~[~ or ~]~
- every backslash at the end of the target

Examples:

#+begin_src org
[[https://www.gnu.org\][Test]]

[[https://www.gnu.org\\][Test]]

[[https://www.gnu.org\]\[brackets need to be escaped \[\] in the path\]][test]]
#+end_src

The scanner must distinguish:

- an escaped closing bracket
- an escaped opening bracket
- a literal final backslash
- a structural target delimiter
- a malformed or incomplete escape sequence

The first example must not be accepted merely by searching forward for the next possible closing brackets.

The second example contains an escaped trailing backslash and must be handled according to GNU Emacs Org semantics.

The third example contains escaped brackets and backslashes in the target and must not terminate prematurely.

Do not implement target parsing with one broad regular expression.

** Description delimiter rules

Descriptions follow different rules from targets.

Square brackets in a description do not generally require target-style escaping.

Examples:

#+begin_src org
[[https://www.gnu.org][Intro to Brazilian Jiu-Jitsu [BJJML]]]

[[file:notes.org::#id][[2026-03-21 Sa] Note]]

[[https://orgmode.org][test [again] oder nicht]]
#+end_src

Expected visible descriptions:

#+begin_example
Intro to Brazilian Jiu-Jitsu [BJJML]
[2026-03-21 Sa] Note
test [again] oder nicht
#+end_example

Do not parse a description as recursively nested Org links.

Nested links are not supported as nested link objects.

Two consecutive closing brackets terminate the described link according to the Org link grammar.

The description scanner must therefore not use arbitrary recursive bracket balancing.

Test ambiguous and malformed inputs:

#+begin_src org
[[https://www.gnu.org][[Test]]]]

[[https://www.gnu.org][[[[[[Test]]]]

[[https://www.gnu.org][[][][]]]]

[[https://orgmode.org][test [[https://test.com]]no more link

[[https://orgmode.org][test [[https://test.com]] me [again] oder nicht ]]
#+end_src

For these inputs:

- follow GNU Emacs Org boundary behaviour
- do not fabricate nested link objects
- do not consume unrelated following text
- preserve trailing text outside the recognized link
- reject incomplete links deterministically
- never panic
- always make forward progress

Do not describe or implement this merely as a balanced-bracket scanner.

Do not implement the complete grammar with one regular expression.

* Planning

This plan is based on the current repository implementation. Where the original broad TODO assumed native Orgize link extraction, native/recovered merging, source rewriting, or link-aware rename support, this plan follows the architecture that already exists in the repository and narrows the implementation to current production capabilities.

** Problem summary

The current repository already has one project-owned link extractor in ~src/parser/link_scanner.rs~. ~OrgizeAdapter::parse_document_core~ does not collect native Orgize ~LINK~ nodes for persistence. Instead it:

- parses the document with Orgize
- uses Orgize only to derive ignored literal ranges and structural source contexts
- scans the original source with ~scan_links~
- stores the resulting ~ParsedLink~ values through the ordinary indexer, database, resolver, and query paths

This existing boundary is documented in ~docs/design/parser-risks.org~ and must remain the architecture for this task.

The reported examples expose three different classes of behavior:

1. The project scanner already recognizes many affected links because description parsing currently stops at the first same-line ~]]~. The scanner nevertheless needs a defined state machine, logical target decoding, exact subranges, and stronger malformed-input tests.
2. Heading title rendering still depends on the Orgize headline syntax tree. When Orgize fails to expose a complete link node, ~normalize_title_elements~ can render the authored bracket syntax or fragmented child nodes instead of the visible link description.
3. Timestamp extraction walks Orgize timestamp descendants independently of the project link scanner. If Orgize classifies ~[2026-03-21 Sa]~ inside a link description as ~TIMESTAMP_INACTIVE~, the adapter can incorrectly persist it as a body timestamp even though GNU Emacs Org treats the complete source form as one link whose description is plain text.

The list-item cases are expected to be recoverable by the existing whole-source scanner because list-item tags are not ignored ranges. They require regression coverage, not a repair of the complete Orgize list AST.

** Confirmed semantic decision: timestamp-looking descriptions

For this source:

- preserve the complete raw description
- render the description literally in a heading title when the link occurs in a headline
- do not add ~[2026-03-21 Sa]~ to ~ParsedHeading.timestamps~
- do not persist a timestamp row for it
- do not match it through timestamp queries

*** Semantics to transfer into the Rust scanner and tests

Use ~org-link-bracket-re~ as the closest reference for the bracket-link boundary rules:

- The target is non-empty.
- Ordinary target characters exclude ~[~, ~]~, and ~\\~.
- Literal brackets in the target are accepted only through the Org escape form.
- Consecutive backslashes before a bracket must be interpreted by parity: an odd final escaping backslash makes the bracket target data; an even run leaves the bracket available as structural syntax after the escaped backslashes are decoded appropriately.
- Backslashes before non-bracket characters remain target content.
- After the structural target-closing bracket, either the second ~]~ closes a target-only link or ~[~ begins a description.
- A described link has a non-empty description in this reference regexp. Add ~[[target][]]~ to the GNU Org golden cases and reject it in the project scanner unless the recorded reference for the supported Org version proves otherwise.
- The description is non-greedy and ends at the first grammar-valid ~]]~.
- A single ~]~, ordinary ~[... ]~ text, timestamp-looking text, and nested-link-looking text before that first ~]]~ are description text; they do not create nested links or timestamps.

The description fragment ~[^z-a]+?~ is an Emacs-regexp idiom that avoids relying on dot matching and can cover newline content. Do not infer the project's multi-line policy from visual inspection alone: verify it with the Emacs golden command. The current ~orgfdb~ contract deliberately remains line-bounded, and that accepted divergence must be recorded explicitly beside the golden result rather than hidden.

Use the other expressions as regression references, not as replacements for current scanner ownership:

- ~org-link-plain-re~ defines useful boundaries for whitespace, punctuation, and balanced ~()~, ~[]~, and ~<>~ groups. Cross-check its cases against the existing project-owned plain-link tests. Do not replace the current configurable ~plain_link_protocols~ with the protocols shown in this runtime snapshot.
- ~org-link-angle-re~ confirms that GNU Org allows spaces and certain continued lines inside angle links. Keep the current project angle-link contract unchanged in this task, but record same-line matches and deliberate multi-line differences.
- ~org-link-types-re~ is evidence for protocol-prefix recognition in the captured Org runtime, not the universal ~orgfdb~ protocol list. Bracket and angle links must continue to support the repository's existing explicit-type rules, and plain links must continue to use configuration.
- ~org-link-any-re~ is useful only as an umbrella cross-check that the specific bracket, angle, and plain expectations compose correctly. Do not port it into production or use it to calculate source-editing ranges.

*** Chosen normalized representation

Extend ~ParsedLink~ in ~src/parser/model.rs~ with parser-level logical and range fields while retaining all current fields:

#+begin_src rust

Field semantics:

- ~raw~ is the exact complete authored link source.
- ~raw_target~ is the exact authored target substring, including Org escaping.
- ~logical_target~ is the decoded target used for classification and resolution.
- ~raw_description~ is the exact authored description without outer delimiters. It is source data, not a recursively parsed container: it must not create additional persisted links or timestamps.
- The heading-title renderer derives display text from ~raw_description~ through one dedicated link-description renderer. That renderer preserves square brackets and timestamp-looking text literally while retaining the project's existing supported title-markup behavior.
- ~byte_start..byte_end~ is the complete end-exclusive UTF-8 byte range.
- ~target_byte_start..target_byte_end~ excludes bracket or angle delimiters and slices to ~raw_target~.
- ~description_byte_start..description_byte_end~, when present, excludes ~][~ and the final ~]]~ and slices to ~raw_description~.
- All ranges are absolute offsets into the original source.
- For plain links, the target range equals the complete range.
- For angle links, the target range excludes ~<~ and ~>~.
- For bracket links, the target range excludes ~[[~, ~][~, and ~]]~.

Add one shared display helper next to title rendering:

#+begin_src rust

               if a description is present,
               otherwise logical_target
#+end_src

~normalize_link_description_for_title~ has this exact contract:

- It returns display text only; it never adds parser objects to ~ParsedOrgDocument~.
- Timestamp-looking text such as ~[2026-03-21 Sa]~ remains visible text.
- Bracket text such as ~[BJJML]~ remains visible text.
- Nested-link-looking text remains literal and does not become another link.
- Markup already supported by normal heading-title rendering keeps the same visible behavior. For example, supported emphasis delimiters are not newly exposed merely because the outer link required scanner recovery.
- The implementation must guard the synthetic parse with prefix and suffix sentinels so a leading TODO-like word or a trailing tag-like string in the description is not reclassified as headline metadata.
- In the dedicated description-normalization mode, any nested ~LINK~ node is emitted as its exact source text rather than rendered recursively. Timestamp nodes are emitted as their exact source text.

Do not add a persisted ~visible_description~ field. Display text is a rendering concern, while ~raw_description~ remains the exact parser fact.

Continue scanning the original source with ~scan_links~ and Orgize-derived ignored ranges.

Do not add a second native-link collector. This avoids:

- duplicate links
- divergence between plain, angle, and bracket handling
- dependence on changing Orgize node behavior
- contradiction with the accepted Phase 3 scanner contract

When a future Orgize version parses the reported forms correctly, normalized ~orgfdb~ behavior remains unchanged because project extraction does not depend on that native node.

*** Scanner boundary policy

The state-machine implementation must be derived from the accepted project contract and cross-checked against the captured GNU ~org-link-bracket-re~ semantics. Do not use the GNU regexp directly for production matching or range calculation.

Keep the current line-bounded project contract:

- A bracket-link candidate begins at ~[[~.
- Its complete closing delimiter must occur before the next newline.
- A malformed candidate does not consume the line or suppress later links.
- Failure advances by one valid UTF-8 character from the original opening position.
- Plain and angle scanning continue after malformed bracket input.

This deliberately preserves the current documented difference from GNU Emacs, which may accept some multi-line links.

** Detailed implementation

*** 1. Refactor bracket parsing into an explicit state machine

Replace ~parse_bracket_inner~ with a byte-oriented parser that returns ranges relative to the complete source and never calculates source offsets from Unicode character counts.

The parser states are conceptually:

#+begin_example
Opening
Target
TargetEscapeRun
TargetDelimiter
Description
Complete
Malformed
#+end_example

The implementation does not need a public enum if a small explicit loop is clearer, but the code must make target and description rules separate.

Target scanning rules:

- Reject an empty target.
- An unescaped ~[~ inside the target is invalid.
- A ~]~ preceded by an odd number of consecutive backslashes is target data, not a delimiter.
- A ~]~ preceded by an even number of consecutive backslashes is structural.
- Structural ~]]~ closes a target-only bracket link.
- Structural ~][~ begins a description.
- Structural ~]~ followed by any other byte makes this candidate malformed.
- Backslashes before ordinary non-bracket characters remain ordinary target characters.
- Newline or end-of-region before a complete closing delimiter makes the candidate malformed.

Description scanning rules:

- Do not use target escape rules in the description.
- Permit ordinary ~[~ and single ~]~ characters.
- The first same-line ~]]~ closes the described link.
- Do not recursively balance brackets.
- Do not create nested link objects from nested-link-looking text.
- Preserve any text after the first recognized complete link as trailing source.
- Newline or end-of-region before ~]]~ makes the candidate malformed.

The state machine must return:

- complete end offset
- raw target range
- optional raw description range

Construct strings only after ranges are validated.
