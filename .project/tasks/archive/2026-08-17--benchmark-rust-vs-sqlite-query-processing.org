Measure the query execution phases before moving more result work from SQLite to Rust.

Round 2 improved the SQLite query path and removed large ID round trips for query-derived relations.

The remaining query cost is not fully attributed between SQLite execution, row decoding, Rust processing, and final result shaping.

The current SQLite profiler is useful for SQL stages, but it does not give precise wall-clock attribution for the complete Rust and SQLite path.

The ~headings.path~ workload is the main candidate for further investigation. At 50'000 results, ~enrich-path-headings~ is the most expensive recorded SQL stage.

*** Goals

- Measure the main query execution and result-shaping phases with direct wall-clock timings.
- Separate SQLite execution cost from Rust-side processing cost.
- Measure the cost of row decoding, grouping, sorting, validation, path construction, and final shaping.
- Determine whether selected work can move from SQLite to Rust without increasing data transfer significantly.
- Compare the current recursive ancestor loader with a Rust-driven ancestor loading strategy.
- Identify optimizations that have measurable value before changing the architecture.

- Do not change normal ~--format json~ output.

- Do not move ~effective_tags~ or ~effective_properties~ inheritance calculation to Rust.

*** Path experiment

Compare the current recursive query-derived ancestor loader with an alternative Rust-driven loader.

Current strategy:

1. Keep the matched heading relation in SQLite.
2. Use recursive SQL to load only required missing ancestors.
3. Build the final heading path in Rust.

Alternative strategy:

1. Load matched headings and their stored outline evidence.
2. Collect required ancestor IDs in Rust.
3. Load missing ancestor heading rows with one or more bounded bulk queries.
4. Build and validate the final heading path in Rust.

The alternative must preserve all current corruption errors.

It must not reload all headings from every matched file.

Keep the existing runtime-limit-safe ID loader for IDs that originate in Rust.

*** Evaluation

For each experiment, record:

- total wall-clock time
- SQLite execution time where directly measurable
- row decoding time
- Rust processing time by phase
- SQL statement count
- rows transferred from SQLite to Rust
- bound parameter count where relevant
- result count

Prefer an optimization only when the benchmark shows a clear improvement.

Reject an optimization that reduces SQLite work but transfers substantially more unused data to Rust.

*** Decision criteria

Keep work in SQLite when it depends on:

- indexed filtering
- relational matching
- joins
- ~EXISTS~ predicates
- ~effective_tags~
- ~effective_properties~
- reusable matched relations

Prefer Rust when the required rows are already loaded and the work consists mainly of:

- grouping
- local sorting
- deduplication
- validation
- path construction
- final result shaping

For heading paths, choose the Rust-driven ancestor loader only if it improves measured end-to-end latency without weakening corruption detection.
