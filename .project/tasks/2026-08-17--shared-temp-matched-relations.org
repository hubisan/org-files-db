* Planning

** Problem summary

Production enrichment currently wraps the exact compiled matched-heading query again for each relation-backed loader.

The existing v9 benchmark shows opposite outcomes for simple and complex matched relations.

Simple relations remain faster when SQLite repeats them, while the complex tag-plus-property relation is substantially faster when materialized once and reused.

The current relation-reuse benchmark still hard-codes an older SQL relation instead of compiling the workload through the current predicate-driven production compiler.

** Goals

- Refresh relation reuse through the current production compiler.
- Keep cheap compiled heading relations query-derived.
- Materialize expensive compiled heading relations once per complete public query.
- Reuse the materialized relation for base heading tag loading and direct-flat enrichment.
- Keep TEMP data local to the connection and current query.
- Clean TEMP state after success and every error path.
- Add complete production A/B coverage with exact result equality.
- Preserve public syntax, results, ordering, validation, and errors.

** Non-goals

- Do not materialize every query.
- Do not choose TEMP from result count or database size.
- Do not add runtime timing calibration.
- Do not add persistent schema objects.
- Do not change link or file relation execution in this task.

** Architecture

Classify the validated heading predicate tree into a small internal relation-reuse cost.

Treat predicate-driven metadata relations as repeated relational work. The supplied evidence covers the tag-plus-property shape, so the initial production selector requires at least two such relations.

Hierarchy, link, timestamp, body-text, and outline subqueries remain query-derived until refreshed benchmark evidence justifies adding them as expensive signals.

Select TEMP when the measured static rule classifies the relation as expensive.

A cheap relation stays query-derived regardless of result count or several enrichment consumers.

An expensive relation may select TEMP with the base effective-tag loader as its only downstream consumer.

When selected, create one TEMP table from the exact compiled heading relation, then expose a parameter-free compiled relation that reads the same columns from that TEMP table.

The initial heading row read, effective-tag load, outline validation, and relation-backed metadata loaders can then reuse that same relation without recompiling public query semantics.

Drop the TEMP table before returning from the complete query path.

** Supplied schema version 10 benchmark

The user ran the required release benchmark with ~100~, ~1'000~, ~10'000~, and ~50'000~ target results.

The refreshed isolated benchmark shows that the current compiler changed the old schema version ~9~ pattern.

- Simple single-loader TEMP loses at every measured size.
- Simple multi-loader TEMP wins only at ~100~ and loses from ~1'000~ upward.
- Complex single-loader TEMP loses at every measured size.
- Complex multi-loader TEMP wins at every measured size and is about ~27.0%~ faster at ~50'000~.

This confirms that isolated consumer count is not a sufficient selector.

The complete production A/B supports the implemented static rule:

| Target results | Expensive single: derived | Expensive single: selective TEMP | Change | Expensive multi: derived | Expensive multi: selective TEMP | Change |
|----------------+---------------------------+----------------------------------+--------+--------------------------+---------------------------------+--------|
| 100 | 0.945 ms | 0.436 ms | -53.9% | 1.153 ms | 0.530 ms | -54.0% |
| 1'000 | 2.411 ms | 1.981 ms | -17.8% | 3.581 ms | 2.895 ms | -19.2% |
| 10'000 | 27.407 ms | 23.793 ms | -13.2% | 40.275 ms | 35.826 ms | -11.0% |
| 50'000 | 157.770 ms | 133.787 ms | -15.2% | 230.889 ms | 200.708 ms | -13.1% |

Every expensive workload selects TEMP and improves complete query latency.

Every cheap workload remains query-derived.

At ~100~ and ~1'000~ target results, cheap selective-versus-disabled medians differ by at most ~0.9%~.

The ~50'000~ cheap-single pair differs by ~3.1%~, but both benchmark records report ~temp_selected=false~ and therefore do not attribute that difference to TEMP execution.

The ~50'000~ expensive single TEMP materialization costs about ~33.8 ms~ and still reduces complete latency by about ~24.0 ms~.

The ~50'000~ expensive multi TEMP materialization costs about ~34.0 ms~ and reduces complete latency by about ~30.2 ms~.

The current rule therefore remains unchanged: at least two predicate-driven metadata relations classify the matched heading relation as expensive.
