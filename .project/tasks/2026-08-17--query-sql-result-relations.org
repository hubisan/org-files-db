* Planning

** Problem summary

Round 1 reduced the ~50'000~-result query baseline substantially.

Large matched ID sets still cross the SQLite and Rust boundary several times.

The round 1 benchmark also shows that query-derived joins beat large dynamic ~IN (...)~ lookups at every measured size.

The full enrichment path still reloads matched heading data for path output.

** Goals

- Keep matched result relations inside SQLite when this reduces measured work.
- Remove the large-ID round trip from heading tag loading.
- Remove separate large-ID outline validation from the production direct-flat path.
- Use query-derived relations for direct properties, effective properties, keywords, and root tags.
- Reuse matched heading rows during path enrichment instead of reloading them.
- Load only required ancestor headings for heading path output.
- Keep ~runtime-limit-in~ as the safe fallback for IDs that originate in Rust.
- Extend the SQL benchmark for relation reuse, complex matches, ~json_each~, and query plans.
- Preserve every public query result and stored-data error contract.

** Non-goals

- Do not change the public query language.
- Do not change normal ~--format json~ output.
- Do not change ~presentation-json~.
- Do not add a persistent materialized table without benchmark evidence.
- Do not add presentation caching or parallel execution.
- Do not change dependencies.

** Architecture

Add an internal execution result that carries the compiled matched SQL relation with the normal query rows.

The public row-only execution functions keep their existing API and discard the internal relation metadata.

The production execute-and-shape path passes the matched relation to result shaping.

Direct-flat metadata loaders join against the compiled matched relation instead of sending matched IDs back through large ~IN (...)~ clauses.

Heading tag loading uses the same compiled heading relation.

The direct-flat path validates ~outline_path~ through the matched relation and keeps the current corruption errors.

The flat heading path reuses the matched query relation instead of loading all headings from matched files.

A recursive query-derived ancestor loader fetches only missing ancestors required to construct paths.

Fallback shaping from caller-supplied ~QueryRows~ keeps the existing ID-based loaders.

** Risks & assumptions

- Re-evaluating a complex matched query for several enrichments can cost more than one shared temporary relation.
- Query-derived joins must use the exact compiled predicate and file restriction semantics.
- Root-file matches need a separate relation from real heading matches.
- Path construction must not lose corruption detection for missing or invalid ~outline_path~ rows.
- Large link includes can introduce different relation shapes and remain on safe fallbacks without benchmark evidence.
- The benchmark decides whether shared temporary relations belong in production after this implementation.

** Open questions

- Does one shared temporary matched relation beat repeated query-derived joins for workloads with several includes?
- Does ~json_each~ beat runtime-limit ~IN (...)~ enough for IDs that truly originate in Rust?
- Are any new indexes justified after the query-plan audit?
