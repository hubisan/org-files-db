* CANCEL Feature - ignore single file

Reason for cancelling:

The existing configuration already supports excluding individual files,
directories and path patterns from the indexed source universe. This
covers the current need without introducing a second exclusion mechanism
inside Org files.

A file-level ~#+orgfdb: ignore~ keyword would mainly provide a portable
exclusion that follows the file when it is moved. There is currently no
concrete use case that justifies the additional discovery,
reconciliation and watcher semantics.

Allow an Org file to declare that it must not be included in the
~org-files-db~ index.

Possible syntax:

#+begin_src org
  ,#+TITLE: Private Note
  ,#+ORGFDB: ignore
#+end_src

The keyword would mean that the file is outside the indexed source
universe, even if its path is otherwise included by the configured files
or directories.

Expected semantics would be:

- detect ~#+orgfdb: ignore~ at file level;
- do not store the file or any of its headings, properties, keywords or
  links in the database;
- if an already indexed file gains ~#+orgfdb: ignore~, remove it during
  the next rebuild or reconciliation;
- if the keyword is removed, make the file eligible for indexing again;
- treat links to an ignored file the same way as links to another file
  outside the indexed source universe;
- make watcher/reconciliation behaviour consistent when the keyword is
  added or removed;
- use only the exact ~ignore~ value initially; do not introduce boolean
  aliases or additional ~orgfdb~ options without a separate use case.

Prefer a file-level keyword over a property such as ~VULPEA_IGNORE~,
because ignoring the file is source/indexing metadata rather than heading
metadata.

* TODO Decide whether eager Rust-side presentation view caching is justified
:PROPERTIES:
:VISIBILITY: folded
:END:

Start this task after payload and parallelism decisions are complete.

Use the final optimized presentation pipeline as the baseline.

Goal: decide whether explicit persistent presentation views justify a Rust-side cache.

Do not implement the production cache in this task.

Evaluate this specific cache model:

- The database has a small set of explicitly registered presentation views.
- Each view defines its query and presentation specification.
- The cache stores the complete materialized presentation output for one database generation.
- The cache is persistent across separate ~orgfdb~ CLI processes.
- A database change makes every registered view cache stale.
- The watcher starts a full rebuild of stale view caches after the database update completes.
- Do not wait for a query to start a rebuild.
- Do not patch cached views from individual changed files.
- Do not reuse a cached view across database generations.
- Do not serve a stale view while a rebuild is in progress.
- If a query requests a rebuilding view, wait until a cache for the current generation is ready.
- If the database changes again during a rebuild, make sure that the final cache matches the newest generation.
- Consecutive changes can skip obsolete intermediate cache generations.
- After restart or recovery, rebuild stale registered views without requiring a query to trigger the rebuild.

Keep the design intentionally simple.

Do not add:

- automatic caching of arbitrary queries
- incremental per-file cache updates
- LRU caching of arbitrary presentation requests
- cross-generation result reuse
- dependency tracking between files and cached results

Use ~database_id~ and ~generation~ to establish cache validity.

A valid cached view must belong to:

- the current database
- the current database generation
- the current registered view definition
- the current presentation wire format

Determine whether an additional producer or cache format version is necessary.

Keep the existing meanings of:

- ~database_id~
- ~generation~
- ~changes~

Do not change ~changes~ into a view-cache invalidation protocol.

Use existing benchmark results for costs that are already measured.

These include:

- database query cost
- presentation CPU cost
- process startup cost
- JSON serialization cost
- payload size
- full CLI elapsed time

Add only the measurements that are necessary to evaluate the registered-view cache.

Measure representative large presentation views.

Compare at least:

- the normal uncached presentation request
- the cost to rebuild and persist a complete view cache
- the cost of a valid cache hit
- the cost to read the cached payload and send it through the normal CLI output path
- the extra write cost that each database change adds
- the wait time for a query that arrives during a rebuild

Test rapid consecutive database changes.

Determine whether obsolete rebuild generations can be skipped without serving stale data.

Use realistic Emacs usage patterns.

Evaluate at least these cases:

- many reads of the same view between database changes
- a database change followed by an immediate view request
- several database changes before the next view request
- several registered views that all require a rebuild after a database change

Separate measured execution costs from estimated transfer costs.

Record cache file sizes for representative result sets.

Estimate the storage and write amplification for a realistic number of registered views.

The main decision question is:

Does eager full rebuilding move enough repeated presentation work out of the query path to justify its persistent storage, rebuild cost, synchronization, and lifecycle complexity?

A cache hit alone is not sufficient evidence.

The rebuild cost after each database change must also be acceptable.

Consider these final outcomes:

- no Rust-side presentation cache
- an eager persistent cache for explicitly registered presentation views

Do not broaden the task to other cache architectures unless the measurements show that this model cannot answer the performance problem.

If the cache is not justified, record the decision and close this task.

If the cache is justified, create separate focused implementation TODOs.

Do not implement those TODOs as part of this decision task.

Acceptance criteria:

- Benchmark evidence supports the final cache decision.
- Measurements use the final optimized presentation pipeline.
- Existing benchmark data is reused where it already answers the question.
- The cache candidate uses explicitly registered presentation views.
- A database change causes an eager full rebuild of stale registered views.
- A query never starts a cache rebuild.
- A query never receives a stale cached view.
- A query waits if the current view cache is still rebuilding.
- Rapid database changes do not require publication of obsolete intermediate generations.
- The decision includes cache-hit, rebuild, persistence, and query-wait costs.
- The decision records representative cache file sizes.
- The decision evaluates several registered views and realistic change frequency.
- Existing ~database_id~, ~generation~, and ~changes~ semantics keep their current meanings.
- The design does not require incremental per-file cache maintenance.
- A no-cache decision requires no further implementation task.
- A cache decision creates separate focused implementation TODOs.
- Performance documentation records the final decision and benchmark evidence.
