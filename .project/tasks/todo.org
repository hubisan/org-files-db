** TODO Compute inherited tags for `all_tags_json`

Goal:
Make `all_tags_json` match its documented schema semantics.

Context:
The schema documents `all_tags_json` as all tags visible on a heading, including inherited tags. Current output only contains local heading tags.

Example:

#+begin_src org
  ,* TODO me :test:
  ,** again :me:
#+end_src

Current output for `again`:

#+begin_src json
{
  "title": "again",
  "all_tags_json": "[\"me\"]"
}
#+end_src

Expected output:

#+begin_src json
{
  "title": "again",
  "all_tags_json": "[\"test\", \"me\"]"
}
#+end_src

Required behavior:

- Keep normalized local tag rows in the `tags` table.
- Compute `all_tags_json` as the visible/effective tag set for each heading.
- Include inherited tags from ancestor headings.
- Include local tags from the heading itself.
- Avoid duplicate tags in `all_tags_json`.
- Preserve a stable deterministic order:
  - ancestor tags from outermost to innermost
  - then local tags
  - or document and test another deterministic order
- Do not change the DB schema unless unavoidable.
- Do not change parser-specific public types unless needed.
- Do not implement inherited properties in this task.

Acceptance criteria:

- A child heading inherits parent tags in `all_tags_json`.
- A heading with both inherited and local tags includes both.
- Duplicate tags are not repeated.
- Local tag rows in `tags` still represent local heading tags only.
- Existing tag tests still pass.
- Add focused parser/indexer/query tests for inherited tag behavior.

** TODO Normalize resolved config paths syntactically

Goal:
Avoid storing syntactically noisy but equivalent paths such as `/path/./file.org`.

Context:
Config paths are resolved before they are used by discovery, indexing, DB writes, and CLI output. Config-relative paths are resolved by joining the config file directory with the configured path. For entries such as `./test.org`, this can currently produce paths like:

#+begin_src json
{
  "file_path": "/path/to/project/.project/local/./test.org"
}
#+end_src

This is functionally equivalent, but noisy and undesirable for stored file identity, JSON output, tests, and future deduplication.

Required behavior:

- Normalize resolved config paths syntactically after config path resolution.
- Remove syntactic `.` path components from resolved paths.
- Apply this to:
  - `db_path`
  - entries in `files`
  - entries in `dirs`
- Keep config-relative paths resolving relative to the config file location.
- Keep absolute paths working unchanged, except for removing syntactic `.` components.
- Keep existing leading `~` expansion behavior unchanged.
- Do not canonicalize paths through the filesystem.
- Do not resolve symlinks.
- Do not require `db_path` to exist.
- For `files` and `dirs`, continue validating existence as before.
- Do not change parser, DB schema, indexer behavior, or CLI JSON field names.
- Do not implement broad path cleanup beyond syntactic `.` normalization unless needed by the existing path APIs.

Acceptance criteria:

- `files = ["./test.org"]` resolves to `/path/to/config-dir/test.org`, not `/path/to/config-dir/./test.org`.
- `dirs = ["./notes"]` resolves to `/path/to/config-dir/notes`, not `/path/to/config-dir/./notes`.
- `db_path = "./org-files-db.sqlite"` resolves to `/path/to/config-dir/org-files-db.sqlite`, not `/path/to/config-dir/./org-files-db.sqlite`.
- Absolute paths containing syntactic `.` components are normalized without resolving symlinks.
- Existing absolute path behavior still works.
- Existing config-relative path behavior still works.
- Existing `~` expansion behavior still works.
- Validation behavior for missing files and missing directories remains unchanged.
- Tests cover config-relative paths with leading `./` for `db_path`, `files`, and `dirs`.
- Tests cover that existing `~` expansion still works together with syntactic path normalization.
