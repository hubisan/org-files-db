* Project goal

~org-files-db~ is a Rust backend library with an optional CLI. It reads Org-mode files, extracts relevant Org structures, and writes them to a SQLite database.

The goal is a robust, fast, and later extensible indexing pipeline for Org files:

- parse Org files
- extract headings, TODO states, priorities, tags, properties, planning data, and links
- store the data in a normalized SQLite database
- provide fast search and JSON output through a ~clap~ CLI
- later map an org-ql-like query language to SQLite/FTS5

~orgize~ is initially used as the parser backend, but it must not be treated as a permanently safe or single source of parsing truth. Therefore, the project must use its own stable parser abstraction and its own internal data model.

Orgize-specific types must not leak into the DB, query, indexer, or CLI layers.

Principle:

#+begin_src text
Orgize / Parser Backend
  -> own ParsedOrgDocument / ParsedHeading model
  -> normalization / diagnostics
  -> SQLite import
  -> query / CLI / JSON API
#+end_src

This keeps the following options open later:

- continue using Orgize if it is stable enough for our purposes
- work around known Orgize bugs locally
- report parser bugs upstream with reproducible fixtures
- switch to a fork, Tree-sitter, a custom parser, or an Emacs-based import if needed

Non-goals for the beginning:

- no complete custom Org-mode parser in the MVP
- no full org-ql compatibility in the MVP
- no direct dependency from the DB layer on Orgize or rowan
- no optimization for maximum performance before the pipeline is correct

* Architecture decisions

** Decision: use Orgize only as an adapter

~orgize~ is used as the first parser backend, but only inside a clearly bounded adapter module.

Allowed:

#+begin_src text
src/parser/orgize_adapter.rs
#+end_src

Not allowed:

- Orgize types in ~db/~
- Orgize types in ~query/~
- Orgize types in ~cli/~
- direct DB inserts from Orgize AST nodes
- direct dependency on ~syntax()~ / rowan outside the adapter

** Decision: own internal parser model

The internal project API is based on our own types:

#+begin_src rust
pub trait OrgParser {
    fn parse_document(
        &self,
        path: &Path,
        content: &str,
    ) -> Result<ParsedOrgDocument>;
}

pub struct ParsedOrgDocument {
    pub file_path: PathBuf,
    pub headings: Vec<ParsedHeading>,
    pub diagnostics: Vec<ParseDiagnostic>,
}

pub struct ParsedHeading {
    pub level: u8,
    pub title: String,
    pub todo_keyword: Option<String>,
    pub priority: Option<char>,
    pub tags: Vec<String>,
    pub properties: Vec<(String, String)>,
    pub planning: ParsedPlanning,
    pub line_number: Option<u32>,
    pub byte_start: usize,
    pub byte_end: usize,
    pub parent_index: Option<usize>,
}
#+end_src

** Decision: parser problems must be visible

Known or suspected parser problems must not be silently ignored.

Instead:

- record a `ParseDiagnostic`
- add a fixture test
- document the behavior
- if useful, prepare an upstream issue for Orgize
- perform DB inserts only with normalized data
