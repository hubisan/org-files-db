* Phase 5: Query engine and optional full-text search

Goal of this phase:

- Build a small, safe query layer for indexed Org graph data.
- Implement the Query Model v0 contract defined in [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]].
- Keep the query model independent from CLI and SQL.
- Support headings, links, and files as explicit query targets.
- Keep full-text search optional and separate from the core query model.
- Return stable JSON that is useful for Emacs/editor integrations.

General rules:

- Query AST/model is independent of CLI and SQL.
- SQL generation must use bound parameters.
- Query execution uses the persisted database, not parser re-analysis.
- Query target is explicit through ~(headings ...)~, ~(links ...)~, and ~(files ...)~.
- Bare predicates are shorthand for heading queries only at the top level.
- Nested relation queries must use explicit target wrappers.
- Query output mode must not change match semantics.
- Include options may enrich results but must not change which objects match.
- Direct parsed facts and effective/derived semantics must stay clearly separated.
- Query results must include enough location data for editor jumps.
- Body text search must fail clearly when body text is unavailable.
- FTS5 is optional and must only be required for FTS-specific functionality.
- Mutation and repair operations are out of scope for Query Model v0.

** TODO Improve hierarchy predicate documentation with direct and transitive examples

Goal:

- Keep the existing predicate names:
  - ~parent~
  - ~children~
  - ~ancestors~
  - ~descendants~
- Improve the documentation so the difference between direct and transitive hierarchy relations is immediately clear.
- Add concise examples without relying on wide Org tables.

Scope:

- Documentation only.
- Do not rename predicates.
- Do not change parser, validator, compiler, storage, or query semantics.
- Do not add aliases.

Required terminology:

- ~parent~ means exactly one level upward.
- ~children~ means exactly one level downward.
- ~ancestors~ means one or more levels upward.
- ~descendants~ means one or more levels downward.
- The direct parent is included among ancestors.
- Direct children are included among descendants.
- The candidate heading itself is never included.
- The synthetic file/root heading participates according to the hierarchy model.

Synthetic root semantics:

- A top-level Org heading has the synthetic file/root heading as its parent.
- The synthetic file/root heading has top-level Org headings as children.
- The synthetic file/root heading is an ancestor of every real heading in the file.
- Every real heading is a descendant of the synthetic file/root heading.
- The synthetic file/root heading has no parent and no ancestors.

- Use short paragraphs and examples instead of a wide comparison table.
- Keep wording aligned between both documents.
- Explain each predicate separately.

Recommended concise descriptions:

- ~parent~ ::
  Matches headings whose direct parent satisfies the nested ~headings~ query. Exactly one level upward is checked.

- ~children~ ::
  Matches headings with at least one direct child satisfying the nested ~headings~ query. Exactly one level downward is checked.

- ~ancestors~ ::
  Matches headings with at least one strict ancestor satisfying the nested ~headings~ query. One or more levels upward are checked, including the direct parent.

- ~descendants~ ::
  Matches headings with at least one strict descendant satisfying the nested ~headings~ query. One or more levels downward are checked, including direct children.
#+end_src
