* Phase 4: Link resolution

Goal of this phase: Resolve stored raw link source facts to known files, file-scoped CUSTOM_ID targets, and indexed Org ID targets.

General rules:

- Resolution never destroys raw link facts.
- Resolution fields stay clearly separated from raw source fields.
- Broken, ambiguous, unresolved, and unsupported targets are represented explicitly.
- Target deletion must not delete source link rows.
- Resolution must not execute link targets.
- Resolution must be deterministic and repeatable.
- Resolution runs after all files, headings, properties, outline paths, and raw links for the rebuild are stored.
- Do not resolve links on demand in read-only CLI commands.
- Do not introduce parallel ~resolved_file_id~ / ~resolved_heading_id~ columns unless the schema contract is deliberately renamed first.

Existing target-ish fields:

- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~

Recommended resolution state fields:

- ~resolution_status~
- ~resolution_diagnostic~

Recommended ~resolution_status~ values:

- ~unresolved~
- ~resolved~
- ~broken~
- ~ambiguous~
- ~unsupported~

Status semantics:

- is ~NULL~ means not attempted
- ~unresolved~ means resolution was attempted but the available universe is not known to be complete.
- ~broken~ means the target is missing inside a known complete context.
- ~ambiguous~ means more than one valid target exists in the applicable context.
- ~unsupported~ means the link form is intentionally not resolved yet.
- ~resolved~ means target fields point to the selected target.

Important distinction:

- ~CUSTOM_ID~ resolution is file-scoped.
- ~id:~ resolution is global in Org semantics and should not be marked broken merely because the ID is absent from the indexed files.
- A missing ~CUSTOM_ID~ can be broken when the target file context is known.
- A missing ~id:~ should be ~unresolved~ unless a complete Org ID location universe is available.

Goal:

- Trim leading and trailing whitespace around star heading-title search targets.
- Compare star heading-title targets case-insensitively.
- Apply the same matching semantics to file star search options and same-file fuzzy star links.
- Preserve raw link source fields.

Scope:

  - ~[[file:target.org::*Heading]]~
  - ~[[file:target.org::*   Heading   ]]~
  - ~<file:target.org::*Heading>~
  - plain ~file:target.org::*Heading~ when extracted by configured plain-link protocols
- Same-file fuzzy star heading links:
  - ~[[*Heading]]~

Observed behavior to support:

- Org trims surrounding whitespace in star heading-title search targets.
- Org matches star heading-title search targets case-insensitively.
- Example:
  - stored heading title: ~Peer heading~
  - link target: ~*   Peer heading   ~
  - result: resolved
- Example:
  - stored heading title: ~Main index~
  - link target: ~*Main Index~
  - result: resolved
- Example:
  - stored heading title: ~Target heading~
  - link target: ~*   Target heading~
  - result: resolved

Star heading-title normalization rules:

- Apply only to star heading-title targets.
- Strip exactly one leading ~*~.
- Trim leading and trailing whitespace from the remaining heading-title target.
- Preserve existing Org link escape handling.
- Existing bracket escape behavior must continue to work:

- Do not mutate stored ~search_option~, ~path~, ~raw_target~, ~raw~, or ~raw_description~.

Star heading-title comparison rules:

- Compare normalized star heading-title targets case-insensitively.
- Search only in the active target scope:
  - resolved target file for ~file:...::*Heading~
  - source file for ~[[*Heading]]~
- Exclude synthetic root headings.
- Preserve deterministic duplicate behavior:
  - if multiple headings match case-insensitively, select the first heading in document order
  - document order must be deterministic, for example ~byte_start~, then ~id~
- Successful matches use:
  - ~resolution_status = resolved~
  - ~resolution_diagnostic = NULL~

Out of scope:

- Do not change CUSTOM_ID or ID matching in this task unless the existing implementation already shares the star-heading matcher and would otherwise break.
- Do not make ~CUSTOM_ID~ or ~ID~ case-insensitive without an explicit Org-behavior test.
- Do not trim ~CUSTOM_ID~ or ~ID~ property values unless an explicit Org-behavior test proves this is required.
- Do not implement new CUSTOM_ID or ID resolution features.
- Do not implement attachment resolution.
- Do not implement regexp, line-number, dedicated-target, or non-star fuzzy resolution.
- Do not change parser extraction.
- Do not change the DB schema.

Implementation notes:

- Use the helper for:
  - file heading-title search options
  - same-file fuzzy star heading links
- Keep raw DB fields unchanged.
- Avoid relying on unspecified SQL row order.
- Either:
  - query candidate headings in scope ordered by ~byte_start~, ~id~ and compare normalized/case-insensitively in Rust
  - or use deterministic SQL case-insensitive comparison with explicit ~ORDER BY byte_start, id~
- Keep existing bracket escape support as a regression case.

Goal:

- Resolve Org links that target ~CUSTOM_ID~ and ~ID~ properties.
- Resolve bracket same-file ~CUSTOM_ID~ links.
- Resolve file-context ~CUSTOM_ID~ search options.
- Resolve ~ID~ links within the indexed ID universe.
- Match ~CUSTOM_ID~ and ~ID~ lookup values using Org-compatible normalization:
  - trim leading and trailing whitespace
  - compare case-insensitively
- Whenever a target resolves to a heading, set both ~target_file_id~ and ~target_heading_id~.
- Preserve raw link source fields.

Scope:

- Same-file ~CUSTOM_ID~ links:
  - ~[[#foo]]~
  - ~[[#foo][Description]]~
- File-context ~CUSTOM_ID~ links:
  - ~[[file:other.org::#foo]]~
  - ~[[file:other.org::#foo][Description]]~
  - ~[[./other.org::#foo]]~
  - ~[[../other.org::#foo]]~
  - ~<file:other.org::#foo>~
  - plain ~file:other.org::#foo~ when extracted by configured plain-link protocols
- Org ID links:
  - ~id:foo~
  - ~[[id:foo]]~
  - ~[[id:foo][Description]]~
  - ~<id:foo>~
  - plain ~id:foo~ when extracted by configured plain-link protocols

Important parser model:

- Same-file ~[[#foo]]~ may be classified as ~link_type = fuzzy~.
- It is still a ~CUSTOM_ID~ target when:
  - ~link_type = fuzzy~
  - ~path~ starts with exactly one leading ~#~
- This is analogous to same-file star heading links:
  - ~[[*foo]]~ resolves by heading title in the source file.
  - ~[[#foo]]~ resolves by ~CUSTOM_ID~ in the source file.
- File-context ~CUSTOM_ID~ links are file links with:
  - ~link_type = file~
  - ~search_option~ beginning with exactly one leading ~#~
- Bare angle or plain ~#foo~ is not a supported CUSTOM_ID link form.
- Angle and plain CUSTOM_ID links require an explicit ~file:...::#foo~ form.

Shared lookup rules:

- Match against indexed heading properties:
  - ~properties.key~
  - ~properties.value~
- Match property keys exactly:
  - ~CUSTOM_ID~
  - ~ID~
- Normalize property target values before lookup.
- Compare property values case-insensitively.
- Do not fuzzy-match property values.
- Do not normalize internal whitespace.
- Exclude synthetic root headings from property-target lookup.
- Do not rely on unspecified SQL row order.
- Define document order using stored heading order, such as ~byte_start~ or the existing heading-order field.
- Raw link source fields must remain unchanged.

Property target normalization:

- Apply only to ~CUSTOM_ID~ and ~ID~ lookup values.
- For ~CUSTOM_ID~:
  - remove exactly one leading ~#~
  - trim leading and trailing whitespace from the remaining value
  - use the normalized value for property lookup
  - store the normalized value in ~target_custom_id~
  - compare case-insensitively against stored ~CUSTOM_ID~ property values
- For ~ID~:
  - use the parsed ID target value from the existing link fields
  - trim leading and trailing whitespace from the value
  - use the normalized value for property lookup
  - store the normalized value in ~target_id~
  - compare case-insensitively against stored ~ID~ property values
- Do not lowercase the stored raw link fields.
- Do not mutate:
  - ~raw~
  - ~raw_target~
  - ~raw_description~
  - ~path~
  - ~search_option~
- Do not normalize internal whitespace:
  - ~" Foo Bar "~ becomes ~"Foo Bar"~
  - ~"Foo  Bar"~ remains ~"Foo  Bar"~

Duplicate target policy:

- Duplicate ~CUSTOM_ID~ targets follow observed Org behavior.
- If multiple matching ~CUSTOM_ID~ properties exist in the active search scope:
  - select the first matching heading in document order
  - set ~target_file_id~ to the matched heading's file
  - set ~target_heading_id~ to the first matching heading
  - set ~resolution_status = resolved~
  - set ~resolution_diagnostic = NULL~
- Duplicate ~ID~ targets are data errors.
- If multiple indexed headings have the same ~ID~ after case-insensitive matching:
  - do not choose a target
  - set ~target_file_id = NULL~
  - set ~target_heading_id = NULL~
  - set ~target_id~ to the normalized requested ID
  - set ~resolution_status = ambiguous~
  - set ~resolution_diagnostic = duplicate id~

Diagnostics policy:

- Successful resolutions use:
  - ~resolution_diagnostic = NULL~
- Missing same-file or file-context ~CUSTOM_ID~ uses:
  - ~resolution_status = broken~
  - ~resolution_diagnostic = custom id not found~
- Missing ~ID~ uses:
  - ~resolution_status = unresolved~
  - ~resolution_diagnostic = id not found~
- Duplicate ~ID~ uses:
  - ~resolution_status = ambiguous~
  - ~resolution_diagnostic = duplicate id~

Out of scope:

- Do not support bare angle ~<#foo>~ as a CUSTOM_ID link.
- Do not support bare plain ~#foo~ as a CUSTOM_ID link.
- Do not resolve ~attachment:~ links.
- Do not resolve regexp search options.
- Do not resolve line-number search options.
- Do not resolve dedicated targets.
- Do not resolve non-star and non-~#~ fuzzy links.
- Do not change file heading-title search option behavior.
- Do not change same-file star fuzzy heading resolution.
- Do not change file-only synthetic root heading behavior.
- Do not scan files outside the indexed DB.
- Do not use Emacs ~org-id-locations~.
- Do not add a DB schema migration.

Implementation notes:

- Prefer a shared helper for property target normalization.
- Keep property key matching exact.
- Implement case-insensitive value comparison deterministically.
- Either:
  - query candidate properties in scope ordered by heading document order and compare normalized values in Rust
  - or use deterministic SQL case-insensitive comparison with explicit ~ORDER BY headings.byte_start, headings.id~
- Preserve deterministic first-match behavior for ~CUSTOM_ID~.
- Preserve strict ambiguous behavior for duplicate ~ID~.
- Keep raw DB link fields unchanged.
