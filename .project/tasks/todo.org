* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** PLAN Persist indexing context and define invalidation rules

Goal: Prevent unchanged files from being skipped when indexing semantics or persisted capabilities have changed.

Acceptance criteria:

- The DB persists an explicit indexing-context version or deterministic fingerprint in ~db_metadata~.
- The invalidation contract covers parser/indexer contract changes, configured default TODO keywords, configured plain-link protocols, body-text persistence, the FTS contract, and other parse- or write-affecting settings introduced later.
- Query-only settings such as ~query.timezone~ do not force reparsing.
- Source-root and ignore-rule changes trigger source-set and link-universe reconciliation even when file bytes are unchanged.
- Each changed context component has a documented action: no action, derived-state rebuild, reparse affected files, or full rebuild.
- A missing or incompatible context value in an older DB fails safe by requiring the necessary rebuild or reindex rather than trusting stale rows.
- ~body_text_available~, ~fts_available~, ~fts_body_indexed~, ~fts_schema_version~, and the indexing-context metadata are updated atomically with the data they describe.
- Global capability flags are never set to available when only a subset of current files satisfies the capability.
- Tests cover config-only changes to TODO defaults, link protocols, body indexing, and FTS settings as applicable.

** TODO Add deterministic change planning

Goal: Classify the current source set against persisted file state before any DB mutation.

Expected change kinds:

- unchanged
- metadata-only
- created
- modified
- deleted

Acceptance criteria:

- ~mtime_ns~ and ~size~ are the fast unchanged check when the indexing context is compatible.
- If either fast signal differs, the current bytes are hashed and compared with the stored hash before deciding whether parsing is required.
- When hashing is required, the same captured bytes and snapshot are reused for preparation if the file is modified rather than reading a second, potentially different version.
- A metadata-only change updates file metadata without replacing parsed rows when the content hash is unchanged.
- The same-metadata verification policy is explicit. A caller can request stronger hash verification rather than being forced to trust ~mtime_ns~ and ~size~ forever.
- The hash algorithm and serialized representation are versioned or algorithm-qualified so future algorithms cannot be compared accidentally.
- New files are prepared and inserted.
- Files that were indexed but are no longer eligible, configured, or present are planned for hard deletion. A missing-status retention model is out of scope unless a separate schema decision is approved.
- Discovery or stat/read errors are distinct from deletions and do not produce destructive plans.
- The existing empty-source safety guard remains effective, and any additional mass-deletion safeguard is documented.
- Planning is deterministic, performs no DB mutation, and returns a report suitable for tests and later CLI/watcher callers.
- Tests cover unchanged files, touched files with identical content, changed content with equal size where practical, created files, deleted files, ignore/config changes, forced verification, and incompatible indexing context.

** TODO Implement transactional change-set application and per-file wrappers

Goal: Apply one or more planned file replacements or removals through one production write path, with a one-file wrapper for Phase 7.

General rules:

- Low-level row replacement or removal functions operate on an existing transaction.
- A higher-level change-set operation owns the transaction, applies file mutations in deterministic path order, reconciles required global derived state at most once, updates trust metadata, and commits.
- A single-file replacement or removal call is a one-item change set, not a separate implementation.

Acceptance criteria:

- A created or modified file can be prepared and replaced transactionally without filesystem events.
- Prepared snapshots are revalidated according to the documented stale-preparation policy before mutation; a known-stale value is retried or rejected rather than committed as current.
- A deleted file hard-deletes its ~files~ row and all owned rows consistently.
- Updating an existing path preserves its file row identity where practical. Heading, link, timestamp, and other surrogate-ID stability is explicitly documented rather than assumed.
- Old headings, TODO keywords, keywords, properties, tags, timestamps, timestamp repeaters, links, heading bodies, outline rows, and other file-owned rows are replaced where applicable.
- Exactly one synthetic level-0 heading and one matching root ~outline_path~ row are recreated for every indexed file.
- The operation works when FTS5 is disabled and keeps any stale on-disk FTS table explicitly untrusted.
- When FTS5 is enabled, no stale FTS row IDs or terms survive. Rebuilding the complete contentless ~heading_fts~ table once per committed change set is acceptable initially.
- FTS trust metadata becomes valid only in the same transaction that creates the matching FTS contents.
- Incoming links to replaced or deleted headings/files do not remain marked ~resolved~ with null or obsolete targets. The current global ~LinkResolver::resolve_all~ may run once per change set before commit.
- The indexed universe passed to link resolution reflects the post-change source set and ignore policy.
- Full rebuild uses the same per-file preparation and row-write primitives rather than maintaining a second import implementation.
- Any parse, validation, SQL, FTS, resolver, or commit error leaves the previously committed DB state intact for the affected transaction.
- Tests cover created, modified, metadata-only, deleted, failed replacement, failed removal where practical, incoming links, FTS enabled/disabled, body indexing enabled/disabled, level-0 rows, and rollback behavior.

** TODO Define batching, interruption, and error semantics

Goal: Process many planned changes efficiently without weakening consistency or making results depend on processing order.

Acceptance criteria:

- Preparation remains outside DB write transactions.
- File mutation order inside a change set is deterministic.
- Full rebuild atomicity is explicitly preserved or deliberately changed with a documented reason. The current all-or-nothing behavior is the default expectation.
- Incremental reconciliation defines whether the complete run is one atomic change set or a sequence of atomic batches.
- If batches are used, the batch size is configurable or selected from measurements rather than guesswork.
- FTS rebuild and global link resolution run at most once per committed change set or batch and are skipped only when the plan proves the corresponding derived state cannot have changed.
- Parse/read failures preserve the previous rows for the failed file and follow a documented fail-fast or continue strategy.
- SQL or reconciliation failure rolls back the complete current transaction or batch.
- Interruption leaves either the previous committed state or complete committed batches, never a partially replaced file or partially reconciled derived state.
- Reports distinguish skipped, metadata-only, created, modified, deleted, failed, and committed files.
- Tests or deterministic fault-injection checks cover failure before mutation, during file-row replacement, during derived-state reconciliation, and during commit where practical.

** TODO Add index integrity and rebuild-equivalence checks

Goal: Prove that incremental operations produce the same logical database as a clean rebuild and that derived/cache rows remain trustworthy.

Acceptance criteria:

- A semantic snapshot comparison is defined by stable source identity such as file path and source positions rather than raw surrogate IDs.
- A clean full rebuild and an incremental sequence reaching the same final corpus produce equivalent canonical facts, outline data, FTS matches when enabled, and link-resolution outcomes.
- Documented operational differences such as ~indexed_at~ and intentionally unstable surrogate IDs are excluded explicitly rather than ignored ad hoc.
- Repeating an unchanged incremental run performs no reparsing and leaves semantic state unchanged.
- Integrity checks cover one level-0 heading per file, one ~outline_path~ row per heading, foreign-key validity, no orphaned file-owned rows, and consistent resolver target/status combinations.
- When FTS is trusted, its row IDs exactly match the canonical heading set and expected title/body policy. When FTS is untrusted or disabled, search metadata reflects that state.
- Checks use ~PRAGMA foreign_key_check~ and targeted repository invariants; ~PRAGMA integrity_check~ may be included for manual or benchmark runs.
- Tests cover create, modify, delete, rename-as-delete-plus-create, configuration invalidation, FTS modes, link targets, and rollback.

- Commands, corpus generation, results, and limitations are documented reproducibly.
