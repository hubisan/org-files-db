* Phase 5: Query engine and optional full-text search

Goal of this phase:

- Build a small, safe query layer for indexed Org graph data.
- Implement the Query Model v0 contract defined in [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]].
- Keep the query model independent from CLI and SQL.
- Support headings, links, and files as explicit query targets.
- Keep full-text search optional and separate from the core query model.
- Return stable JSON that is useful for Emacs/editor integrations.

General rules:

- Query AST/model is independent of CLI and SQL.
- SQL generation must use bound parameters.
- Query execution uses the persisted database, not parser re-analysis.
- Query target is explicit through ~(headings ...)~, ~(links ...)~, and ~(files ...)~.
- Bare predicates are shorthand for heading queries only at the top level.
- Nested relation queries must use explicit target wrappers.
- Query output mode must not change match semantics.
- Include options may enrich results but must not change which objects match.
- Direct parsed facts and effective/derived semantics must stay clearly separated.
- Query results must include enough location data for editor jumps.
- Body text search must fail clearly when body text is unavailable.
- FTS5 is optional and must only be required for FTS-specific functionality.
- Mutation and repair operations are out of scope for Query Model v0.

** REVIEW [#B] Implement CLI command ~query~
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:API_CONTRACT_CHANGE: Yes
:END:

- Task file: [[file:2026-07-09--implement-cli-command-query.org]]

Depends on:

- Implement query AST and parser
- Implement query semantic validation and normalization
- Implement safe SQL translation and core metadata query execution
- Implement query result shaping and JSON output model

Goal:

- Expose Query Model v0 through the CLI.

Examples:

#+begin_src shell
orgfdb query --json '(todo "NEXT")'
orgfdb query --json '(headings (tags "project" :match :all))'
orgfdb query --json '(links (status "broken"))'
orgfdb query --json '(files (file-title "Projects"))'
orgfdb query --json --output outline '(headings (title "sqlite"))'
orgfdb query --json --include path,links '(headings (todo "NEXT"))'
#+end_src

Rules:

- ~query~ uses the DB layer, not the parser.
- ~query~ is read-only.
- ~query~ must not scan Org files.
- ~query~ must not rebuild or mutate the database.
- CLI flags control output and includes, not query semantics.
- Query syntax and semantics are defined by [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]].

Acceptance criteria:

- ~orgfdb query~ accepts Query Model v0 syntax.
- Query output is JSON when ~--json~ is passed.
- Query supports heading, link, and file targets.
- Query supports flat output.
- Query supports outline output.
- Query supports include options from the specification.
- Invalid query syntax returns an understandable error.
- Invalid query semantics return an understandable error.
- Unsupported backend requirements return an understandable error.
- CLI docs link to [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]] once the command is stable enough.

- If body text is unavailable, the query returns a clear error.
- Tests cover available body text, unavailable body text, multiple terms, unsupported regexp matching, no Org file scanning, and no DB mutation.

** TODO [#C] Enable optional SQLite FTS5 for full-text search
:PROPERTIES:
:PRIORITY: Low
:RISK: Medium
:DB_SCHEMA_CHANGE: Maybe
:END:

Depends on:

- Implement body text availability for ~(has-text ...)~

Goal:

- Add an optional FTS5 backend for faster title and body text search.

Planned logical FTS columns when FTS5 is enabled:

#+begin_src sql
title
body
#+end_src

The exact FTS5 schema should be decided during implementation. Prefer an external-content or contentless FTS5 design if that avoids duplicating stored body text.

Rules:

- FTS5 support is configured through ~search.fts5_enabled~.
- Body text storage/indexing is configured separately through ~search.index_body_text~.
- FTS5 indexes the already stored body text when both ~search.fts5_enabled~ and ~search.index_body_text~ are enabled.
- FTS5 must not become the only storage location for body text.
- If body text storage/indexing is disabled, FTS5 may still index heading titles, but it must not index heading bodies.
- FTS5 must not be required for non-FTS query functionality.
- Query semantics must remain defined by [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]], not by FTS5 behavior.
- FTS-specific functionality must fail clearly when FTS5 is disabled.
- Query execution must not scan Org files.
- Query execution must not mutate parsed heading metadata facts.

Acceptance criteria:

- If FTS5 is disabled, rebuild works without creating or writing ~heading_fts~.
- If FTS5 is enabled, ~heading_fts~ is created and maintained.
- ~heading_fts.rowid~ matches ~headings.id~.
- Heading titles are indexed when FTS5 is enabled.
- Heading body text is indexed only when both ~search.fts5_enabled~ and ~search.index_body_text~ are enabled.
- FTS-backed search can match title-only, body-only, or both where supported.
- Body text storage/indexing can be disabled even when FTS5 is enabled.
- FTS5 does not duplicate raw body text unless explicitly justified by the chosen schema.
- Queries or commands using unavailable FTS-specific functionality return clear errors.
- Tests cover enabled FTS5, disabled FTS5, title indexing, optional body indexing, disabled body indexing, no raw body duplication where the chosen schema supports that, no Org file scanning, and no DB mutation.
