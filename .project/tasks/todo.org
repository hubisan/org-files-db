* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** PLAN Implement transactional change application and prove rebuild equivalence

Goal: Apply planned changes through one deterministic transactional production path, define interruption and batching semantics, and prove that the resulting database is equivalent to a clean rebuild.

General rules:

- Low-level file replacement, metadata update, and removal functions operate on an existing transaction.
- A higher-level change-set operation owns the transaction.
- A single-file replacement or removal is implemented as a one-item change set, not through a separate mutation implementation.
- Preparation remains outside DB write transactions.
- Prepared snapshots are revalidated immediately before mutation according to the documented stale-preparation policy.
- A known-stale prepared value is retried or rejected and must not be committed as current.
- File mutations inside a change set are applied in deterministic canonical identity or path order.
- Full rebuild uses the same per-file preparation and row-write primitives rather than maintaining a separate import implementation.
- Full rebuild retains its all-or-nothing transaction unless a later measured reason justifies changing it.
- Incremental reconciliation initially uses one atomic change set unless measurements justify explicit batching.
- If batching is introduced, the batch size and interruption semantics must be documented and based on measurements rather than guesswork.

Acceptance criteria:

- Created and modified files can be prepared and replaced transactionally without filesystem events.
- Metadata-only changes update file metadata without replacing parsed file-owned rows.
- Deleted files hard-delete their ~files~ row and all owned rows consistently.
- Updating an existing physical file preserves its file-row identity where practical.
- Stability or instability of heading, link, timestamp, and other surrogate IDs is explicitly documented rather than assumed.
- Replacing a file removes all previous file-owned headings, TODO keywords, keywords, properties, tags, timestamps, timestamp repeaters, links, heading bodies, outline rows, and other applicable rows.
- Exactly one synthetic level-0 heading and one matching root ~outline_path~ row are recreated for every indexed file.
- The operation works when FTS5 is disabled and leaves any stale on-disk FTS table explicitly untrusted.
- When FTS5 is enabled, no stale FTS row IDs or terms survive.
- Rebuilding the complete contentless ~heading_fts~ table once per committed change set is acceptable initially.
- FTS trust metadata becomes valid only in the same transaction that creates the matching FTS contents.
- Global FTS reconciliation runs at most once per committed change set or batch.
- Incoming links to replaced or deleted headings or files do not remain marked ~resolved~ with missing or obsolete targets.
- The current global ~LinkResolver::resolve_all~ may run once per committed change set before commit.
- Link resolution uses the post-change indexed universe and the current inclusion and exclusion policy.
- Global link reconciliation runs at most once per committed change set or batch.
- It may be skipped only when the plan proves that link-derived state cannot have changed.
- Any parse, snapshot validation, SQL, FTS, resolver, metadata, or commit error rolls back the complete current transaction or batch.
- A failed replacement preserves the previously committed rows for that file.
- A failed deletion preserves the previously committed file and owned rows.
- Interruption leaves either the previous committed state or complete committed batches, never a partially replaced file or partially reconciled derived state.
- The failure strategy is explicit: preparation and validation failures occur before mutation; transaction failures are fail-fast and roll back the complete current change set or batch.
- Reports distinguish planned, skipped, metadata-only, created, modified, deleted, failed, rolled-back, and committed files.

Integrity and equivalence criteria:

- A semantic database snapshot is defined using stable source identity, file paths, source positions, and canonical values rather than raw surrogate IDs.
- Operational fields such as ~indexed_at~ and intentionally unstable surrogate IDs are explicitly excluded from semantic comparison.
- A clean full rebuild and an incremental sequence reaching the same final corpus produce equivalent canonical facts.
- Equivalence covers files, level-0 roots, headings, TODO keywords, keywords, properties, tags, timestamps, timestamp repeaters, links, heading bodies where enabled, outline data, link-resolution outcomes, and FTS matches where enabled.
- Repeating an unchanged incremental run performs no reparsing and leaves semantic state unchanged.
- Integrity checks verify exactly one level-0 heading per file.
- Integrity checks verify exactly one ~outline_path~ row per heading.
- Integrity checks verify foreign-key validity and no orphaned file-owned rows.
- Resolver target fields and statuses must form valid documented combinations.
- When FTS is trusted, its row IDs exactly match the canonical heading set and expected title/body policy.
- When FTS is disabled or untrusted, search metadata accurately records that state.
- Checks use ~PRAGMA foreign_key_check~ and targeted repository invariants.
- ~PRAGMA integrity_check~ may be included for manual or benchmark validation.

Tests:

- Tests cover created, modified, metadata-only, deleted, and unchanged files.
- Tests cover rename as deletion plus creation.
- Tests cover failed preparation, failed replacement, failed removal where practical, derived-state failure, and commit failure where practical.
- Tests cover incoming links to modified and deleted targets.
- Tests cover FTS enabled and disabled.
- Tests cover body indexing enabled and disabled.
- Tests cover level-0 and outline invariants.
- Tests cover configuration and indexing-context invalidation.
- Tests compare a clean full rebuild with equivalent incremental create, modify, and delete sequences.
- Deterministic fault injection covers failure before mutation, during file-row replacement, during derived-state reconciliation, and during commit where practical.

** TODO Establish SQLite query-performance baseline

Goal: Measure whether the current schema and existing indexes are fast enough for the intended Query Model v0 workload before changing indexes.

Note:

- The project is query-oriented, but a separate data warehouse is unnecessary unless measurements demonstrate a real bottleneck.
- This task measures and documents existing behaviour. It does not change persistent indexes.

Acceptance criteria:

- A reproducible benchmark corpus defines file count, heading count, hierarchy shape, tags, properties, timestamps, links, body-text volume, and representative selectivity.
- The corpus includes both shallow and wide outlines and deep hierarchical outlines.
- Common queries are generated through the real Query Model v0 compiler where possible rather than only handwritten SQL.
- Workloads include TODO predicates, tags, properties, links and link status, planning and timestamps, file predicates, outline ancestors, descendants and subtrees, and representative result shaping.
- FTS query performance is measured when FTS5 is enabled.
- FTS measurements include title-only and body-enabled databases.
- Materialized-path subtree queries are measured for shallow, wide, and deep outlines.
- ~EXPLAIN QUERY PLAN~ output is recorded for representative queries.
- Query plans are related to the indexes already present in ~sql/schema.sql~.
- Measurements distinguish warm and cold behaviour where practical.
- Measurements report result counts and use repeated runs.
- SQLite version, build capabilities, relevant pragmas, hardware assumptions, and command configuration are documented.
- Baseline database size is recorded.
- Existing index size and rebuild/write cost are recorded so read performance is not evaluated in isolation.
- Commands, corpus generation, raw results, summaries, and limitations are documented reproducibly.
- No index is added or removed merely because it appears theoretically useful.

** TODO Tune SQLite indexes from measured query plans

Goal: Add, remove, or change indexes only where the performance baseline demonstrates a useful workload improvement.

Acceptance criteria:

- Existing indexes are reviewed for actual planner use, redundancy, storage cost, and write cost before new indexes are proposed.
- Every candidate change is tied to a measured query or a clearly documented expected production workload.
- Before and after results include ~EXPLAIN QUERY PLAN~, latency, result count, database size, and rebuild or incremental-write cost.
- Improvements are measured against the same reproducible corpus and environment used by the baseline.
- Typical exact-match predicates and relation joins are distinguished from substring and regexp predicates that ordinary B-tree indexes cannot accelerate directly.
- Candidate indexes that do not provide a meaningful measured benefit are rejected and documented.
- Redundant or unused indexes may be removed only when measurements and planner inspection support the change.
- Persistent index changes bump ~CURRENT_SCHEMA_VERSION~.
- Persistent index changes include migration tests and fresh-schema tests.
- FTS-specific tuning remains conditional on FTS5 support.
- FTS tuning does not weaken existing trust-metadata and rebuild-equivalence contracts.
- The accepted index set contains no known redundant index without a documented reason.
- Final before and after measurements, accepted changes, rejected candidates, and limitations are documented so later work does not repeat the same experiments.
