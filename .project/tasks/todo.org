* Projektziel

`org-files-db` ist eine Rust-Backend-Library mit optionalem CLI, die Org-mode-Dateien einliest, relevante Org-Strukturen extrahiert und in eine SQLite-Datenbank überträgt.

Das Ziel ist eine robuste, schnelle und später erweiterbare Index-Pipeline für Org-Dateien:

- Org-Dateien parsen
- Headings, TODO-Status, Prioritäten, Tags, Properties, Planning-Daten und Links extrahieren
- Daten normalisiert in SQLite speichern
- schnelle Suche und JSON-Ausgabe über ein `clap`-CLI bereitstellen
- später eine org-ql-artige Query-Sprache auf SQLite/FTS5 abbilden

`orgize` wird initial als Parser-Backend verwendet, gilt aber nicht als dauerhaft sichere oder alleinige Parsing-Wahrheit. Das Projekt muss deshalb eine eigene stabile Parser-Abstraktion und ein eigenes internes Datenmodell verwenden.

Orgize-spezifische Typen dürfen nicht in DB-, Query-, Indexer- oder CLI-Schichten leaken.

Grundsatz:

#+begin_src text
Orgize / Parser Backend
  -> eigenes ParsedOrgDocument / ParsedHeading Modell
  -> Normalisierung / Diagnostics
  -> SQLite Import
  -> Query / CLI / JSON API
#+end_src

So bleibt später möglich:

- Orgize weiterzuverwenden, wenn es für unsere Zwecke stabil genug ist
- bekannte Orgize-Bugs lokal zu umgehen
- Parser-Bugs mit reproduzierbaren Fixtures upstream zu melden
- bei Bedarf auf einen Fork, Tree-sitter, einen eigenen Parser oder einen Emacs-basierten Import zu wechseln

Nicht-Ziele für den Anfang:

- kein vollständiger eigener Org-mode-Parser im MVP
- keine vollständige org-ql-Kompatibilität im MVP
- keine direkte Abhängigkeit der DB-Schicht von Orgize oder rowan
- keine Optimierung auf Maximal-Performance, bevor die Pipeline korrekt funktioniert

* Architekturentscheidungen

** Entscheidung: Orgize nur als Adapter verwenden

`orgize` wird als erstes Parser-Backend verwendet, aber nur in einem klar begrenzten Adapter-Modul.

Erlaubt:

#+begin_src text
src/parser/orgize_adapter.rs
#+end_src

Nicht erlaubt:

- Orgize-Typen in `db/`
- Orgize-Typen in `query/`
- Orgize-Typen in `cli/`
- direkte DB-Inserts aus Orgize-AST-Knoten
- direkte Abhängigkeit auf `syntax()` / rowan ausserhalb des Adapters

** Entscheidung: eigenes internes Parser-Modell

Die interne Projekt-API basiert auf eigenen Typen:

#+begin_src rust
pub trait OrgParser {
    fn parse_document(
        &self,
        path: &Path,
        content: &str,
    ) -> Result<ParsedOrgDocument>;
}

pub struct ParsedOrgDocument {
    pub file_path: PathBuf,
    pub headings: Vec<ParsedHeading>,
    pub diagnostics: Vec<ParseDiagnostic>,
}

pub struct ParsedHeading {
    pub level: u8,
    pub title: String,
    pub todo_keyword: Option<String>,
    pub priority: Option<char>,
    pub tags: Vec<String>,
    pub properties: Vec<(String, String)>,
    pub planning: ParsedPlanning,
    pub line_number: Option<u32>,
    pub byte_start: usize,
    pub byte_end: usize,
    pub parent_index: Option<usize>,
}
#+end_src

** Entscheidung: Parser-Probleme werden sichtbar gemacht

Bekannte oder vermutete Parser-Probleme werden nicht stillschweigend ignoriert.

Stattdessen:

- `ParseDiagnostic` erfassen
- Fixture-Test hinzufügen
- Verhalten dokumentieren
- falls sinnvoll: Upstream-Issue für Orgize vorbereiten
- DB-Insert nur mit normalisierten Daten ausführen

* NEXT Projekt neu aufsetzen

Die Projektstruktur muss neu aufgesetzt werden. Der alte Entwurf ist nicht mehr aktuell, weil die Parser-Strategie angepasst wurde: Orgize wird nicht direkt als zentrale Projektarchitektur verwendet, sondern nur als austauschbarer Adapter hinter einer eigenen Parser-Abstraktion.

Bitte lies diese Datei vollständig, damit du verstehst, was das Projekt erreichen soll, und passe danach die Struktur entsprechend an.

#+begin_src text

  config/
    mod.rs

Wichtige Architekturregeln:

- `parser/orgize_adapter.rs` darf Orgize direkt verwenden.
- Alle anderen Module arbeiten nur mit eigenen Typen aus `parser/model.rs`.
- Bekannte Parser-Abweichungen werden als Diagnostics oder Fixture-Regressionsfälle dokumentiert.
- DB-Inserts dürfen nicht direkt aus Orgize-AST-Knoten entstehen.
- Der Indexer orchestriert Parser und DB, enthält aber keine Orgize-spezifische Logik.

Akzeptanzkriterien:

- Neue Modulstruktur ist angelegt.
- `lib.rs` exportiert die Kernmodule.
- `main.rs` bleibt dünn und ruft nur CLI-Code auf.
- Orgize-Abhängigkeit ist auf den Parser-Adapter begrenzt.
- Bestehende alte Struktur ist entweder migriert oder bewusst entfernt.
