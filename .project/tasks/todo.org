* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** REVIEW [#B] Materialize ~effective_properties~ in schema version 10
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: Yes
:API_CONTRACT_CHANGE: No
:END:

Task file: [[file:2026-07-25--materialize-effective-properties-schema-10.org][Materialize effective properties in schema version 10]]

Goal:

- Replace recursive query-time property resolution with a normalized and transactionally maintained ~effective_properties~ projection.
- Keep ~properties~ as the canonical source and treat ~effective_properties~ as mandatory derived state analogous to ~outline_path~.
- Preserve the existing public property-query and JSON contracts.

Measured motivation:

- The 1,000-file baseline measured approximately 200 ms median for a direct property query and approximately 4.7 seconds median for an inherited property query.
- The old SQL reconstructed heading ancestry and property state for every candidate heading.

*** Final schema

#+begin_src sql
CREATE TABLE effective_properties (
    heading_id      INTEGER NOT NULL,
    file_id         INTEGER NOT NULL,
    key             TEXT NOT NULL,
    local_value     TEXT,
    effective_value TEXT NOT NULL,
    PRIMARY KEY (heading_id, key),
    FOREIGN KEY (heading_id) REFERENCES headings(id) ON DELETE CASCADE,
    FOREIGN KEY (file_id) REFERENCES files(id) ON DELETE CASCADE
);

CREATE INDEX idx_effective_properties_file
ON effective_properties(file_id);
#+end_src

Column semantics:

- ~local_value IS NULL~ means the heading has no local definition for the key.
- An empty string remains an explicitly empty local or effective value.
- ~effective_value~ contains the value visible at the heading after applying the existing root, ancestor, replacement, and append rules.
- The synthetic level-0 root is included.

*** Canonical and derived-state contract

- ~properties~ remains the only canonical property representation.
- ~effective_properties~ is fully rebuildable from headings and canonical property rows.
- ~#+PROPERTY~, ~#+CATEGORY~, root property drawers, and heading property drawers participate because the parser normalizes them into ~properties~.
- Ordinary keywords such as ~TITLE~ and ~AUTHOR~ remain keywords.
- Property inheritance never crosses a file boundary.
- Property-key normalization is shared by parsing, derivation, migration, and query compilation.

*** Resolution semantics

- Preserve duplicate handling at one location.
- Preserve the last applicable non-append definition.
- Preserve append rows in source order.
- Preserve append-only local definitions and appending to inherited values.
- Preserve explicit empty values and the distinction between missing and locally empty values.
- Derive one row per visible heading and property key by traversing each file tree from root to leaves.

*** Indexing and migration

- Full rebuild, file creation, and modified-file replacement derive and insert the projection in the same transaction as canonical file data.
- File deletion removes derived rows through foreign-key cascades.
- Metadata-only updates do not regenerate the projection.
- Schema version 9 migrates to version 10 without reparsing Org files.
- Migration processes each file independently and validates exactly one root, same-file parents, complete root reachability, and absence of parent cycles.
- Schema creation, backfill, validation, and schema-version advancement share the database initialization transaction and roll back together on failure.

*** Query and output contract

- Default and explicit ~:inherit t~ heading property predicates use ~effective_value~.
- ~:inherit nil~ uses ~local_value~ and requires a local definition.
- Key-only existence, exact value matching, regexp matching, nested predicates, and existing root/file semantics remain unchanged.
- File-target property predicates retain their direct root semantics.
- Included effective property output loads from ~effective_properties~.
- The public query syntax and JSON shape do not change.
- Normal property query SQL no longer contains recursive property-resolution CTEs.

*** Required verification

- Fresh schema uses version 10 and the exact explicit index inventory.
- Real version-9 databases backfill effective properties transactionally.
- Invalid cross-file parents, missing parents, multiple roots, cycles, and unreachable headings fail migration without partial schema advancement.
- Migration output equals a clean version-10 rebuild using stable identities.
- Root inheritance, parent inheritance, local replacement, append-only values, inherited append, explicit empty values, ~CATEGORY~, and ordinary keywords remain correct.
- Replacement removes stale effective rows, deletion cascades rows, and metadata-only updates leave rows unchanged.
- Query SQL uses ~effective_properties~ and contains no legacy recursive property resolver.

*** Deferred performance verification

- Keep the existing benchmark runner unchanged in this task.
- After correctness review, run a focused current-schema measurement for direct and inherited property workloads on a smaller deterministic corpus before deciding whether a larger final run is needed.

*** Checks

- ~cargo fmt --all --check~
- ~cargo clippy --all-targets --all-features -- -D warnings~
- ~cargo test~
- ~cargo build --all-targets --all-features~
- ~git diff --check~
- ~make ci~

** TODO [#B] Replace ~all_tags_json~ with normalized effective tags
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: Yes
:API_CONTRACT_CHANGE: No
:END:

Depends on:

- Materialize effective properties in schema version 10.

Goal:

- Store effective tag membership in a normalized ~effective_tags~ projection.
- Remove ~headings.all_tags_json~ as redundant derived state.
- Use canonical direct tag rows for local matching and normalized effective tag rows for inherited matching and output.
- Implement this directly without a separate measurement gate.

Architecture:

- The existing ~tags~ table remains the canonical source of tags defined directly on a heading or file/root.
- ~effective_tags~ becomes the mandatory derived projection of all tags visible on each heading.
- Root-level ~FILETAGS~ participate when inheritance and root participation are enabled.
- The projection is maintained transactionally in the same manner as ~outline_path~ and ~effective_properties~.
- ~all_tags_json~ must not remain as a second effective-tag cache after ~effective_tags~ is authoritative.

Schema:

- Bump the database schema version from 10 to 11.
- Add an ~effective_tags~ table containing at least:
  - ~heading_id~
  - ~file_id~
  - ~tag~
  - a flag indicating whether the tag remains visible when root/FILETAGS participation is excluded
  - deterministic ordering metadata if required to preserve the current JSON tag order
- Enforce uniqueness for ~(heading_id, tag)~.
- Reference headings and files with foreign keys and cascade derived rows when their owner is deleted.
- Add an index supporting inherited tag lookup by ~(tag, heading_id)~.
- Add a partial index supporting inherited lookup without root participation.
- Remove ~all_tags_json~ from the fresh ~headings~ schema and from all corresponding row models and SQL projections.

Effective tag semantics:

- Preserve current tag normalization and case behaviour.
- Deduplicate a tag inherited through more than one level.
- Include local tags, ancestor tags, and root ~FILETAGS~ in the default effective set.
- For ~:without-root t~, retain a tag when it is also supplied locally or by a real ancestor even when the same tag is present in ~FILETAGS~.
- For ~:inherit nil~, use only canonical direct rows from ~tags~.
- Preserve deterministic output ordering according to the current public output contract.

Derivation:

- Implement effective-tag derivation as a pure operation over one prepared heading tree.
- Walk the tree from root to leaves while carrying the effective tag set.
- Calculate both normal visibility and visibility with root participation excluded.
- Produce at most one row per heading and tag.
- Do not reconstruct ancestor tag sets through recursive SQL during each query.

Transactional maintenance:

- A created or modified file regenerates all of its ~effective_tags~ rows in the same transaction as headings, direct tags, and other derived state.
- A metadata-only change leaves the projection unchanged.
- File replacement and deletion must not leave stale effective tags.
- Full rebuild and incremental replacement must use the same derivation path.
- Any effective-tag failure rolls back the affected transaction.

Migration:

- Add a transactional migration from schema version 10 to 11.
- Create and backfill ~effective_tags~ from canonical headings and direct ~tags~ rows.
- Verify the backfilled normalized rows before removing or ceasing to use ~all_tags_json~.
- Remove the obsolete ~all_tags_json~ column using the project's supported SQLite migration strategy.
- Advance the schema version only after the projection and schema transition complete successfully.
- Do not require Org-file reparsing when the canonical direct tag rows are sufficient.

Query compiler:

- Compile ~(tags ... :inherit nil)~ against canonical ~tags~.
- Compile inherited tag predicates against ~effective_tags~.
- Apply the root-exclusion flag for ~:inherit t :without-root t~.
- Preserve ~:match :any~, ~:match :all~, ~tags-all~, regexp matching, root-result behaviour, and bound parameters.
- Remove recursive per-heading lineage resolution from tag predicate SQL.

Output:

- Build public effective tag arrays from ~effective_tags~.
- Preserve the existing JSON field and its semantics.
- Remove JSON decoding of ~headings.all_tags_json~ from query execution and result shaping.
- Ensure flat, outline, path, source, target, and included result objects all obtain effective tags from the same normalized source.

Integrity and equivalence:

- Require the file/root and every real heading to have exactly the expected normalized effective tag rows.
- Verify no duplicate, stale, or orphaned effective tags exist.
- Include ~effective_tags~ in semantic rebuild-versus-incremental comparisons.
- Ensure direct ~tags~, derived ~effective_tags~, and public tag output cannot disagree after a committed transaction.

Tests:

- Cover local tags and ~:inherit nil~.
- Cover parent and multi-level ancestor inheritance.
- Cover root ~FILETAGS~ inheritance.
- Cover ~:without-root t~.
- Cover the same tag supplied by root and a real ancestor.
- Cover duplicate tags across multiple levels.
- Cover ~:match :any~, ~:match :all~, ~tags-all~, and regexp matching.
- Cover root/file results and real heading results.
- Cover deterministic JSON tag ordering.
- Cover creation, modification, metadata-only change, deletion, migration, rollback, and rebuild equivalence.
- Assert that inherited tag query plans use ~effective_tags~ rather than recursive lineage SQL.
- Assert that the fresh schema and runtime SQL no longer reference ~all_tags_json~.

Acceptance criteria:

- Fresh databases use schema version 11.
- Version-10 databases migrate deterministically to version 11.
- ~effective_tags~ is the only stored effective-tag representation.
- ~headings.all_tags_json~ is removed.
- Direct and effective tag query semantics remain unchanged.
- Public JSON tag output remains compatible and deterministic.
- Full rebuild and incremental replacement maintain normalized effective tags transactionally.
- Integrity and semantic-equivalence checks include the new projection.
- ~make ci~ passes.
