* Phase 5: Query engine and optional full-text search

Goal of this phase:

- Build a small, safe query layer for indexed Org graph data.
- Implement the Query Model v0 contract defined in [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]].
- Keep the query model independent from CLI and SQL.
- Support headings, links, and files as explicit query targets.
- Keep full-text search optional and separate from the core query model.
- Return stable JSON that is useful for Emacs/editor integrations.

General rules:

- Query AST/model is independent of CLI and SQL.
- SQL generation must use bound parameters.
- Query execution uses the persisted database, not parser re-analysis.
- Query target is explicit through ~(headings ...)~, ~(links ...)~, and ~(files ...)~.
- Bare predicates are shorthand for heading queries only at the top level.
- Nested relation queries must use explicit target wrappers.
- Query output mode must not change match semantics.
- Include options may enrich results but must not change which objects match.
- Direct parsed facts and effective/derived semantics must stay clearly separated.
- Query results must include enough location data for editor jumps.
- Body text search must fail clearly when body text is unavailable.
- FTS5 is optional and must only be required for FTS-specific functionality.
- Mutation and repair operations are out of scope for Query Model v0.

** TODO [#B] Normalize heading titles and title-query matching
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:API_CONTRACT_CHANGE: Yes
:END:

Goal:

- Fix heading title normalisation so ~title~ contains only the semantic heading title.
- Always remove priority cookies from ~title~.
- Always remove statistics cookies from ~title~.
- Ensure title queries match against the cleaned ~headings.title~ value.
- Preserve the source-oriented representation in ~title_raw~.

Example:

#+begin_src org
,* REVIEW [#B] Statistic Cookies [0/1]
#+end_src

Expected parsed and persisted values:

#+begin_src json
{
  "todo_keyword": "REVIEW",
  "priority": "B",
  "title": "Statistic Cookies",
  "title_raw": "[#B] Statistic Cookies [0/1]"
}
#+end_src

Current incorrect result:

#+begin_src json
{
  "todo_keyword": "REVIEW",
  "priority": "B",
  "title": "[#B] Statistic Cookies [0/1]",
  "title_raw": "[#B] Statistic Cookies [0/1]"
}
#+end_src

Rules:

- ~title~ must not contain the TODO keyword.
- ~title~ must not contain a priority cookie such as ~[#A]~, ~[#B]~, or ~[#C]~.
- ~title~ must not contain a statistics cookie such as ~[0/1]~, ~[2/5]~, or ~[50%]~.
- ~title_raw~ keeps priority and statistics cookies according to the existing raw-title contract.
- The separately parsed ~priority~ field remains unchanged.
- Statistics cookies should be removed using Org syntax information where available.
- Arbitrary bracketed text such as ~[Linux]~ or ~[RFC]~ must remain part of ~title~.
- Removing cookies must not leave leading, trailing, or duplicate whitespace in ~title~.
- Built-in and configured TODO keywords must behave identically.
- The normal ~title~ query predicate uses ~headings.title~.
- Priority and statistics cookies must not participate in normal title matching.
- ~title_raw~ is source-oriented output and must not be used by the normal ~title~ predicate.
- Existing indexed data must be rebuilt after this parser change.

Examples:

#+begin_src org
,* TODO [#A] Prepare release
,* REVIEW [#B] Statistic Cookies [0/1]
,* NEXT Progress [50%]
,* TODO Support [Linux]
#+end_src

Expected normalised titles:

#+begin_src text
Prepare release
Statistic Cookies
Progress
Support [Linux]
#+end_src

Expected query behaviour:

#+begin_src lisp
(title "Prepare release")
(title "Statistic Cookies")
(title "Progress")
(title "Support [Linux]")
#+end_src

These queries must match the corresponding headings.

These queries must not match through the normal ~title~ predicate:

#+begin_src lisp
(title "[#A] Prepare release")
(title "[#B] Statistic Cookies [0/1]")
(title "Progress [50%]")
#+end_src

Implementation notes:

- Reuse the parsed priority field instead of relying on reparsing a synthetic heading to remove the priority cookie.
- Detect statistics cookies through Orgize syntax nodes where possible.
- Avoid a broad bracket-removal regular expression because normal bracketed title text must remain intact.
- Keep ~title_raw~ unchanged according to the current contract.
- Rebuild the database after the parser change so existing rows receive the cleaned ~title~ value.

Acceptance criteria:

- A priority cookie is always absent from ~title~.
- A fraction statistics cookie is always absent from ~title~.
- A percentage statistics cookie is always absent from ~title~.
- Priority and statistics cookies remain present in ~title_raw~.
- The ~priority~ field continues to contain the parsed priority.
- Configured TODO keywords such as ~REVIEW~ are handled correctly.
- Built-in TODO keywords are handled correctly.
- Statistics cookies at the beginning, middle, and end of a title are removed cleanly.
- Normal bracketed title text is preserved.
- Links and supported inline markup continue to be normalised correctly.
- Title queries use the normalised ~headings.title~ value.
- Priority and statistics cookies do not participate in ~title~ predicate matching.
- Query results expose the cleaned ~title~ after rebuilding the database.
- ~title_raw~ remains available for source-oriented output but is not used by the normal ~title~ predicate.
- Regression tests cover title queries against headings containing priority and statistics cookies.
- Regression tests cover priority-only, statistics-only, and combined priority/statistics cases.
- Existing parser, persistence, query, and JSON-output tests continue to pass.

** TODO [#B] Align ~title~ with root/file matching semantics
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:API_CONTRACT_CHANGE: Yes
:END:

Depends on:

- Implement effective root, tag, property, and keyword semantics for queries
- Implement query result shaping and JSON output model
- [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]]

Goal:

- Make ~title~ root/file behavior explicit and consistent with Query Model v0.

Problem:

- Query Model v0 says the root can act as a synthetic heading context for selected heading predicates.
- For root/file context, ~title~ should match the file/root title.
- The current ~title~ predicate contract only documents ~:regexp~ and ~:exact~.
- The current validator/backend likely treat ~title~ as a real-heading-only predicate.

Required decision:

- ~title~ on real headings matches heading titles.
- ~title :with-root t~ also allows the file/root node to match by file/root title.
- ~title :with-root nil~ excludes file/root title matching.
- ~title~ without explicit ~:with-root~ should use the Query Model v0 default for root inclusion.
- ~title :with-root t~ must not behave like ~file-title~.
- ~file-title~ continues to filter headings by their containing file title.
- File/root matches must be represented as ~kind = "file"~, not as fake headings.

Rules:

- Do not change ~file-title~ semantics.
- Do not make ~title :with-root t~ match every heading in a file just because the file title matches.
- Do not represent root/file matches as fake heading rows.
- Output mode and include options must not change match semantics.
- SQL must still use bound parameters for user-provided title values.
- Query execution must remain read-only and DB-backed.

Acceptance criteria:

- Query Model v0 documents ~title~ root behavior and allowed ~:with-root~ option.
- Validator accepts ~:with-root~ on heading ~title~.
- Validator rejects invalid ~:with-root~ values.
- SQLite backend implements root/file title matching for ~title :with-root t~.
- ~title :with-root t~ can return a file/root match represented as ~kind = "file"~.
- ~title :with-root nil~ matches real heading titles only.
- ~file-title~ still filters headings by containing file title.
- Tests cover:
  - real heading title match
  - root/file title match
  - ~title :with-root nil~
  - difference between ~title :with-root t~ and ~file-title~
  - flat output
  - outline output
  - file/root result uses ~kind = "file"~
  - no fake heading output for root

** TODO [#B] Complete timestamp timezone and explicit-time query semantics
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:DB_SCHEMA_CHANGE: Maybe
:API_CONTRACT_CHANGE: Yes
:END:

Depends on:

- Implement safe SQL translation and core metadata query execution
- Implement CLI command ~query~
- [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]]

Goal:

- Complete and document the semantics of ~today~, integer day offsets, optional query timezones, datetime arguments, and ~:with-time~ filtering.
- Keep relative date handling consistent with the timezone-naive representation of indexed Org timestamps.

Current behavior:

- ~today~ and integer day offsets use the current local system timezone.
- An explicitly configured query timezone should override the local system timezone.
- Stored Org planning timestamps use timezone-naive epoch-based integer values.
- The SQLite metadata backend currently rejects ~:with-time~ as unsupported.

Rules:

- The query timezone is optional.
- If a query timezone is configured, ~today~ and integer day offsets use that timezone.
- If no query timezone is configured, the current local system timezone is used.
- ~today~ means the current calendar date in the effective query timezone.
- Integer day offsets are calendar-day offsets relative to ~today~.
- Resolved dates and datetimes are encoded using the same timezone-naive representation as indexed Org timestamps.
- Stored Org timestamps must not be converted between timezones.
- Date-only ~:to~ bounds include the complete specified day by using an exclusive next-day boundary.
- Datetime arguments use the explicit hour and minute without timezone conversion.
- ~:with-time t~ matches only Org timestamps containing an explicit time.
- ~:with-time nil~ matches only date-only Org timestamps.
- Omitting ~:with-time~ matches both forms.
- If explicit-time information is unavailable in persisted facts, ~:with-time~ must return a clear unsupported-backend error.

Possible configuration:

#+begin_src toml
[query]
timezone = "Europe/Zurich"
#+end_src

If ~query.timezone~ is absent, the current local system timezone is used.

Possible schema extension:

#+begin_src sql
scheduled_has_time INTEGER
    CHECK (scheduled_has_time IN (0, 1) OR scheduled_has_time IS NULL),

deadline_has_time INTEGER
    CHECK (deadline_has_time IN (0, 1) OR deadline_has_time IS NULL),

closed_has_time INTEGER
    CHECK (closed_has_time IN (0, 1) OR closed_has_time IS NULL)
#+end_src

Acceptance criteria:

- ~(deadline :on today)~ uses the current calendar date in the effective query timezone.
- Explicit timezone configuration overrides the local system timezone.
- Absence of timezone configuration uses the current local system timezone.
- Integer offsets use the same effective timezone and calendar date as ~today~.
- Date-only ~:from~, ~:to~, and ~:on~ semantics are documented and tested.
- Datetime query arguments are documented and tested.
- Tests cover explicit ~UTC~ and ~Europe/Zurich~ timezones.
- Tests cover fallback to the local system timezone.
- Tests cover execution around local midnight.
- Tests cover a daylight-saving transition where supported.
- ~:with-time~ is implemented from persisted facts or remains clearly documented as unsupported.
- Date-only timestamps and explicit midnight timestamps can be distinguished if ~:with-time~ is implemented.
- Query SQL continues to use bound parameters for user-provided values.
