* Phase 7: Watcher-driven incremental updates

Goal of this phase:

- Translate filesystem changes into bounded Phase 6 reconciliation without duplicating indexing semantics.
- Keep filesystem observation, event normalization, reconciliation policy, and Phase 6 execution as separate testable layers.
- Ensure watcher-driven updates converge to the same committed DB state as a normal Phase 6 reconciliation.

General rules:

- The watcher produces normalized candidate paths and reconciliation requests only.
- Phase 6 discovery, classification, change planning, preparation, transactional application, and committed-state validation remain the single source of indexing semantics.
- Raw filesystem event kinds are hints. They must never directly select DB replacement, metadata update, or deletion operations.
- Filesystem event handling must remain separate from parsing and DB mutation logic.
- The watcher must not maintain core or derived DB state itself.
- Watcher-triggered updates inherit the complete Phase 6 source-universe, indexing-context, FTS, link-resolution, trust-metadata, stale-plan, zero-input-safety, and rollback contract.
- Phase 6 source roots, explicit files, directory exclusions, file exclusions, canonical identity, missing-path identity, and deterministic ordering must be reused.
- Do not introduce a second discovery, exclusion, canonicalization, or indexed-file identity model.
- Temporary source-root unavailability must not silently become mass deletion.
- Backend uncertainty must request full Phase 6 reconciliation rather than guessing individual mutations.
- DB writes remain serialized. Parallel parsing or event processing belongs to Phase 8 only if later required.
- The project-wide platform contract applies: Linux and Unix-like systems, including macOS where supported by the selected backend, are supported. Windows is not supported.
- Do not add Windows-specific watcher backends, path conversion, rename handling, tests, or compatibility abstractions.
- Preserve the byte-oriented Unix path identity and symlink semantics established by Phase 6.
- Each implementation task must leave the repository in a complete and testable state before being marked DONE.
- Documentation must describe the implementation that actually exists. Do not document speculative behavior as completed.

Goal:

- Convert backend-specific filesystem event bursts into deterministic candidate-path batches and explicit reconciliation requests without using a live watcher.

Implementation requirements:

- Introduce an internal backend-independent watcher input model.
- Its output must contain only:
  - normalized candidate paths;
  - or a request for full Phase 6 reconciliation.
- Treat create, modify, remove, rename, metadata, and other raw event kinds only as path hints.
- Preserve both old and new paths for rename-style events when the backend provides both.
- Support deleted and renamed-away paths without requiring them to exist.
- Reuse Phase 6 path and indexed-identity rules where applicable.
- Coalesce duplicate and redundant paths.
- Produce deterministic ordering independent of raw event order where the final candidate set is equivalent.
- A reconciliation request supersedes path-specific candidates in the same batch.
- Ignore irrelevant paths through Phase 6-compatible source-universe and exclusion classification.
- Do not add ~notify~, sleeping, threads, channels, filesystem polling, or CLI behavior in this task.

Acceptance criteria:

- Create followed by modify produces one candidate.
- Modify followed by remove retains the path as a candidate for Phase 6 classification.
- Remove followed by create retains the path as a candidate for Phase 6 classification.
- Rename with both paths produces old-path and new-path candidates.
- Rename with incomplete information requests reconciliation when bounded correctness cannot be guaranteed.
- Backend overflow, dropped-event, rescan, or equivalent uncertainty maps to reconciliation.
- Candidate ordering is deterministic.
- Excluded or unrelated paths do not reach Phase 6 execution.
- Empty batches perform no DB work and cannot bypass Phase 6 safeguards.

Required tests:

- modify plus remove;
- remove plus create;
- rename with old and new paths;
- incomplete rename;
- duplicate paths;
- excluded paths;

** TODO [#A] Persist and validate configured source-root identity
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: Metadata
:API_CONTRACT_CHANGE: Yes
:END:

Goal:

- Prevent an automatically started full reconciliation from treating a replaced configured directory root as the authoritative continuation of the previously indexed root.

Scope:

- Apply only to configured directory roots.
- Explicit-file inputs remain unchanged.
- Individual files and discovered subdirectories do not receive persistent filesystem identities.
- The watcher must reuse this Phase 6 safety contract and must not persist or validate root identity independently.

Implementation requirements:

- Introduce one Phase 6 root-evidence model for configured directory roots.
- For every configured directory root, record:
  - the configured logical path using the existing native Unix path representation;
  - the canonical root path where available;
  - the native root identity required to detect replacement;
  - the configured recursive or non-recursive mode.
- Reuse existing Phase 6 or Unix filesystem-identity primitives where possible.
- Do not introduce a second watcher-specific root-identity model.
- Persist the complete deterministic root-evidence set as part of the committed Phase 6 indexing state.
- Prefer the existing metadata infrastructure unless repository inspection proves that a separate schema object is required.

Reconciliation contract:

- At the beginning of a full reconciliation:
  - capture current evidence for all configured directory roots;
  - compare it with the evidence from the last successful commit.
- Reject automatic reconciliation when a previously recorded root:
  - is missing;
  - is inaccessible;
  - resolves to a different canonical root;
  - has a different native root identity;
  - or no longer has the expected directory type.
- Carry the captured root evidence in the Phase 6 reconciliation plan.
- Capture the evidence again after discovery and during stale-plan validation.
- Capture it once more immediately before committing the transaction.
- Reject the plan as stale if the evidence differs at any validation point.
- A rejected plan must leave all previously committed DB and metadata state unchanged.
- Persist updated evidence in the same transaction as the successfully applied reconciliation.

Initialisation and migration:

- When the database contains no indexed files, initialise root evidence automatically on the first successful reconciliation.
- When indexed files exist but committed root evidence is missing, automatic watcher reconciliation must refuse to proceed.
- Existing indexed state without evidence may be adopted only through the explicit manual acceptance path.

Intentional root replacement:

- Add an explicit manual option for accepting changed configured root identities.
- The option must be available only through the normal manual rebuild or reconciliation command, not enabled automatically by the watcher.
- Acceptance permits replacement of the previously persisted identity but does not disable stability checks during the current reconciliation.
- Acceptance of a new root identity must not imply ~allow-empty~.
- Existing zero-input safety remains independent and unchanged.
- The new evidence becomes authoritative only after a successful commit.

Acceptance criteria:

- An unchanged configured root continues through normal no-change reconciliation.
- A root replaced at the same logical path while the watcher was stopped is rejected before indexed data can be removed.
- A partially populated replacement root is also rejected.
- A same-device root inode replacement is detected where supported by the existing Unix identity contract.
- A root changed between initial capture and discovery is rejected as stale.
- A root changed after planning but before commit causes transaction rollback.
- Failure for one configured root rejects the complete reconciliation.
- Normal creation, modification, rename, and deletion of files within an unchanged root continue to work.
- Legitimate deletion of all files within the same unchanged root remains possible under the existing zero-input rules.
- Intentional root replacement succeeds only through the explicit manual acceptance option.
- The watcher never accepts changed root identity automatically.
- Rejection preserves files, headings, bodies, links, FTS state, indexing context, trust metadata, and prior root evidence.
- No Phase 8 parallelism is introduced.

Required tests:

- first reconciliation initialises evidence for an empty database;
- unchanged-root startup uses the normal unchanged path;
- reachable but empty replacement root before startup is rejected;
- partially populated replacement root before startup is rejected;
- same-path and same-device root replacement is rejected;
- one replaced root among multiple configured roots rejects the complete plan;
- root replacement during discovery is rejected;
- root replacement immediately before commit rolls back all DB changes;
- indexed database without root evidence requires explicit adoption;
- explicit acceptance commits the new root evidence;
- explicit acceptance without ~allow-empty~ still respects zero-input safety;
- normal deletion inside an unchanged root continues to work;
- watcher startup reports the root-identity error without modifying the database.
