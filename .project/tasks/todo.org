* CANCEL Feature - ignore single file

Reason for cancelling:

The existing configuration already supports excluding individual files,
directories and path patterns from the indexed source universe. This
covers the current need without introducing a second exclusion mechanism
inside Org files.

A file-level ~#+orgfdb: ignore~ keyword would mainly provide a portable
exclusion that follows the file when it is moved. There is currently no
concrete use case that justifies the additional discovery,
reconciliation and watcher semantics.

Allow an Org file to declare that it must not be included in the
~org-files-db~ index.

Possible syntax:

#+begin_src org
  ,#+TITLE: Private Note
  ,#+ORGFDB: ignore
#+end_src

The keyword would mean that the file is outside the indexed source
universe, even if its path is otherwise included by the configured files
or directories.

Expected semantics would be:

- detect ~#+orgfdb: ignore~ at file level;
- do not store the file or any of its headings, properties, keywords or
  links in the database;
- if an already indexed file gains ~#+orgfdb: ignore~, remove it during
  the next rebuild or reconciliation;
- if the keyword is removed, make the file eligible for indexing again;
- treat links to an ignored file the same way as links to another file
  outside the indexed source universe;
- make watcher/reconciliation behaviour consistent when the keyword is
  added or removed;
- use only the exact ~ignore~ value initially; do not introduce boolean
  aliases or additional ~orgfdb~ options without a separate use case.

Prefer a file-level keyword over a property such as ~VULPEA_IGNORE~,
because ignoring the file is source/indexing metadata rather than heading
metadata.

Evaluate compact representations for repeated presentation data.

Candidate techniques include:

- positional arrays instead of repeated object keys
- shared field schemas emitted once per payload for positional arrays
- omission rules where ~search_text~ and ~display_text~ are identical
- compact semantic role encoding
- removal of data already available through ~result_index~

#+begin_src json

}
#+end_src

The exact representation is not prescribed by this example.

Benchmark alternative representations before selecting the final format.

Do not require the Emacs client to guess the meaning of an array position.

Do not depend only on undocumented positional knowledge in the client.

- define the exact meaning and order of every field
- emit the schema once instead of repeating field names for each object
- keep the schema stable within one wire-format version
- do not silently change positional meanings
- version the wire format if an incompatible positional change is required

If an optional array value is omitted, its meaning must remain unambiguous.

Do not shift later positional values when an earlier optional value is absent unless the wire format defines a separate explicit array shape.

For example, a missing ~display_text~ can use a documented sentinel or another explicit compact representation.

Do not make the client infer whether a value is ~display_text~ or ~role~ from its contents.

Prefer simple wire rules over complex compression logic.

Every compact representation and omission rule must be explicit in the wire-format documentation.

Keep compact field names and positional representations limited to ~presentation-json~.

Keep the normal ~--format json~ contract unchanged.

Do not add JSONL in this task.

Do not add streaming in this task.

Do not add a presentation cache in this task.

Require semantic equality before comparing performance.

Compare at least:

- current object representation
- positional arrays with shared schemas
- useful omission rules
- short object keys where objects remain and the saving is material

Do not keep a compact representation only because its raw JSON is smaller.

Also consider parsing simplicity and complete presentation processing cost.

Measure:

- payload bytes
- serialization time
- presentation processing time
- total CLI time

Record enough information to show which representation provides each reduction.

Update the wire-format documentation after the final representation is selected.

Document:

- every shared schema
- every positional field and its index
- every omission rule
- every sentinel or compact value encoding
- wire-format versioning rules for positional layouts
- which compact rules apply only to ~presentation-json~
