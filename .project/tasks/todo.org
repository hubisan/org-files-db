* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** CONTINUE [#B] Materialize ~effective_properties~ in schema version 10
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: Yes
:API_CONTRACT_CHANGE: No
:END:

Task file: [[file:2026-07-25--materialize-effective-properties-schema-10.org][Materialize effective properties in schema version 10]]

Goal:

- Replace recursive query-time property resolution with a normalized and transactionally maintained ~effective_properties~ projection.
- Treat ~properties~ as the canonical source and ~effective_properties~ as mandatory derived state analogous to ~outline_path~.
- Preserve the complete existing property semantics and public query contract.
- Reduce direct and inherited property query latency to an interactive range.

Measured motivation:

- The 1,000-file benchmark measured approximately 200 ms median for a direct property query.
- The inherited property query required approximately 4.7 seconds median and approximately 5 seconds p95.
- The current SQL repeatedly reconstructs heading lineages, local property summaries, and effective values for every candidate heading.
- The same deterministic values should instead be calculated once when a file is indexed.

*** Design decisions

- Keep ~properties~ as the only canonical property representation.
- Add ~effective_properties~ as a fully rebuildable derived projection.
- Create one row per heading and visible property key.
- Include the synthetic level-0 root heading in the projection.
- Store local, normally effective, and root-excluding effective values in the same row.
- Preserve the distinction between:
  - no local definition;
  - an explicitly empty local definition;
  - no effective value without root participation;
  - an explicitly empty effective value.
- Do not create effective rows from arbitrary keywords.
- Property facts already normalized into ~properties~ from ~#+PROPERTY~, ~#+CATEGORY~, or property drawers participate automatically.
- Keep file-target property queries as direct root-property queries.
- Do not change the public query syntax or JSON result contract.

*** Schema version 10

Add:

#+begin_src sql
CREATE TABLE effective_properties (
    heading_id                   INTEGER NOT NULL,
    file_id                      INTEGER NOT NULL,
    key                          TEXT NOT NULL,
    local_value                  TEXT,
    effective_value              TEXT NOT NULL,
    effective_value_without_root TEXT,

    PRIMARY KEY (heading_id, key),

    FOREIGN KEY (heading_id)
        REFERENCES headings(id)
        ON DELETE CASCADE,

    FOREIGN KEY (file_id)
        REFERENCES files(id)
        ON DELETE CASCADE
);
#+end_src

Column semantics:

- ~local_value IS NULL~ means that the heading has no local definition for the key.
- ~local_value = ''~ means that the heading explicitly defines an empty local value.
- ~effective_value~ contains the resolved value including the level-0 root.
- ~effective_value_without_root IS NULL~ means that no value exists after excluding the level-0 root.
- ~effective_value_without_root = ''~ means that a real heading or real ancestor explicitly resolves the property to an empty value.
- The level-0 root row has ~effective_value_without_root = NULL~.

Add indexes:

#+begin_src sql
CREATE INDEX idx_effective_properties_key_value_heading
ON effective_properties(key, effective_value, heading_id);

CREATE INDEX idx_effective_properties_key_without_root_value_heading
ON effective_properties(key, effective_value_without_root, heading_id)
WHERE effective_value_without_root IS NOT NULL;

CREATE INDEX idx_effective_properties_key_local_value_heading
ON effective_properties(key, local_value, heading_id)
WHERE local_value IS NOT NULL;

CREATE INDEX idx_effective_properties_file
ON effective_properties(file_id);
#+end_src

Schema rules:

- Bump ~CURRENT_SCHEMA_VERSION~ from 9 to 10.
- Include the exact table and explicit indexes in fresh-schema inventory tests.
- Do not depend on SQLite autoindex names.
- Keep all index names deterministic.

*** Property derivation

Extract the existing tested property-resolution rules into one pure derivation component.

Inputs:

- prepared heading tree for one file;
- canonical ~properties~ rows;
- normalized property keys;
- source ordering;
- append flags;
- heading levels and parent relationships.

Outputs:

- one derived row per heading and visible key;
- ~local_value~;
- ~effective_value~;
- ~effective_value_without_root~.

Rules:

- Reuse the existing property semantics rather than defining a new approximation.
- Preserve duplicate handling at one location.
- Preserve the last applicable non-append definition.
- Preserve append order.
- Preserve appends before and after replacement definitions according to the existing contract.
- Preserve append-only definitions.
- Preserve appending to inherited values.
- Preserve explicit empty values and empty append rows.
- Preserve root, ancestor, and current-heading precedence.
- Make the result independent of generated database row IDs.

Algorithm shape:

- Collapse canonical property rows into a local resolved state per heading and key.
- Traverse the heading tree once from root to leaves.
- Carry the parent effective state into each child.
- Apply the local resolved state to obtain the normal effective value.
- Independently carry a state that begins empty below the root to obtain the root-excluding value.
- Emit derived rows only after the values for the heading are complete.
- Keep complexity proportional to the number of headings, property rows, and propagated visible keys in the file.
- Do not perform one upward ancestry traversal per heading.

*** Indexing and transactional maintenance

Use the same effective-property derivation for:

- full rebuild;
- newly created files;
- modified-file replacement;
- schema migration backfill;
- clean-reference rebuilds used by equivalence tests.

Transactional order for a created or replaced file:

- insert the file and headings;
- insert canonical property rows;
- derive effective properties from the prepared file representation;
- map prepared headings to persisted heading IDs;
- insert ~effective_properties~;
- insert or update the remaining derived state;
- commit the complete file replacement.

Rules:

- Derivation and insertion occur inside the controlled replacement transaction.
- A failure rolls back canonical and derived changes together.
- A metadata-only update does not regenerate effective properties.
- Deleting or replacing headings removes derived rows through foreign-key cascades.
- No committed database may contain new canonical property facts with stale effective rows.
- Verifying stale plans must happen before applying any derived state.

*** Migration from schema version 9

Implement a transactional 9-to-10 migration.

Migration steps:

- verify that the database is an expected version-9 database;
- create ~effective_properties~ and its indexes;
- read existing headings and canonical property rows grouped by file;
- reconstruct each file's heading tree from stored parent relationships;
- run the same derivation component used by normal indexing;
- insert all derived rows;
- run foreign-key and projection-integrity checks;
- update the stored schema version only after successful backfill;
- roll back the entire migration on any failure.

Migration constraints:

- Do not require reparsing source Org files.
- Do not silently rebuild the whole database from disk.
- Do not derive values from old query output or serialized JSON caches.
- Existing canonical ~properties~ rows must be sufficient.
- Migration and fresh rebuild must produce identical stable snapshots.

*** Query compiler changes

Heading property queries:

- Default inherited query:

#+begin_src lisp
(property "OWNER" "Alice")
#+end_src

uses ~effective_value~.

- Explicit inherited query:

#+begin_src lisp
(property "OWNER" "Alice" :inherit t)
#+end_src

uses ~effective_value~.

- Local query:

#+begin_src lisp
(property "OWNER" "Alice" :inherit nil)
#+end_src

uses ~local_value~ and requires ~local_value IS NOT NULL~.

- Inherited query excluding the root:

#+begin_src lisp
(property "OWNER" "Alice" :inherit t :without-root t)
#+end_src

uses ~effective_value_without_root~ and requires it to be non-null.

- A key-only query uses the same selected value column but checks existence rather than equality.
- Regexp queries apply the existing regexp function to the selected materialized value.
- Default value matching remains exact and case behaviour remains unchanged.
- SQL parameters remain bound.
- Nested property predicates in hierarchy and link relation queries use the same projection.

Root behavior:

- A root/file result may match a normal inherited property query through its level-0 row.
- A root/file result must not match ~:without-root t~.
- ~:inherit nil~ on the root evaluates its direct root property.
- File-target property queries retain their existing direct-root semantics and reject ~:inherit~.

Remove from normal query execution:

- recursive property lineage CTEs;
- repeated local property aggregation;
- per-candidate effective-value folding;
- repeated temporary ordering for the same property rows.

*** Output and includes

- Preserve the current JSON fields and value semantics.
- Use canonical property rows for explicitly direct/source-oriented property output.
- Use ~effective_properties~ whenever output requires effective property values.
- Do not expose ~local_value~, ~effective_value~, or ~effective_value_without_root~ as new public fields merely because they exist internally.
- Preserve deterministic property ordering.
- Do not change output matching through include options.
