* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** TODO [#B] Materialize effective properties in schema version 10
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: Yes
:API_CONTRACT_CHANGE: No
:END:

Depends on:

- Complete the measured SQLite index-profile decisions for schema version 9.
- Existing effective property semantics and regression tests.

Goal:

- Replace query-time recursive property resolution with a normalized, materialized ~effective_properties~ projection.
- Treat the projection as mandatory derived database state analogous to ~outline_path~, not as an optional cache.
- Preserve all existing property query and output semantics while making direct and inherited property queries suitable for interactive use.

Measured reason:

- The 1,000-file benchmark measured approximately 200 ms for a direct property query and approximately 4.7 seconds median for an inherited property query.
- The current implementation repeatedly reconstructs heading lineages, local property summaries, and effective values inside correlated subqueries.
- Property resolution should instead be performed once when a file is indexed or replaced.

Canonical source contract:

- The existing ~properties~ table remains the canonical source of property facts.
- ~effective_properties~ is derived exclusively from canonical headings and property rows.
- Property drawer rows and property-like keyword rows already normalized into ~properties~ must use identical resolution rules.
- Root property sources include supported ~#+PROPERTY~ declarations, ~#+CATEGORY~, and level-0 property drawer rows.
- Generic keywords such as ~TITLE~ and ~AUTHOR~ must not become properties merely because an effective-property projection exists.
- The separate ~keywords~ table and ~(keyword ...)~ predicate retain their current root/file-level semantics.

Schema:

- Bump the database schema version from 9 to 10.
- Add a normalized ~effective_properties~ table with one row per visible property key and heading.
- Store at least:
  - ~heading_id~
  - ~file_id~
  - normalized ~key~
  - nullable ~local_value~
  - ~effective_value~
  - nullable ~effective_value_without_root~
- Use ~NULL~ for ~local_value~ when the heading does not define the property locally.
- Preserve an explicitly defined empty local value as an empty string rather than ~NULL~.
- Use ~NULL~ for ~effective_value_without_root~ when the key exists only through the file/root context.
- Enforce uniqueness for ~(heading_id, key)~.
- Reference headings and files with foreign keys and cascade derived rows when their owning heading or file is deleted.

Indexes:

- Add an index supporting exact inherited lookups by ~(key, effective_value, heading_id)~.
- Add a partial index supporting direct lookups by ~(key, local_value, heading_id)~ where ~local_value IS NOT NULL~.
- Add a partial index supporting root-excluding lookups by ~(key, effective_value_without_root, heading_id)~ where ~effective_value_without_root IS NOT NULL~.
- Keep index names and the complete schema inventory deterministic and tested.

Resolution semantics:

- Preserve the current key normalization rules.
- Preserve source order where it affects property resolution.
- The last applicable non-append value at one location wins.
- Append rows are combined in their defined source order.
- Append-only local definitions can extend an inherited value.
- A local non-append definition replaces the inherited base before local appends are applied.
- Root, ancestor, and current-heading precedence must remain unchanged.
- Missing values, explicitly empty values, empty bases, and empty append values must remain distinguishable where required by the current semantics.
- Effective resolution must be deterministic and independent of surrogate row IDs.

Derivation:

- Implement property derivation as a pure, testable operation over one prepared file and its heading tree.
- Resolve local property values once per heading and key.
- Walk the tree from root to leaves and propagate effective values downward.
- Calculate both the normal effective value and the effective value with root participation excluded.
- Map the derived rows to stored heading IDs during transactional application.
- Do not execute recursive property SQL once per candidate heading during query execution.

Transactional maintenance:

- Full rebuild and incremental replacement must use the same derivation and insertion path.
- A created or modified file regenerates all of its ~effective_properties~ rows in the same transaction as its headings and canonical properties.
- A deleted file removes its derived rows through the controlled file deletion path.
- A metadata-only change must not regenerate effective properties.
- Any derivation or insertion failure must roll back the complete affected transaction.
- No committed database may contain new canonical property rows with stale effective-property rows.

Migration:

- Add a transactional migration from schema version 9 to 10.
- Create and backfill ~effective_properties~ from existing headings and canonical property rows.
- Do not require reparsing Org files when the existing database contains all required canonical facts.
- Advance the stored schema version only after the table, indexes, and backfill complete successfully.
- Preserve the previous database unchanged when migration fails.

Query compiler:

- Compile ~(property KEY VALUE :inherit nil)~ against ~local_value~.
- Compile the default inherited form against ~effective_value~.
- Compile ~:inherit t :without-root t~ against ~effective_value_without_root~.
- Preserve key-only existence queries, exact value matching, regexp matching, root-result behaviour, and bound SQL parameters.
- Remove the recursive lineage and effective-value CTEs from normal property predicate execution.
- Ensure nested property predicates in relation queries use the same materialized projection.

Output:

- Preserve the existing public JSON contract for included direct and effective properties.
- Load included effective properties from ~effective_properties~ rather than recomputing them.
- Keep direct property output sourced from canonical/local values according to the current include contract.
- Do not expose internal projection columns unless already required by the public API.

Integrity and equivalence:

- Extend semantic database snapshots to include effective properties using stable file paths, heading source positions, keys, and values rather than raw surrogate IDs.
- Verify that every stored effective row references the correct file and heading.
- Verify that no stale or orphaned effective rows survive replacement or deletion.
- Verify that a clean rebuild and an equivalent incremental sequence produce identical effective-property projections.
- Include ~effective_properties~ in foreign-key and derived-state integrity checks.

Tests:

- Cover a direct drawer property.
- Cover a root-level property drawer.
- Cover ~#+PROPERTY~ as a root property source.
- Cover ~#+CATEGORY~ as a root property source and inherited ~CATEGORY~ lookup.
- Cover a generic keyword that remains a keyword and does not become a property.
- Cover root inheritance, parent inheritance, and multiple ancestor levels.
- Cover local replacement of an inherited value.
- Cover append-only local values and append onto an inherited value.
- Cover multiple appends and the last local base definition winning.
- Cover explicit empty values, missing values, empty base plus append, and empty append rows.
- Cover ~:inherit nil~, default inheritance, and ~:without-root t~.
- Cover key-only existence and value matching.
- Cover file creation, modification, metadata-only change, deletion, migration, rollback, and rebuild equivalence.
- Assert that representative property query plans use ~effective_properties~ and no longer contain the recursive property-resolution CTE.
- Run a focused benchmark and record direct and inherited property query latency after the change.

Acceptance criteria:

- Fresh databases use schema version 10.
- Version-9 databases migrate deterministically to version 10.
- Existing property semantics and public output remain unchanged.
- ~#+CATEGORY~ and supported ~#+PROPERTY~ facts participate in effective property resolution.
- Arbitrary root keywords do not silently become properties.
- Direct and inherited property predicates read the materialized projection.
- Full rebuild and incremental replacement maintain the projection transactionally.
- Integrity and semantic-equivalence checks include the new derived table.
- The focused benchmark shows a substantial reduction from the current approximately 200 ms direct and 4.7 second inherited measurements.
- ~make ci~ passes.
