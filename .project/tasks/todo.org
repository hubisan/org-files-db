* Phase 4: Link resolution

Goal of this phase: Resolve stored raw link source facts to known files, file-scoped CUSTOM_ID targets, and indexed Org ID targets.

General rules:

- Resolution never destroys raw link facts.
- Resolution fields stay clearly separated from raw source fields.
- Broken, ambiguous, unresolved, and unsupported targets are represented explicitly.
- Target deletion must not delete source link rows.
- Resolution must not execute link targets.
- Resolution must be deterministic and repeatable.
- Resolution runs after all files, headings, properties, outline paths, and raw links for the rebuild are stored.
- Do not resolve links on demand in read-only CLI commands.
- Do not introduce parallel ~resolved_file_id~ / ~resolved_heading_id~ columns unless the schema contract is deliberately renamed first.

Existing target-ish fields:

- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~

Recommended resolution state fields:

- ~resolution_status~
- ~resolution_diagnostic~

Recommended ~resolution_status~ values:

- ~unresolved~
- ~resolved~
- ~broken~
- ~ambiguous~
- ~unsupported~

Status semantics:

- is ~NULL~ means not attempted
- ~unresolved~ means resolution was attempted but the available universe is not known to be complete.
- ~broken~ means the target is missing inside a known complete context.
- ~ambiguous~ means more than one valid target exists in the applicable context.
- ~unsupported~ means the link form is intentionally not resolved yet.
- ~resolved~ means target fields point to the selected target.

Important distinction:

- ~CUSTOM_ID~ resolution is file-scoped.
- ~id:~ resolution is global in Org semantics and should not be marked broken merely because the ID is absent from the indexed files.
- A missing ~CUSTOM_ID~ can be broken when the target file context is known.
- A missing ~id:~ should be ~unresolved~ unless a complete Org ID location universe is available.

** TODO [#C] Reduce resolver diagnostics
:PROPERTIES:
:PRIORITY: Low
:RISK: Low
:DB_SCHEMA_CHANGE: No
:API_CONTRACT_CHANGE: No
:END:

Depends on:

- [[*Resolve file links with heading-title search options][Resolve file links with heading-title search options]]
- [[*Resolve same-file fuzzy star heading links][Resolve same-file fuzzy star heading links]]

Goal:

- Keep ~resolution_diagnostic~ focused, short, and useful in table output.
- Avoid diagnostics for successful, expected resolver behavior.
- Shorten diagnostics for unsuccessful resolver outcomes.
- Reduce DB noise and output width in manual/debug queries.

Policy:

- ~resolution_diagnostic~ should usually be ~NULL~ when ~resolution_status = resolved~.
- Successful Org-compatible fallback behavior should not store diagnostics.
- Unsuccessful outcomes may store diagnostics, but they should be short and stable.
- Diagnostics should explain the reason category, not the full resolver story.

Resolution diagnostic rules:

- For ~resolved~:
  - set ~resolution_diagnostic = NULL~
  - including duplicate heading matches where the first heading in document order was selected
- For ~broken~:
  - keep a short diagnostic explaining what was missing
- For ~ambiguous~:
  - keep a short diagnostic explaining why no unique target could be selected
- For ~unsupported~:
  - keep a short diagnostic explaining the unsupported link form or resolver scope
- For ~unresolved~:
  - keep a short diagnostic only when it adds useful context

Preferred diagnostic style:

- Use short, stable messages.
- Prefer messages suitable for narrow table output.
- Avoid long explanatory sentences.
- Avoid mentioning implementation internals unless necessary.
- Avoid diagnostics for normal successful resolution.
- Prefer lowercase, no trailing period.

Suggested diagnostics:

- ~heading not found~
- ~same-file heading not found~
- ~duplicate target~
- ~unsupported link type~
- ~unsupported search option~
- ~outside indexed universe~
- ~missing in indexed universe~
- ~unsupported path form~
- ~target file unresolved~
- ~target file broken~

Acceptance criteria:

- Resolved links normally have ~resolution_diagnostic = NULL~.
- Duplicate heading-title matches that select the first heading have ~resolution_status = resolved~ and ~resolution_diagnostic = NULL~.
- Duplicate same-file star heading matches that select the first heading have ~resolution_status = resolved~ and ~resolution_diagnostic = NULL~.
- Broken heading-title search keeps a short diagnostic such as ~heading not found~.
- Broken same-file star heading search keeps a short diagnostic such as ~same-file heading not found~.
- Unsupported fallback keeps a short diagnostic such as ~unsupported link type~.
- Unresolved outside-universe file targets use a short diagnostic such as ~outside indexed universe~.
- Broken in-universe file targets use a short diagnostic such as ~missing in indexed universe~.
- Existing raw link fields remain unchanged.
- Tests are updated to assert the new diagnostic policy.
- ~make ci~ passes.

** TODO Resolve property-based heading links
:PROPERTIES:
:PRIORITY: High
:RISK: High
:DB_SCHEMA_CHANGE: No

:END:

Depends on:

- [[*Implement deterministic link resolution pass after rebuild][Implement deterministic link resolution pass after rebuild]]
- [[*Resolve file links to known indexed files][Resolve file links to known indexed files]]

Goal:

- Resolve heading links that target Org properties such as ~ID~ and ~CUSTOM_ID~.
- Use one shared property-target lookup mechanism with different search scopes and missing-target semantics.

General property lookup model:

- Each resolver case defines:
  - property key
  - property value
  - search scope
  - status for no match
- Exactly one match resolves to a heading.
- Multiple matches are ambiguous.
- No match is either ~broken~ or ~unresolved~, depending on whether the search scope is known to be complete.

Shared matching rules:

- Match against heading properties:
  - ~properties.key~
  - ~properties.value~
- If exactly one matching heading exists:
  - set ~target_heading_id~
  - set ~resolution_status = resolved~
- If multiple matching headings exist:
  - set ~target_heading_id = NULL~
  - set ~resolution_status = ambiguous~
  - set ~resolution_diagnostic~ explaining that multiple headings match the property target.
  - do not choose an arbitrary target.
- Raw link source fields must remain unchanged.

** TODO [#C] Resolve file-only links to synthetic root headings
:PROPERTIES:
:PRIORITY: Low
:RISK: Medium
:DB_SCHEMA_CHANGE: No
:API_CONTRACT_CHANGE: Maybe
:END:

Depends on:

- [[*Resolve file links to known indexed files][Resolve file links to known indexed files]]
- [[*Resolve file links with heading-title search options][Resolve file links with heading-title search options]]
- [[*Resolve same-file fuzzy star heading links][Resolve same-file fuzzy star heading links]]
- [[*Resolve property-based heading links][Resolve property-based heading links]]

Goal:

- Resolve file-only links to the synthetic root heading of the target file.
- Treat the synthetic root heading as the document-level target for links that point to a file but not to a specific heading.
- Make resolved file-only links queryable through both ~target_file_id~ and ~target_heading_id~.
- Apply this as a resolver fallback after all more specific heading-resolution steps.

Contract decision:

- Synthetic root headings are always stored.
- Root-heading targeting is always enabled because synthetic root headings are part of the persisted DB model.
- No user-facing option is introduced.
- More specific heading targets always win over the root fallback.

Supported forms:

- ~[[file:notes.org]]~
- ~[[./notes.org]]~
- ~[[../notes.org]]~
- ~[[/absolute/path/notes.org]]~
- ~<file:notes.org>~
- plain ~file:notes.org~ when extracted by configured plain-link protocols

Resolution rules:

- Apply only to links that:
  - have ~link_type = file~
  - have ~target_file_id~ set
  - have ~resolution_status = resolved~
  - have ~search_option IS NULL~
  - have ~target_heading_id IS NULL~
- Find the synthetic root heading for ~target_file_id~.
- Set ~target_heading_id~ to that root heading.
- Keep ~target_file_id~ unchanged.
- Keep ~resolution_status = resolved~.
- Keep ~resolution_diagnostic = NULL~.
- Keep ~target_custom_id = NULL~.
- Keep ~target_id = NULL~.
- Do not override links that already resolved to a specific heading.
- Do not apply to broken, unresolved, ambiguous, or unsupported links.
- Do not apply to file links with any ~search_option~.

Synthetic root selection rules:

- The root heading must belong to the resolved target file.
- The root heading is identified by the existing synthetic-root contract, for example:
  - ~level = 0~
  - ~parent_id IS NULL~
- If no synthetic root heading exists:
  - leave ~target_heading_id = NULL~
  - keep ~target_file_id~
  - keep ~resolution_status = resolved~
  - set a stable diagnostic only if this is considered DB corruption.
- If multiple synthetic root headings exist for one file:
  - do not pick an arbitrary root heading.
  - mark the link ~ambiguous~ or report a data-integrity diagnostic according to the root-heading contract.

Out of scope:

- Do not create synthetic root headings in this task.
- Do not change parser-level heading semantics.
- Do not map file links with search options to root headings.
- Do not override heading-title, CUSTOM_ID, ID, or fuzzy heading targets.
- Do not resolve attachments.

Acceptance criteria:

- Resolved file-only links set ~target_file_id~ and ~target_heading_id~ to the target file's synthetic root heading.
- File links with ~::*Heading~ are not overwritten by the root heading.
- File links with ~::#custom-id~ are not mapped to root.
- Broken file links do not get root heading targets.
- Unresolved outside-universe file links do not get root heading targets.
- Unsupported links do not get root heading targets.
- Relative, absolute, angle, and plain file-only links are covered by tests where supported by the parser.
- Tests verify that specific heading targets are not overwritten.
- Tests verify raw link fields remain unchanged.
- ~make ci~ passes.
