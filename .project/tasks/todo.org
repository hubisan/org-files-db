Real-world validation:

- The indexer was tested against the user's long-established personal Org corpus.
- The corpus contains approximately 570 Org files accumulated through many years of using Org to organize personal information, tasks, projects, and other areas of life.
- A complete rebuild finished subjectively almost instantly.
- The current sequential implementation therefore already satisfies the practical performance requirement for the primary real-world workload.
- Additional synthetic parser-heavy benchmarks would not address an observed user problem and are not required before closing the phase.

Operational context:

- A complete rebuild is required only for initial database creation, recovery, or indexing-context changes.
- After the initial rebuild, the Phase 7 watcher processes only changed files through the existing incremental reconciliation pipeline.
- Typical watcher batches contain one or only a few changed files and complete effectively instantly for the real-world corpus.
- Parallel parsing would therefore not improve the normal operating path.
- The only potentially affected operation would be an already fast and infrequent full rebuild.

** Known Orgize parsing failures

Orgize currently fails to recognize some valid links whose descriptions contain square brackets.

Example:

#+begin_src org
[[https://medium.com/@Graphling/intro-to-brazilian-jiu-jitsu-modeling-language-bjjml-9dd689ddd048][Intro to Brazilian Jiu-Jitsu Modeling Language [BJJML] | by Graphling | Medium]]
#+end_src

Expected description:

#+begin_example
Intro to Brazilian Jiu-Jitsu Modeling Language [BJJML] | by Graphling | Medium
#+end_example

Orgize may expose the complete source as plain ~TEXT~ rather than as a ~LINK~ node.

Links whose descriptions begin with inactive timestamps are also affected:

#+begin_src org
[[file:../notes/gesundheit/leiden/leiden.org::#3b8e6503-ec59-463b-8f86-66a07d356afc][[2026-03-21 Sa] (circa) Rechte Ferse bei Bouldern angeschlagen]]

[[file:../notes/gesundheit/leiden/2022-12-operation-nasenscheidenwand.org][[2022-12-13 Di] Operation Nasenscheidenwand & Nebenhöhlen]]

[[file:../notes/gesundheit/leiden/leiden.org::#f22e2595-302b-4263-85d5-0394a16ac405][[2026-03-21 Sa] Schmerzen Fuss unten vorne]]
#+end_src

Orgize may expose these as a sequence such as:

#+begin_example
TEXT
TIMESTAMP_INACTIVE
TEXT
#+end_example

instead of one complete link.

Orgize also misclassifies links at the beginning of list items when their target contains ~::~:

#+begin_src org
- [[test.org::Heading]]
- [[test.org::#1]]
#+end_src

The beginning of the link may be interpreted as a descriptive-list tag because of the ~::~ inside the target.

This ordinary paragraph form is recognized correctly and must remain correct:

#+begin_src org
Parsed as link: [[test.org::Heading]]
#+end_src

** Org target escaping rules

The compatibility scanner must follow Org link-target escaping rules.

In the link target, escaping is required for:

- every literal ~[~
- every literal ~]~
- every backslash immediately preceding ~[~ or ~]~
- every backslash at the end of the target

Examples:

#+begin_src org
[[https://www.gnu.org\][Test]]

[[https://www.gnu.org\\][Test]]

[[https://www.gnu.org\]\[brackets need to be escaped \[\] in the path\]][test]]
#+end_src

The scanner must distinguish:

- an escaped closing bracket
- an escaped opening bracket
- a literal final backslash
- a structural target delimiter
- a malformed or incomplete escape sequence

The first example must not be accepted merely by searching forward for the next possible closing brackets.

The second example contains an escaped trailing backslash and must be handled according to GNU Emacs Org semantics.

The third example contains escaped brackets and backslashes in the target and must not terminate prematurely.

Do not implement target parsing with one broad regular expression.

** Description delimiter rules

Descriptions follow different rules from targets.

Square brackets in a description do not generally require target-style escaping.

Examples:

#+begin_src org
[[https://www.gnu.org][Intro to Brazilian Jiu-Jitsu [BJJML]]]

[[file:notes.org::#id][[2026-03-21 Sa] Note]]

[[https://orgmode.org][test [again] oder nicht]]
#+end_src

Expected visible descriptions:

#+begin_example
Intro to Brazilian Jiu-Jitsu [BJJML]
[2026-03-21 Sa] Note
test [again] oder nicht
#+end_example

Do not parse a description as recursively nested Org links.

Nested links are not supported as nested link objects.

Two consecutive closing brackets terminate the described link according to the Org link grammar.

The description scanner must therefore not use arbitrary recursive bracket balancing.

Test ambiguous and malformed inputs:

#+begin_src org
[[https://www.gnu.org][[Test]]]]

[[https://www.gnu.org][[[[[[Test]]]]

[[https://www.gnu.org][[][][]]]]

[[https://orgmode.org][test [[https://test.com]]no more link

[[https://orgmode.org][test [[https://test.com]] me [again] oder nicht ]]
#+end_src

For these inputs:

- follow GNU Emacs Org boundary behaviour
- do not fabricate nested link objects
- do not consume unrelated following text
- preserve trailing text outside the recognized link
- reject incomplete links deterministically
- never panic
- always make forward progress

Goal: Expose a stable database generation that changes only after a successful index update has been committed.

External clients such as ~org-files-db.el~ must be able to determine whether cached query results still represent the current database state without relying only on SQLite file modification times.

The generation is a database-wide monotonic integer.

It changes when a successful indexing operation commits a logical database change.

It does not change when an operation:

- only inspects the database
- finds that no indexed data changed
- starts but fails
- rolls back
- receives a filesystem event before reconciliation
- performs SQLite maintenance without changing the logical index state

** Database schema

Add persistent index-state metadata.

Prefer one dedicated singleton table:

#+begin_src sql
CREATE TABLE index_state (
    singleton       INTEGER PRIMARY KEY CHECK (singleton = 1),
    generation      INTEGER NOT NULL,
    last_indexed_at TEXT NOT NULL
);
#+end_src

Initialize it during schema creation or migration:

#+begin_src sql
INSERT INTO index_state (
    singleton,
    generation,
    last_indexed_at
)
VALUES (
    1,
    0,
    CURRENT_TIMESTAMP
);
#+end_src

The exact timestamp storage format must follow the existing database timestamp conventions.

Do not use a process-local counter.

The value must survive:

- process restarts
- watcher restarts
- rebuilds
- incremental indexing
- opening the database from another client

** Generation semantics

Increment ~generation~ only when the logical indexed state changes successfully.

Examples that increment the generation:

- one or more files are added
- one or more files are replaced after content changes
- one or more indexed files are deleted
- derived link-resolution state changes
- a full rebuild commits a changed index
- an incremental reconciliation commits changes

Examples that do not increment the generation:

- a query
- a search
- a status request
- a watcher batch containing no effective changes
- a rebuild producing the same persisted logical state, where this can be determined
- a failed parse
- a failed database write
- a rolled-back transaction
- an ignored filesystem event
- a watcher debounce cycle before reconciliation
- a SQLite WAL checkpoint

The generation represents committed query-visible database state, not filesystem activity.

** Transactional update

Update the index generation inside the same database transaction as the corresponding index mutation.

Conceptually:

#+begin_src sql
BEGIN;

-- Add, replace, or delete indexed data.
-- Update derived state required by queries.

UPDATE index_state
SET generation = generation + 1,
    last_indexed_at = CURRENT_TIMESTAMP
WHERE singleton = 1;

COMMIT;
#+end_src

The new generation must become visible only when the complete indexing transaction commits.

If any part of the transaction fails:

- roll back all index changes
- do not publish a new generation
- do not update ~last_indexed_at~

A client observing a new generation must be able to assume that the corresponding database state is completely committed and queryable.

** Define logical change detection

Before incrementing the generation, determine whether the operation produced an effective logical change.

Reuse existing change-planning information where possible.

For incremental indexing, a generation change may be based on a non-empty committed plan containing operations such as:

- add
- replace
- delete

If global derived-state maintenance changes persisted query-visible data, that also counts as a logical change.

Do not increment once per file.

Increment once per successfully committed logical batch or operation.

Examples:

#+begin_example
watcher batch modifies 12 files
→ generation increases by 1

full rebuild changes 5,000 rows
→ generation increases by 1

incremental command finds all files unchanged
→ generation remains unchanged
#+end_example

Document the chosen batch boundary.

** Full rebuild behaviour

A full rebuild must preserve monotonic generation semantics.

Do not reset the generation to zero when rebuilding the database contents.

When rebuilding in the existing database:

- retain the current generation
- increment it once after the changed rebuilt state commits

If rebuild creates a completely new database file:

- initialize its generation deterministically
- document that replacing the database file creates a new database identity
- expose enough information for clients to distinguish the replacement from an unchanged older database

Prefer also exposing a persistent database identity.

** Database identity

Add a stable database identifier so clients can distinguish:

- the same database at a newer generation
- a different database that happens to have the same generation
- a newly recreated database file

Conceptually:

#+begin_src sql
ALTER TABLE index_state
ADD COLUMN database_id TEXT NOT NULL;
#+end_src

Or include it in the initial schema:

#+begin_src sql

    singleton       INTEGER PRIMARY KEY CHECK (singleton = 1),
    database_id     TEXT NOT NULL,
    generation      INTEGER NOT NULL,
    last_indexed_at TEXT NOT NULL
);
#+end_src

Generate ~database_id~ once when the database is first initialized.

Use a stable unique value such as a UUID.

Do not change it for ordinary indexing, watcher runs, or rebuilds that preserve the same database.

When a database is recreated from scratch, a new identifier is expected.

External cache keys may then use:

#+begin_example
database_id + generation
#+end_example
