** DONE [2026-06-23 Tue 16:37] Parse properties drawer and file-level properties

[[./archive/2026-06-23--parse-properties-drawer-and-file-level-properties.org]]

Goal:
Extract direct Org properties from property drawers and file-level property declarations, store them as queryable property rows, and attach buffer-level properties to the synthetic level 0 heading.

This task stores direct property definitions only. It does not materialize inherited or effective properties.

Sources:

- buffer-level property drawer before the first regular heading:
  #+begin_src org
    :PROPERTIES:
    :CATEGORY: Level 0 Category Property
    :WHATEVER: test
    :ID: 7dad9b62-a3cc-43ec-a60f-e650bdaeae6d
    :END:
    ,#+TITLE: Test

    ,* Heading level 1
  #+end_src

- heading property drawers:
  #+begin_src org
    ,* Task
    :PROPERTIES:
    :ID: abc
    :CUSTOM_ID: task
    :Effort: 0:30
    :END:
  #+end_src

- file-level property keywords:
  #+begin_src org
    #+PROPERTY: Effort_ALL 0:10 0:30 1:00
    #+PROPERTY: var foo=1
    #+PROPERTY: var+ bar=2
    #+CATEGORY: project
  #+end_src

Implementation notes:

- Prefer Orgize syntax nodes for property drawers and node properties instead of reimplementing Org property drawer parsing with custom regex/FSM logic.
- If Orgize does not parse a malformed drawer as a property drawer, ignore it for this task.
- The parser/DB should store direct source facts. Effective property resolution, inheritance, overwrite semantics, and append resolution are query/API concerns and are explicitly deferred.
- Keep ~keywords~ and ~properties~ separate:
  - ~keywords~ stores raw Org keyword lines such as ~#+TITLE~, ~#+STARTUP~, ~#+PROPERTY~, and ~#+CATEGORY~.
  - ~properties~ stores queryable property definitions.
- Semantic keyword lines may be represented twice:
  - ~#+PROPERTY~ is stored as a raw keyword and additionally as a property with source ~property_keyword~.
  - ~#+CATEGORY~ is stored as a raw keyword and additionally as a property with source ~category_keyword~.
- File-level ~#+PROPERTY~ lines may occur anywhere in the buffer. Store them as properties attached to the synthetic level 0 heading.
- Buffer-level property drawers before the first regular heading are attached to the synthetic level 0 heading.
- Heading property drawers are attached to the corresponding regular heading.
- Keys are normalized before DB insertion by converting to uppercase only. Do not otherwise rewrite key characters.
  - ~drawer_prop~ becomes ~DRAWER_PROP~
  - ~Custom_Id~ becomes ~CUSTOM_ID~
  - ~add-value~ becomes ~ADD-VALUE~
- A trailing ~+~ on a property key is an append operator, not part of the key.
  - ~:var+: value~ becomes key ~VAR~, value ~value~, append = 1.
  - ~#+PROPERTY: var+ value~ becomes key ~VAR~, value ~value~, append = 1.
- Do not compute inherited properties in this task.
- Do not store inherited/effective rows in the ~properties~ table.
- If effective properties are needed later, implement them as SQL/API logic, a view, or a separate cache table.

Suggested schema adjustment:

#+begin_src sql
CREATE TABLE IF NOT EXISTS properties (
    id              INTEGER PRIMARY KEY,
    heading_id      INTEGER NOT NULL,
    key             TEXT NOT NULL,
    value           TEXT,
    source          TEXT NOT NULL CHECK (
                        source IN (
                            'property_drawer',
                            'property_keyword',
                            'category_keyword'
                        )
                    ),
    append          INTEGER NOT NULL DEFAULT 0 CHECK (append IN (0, 1)),
    line_number     INTEGER,
    FOREIGN KEY (heading_id)
        REFERENCES headings(id)
        ON DELETE CASCADE
);
#+end_src

Suggested indexes:

#+begin_src sql
CREATE INDEX IF NOT EXISTS idx_properties_heading_key
ON properties (heading_id, key);

CREATE INDEX IF NOT EXISTS idx_properties_key_value
ON properties (key, value);

CREATE INDEX IF NOT EXISTS idx_properties_id_lookup
ON properties (value)
WHERE key = 'ID';

CREATE INDEX IF NOT EXISTS idx_properties_custom_id_lookup
ON properties (value)
WHERE key = 'CUSTOM_ID';
#+end_src

** TODO Consider safe parsing of Emacs `.dir-locals.el` for Org TODO keywords

Goal:
Decide whether `org-files-db` should support directory-local Org TODO keyword
defaults by safely parsing `.dir-locals.el`.

Possible supported subset:

#+begin_src emacs-lisp
((org-mode . ((org-todo-keywords . ((sequence "TODO(t)" "NEXT(n)" "|" "DONE(d)" "CANCEL(c)"))))))
#+end_src

Rules:

- Parse only data, do not evaluate Emacs Lisp.
- Support only `org-mode` / `nil` entries.
- Support only `org-todo-keywords`.
- Support `sequence` first; optionally `type` later.
- Treat keywords before `|` as open and after `|` as closed.
- Preserve fast-selection keys when supported.
- Ignore or warn on unsupported forms.
- Define precedence separately:
  1. file-local `#+TODO:`
  2. nearest supported `.dir-locals.el`
  3. `config.toml`
  4. built-in defaults

Non-goal:
- Do not execute `.dir-locals.el`.
- Do not support arbitrary Emacs directory-local variables.
