* CANCEL Feature - ignore single file

Reason for cancelling:

The existing configuration already supports excluding individual files,
directories and path patterns from the indexed source universe. This
covers the current need without introducing a second exclusion mechanism
inside Org files.

A file-level ~#+orgfdb: ignore~ keyword would mainly provide a portable
exclusion that follows the file when it is moved. There is currently no
concrete use case that justifies the additional discovery,
reconciliation and watcher semantics.

Allow an Org file to declare that it must not be included in the
~org-files-db~ index.

Possible syntax:

#+begin_src org
  ,#+TITLE: Private Note
  ,#+ORGFDB: ignore
#+end_src

The keyword would mean that the file is outside the indexed source
universe, even if its path is otherwise included by the configured files
or directories.

Expected semantics would be:

- detect ~#+orgfdb: ignore~ at file level;
- do not store the file or any of its headings, properties, keywords or
  links in the database;
- if an already indexed file gains ~#+orgfdb: ignore~, remove it during
  the next rebuild or reconciliation;
- if the keyword is removed, make the file eligible for indexing again;
- treat links to an ignored file the same way as links to another file
  outside the indexed source universe;
- make watcher/reconciliation behaviour consistent when the keyword is
  added or removed;
- use only the exact ~ignore~ value initially; do not introduce boolean
  aliases or additional ~orgfdb~ options without a separate use case.

Prefer a file-level keyword over a property such as ~VULPEA_IGNORE~,
because ignoring the file is source/indexing metadata rather than heading
metadata.

** SQLite variable limit

Respect the actual SQLite runtime limit for bound variables.

Use ~SQLITE_LIMIT_VARIABLE_NUMBER~ as the authoritative connection limit.

Modern SQLite commonly uses a default limit of ~32766~ variables per SQL statement.

Older SQLite versions used a default limit of ~999~.

The runtime limit can also be lower than the compiled default.

Do not hard-code ~900~ as the normal chunk size.

Derive the safe ID capacity from:

#+begin_example
SQLITE_LIMIT_VARIABLE_NUMBER
- parameters used outside the ID list
= available ID parameters
#+end_example

Keep the implementation correct when the runtime limit is smaller.

Add tests that exercise a small configured variable limit.

** Compare SQL strategies

Compare the current chunked ~IN (...)~ strategy with alternatives.

Evaluate at least:

- larger chunks based on the runtime variable limit
- temporary tables for result IDs
- SQLite joins against temporary ID relations
- common table expressions where useful
- fewer enrichment queries with broader joins
- additional persistent or materialized tables where measured query patterns justify them

Do not add a persistent materialized table without benchmark evidence.

For a materialized table, include these costs in the decision:

- rebuild cost
- incremental update cost
- database size
- write amplification
- schema complexity
- query improvement

Prefer database work when SQLite can perform the operation efficiently.

Prefer Rust post-processing when it removes expensive or repeated SQL work without increasing transferred data significantly.

Avoid moving work to Rust only to hide an inefficient SQL access pattern.

** Query shape

Review whether enrichment needs to start from large Rust ID lists.

Where practical, keep the matching result set inside SQLite and join enrichment data to that result set.

Compare:

#+begin_example
query
  -> collect many IDs in Rust
  -> send IDs back through many IN clauses
  -> enrich
#+end_example

with approaches such as:

#+begin_example
query result relation
  -> join enrichment data in SQLite
  -> return complete result data
#+end_example

Keep one database snapshot for one query response.

Do not change public query semantics.

Do not change the existing ~--format json~ contract.

Do not add presentation caching in this task.

Do not add presentation parallelism in this task.
