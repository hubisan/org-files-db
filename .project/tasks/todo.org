* Phase 4: Link resolution

Goal of this phase: Resolve stored raw link source facts to known files, file-scoped CUSTOM_ID targets, and indexed Org ID targets.

General rules:

- Resolution never destroys raw link facts.
- Resolution fields stay clearly separated from raw source fields.
- Broken, ambiguous, unresolved, and unsupported targets are represented explicitly.
- Target deletion must not delete source link rows.
- Resolution must not execute link targets.
- Resolution must be deterministic and repeatable.
- Resolution runs after all files, headings, properties, outline paths, and raw links for the rebuild are stored.
- Do not resolve links on demand in read-only CLI commands.
- Do not introduce parallel ~resolved_file_id~ / ~resolved_heading_id~ columns unless the schema contract is deliberately renamed first.

Existing target-ish fields:

- ~path_absolute~
- ~target_file_id~
- ~target_heading_id~
- ~target_custom_id~
- ~target_id~

Recommended resolution state fields:

- ~resolution_status~
- ~resolution_diagnostic~

Recommended ~resolution_status~ values:

- ~unresolved~
- ~resolved~
- ~broken~
- ~ambiguous~
- ~unsupported~

Status semantics:

- ~unresolved~ means resolution was attempted but the available universe is not known to be complete.
- ~broken~ means the target is missing inside a known complete context.
- ~ambiguous~ means more than one valid target exists in the applicable context.
- ~unsupported~ means the link form is intentionally not resolved yet.
- ~resolved~ means target fields point to the selected target.

Important distinction:

- ~CUSTOM_ID~ resolution is file-scoped.
- ~id:~ resolution is global in Org semantics and should not be marked broken merely because the ID is absent from the indexed files.
- A missing ~CUSTOM_ID~ can be broken when the target file context is known.
- A missing ~id:~ should be ~unresolved~ unless a complete Org ID location universe is available.

- Resolve after all pending files are indexed in the rebuild transaction.

- Prefer a small resolver module over spreading resolution SQL through the indexer.

Suggested shape:

#+begin_src rust

#+end_src

Resolver responsibilities:

- Reset previous resolution fields for all links before resolving.
- Resolve supported link types in deterministic order.
- Mark unsupported link forms as ~unsupported~.
- Mark missing targets as ~broken~ only when the target context is known to be complete.
- Mark duplicate matches as ~ambiguous~.
- Mark missing global Org IDs as ~unresolved~ unless a complete Org ID location universe is available.
- Never modify raw source-fact fields.
- Never execute link targets.

Acceptance criteria:

- Rebuild remains transactional.
- Resolution sees all files from the current rebuild.
- Running rebuild twice produces the same resolution fields.
- Resolver updates only target/resolution fields.
- Tests cover cross-file resolution where the target file is indexed after the source file.
- Tests cover repeat rebuild consistency.
- Tests cover unsupported link types staying as stored raw facts with ~resolution_status = unsupported~.
- Tests verify raw link fields are unchanged after resolution.

- Existing ~search_option~ values remain unchanged.

** TODO [#A] Resolve attachment links where the attachment base is known
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:DB_SCHEMA_CHANGE: Maybe
:API_CONTRACT_CHANGE: Maybe
:END:

Depends on:

- [[*Resolve file links to known indexed files][Resolve file links to known indexed files]]
- [[*Resolve Org ID links within indexed ID universe][Resolve Org ID links within indexed ID universe]]

Goal:

- Resolve ~attachment:~ links to known indexed files when the attachment base directory can be derived safely.

Background:

- Org attachment resolution depends on Org attachment settings and heading context.
- Attachments may be based on heading ~ID~.
- Attachment behavior may also depend on configured attachment directories.
- The resolver must not guess a global attachment path without a defined contract.

Supported initial scope:

- Resolve only attachment links whose base directory can be derived from indexed data.
- Resolve only to files already known in the ~files~ table.
- Do not scan arbitrary attachment directories in this task.
- Do not add non-Org attachment files to the DB in this task.
- If the attachment base cannot be determined, mark the link as ~unsupported~.
- If the attachment base is known but the target is not an indexed file, mark it as ~broken~.

Resolution rules:

- Determine the source heading for the attachment link.
- Determine the attachment base for that heading using the supported attachment contract.
- Join the attachment base with the raw attachment path.
- Normalize the resulting absolute path.
- Store the normalized path in ~path_absolute~.
- If the normalized path matches an indexed row in ~files.path~:
  - set ~target_file_id~
  - set ~resolution_status = resolved~
- If the attachment base is known but no indexed file matches:
  - set ~target_file_id = NULL~
  - set ~resolution_status = broken~
  - set ~resolution_diagnostic~ explaining that the attachment target is not indexed or missing.
- If the attachment base cannot be derived:
  - set ~target_file_id = NULL~
  - set ~resolution_status = unsupported~
  - set ~resolution_diagnostic~ explaining that this attachment form is not supported yet.

Acceptance criteria:

- Supported attachment-base rules are documented before implementation.
- Attachment links with known base and indexed target resolve to ~target_file_id~.
- Attachment links with known base and missing target are marked ~broken~.
- Attachment links without derivable base are marked ~unsupported~.
- Attachment resolution does not scan arbitrary directories.
- Attachment resolution does not add non-indexed files to the DB.
- Attachment resolution does not execute or open targets.
- Tests cover resolved, broken, and unsupported attachment links.
- Tests cover attachment links attached to the correct source heading.

Goal:

- Resolve heading links that target Org properties such as ~ID~ and ~CUSTOM_ID~.
- Use one shared property-target lookup mechanism with different search scopes and missing-target semantics.

General property lookup model:

- Each resolver case defines:
  - property key
  - property value
  - search scope
  - status for no match
- Exactly one match resolves to a heading.
- Multiple matches are ambiguous.
- No match is either ~broken~ or ~unresolved~, depending on whether the search scope is known to be complete.

Shared matching rules:

- Match against heading properties:
  - ~properties.key~
  - ~properties.value~
- If exactly one matching heading exists:
  - set ~target_heading_id~
  - set ~resolution_status = resolved~
- If multiple matching headings exist:
  - set ~target_heading_id = NULL~
  - set ~resolution_status = ambiguous~
  - set ~resolution_diagnostic~ explaining that multiple headings match the property target.
  - do not choose an arbitrary target.
- Raw link source fields must remain unchanged.

  - ~target_heading_id = NULL~
  - ~target_id~ to the raw ID target if useful for diagnostics.
  - ~resolution_status = ambiguous~

Acceptance criteria:

- ~id:foo~ resolves when exactly one indexed heading has ~:ID: foo~.
