* Phase 5: Query engine and optional full-text search

Goal of this phase:

- Build a small, safe query layer for indexed Org graph data.
- Implement the Query Model v0 contract defined in [[file:../../docs/reference/query-model-v0.org][Query Model v0 Specification]].
- Keep the query model independent from CLI and SQL.
- Support headings, links, and files as explicit query targets.
- Keep full-text search optional and separate from the core query model.
- Return stable JSON that is useful for Emacs/editor integrations.

General rules:

- Query AST/model is independent of CLI and SQL.
- SQL generation must use bound parameters.
- Query execution uses the persisted database, not parser re-analysis.
- Query target is explicit through ~(headings ...)~, ~(links ...)~, and ~(files ...)~.
- Bare predicates are shorthand for heading queries only at the top level.
- Nested relation queries must use explicit target wrappers.
- Query output mode must not change match semantics.
- Include options may enrich results but must not change which objects match.
- Direct parsed facts and effective/derived semantics must stay clearly separated.
- Query results must include enough location data for editor jumps.
- Body text search must fail clearly when body text is unavailable.
- FTS5 is optional and must only be required for FTS-specific functionality.
- Mutation and repair operations are out of scope for Query Model v0.

** TODO Resolve appended property values for query matching
:PROPERTIES:
:PRIORITY: Medium
:RISK: Medium
:DB_SCHEMA_CHANGE: No
:API_CONTRACT_CHANGE: Yes
:END:

Goal:

- Preserve property rows exactly as indexed.
- Resolve rows marked with ~append = 1~ into an effective property value when evaluating property queries.
- Support append semantics for:
  - file-level ~#+PROPERTY~ keywords
  - heading property drawers
- Use resolved values for property predicate matching and effective property output.
- Do not replace the existing raw property rows with precomputed combined rows.

Current storage:

File-level property keywords:

#+begin_src org
,#+PROPERTY: keyword_append foo=1
,#+PROPERTY: keyword_append+ bar=2
#+end_src

are stored as:

#+begin_src text
KEYWORD_APPEND | foo=1 | append = 0
KEYWORD_APPEND | bar=2 | append = 1
#+end_src

Heading drawer properties:

#+begin_src org
,* Task with append operator in drawer
:PROPERTIES:
:add-value: is
:add-value+: valid
:END:
#+end_src

are stored as:

#+begin_src text
ADD-VALUE | is    | append = 0
ADD-VALUE | valid | append = 1
#+end_src

This raw representation is correct and must remain unchanged.

Required effective values:

#+begin_src text
KEYWORD_APPEND = foo=1 bar=2
ADD-VALUE = is valid
#+end_src

Resolution order:

- Resolve property rows in source order.
- Use ~line_number~ as the primary source-order field.
- Use property row ~id~ as a stable secondary ordering field where necessary.
- Match keys using their normalized property key.

Local resolution algorithm:

- Start without an effective value for the property key.
- For a row with ~append = 0~:
  - replace the current effective value with the row value
- For a row with ~append = 1~:
  - append the row value to the current effective value
  - separate non-empty components with one space
- If an append row has no preceding effective value, initialize the value with the appended row value.
- Preserve the contents of each stored value.
- Do not split or reinterpret values such as ~foo=1~.

Examples:

#+begin_src text
VALUE = first, append = 0
VALUE = second, append = 1
VALUE = third, append = 1

effective VALUE = first second third
#+end_src

#+begin_src text
VALUE = first, append = 0
VALUE = replacement, append = 0
VALUE = final, append = 1

effective VALUE = replacement final
#+end_src

#+begin_src text
VALUE = first, append = 1

effective VALUE = first
#+end_src

Empty values:

- Do not introduce leading, trailing, or duplicate separator spaces solely because a component is empty.

Examples:

#+begin_src text
VALUE = "", append = 0
VALUE = valid, append = 1

effective VALUE = valid
#+end_src

#+begin_src text
VALUE = valid, append = 0
VALUE = "", append = 1

effective VALUE = valid
#+end_src

Duplicate non-append rows:

Given:

#+begin_src org
,#+PROPERTY: keyword_overwritten_by_second invalid
,#+PROPERTY: keyword_overwritten_by_second valid
#+end_src

the raw rows remain preserved, while the effective value is:

#+begin_src text
KEYWORD_OVERWRITTEN_BY_SECOND = valid
#+end_src

A later row with ~append = 0~ replaces the previous local effective value.

Direct property queries:

- ~:inherit nil~ means only property rows stored directly on the candidate object participate.
- Append resolution still applies among those direct rows.
- A file/root candidate uses property rows stored on its synthetic level-0 heading.
- A real heading candidate uses rows stored directly on that heading.

Example:

#+begin_src lisp
(headings
  (property "ADD-VALUE" "is valid" :inherit nil))
#+end_src

Expected:

- the heading containing the property drawer matches
- an exact query for only ~"valid"~ does not match
- an exact query for ~"is valid"~ matches

Root property query:

#+begin_src lisp
(headings
  (property "KEYWORD_APPEND" "foo=1 bar=2" :inherit nil))
#+end_src

Expected:

- the file/root object matches
- real headings do not match through inheritance because ~:inherit nil~ is used

Inherited property queries:

- With ~:inherit t~, resolve local effective values before applying inheritance.
- Root-level appended properties participate in inheritance like other effective root properties.
- Real headings inheriting:

#+begin_src text
KEYWORD_APPEND = foo=1 bar=2
#+end_src

must match:

#+begin_src lisp
(property "KEYWORD_APPEND" "foo=1 bar=2" :inherit t)
#+end_src

- To exclude the root result while preserving inheritance from the root, combine the query with ~(level > 0)~:

#+begin_src lisp
(headings
  (and
    (level > 0)
    (property "KEYWORD_APPEND" "foo=1 bar=2" :inherit t)))
#+end_src

Inheritance precedence:

- Resolve append operations locally for each file/root object or real heading.
- Apply normal property inheritance after local resolution.
- The nearest local effective definition wins.
- Do not concatenate effective values across unrelated hierarchy levels.

Example:

#+begin_src org
:PROPERTIES:
:VALUE: root
:END:

,* Parent
:PROPERTIES:
:VALUE: parent
:VALUE+: appended
:END:

,** Child
#+end_src

Local effective values:

#+begin_src text
root VALUE   = root
parent VALUE = parent appended
child VALUE  = undefined
#+end_src

With ~:inherit t~, the child inherits:

#+begin_src text
VALUE = parent appended
#+end_src

It must not inherit:

#+begin_src text
VALUE = root parent appended
#+end_src

Property predicate behavior:

- Property existence queries use the resolved presence of the key.
- Property value queries compare against the resolved value.
- Exact matching compares against the complete resolved value.
- Non-exact matching applies the existing string matching mode to the resolved value.
- Existing case-handling and key-normalization rules remain unchanged.
- Queries must not match an individual raw component when the effective value is a combined value, unless the selected non-exact matching mode independently permits it.

Examples:

#+begin_src lisp
(headings
  (property "ADD-VALUE" "is valid" :exact t :inherit nil))
#+end_src

matches the drawer heading.

#+begin_src lisp
(headings
  (property "ADD-VALUE" "valid" :exact t :inherit nil))
#+end_src

does not match because the effective value is ~is valid~.

Output behavior:

- Raw property output must continue to expose the original rows and their ~append~ flags.
- Effective property output must expose the resolved value once per effective property key.
- Do not silently replace raw records with one synthetic record.
- Clearly distinguish raw property rows from resolved effective properties in result hydration.
- Includes must not change whether a candidate matches.

Implementation requirements:

- Implement one shared property resolver used by:
  - direct property query matching
  - inherited property query matching
  - root/file property matching
  - effective property hydration
- Do not duplicate concatenation logic across several SQL compiler branches.
- Resolve values deterministically using source order.
- Do not rely on incidental SQLite row order.
- Preserve bound SQL parameters.
- Keep validation separate from SQL generation.
- Ensure file/root candidates and real heading candidates use identical local resolution semantics.
- Preserve all raw database rows and append flags.
- Do not add a schema migration.

Documentation:

- Update ~docs/reference/query-model-v0.org~.
- Update ~docs/cli.org~.
- Document that:
  - raw property rows preserve append operations
  - property predicates operate on resolved values
  - a non-append row replaces the current local value
  - an append row concatenates its value using one separating space
  - append resolution happens locally before inheritance
  - ~:inherit nil~ still resolves direct append rows
  - ~:inherit t~ applies inheritance to locally resolved values
  - raw and effective property output are distinct
