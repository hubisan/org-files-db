* Phase 3: Org link extractor

** Goal of this phase
:PROPERTIES:
:VISIBILITY: folded
:END:

Extract Org links as raw source facts and store them in SQLite without depending on Orgize's link support being complete. Link resolution to files, headings, IDs, CUSTOM_IDs, org-id-locations, dedicated targets, or relationship graphs belongs to later phases.

Core rules:

- Store source facts only.
- Do not resolve link targets in Phase 3.
- Do not execute action-like links such as ~shell:~ or ~elisp:~.
- Keep raw link text and byte ranges as the source of truth.
- Use Orgize for document structure where useful, but do not rely on Orgize as the source of link-token truth.
- Implement a project-owned raw-text scanner for link tokens.
- Bracket links and angle links are syntax-driven.
- Plain links are protocol-list-driven.
- Bracket links, angle links, and configured plain links are the supported Phase 3 link formats.
- Radio targets are not supported.
- Link abbreviations are not supported.
- Relationship markers in descriptions are not supported.
- Multi-line bracket and angle links are not supported.
- Dedicated targets such as ~<<target>>~ are not stored as link facts.
- Links outside regular headings attach to the synthetic level-0/root heading.
- Links should always have a ~heading_id~; missing root attachment is an indexing invariant violation.
- User-facing CLI output must expose enough source location data for editor jumps.

** Phase 3 link extraction contract
:PROPERTIES:
:CUSTOM_ID: phase3-link-contract
:VISIBILITY: folded
:END:

This is the contract that implementation, tests, storage, rebuild, and CLI tasks must follow.

*** Source-fact contract

- Link extraction is source-fact extraction only.
- No link target resolution happens in Phase 3.
- Raw source text and byte ranges are the source of truth.
- Link targets are never executed, evaluated, shell-expanded, or used as SQL/code.
- All link fields must be written through parameterized SQL statements.
- Raw link content must not be interpolated into SQL strings.

*** Supported formats

Supported ~format~ values:

- ~bracket~
- ~angle~
- ~plain~

Dedicated targets are not represented as a ~format~ value.

*** Bracket links

Supported:

- ~[[target]]~
- ~[[target][description]]~

Rules:

- If bracket syntax is valid, extract the link.
- Explicit typed targets store the prefix before the first ~:~ as ~link_type~.
- Unknown explicit types are preserved as their ASCII-lowercase prefix.
- The target part is stricter than the description part.
- The description part is permissive.
- In the description part, arbitrary characters may appear, including unescaped ~[~ and ~]~.
- Nested-looking bracket sequences in descriptions are allowed.
- A bracket link closes only at the first valid same-line ~]]~ delimiter.
- Multi-line bracket links are not supported.
- If a bracket link would require crossing a newline to close, treat it as not-a-link and continue scanning.

Minimal classification for targets without explicit type:

- ~[[#custom-id]]~ => ~link_type = custom-id~
- ~[[*Heading]]~ => ~link_type = fuzzy~
- ~[[dedicated]]~ => ~link_type = fuzzy~

Implicit file bracket links:

- Classify as file-like only when the target starts with:
  - ~./~
  - ~../~
  - ~/~
  - ~/~ 
- ~[[notes.org]]~ remains fuzzy, not file.

Examples:

#+begin_src org
  [[target]]
  [[target][description]]
  [[file:notes.org]]
  [[./notes.org]]
  [[../notes.org]]
  [[~/notes.org]]
  [[/tmp/notes.org]]
  [[#custom-id]]
  [[*Heading]]
  [[dedicated]]
  [[unknown:foo]]
  [[shell:ls]]
#+end_src

*** Angle links

Supported:

- ~<type:path>~

Rules:

- Angle links are syntax-driven.
- The type is the substring before the first ~:~.
- The type does not need to be predefined.
- Unknown explicit types are preserved as their ASCII-lowercase prefix.
- The closing ~>~ must be on the same line.
- Spaces inside the path are allowed.
- If an angle link would require crossing a newline to close, treat it as not-a-link and continue scanning.
- Angle links are extracted by the project scanner, regardless of whether Orgize exposes them.

Examples:

#+begin_src org
  <https://example.com/some path with spaces>
  <file:~/code/main.c::255>
  <jira:ABC-123>
  <unknown:foo>
  <shell:ls *.org>
#+end_src

*** Plain links

Supported:

- ~type:path~

Rules:

- Plain links are protocol-list-driven.
- Plain links are extracted only when ~type~ is enabled through the plain-link protocol configuration.
- Orgize plain-link support is not part of the contract.
- Plain links stop at whitespace or another hard delimiter.
- Deterministic trailing punctuation is trimmed from the stored link span.

Trimmed trailing punctuation for plain links:

- ~.~
- ~,~
- ~;~
- ~:~
- ~!~
- ~?~
- ~)~
- ~]~
- ~}~

The stored ~raw~, ~byte_start~, and ~byte_end~ refer to the final trimmed link span.

Examples:

#+begin_src org
https://example.org
file:notes.org
id:abc123
mailto:person@example.org
jira:ABC-123
#+end_src

*** Link config contract

Final Phase 3 config contract:

#+begin_src toml
  [links]
  plain_protocols = [
    "http",
    "https",
    "file",
    "file+sys",
    "file+emacs",
    "ftp",
    "news",
    "mailto",
    "help",
    "info",
    "shortdoc",
    "id"
  ]

  custom_protocols = []
  parse_property_drawers = true
  parse_keyword_values = false
#+end_src

Config semantics:

- Missing ~plain_protocols~ uses the default list.
- ~plain_protocols = []~ disables the default plain-link protocols only.
- ~custom_protocols~ remains active even when ~plain_protocols = []~.
- Effective plain-link protocols are ~plain_protocols + custom_protocols~.
- To disable all plain-link extraction, set both:
  - ~plain_protocols = []~
  - ~custom_protocols = []~
- ~custom_protocols~ affects plain-link detection only.
- ~custom_protocols~ does not affect bracket links.
- ~custom_protocols~ does not affect angle links.
- Bracket links and angle links do not require their protocol/type to be listed in config.
- Bracket links with unknown explicit types are still extracted.
- Angle links with unknown explicit types are still extracted.
- Action-like protocols such as ~shell~ and ~elisp~ are not enabled by default for plain links.
- Action-like protocols may still be stored when they occur in bracket or angle syntax.
- Action-like protocols are never executed.

*** Search option splitting

Split ~path::search_option~ only for file-like links.

File-like links include:

- explicit ~file~
- explicit ~file+sys~
- explicit ~file+emacs~
- implicit file bracket links starting with ~./~, ~../~, ~~/~, or ~/~

Rules:

- Split at the first ~::~.
- Preserve ~raw~ and ~raw_target~ unchanged.
- Store ~path~ and ~search_option~ separately.
- Do not validate the search option.
- Do not resolve the search option.
- Do not split search options for ~id~, ~attachment~, ~docview~, or arbitrary custom types in Phase 3.

Examples:

#+begin_src org
  [[file:~/code/main.c::255]]
  [[file:~/xx.org::*My Target]]
  [[file:~/xx.org::#my-custom-id]]
  [[file:~/xx.org::/regexp/]]
  [[file:::find me]]
  [[./org-test-links.org::10]]
  <file:~/code/main.c::255>
  file:~/code/main.c::255
#+end_src

*** Unsupported forms

Not supported in Phase 3:

- Radio targets.
- Link abbreviations.
- Multi-line bracket links.
- Multi-line angle links.
- Relationship markers in descriptions.
- Dedicated targets as link facts.

Dedicated target policy:

- ~<<target>>~ is not stored as a link fact.
- Dedicated target indexing, if needed, belongs to a separate target/source-fact feature.
- ~[[target]]~ links pointing to dedicated targets are still stored as fuzzy bracket links.

Relationship marker policy:

- Relationship markers in descriptions are not part of the Phase 3 link syntax contract.
- No relation column or relation table is added in Phase 3.
- ~raw_description~ is preserved exactly, but no relationship syntax is parsed.

*** Ignored regions

Ignore links inside:

- Verbatim markup.
- Code markup.
- Source blocks.
- Inline source forms where reliably detectable.
- Example blocks.
- Colon example lines.
- Comment blocks.
- Comment lines.
- Export blocks.
- Inline export forms where reliably detectable.
- File-level keywords, including ~#+PROPERTY~.

Examples of ignored regions:

#+begin_src org

  Inside ~https://orgmode.org~
  Inside =https://orgmode.org=

  ,#+BEGIN_SRC emacs-lisp
    [[https://www.example.com][no real link]]
    https://www.example.com
  ,#+END_SRC

  src_elisp{"https://orgmode.org"}

  ,#+BEGIN_EXAMPLE
    [[https://www.example.com][no real link]]
    https://www.example.com
  ,#+END_EXAMPLE

  : [[https://www.example.com][no real link]]
  : https://www.example.com

  ,#+BEGIN_COMMENT
  [[https://orgmode.org][link in comment block]]
  ,#+END_COMMENT

  # [[mailto:emacs-orgmode@gnu.org]]
  # file:src/
  # [[https://orgmode.org]]

  ,#+BEGIN_EXPORT HTML
  https://orgmode.org
  [[https://orgmode.org][link in html block]]
  ,#+END_EXPORT

  @@html:https://orgmode.org@@

  ,#+TITLE: https://orgmode.org
  ,#+AUTHOR: https://orgmode.org
  ,#+PROPERTY: link_to_ignore https://orgmode.org
#+end_src

*** Source context

Every stored link fact has a ~source_context~.

Required values for Phase 3:

- ~normal~
- ~heading~
- ~property_drawer~
- ~drawer~
- ~verse_block~
- ~quote_block~
- ~center_block~
- ~justify_block~

Rules:

- Links in property drawers are deliberately parsed and stored with ~source_context = property_drawer~.
- Links in normal drawers are deliberately parsed and stored with ~source_context = drawer~.
- Phase 3 does not store ~drawer_name~.
- Phase 3 does not store ~property_name~.

*** Byte and line semantics

- ~byte_start~ and ~byte_end~ are zero-based half-open byte ranges: ~[byte_start, byte_end)~.
- ~line~ is 1-based for editor jumps.
- No column field is required in Phase 3.

*** Heading/root behavior

- Links are attached to the containing heading.
- Links before the first regular heading attach to the synthetic level-0/root heading.
- Links should always have a ~heading_id~.
- Root links are always included in CLI/API output.
- Root links use ~heading_level = 0~.
- Root links use an empty ~heading_path~, following the existing heading JSON convention.
- If a link cannot be attached to any heading including root, that is an indexing invariant violation.

*** Orgize dependency boundary

- Orgize is used for structural context where reliable:
  - headings
  - sections
  - drawers
  - blocks
  - ignored ranges
- Orgize link nodes are optional cross-checks.
- Orgize link nodes are not the project contract.
- If Orgize detects a link that the scanner intentionally does not support, the scanner contract wins.
- If the scanner detects a supported link that Orgize misses, the scanner contract wins.
- Code should avoid depending directly on unstable Orgize internals.
- Use a local adapter around Orgize-derived structure.

Known Orgize mismatch policy:

- Plain links may appear as plain text in Orgize because plain-link recognition depends on known link types.
- Angle-link support may be incomplete or absent.
- Property drawer links may not appear as link nodes even though they work as links in Org usage.
- Multi-line and permissive-description edge cases may differ from Org behavior.
- These cases should not block Phase 3.
- The project scanner handles supported link syntax directly.

Relevant Orgize issues to reference in project notes:

- https://github.com/PoiScript/orgize/issues/88
- https://github.com/PoiScript/orgize/issues/91

Upstream policy:

- Report general Orgize parser correctness issues upstream with minimal reproducible examples.
- Do not report project-specific indexing policy as Orgize bugs.
- Do not block Phase 3 on upstream fixes.
- Keep local scanner/adapter behavior documented and tested.

Friendly-fork policy:

- A friendly fork is a last resort only.
- Fork only if:
  - the fix belongs generally in Orgize,
  - the patch is small and well-tested,
  - a reasonable upstream attempt was made,
  - upstream remains inactive,
  - maintaining a fork is cheaper than keeping the behavior isolated locally.
- Do not fork or vendor Orgize changes as part of Phase 3 unless a separate task explicitly accepts that cost.
