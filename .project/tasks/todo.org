* Phase 6: Robust incremental indexer core

Goal of this phase:

- Turn the current all-or-nothing rebuild into a deterministic indexing core that can discover, classify, prepare, replace, and remove files without requiring a watcher.
- Keep full rebuild as a complete recovery path while making the same per-file preparation and DB write primitives reusable by later incremental entry points.
- Leave Phase 7 responsible for filesystem events and Phase 8 responsible for parallel execution rather than duplicating indexing semantics there.

Existing groundwork:

- ~discover_org_files~ already supports explicit files, per-directory recursive or non-recursive discovery, canonical-path deduplication, and deterministic ordering.
- The current rebuild reads and parses every discovered file before opening one all-or-nothing DB transaction.
- The ~files~ table already stores ~mtime_ns~, ~size~, optional ~content_hash~, and ~indexed_at~.
- ~DbWriter::rebuild_file~ and ~DbWriter::delete_file_data~ exist only as test scaffolding and do not yet maintain production FTS or link-resolution state.
- The current FTS maintenance and ~LinkResolver::resolve_all~ operations are global. Phase 6 may keep them global initially, but they must run at the correct transaction boundary.

General rules:

- File reading, hashing, TODO keyword resolution, parsing, and normalization happen outside DB write transactions.
- DB mutation and all required derived-state reconciliation happen inside controlled transactions.
- Discovery policy, file eligibility, and indexed-universe semantics must be reusable by Phase 7.
- Full rebuild and incremental reconciliation must use the same normalized per-file write path.
- A successful indexing operation must not expose stale ~outline_path~, trusted ~heading_fts~, search metadata, or link-resolution snapshots.
- Full rebuild and incremental reconciliation over the same final source set must produce semantically equivalent stored facts. Any exclusions such as ~indexed_at~ or surrogate row IDs must be explicit and documented.
- Changes to parser/indexer semantics or parse-affecting configuration must invalidate change-detection decisions safely; unchanged file bytes alone are not sufficient.
- Targeted link resolution and incremental FTS optimization may be deferred, but correctness may not be deferred. A global reconciliation pass is acceptable initially.
- Watcher integration, debounce, and parallel parsing remain out of scope for this phase.

** Tune SQLite indexes from measured query plans

Goal: Add, remove, or change indexes only where the performance baseline demonstrates a useful workload improvement.

Acceptance criteria:

- Existing indexes are reviewed for actual planner use, redundancy, storage cost, and write cost before new indexes are proposed.
- Every candidate change is tied to a measured query or a clearly documented expected production workload.
- Before and after results include ~EXPLAIN QUERY PLAN~, latency, result count, database size, and rebuild or incremental-write cost.
- Improvements are measured against the same reproducible corpus and environment used by the baseline.
- Typical exact-match predicates and relation joins are distinguished from substring and regexp predicates that ordinary B-tree indexes cannot accelerate directly.
- Candidate indexes that do not provide a meaningful measured benefit are rejected and documented.
- Redundant or unused indexes may be removed only when measurements and planner inspection support the change.
- Persistent index changes bump ~CURRENT_SCHEMA_VERSION~.
- Persistent index changes include migration tests and fresh-schema tests.
- FTS-specific tuning remains conditional on FTS5 support.
- FTS tuning does not weaken existing trust-metadata and rebuild-equivalence contracts.
- The accepted index set contains no known redundant index without a documented reason.
- Final before and after measurements, accepted changes, rejected candidates, and limitations are documented so later work does not repeat the same experiments.

Goal:

- Fix the comparability defects discovered in the completed 1,000-file index-profile benchmark before making any production index decisions.

Context:

- A relative benchmark ~--work-dir~ caused the ~file-path~ and ~file-dir~ workloads to use relative paths while the production index stored canonical absolute paths.
- The affected positive lookup workloads therefore returned zero results.
- Corpus directory names currently contain profile IDs of different lengths.
- Because absolute source paths are stored in the database, those different directory-name lengths contaminate whole-database size comparisons between profiles.
- The benchmark must remain a measurement-only facility.
- Production schema version 8 and all candidate decisions must remain unchanged.

Implementation:

- Resolve the supplied benchmark work directory to a canonical absolute path before creating any corpus directories, databases, workload expressions, or recorded command paths that depend on it.
- Ensure that ~file-path~ and ~file-dir~ workload parameters use the same canonical absolute path representation stored by the production indexing path.
- Replace profile-derived corpus directory names with deterministic fixed-width internal names such as ~variant-00~ through ~variant-23~.
- Preserve the existing FTS mode, profile ID, and profile kind in the JSON report.
- Keep a deterministic mapping between each fixed-width internal variant directory and its reported benchmark identity.
- Ensure that all variant corpus paths have equal lengths so stored path data cannot bias database-size comparisons.
- Mark workloads intended as positive lookups explicitly in the benchmark definition or otherwise maintain an unambiguous expected-result contract.
- Fail the benchmark with a clear diagnostic when a positive lookup unexpectedly returns zero results.
- Include the workload ID, variant ID, profile ID, FTS mode, expression, and unexpected result count in that diagnostic.
