** TODO Support simplified file-local TODO keyword lines

Goal:
Support the Org file-local TODO keyword line forms needed for keyword
recognition, without modeling full Org TODO semantics.

This is a follow up of: [[file:archive/2026-06-18--respect-file-local-todo-keyword-config-in-parser-indexer-pipeline.org]]

Context:
Org allows file-local TODO keyword definitions using `#+TODO:`,
`#+SEQ_TODO:`, and `#+TYP_TODO:`. These lines may appear anywhere in the file
and apply file-wide.

For now, org-files-db does not model fast-selection keys and does not
distinguish `SEQ_TODO` from `TYP_TODO` semantically. All supported local TODO
keyword lines are treated as equivalent keyword definition lines for heading
TODO detection.

Design decisions:

- Treat `#+TODO:`, `#+SEQ_TODO:`, and `#+TYP_TODO:` as equivalent.
- Collect all supported local TODO keyword lines from anywhere in the file.
- Apply the collected local keyword set globally to the whole file.
- If at least one local TODO keyword line exists, override project/default TODO
  keywords for that file.
- Do not implement position-dependent TODO keyword semantics.
- Do not model fast-selection metadata.
- Strip fast-selection suffixes such as `(t)`, `(w@)`, or `(c)` for keyword
  matching and otherwise ignore them.
- Do not distinguish sequence and type TODO semantics.
- Do not change the DB schema.
- Do not change CLI JSON field names.

Required behavior:

- Keywords before `|` are open TODO keywords.
- Keywords after `|` are closed TODO keywords.
- If no `|` exists, treat the last keyword on that line as closed and preceding
  keywords as open.
- If the left side before `|` is empty, all keywords after `|` are closed.
- If the right side after `|` is empty, all keywords before `|` are open.
- Recognized TODO keywords are removed from normalized/display title fields
  according to the existing title semantics.
- Unrecognized keywords remain part of the title.

Example:

#+begin_src org
,#+TODO: this

,* this sdfdsf

,#+TODO: | that

,* that sdfdsf
#+end_src

Expected behavior:

- `this` is recognized as an open TODO keyword.
- `that` is recognized as a closed TODO keyword.
- Both apply globally to the whole file.

Larger fixture:

#+begin_src org
,#+TITLE: Testing local keywords
,#+TODO: one(t) two(n) | three(d) four(w@)
,#+TODO: FIVE SIX |
,#+TYP_TODO: seven | eight
,#+SEQ_TODO: nine | ten
,#+TODO: | eleven(c)
,#+STARTUP: showall

,* TODO invalid keyword, even though it is a default it is overwritten
,* DONE invalid keyword, even though it is a default it is overwritten

,* one valid, type open
,* two valid, type open
,* three valid, type closed
,* four valid, type closed
,* FIVE valid, type open
,* SIX valid, type open
,* seven valid, type open
,* eight valid, type closed
,* nine valid, type open
,* ten valid, type closed
,* eleven valid, type closed
#+end_src

Expected behavior for the larger fixture:

- `one`, `two`, `FIVE`, `SIX`, `seven`, and `nine` are recognized as open TODO
  keywords.
- `three`, `four`, `eight`, `ten`, and `eleven` are recognized as closed TODO
  keywords.
- `TODO` and `DONE` are not recognized because file-local keywords override
  defaults and they are not listed locally.
- Recognized TODO keywords are removed from normalized/display title fields.
- Unrecognized default keywords remain part of the title.

Acceptance criteria:

- Multiple file-local TODO keyword lines are accumulated.
- `#+TODO:`, `#+SEQ_TODO:`, and `#+TYP_TODO:` are supported.
- Local TODO keyword lines appearing after headings still apply globally.
- Empty left side before `|` is supported.
- Empty right side after `|` is supported.
- Fast-selection suffixes are stripped for matching.
- Fast-selection metadata is otherwise ignored.
- Defaults are overridden when local TODO lines exist.
- Existing default/project TODO keyword behavior still works when no local TODO
  lines exist.
- Existing title normalization behavior is preserved.
- Focused tests cover the behavior above.
  
** TODO Support multiple file-wide `#+TITLE:` keywords

Goal:
Handle Org's file-wide title semantics when multiple `#+TITLE:` keywords appear
in a file.

Context:
Org supports long titles by allowing multiple `#+TITLE:` lines. These lines may
appear anywhere in the file, including after headings. Org treats them as
file-wide export/title metadata and combines their values.

Example:

#+begin_src org
,#+TITLE: Title can span
,#+TITLE: multiple lines,
,#+AUTHOR: Hubisan

,* Unfortunately Everywhere

,#+TITLE: even here
#+end_src

Expected effective file title:

#+begin_src text
Title can span multiple lines, even here
#+end_src

Required behavior:

- Detect all `#+TITLE:` keywords from anywhere in the file.
- Treat `#+TITLE:` keywords as file-wide metadata, not section-local metadata.
- Preserve document order when combining multiple title values.
- Combine multiple title values with a single space between non-empty parts.
- Trim surrounding whitespace from each title value before combining.
- Ignore empty `#+TITLE:` values unless existing project conventions require
  preserving them.
- Keep the level 0/root heading title consistent with the effective file title.
- Keep existing single-title behavior working.
- Do not change the DB schema unless unavoidable.
- Do not change CLI JSON field names.
- Do not implement broader export metadata handling in this task.
- Do not implement full Org export behavior beyond `#+TITLE:` collection.

Acceptance criteria:

- A file with one `#+TITLE:` keeps the current behavior.
- A file with multiple top-level `#+TITLE:` lines combines them in document
  order.
- A file with a later `#+TITLE:` after a heading still includes that value in
  the effective file title.
- The level 0/root heading uses the combined effective title.
- Regular headings are not affected by later `#+TITLE:` keywords.
- Existing title normalization behavior for headings remains unchanged.
- Focused parser/indexer tests cover multiple `#+TITLE:` lines.
- A regression test covers a `#+TITLE:` appearing after a heading.

** TODO Normalize resolved config paths syntactically

Goal:
Avoid storing syntactically noisy but equivalent paths such as `/path/./file.org`.

Context:
Config paths are resolved before they are used by discovery, indexing, DB writes, and CLI output. Config-relative paths are resolved by joining the config file directory with the configured path. For entries such as `./test.org`, this can currently produce paths like:

#+begin_src json
{
  "file_path": "/path/to/project/.project/local/./test.org"
}
#+end_src

This is functionally equivalent, but noisy and undesirable for stored file identity, JSON output, tests, and future deduplication.

Required behavior:

- Normalize resolved config paths syntactically after config path resolution.
- Remove syntactic `.` path components from resolved paths.
- Apply this to:
  - `db_path`
  - entries in `files`
  - entries in `dirs`
- Keep config-relative paths resolving relative to the config file location.
- Keep absolute paths working unchanged, except for removing syntactic `.` components.
- Keep existing leading `~` expansion behavior unchanged.
- Do not canonicalize paths through the filesystem.
- Do not resolve symlinks.
- Do not require `db_path` to exist.
- For `files` and `dirs`, continue validating existence as before.
- Do not change parser, DB schema, indexer behavior, or CLI JSON field names.
- Do not implement broad path cleanup beyond syntactic `.` normalization unless needed by the existing path APIs.

Acceptance criteria:

- `files = ["./test.org"]` resolves to `/path/to/config-dir/test.org`, not `/path/to/config-dir/./test.org`.
- `dirs = ["./notes"]` resolves to `/path/to/config-dir/notes`, not `/path/to/config-dir/./notes`.
- `db_path = "./org-files-db.sqlite"` resolves to `/path/to/config-dir/org-files-db.sqlite`, not `/path/to/config-dir/./org-files-db.sqlite`.
- Absolute paths containing syntactic `.` components are normalized without resolving symlinks.
- Existing absolute path behavior still works.
- Existing config-relative path behavior still works.
- Existing `~` expansion behavior still works.
- Validation behavior for missing files and missing directories remains unchanged.
- Tests cover config-relative paths with leading `./` for `db_path`, `files`, and `dirs`.
- Tests cover that existing `~` expansion still works together with syntactic path normalization.
