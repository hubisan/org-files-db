Goal: Allow external clients such as ~org-files-db.el~ to cache saved query views reliably and refresh them only after committed query-visible database changes.

A cache belongs to a complete saved view, not to an individual file.

A saved view may contain:

- a query or search expression
- a result target such as headings, links, or files
- selected columns
- sorting
- display options
- optional result limits

The database must expose:

- a stable database identity
- a monotonic committed generation
- a persistent journal of files affected by each generation
- a lightweight status command
- a changes-since command
- a machine-safe way to rerun an existing query only for selected files

The affected-file journal is an optimisation for cached query views. It does not change the cache into separate per-file caches.

For an incrementally refreshable query view, Emacs may:

1. remove cached rows belonging to affected files
2. rerun the same query restricted to affected non-deleted files
3. merge the refreshed rows into the cached view
4. apply the saved view sorting again
5. store the new generation

When selective refresh is not provably correct, Emacs must rerun the complete view.

** Fixed public semantics

The implementation must follow these decisions.

*** Database identity

Every database has one persistent ~database_id~.

The identifier:

- is created once when the database is initialized
- survives process restarts
- survives watcher restarts
- survives incremental indexing
- survives ordinary rebuilds that preserve the database file
- changes when a database is recreated from scratch

External caches identify their database using:

#+begin_example
database_id
#+end_example

A changed ~database_id~ means that all cached views for the previous database must be discarded.

*** Generation

Every database has one persistent monotonic integer ~generation~.

The generation represents committed query-visible database state.

It advances:

- once for one committed full rebuild batch
- once for one committed incremental batch
- once for one committed watcher reconciliation batch
- once when one or more files are added
- once when one or more files are replaced
- once when one or more indexed files are deleted
- once when persisted derived state changes query-visible results

It does not advance:

- once per changed file
- for queries
- for searches
- for status requests
- for changes-since requests
- for discovery or planning
- for ignored filesystem events
- for watcher debounce activity
- for a watcher batch with no effective changes
- for a failed parse
- for a failed write
- for a rolled-back transaction
- for SQLite maintenance such as WAL checkpoints
- for an operation that can prove that persisted logical state is unchanged

One watcher batch affecting 12 files advances the generation by exactly one.

*** Changed timestamp

Store:

#+begin_example
last_changed_at
#+end_example

Update it only when the generation advances.

Do not call this field ~last_indexed_at~, because a successful no-op indexing operation does not update it.

The timestamp format must follow the repository's existing UTC timestamp conventions.

*** Affected files

Each committed generation records the files whose persisted query-visible state changed.

Record all query-visible affected files, not only files whose source text changed.

Examples:

- A changed Org file is affected.
- A newly indexed Org file is affected.
- A deleted Org file is affected.
- A source file whose persisted outgoing-link resolution changed is affected.
- A source file whose indexed derived state changed is affected.
- A target-file deletion may therefore affect the deleted target path and several surviving source files that link to it.

Public file actions are:

#+begin_example
upsert
delete
#+end_example

~upsert~ means:

- remove cached rows owned by this file
- rerun the saved query for this file
- insert any new matching rows

~delete~ means:

- remove cached rows owned by this file
- do not query the deleted path again

Do not expose separate public actions for add, replace, link-resolution change, FTS change, or rename.

A rename is represented as:

#+begin_example
delete old/path.org
upsert new/path.org
#+end_example

Store the canonical persisted path representation already used by the ~files~ table.

A deleted path must remain available in the journal after its ~files~ row has been deleted.

*** Full invalidation

A generation may be marked:

#+begin_example
full_invalidation = true
#+end_example

Use full invalidation when the complete query-visible change cannot be safely represented as an exact finite affected-file set.

Examples include:

- migration of an existing database to the generation schema
- database repair
- a rebuild path that cannot reliably derive an exact delta
- a global derived-state mutation that cannot safely be attributed to files
- an internal invariant failure while constructing an otherwise committed delta

Do not silently emit an incomplete file list.

When any generation in the requested range has ~full_invalidation = true~, the changes-since command instructs the client to rebuild the complete cached view.

*** View-cache refresh safety

Saved query views remain cached as complete query result sets.

Selective file-based refresh is valid only when all of the following are true:

- every result row is owned by one indexed source file
- the complete cached result set is available
- the view has no result limit or offset
- the view is not truncated
- the result semantics do not depend on corpus-wide ranking
- the client can reapply the saved view sorting after merging

Structural ~query~ views over headings, links, and files are expected to support selective refresh when these conditions hold.

~search~ views must be fully rerun after any generation change unless a later task proves that partial refresh preserves ranking and result semantics.

FTS ranking may depend on corpus-wide statistics, so a changed file can affect scores of otherwise unchanged rows.

Query views using ~limit~, ~offset~, top-N behaviour, or other truncation must also be fully rerun.

The Rust implementation does not need to understand every Emacs view option. It must expose enough stable information for ~org-files-db.el~ to choose between:

#+begin_example
unchanged
patch
rebuild
#+end_example

- changed or newly indexed files are ~upsert~
- deleted indexed files are ~delete~

Do not use raw filesystem events as the journal source.

A full rebuild that commits changed query-visible state increments generation once.

*** Query view refresh

For a query view that is safe to patch:

1. Call ~orgfdb changes~ with the cached database ID and generation.
2. If ~cache_action = unchanged~, keep the cache.
3. If ~cache_action = rebuild~, rerun the complete query.
4. If ~cache_action = patch~:
   - remove all cached rows whose owning file is in ~upsert_files~
   - remove all cached rows whose owning file is in ~deleted_files~
   - rerun the same query restricted to ~upsert_files~
   - merge the returned rows
   - reapply the saved view sorting
   - store ~to_generation~

This remains one cache for the complete view.

The file path is only an internal ownership key used to replace affected portions.

*** Query views requiring full refresh

Rerun the complete query when the saved view:

- uses a result limit
- uses an offset
- stores only a truncated result set
- depends on a global aggregate
- uses semantics that cannot be reconstructed by replacing file-owned rows
- cannot reapply its sorting deterministically

*** Search view refresh

Rerun the complete search view whenever generation changes.

Do not patch search results by affected file in this task.

*** Race handling

A client may receive another database change while refreshing a view.

The documented safe algorithm is:

1. read changes up to generation N
2. perform the patch or rebuild
3. call status or changes again
4. publish the refreshed cache only if the database is still at generation N
5. otherwise continue from N or repeat the refresh

Do not require a long-lived read transaction across separate CLI processes.

The generation check is the consistency boundary.

→ different or recreated database; rebuild cached views

cache_action unchanged
→ keep the view cache

cache_action patch
→ replace cached rows owned by affected files

cache_action rebuild
→ rerun the complete saved view
#+end_example

Do not claim that the generation represents source Org changes before indexing commits them.

Do not claim that affected files contain only source-text changes.

** Non-goals

This task does not implement:

- the Emacs cache itself
- cache persistence inside Emacs
- one database cache per file
- selective FTS search refresh
- watcher JSON events
- automatic journal pruning
- webhook or push notifications
- database-file monitoring inside ~orgfdb~
- source file hashes in the public changes response
- row-level change journals
- per-query dependency tracking inside the Rust database
- automatic analysis of whether an arbitrary saved Emacs view is patch-safe

The Emacs package decides whether a saved view uses patch or full rebuild based on the documented rules.

** Acceptance criteria

- Every database has a stable persistent ~database_id~.
- Every database has a persistent monotonic ~generation~.
- New databases begin at generation zero.
- Migrated populated databases begin at generation one with full invalidation.
- Generation advances inside the same transaction as query-visible index changes.
- One committed logical batch advances generation exactly once.
- No-op, failed, and rolled-back operations do not advance generation.
- ~last_changed_at~ changes only when generation changes.
- Every committed generation has a valid generation-batch record.
- Normal incremental batches record exact affected paths.
- Deleted paths remain available in the journal.
- Derived link-resolution changes mark owning source files as affected.
- Full invalidation is used instead of an incomplete file list.
- Ordinary rebuilds preserve database identity.
- Database recreation creates a new identity.
- ~orgfdb status --format json~ is read-only and inexpensive.
- ~orgfdb changes --format json~ returns ~unchanged~, ~patch~, or ~rebuild~ deterministically.
- Several generations collapse to final net actions per path.
- Database-ID changes cause complete cached-view rebuilding.
- File-restricted query execution supports machine-safe bulk path input.
- Restricted queries return only rows owned by selected files.
- Machine-readable result rows expose their owning canonical file path.
- A selectively patched complete query view equals a fresh unrestricted query result.
- Search views are documented to rerun fully after generation changes.
- Limited, offset, or truncated views are documented to rerun fully.
- Concurrent readers observe only complete committed generations and journal data.
- SQLite file events are wake-up signals only; generation remains authoritative.
- Existing databases migrate without losing indexed data.
- Existing query, search, rebuild, watcher, resolver, and FTS tests remain green.
- All targeted checks pass.
- ~make ci~ passes.
