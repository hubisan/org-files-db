* Phase 8: Evaluate and optionally implement parallel parsing and preparation

Goal of this phase:

- Determine whether parallel parsing and preparation of independent changed Org files materially improves realistic rebuild and reconciliation workloads.
- Implement bounded parallel parsing and preparation only if measurements justify the added complexity.
- Preserve the Phase 6 indexing semantics and the Phase 7 watcher execution model unchanged.

Scope:

- Parallel execution is considered only for independent per-file parsing and preparation.
- A preparation job may parse already loaded file content and convert parser output into complete owned model-ready file data.
- File discovery remains sequential.
- Source-universe construction remains sequential.
- File metadata reads, content reads, and content hashing remain sequential.
- Change planning remains sequential.
- Processing inside one individual file remains sequential.
- DB writes remain sequential and transactionally controlled.
- FTS maintenance, link resolution, effective-state refresh, metadata updates, and other derived-state maintenance remain sequential.
- Watcher event collection, debouncing, reconciliation, and batch execution remain sequential.
- Multiple watcher reconciliation or application cycles must not run concurrently.

Reason for separate phase:

- Phase 6 already separates deterministic discovery, change planning, per-file preparation, ordered DB application, and full-rebuild recovery.
- Phase 7 reuses that pipeline and adds filesystem event collection, debouncing, recovery, and lifecycle handling without changing indexing semantics.
- Parsing is the only Phase 6 preparation step considered for parallel execution in this phase.
- Parallel parsing affects scheduling, memory use, error aggregation, cancellation behavior, and deterministic result ordering even though all surrounding stages remain sequential.

General rules:

- Keep the sequential Phase 6 parsing and preparation path as the reference behavior and fallback.
- Phase 6 discovery and change planning remain the single source of ordered preparation jobs.
- Do not add a separate parallel rebuild or watcher pipeline.
- Do not parallelize file discovery, metadata inspection, file reading, hashing, change planning, DB mutation, FTS maintenance, link resolution, derived-state maintenance, metadata updates, transaction management, or watcher control flow.
- File contents required for parsing are loaded before parallel execution begins.
- Worker jobs receive owned, independent parse inputs and return owned preparation results.
- Do not share mutable parser state across workers.
- Do not perform worker-side filesystem traversal, file reads, hashing, DB lookups, or DB writes.
- Parse completion order must not affect:
  - DB mutation order
  - semantic DB contents
  - FTS state
  - link-resolution state
  - source-universe metadata
  - indexing-context fingerprints
  - error ordering
- Completed preparation results are restored to deterministic change-plan order before DB application.
- One parse or preparation failure prevents the complete planned change set from being applied.
- Parallel behavior must be bounded, configurable, and disableable.
- Do not introduce a thread-pool dependency before the benchmark decision.
- A worker-count default or activation threshold may be introduced only from measured results.
- The parallel pipeline follows the project-wide platform contract: Linux and Unix-like systems, including macOS, are supported; Windows is not supported.
- Do not introduce Windows-specific path, filesystem, thread-pool, or watcher compatibility abstractions.
- Worker inputs and results preserve the byte-oriented Unix file identity defined in Phase 6.

- File reading and hashing are measured but are not candidates for parallel implementation in this phase.
- Watcher event collection, debounce latency, and idle runtime are outside this benchmark.

- Decision criteria are documented before implementation without inventing unsupported performance targets.

** TODO Decide whether parallel parsing and preparation are justified

Goal:

- Make an explicit evidence-based decision before adding a thread pool or parallel scheduler.

Possible decisions:

- keep parsing and preparation sequential
- provide opt-in parallel parsing and preparation
- enable parallel parsing and preparation automatically above a measured changed-file threshold

Acceptance criteria:

- The decision considers:
  - small collections
  - large collections
  - changed-file count rather than only total indexed-file count
  - parser-heavy and body-heavy files
  - FTS-enabled and FTS-disabled application cost
  - CPU use
  - peak memory
  - variance
  - deterministic behavior
  - implementation and maintenance complexity
- The decision explicitly confirms that discovery, reading, hashing, DB application, and watcher execution remain sequential.
- Rayon or another scheduler is not made mandatory before this decision.
- If measurements show no meaningful end-to-end benefit, Phase 8 closes without implementing parallel execution.
- If benefit exists only for unusually large parse job sets, the feature remains opt-in or threshold-based.
