* Planning

** Problem summary

The schema version ~10~ direct phase profiles still attribute tens of milliseconds to ~final-result-shaping~ at ~50'000~ heading results.

The direct-flat path owns ~QueryRows~ but currently shapes rows through shared references. Heading and file result construction therefore clones row-owned strings and optional strings into final result nodes.

The current direct phase profile treats the complete shaping loop as one operation. It does not separate JSON tag decoding, metadata attachment, path component derivation, and final node construction.

** Goals

- Refresh the final shaping baseline on the stable selective TEMP query path.
- Split the direct shaping profile enough to identify a concrete candidate.
- Keep diagnostic timing outside authoritative latency samples.
- Retain only a local ownership or allocation change with exact result equality and end-to-end benefit.
- Keep normal JSON semantics, ordering, validation, and errors unchanged.

** Non-goals

- Do not change query compilation.
- Do not change matched relation reuse selection.
- Do not move relational work from SQLite to Rust.
- Do not optimize serialization or ~presentation-json~.
- Do not repeat heading-path loader work without new evidence.

** Architecture

Keep the existing complete ~final-result-shaping~ timer as the authoritative direct shaping phase.

Add measurement-only detail records under a separate direct profile phase so detail timers do not double-count the existing phase summary.

For heading rows, separate:

- ~all_tags_json~ decoding
- metadata attachment from already loaded maps
- final node construction, including row-owned string clones

For file rows, separate:

- path-derived ~name~ and ~dir~ construction;
- metadata attachment;
- final node construction.

Record one aggregate operation per detail category instead of one record per result.

After the local benchmark identifies the dominant cost, test one ownership/allocation candidate against the same baseline.

** Execution plan

1. Add a direct shaping detail phase and aggregate timers for direct-flat shaping.
2. Increase the query SQL benchmark output schema version for the new profile detail.
3. Run the existing ~100~, ~1'000~, ~10'000~, and ~50'000~ workload matrix locally.
4. Inspect the ~50'000~ normal, properties, effective-properties, and path detail operations.
5. Define one measured candidate before changing production shaping.
6. Benchmark the candidate with exact public result equality and enough samples to distinguish noise.
7. Keep or reject the candidate from complete query latency.
8. Remove diagnostic detail that is not useful after the decision, or document why retained profiling remains useful.
9. Update ~docs/query-sql-performance.org~ with the baseline, candidate evidence, and final decision.
