Review and update direct Rust dependencies

Start this task after the bundled SQLite runtime is stable.

Goal: update direct Rust dependencies without mixing unrelated behavior changes.

Audit every direct dependency in ~Cargo.toml~ against current stable releases.

Do not repeat the ~rusqlite~ migration from the bundled SQLite task.

Update compatible patch and minor releases in small logical groups.

Test breaking major-version updates one dependency at a time.

Treat pre-release dependencies, including ~orgize~, as separate decisions.

Keep each dependency on the newest release that passes project compatibility checks.

If a current release requires an unwanted behavior change, record why the dependency stays pinned.

Do not refactor project code beyond changes required by dependency APIs.

Update ~Cargo.lock~ after the final dependency selection.

Run ~make ci~ after each breaking dependency migration.

Run the final complete ~make ci~ after all accepted updates.

Repeat a performance benchmark only if an updated dependency affects query execution or benchmark behavior.

Acceptance criteria:

- Every direct dependency has a recorded update decision.
- Compatible updates are applied.
- Breaking updates are isolated and tested.
- Held-back dependencies have a concrete reason.
- ~Cargo.lock~ matches the final dependency set.
- No unrelated refactor is mixed into the task.
- ~make ci~ passes.

* Planning

** Problem summary

Most direct dependencies already resolve to current releases within their existing version ranges.

A small compatible group has newer releases in the same API line.

Three dependencies require isolated breaking migrations: ~sha2~, ~signal-hook~, and ~toml~.

~orgize~ needs a separate pre-release decision because the project uses the ~0.10.0-alpha~ API.

** Goals

- Record one update decision for every direct dependency.
- Apply compatible updates before breaking migrations.
- Test each breaking migration separately.
- Keep the final dependency set reproducible through ~Cargo.lock~.

** Non-goals

- Do not repeat the completed ~rusqlite~ migration.
- Do not refactor code that is unrelated to dependency APIs.
- Do not replace ~orgize~ with another Org parser.
- Do not change query behavior as part of this task.

** Risks & assumptions

The compatible group can still expose a compiler or lint change.

The three breaking migrations can require source changes even when their common APIs look unchanged.

~toml~ is the highest behavior risk because it parses user configuration files.
