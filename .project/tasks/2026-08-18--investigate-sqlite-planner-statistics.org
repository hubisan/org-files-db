* Planning

** Problem summary

The production database lifecycle does not run ~ANALYZE~ or ~PRAGMA optimize~.

Schema creation creates the production indexes but does not create planner statistics.

A full rebuild can replace all indexed Org data without refreshing planner statistics.

Incremental indexing can also change table and index distributions without refreshing planner statistics.

The bundled SQLite runtime enables ~SQLITE_ENABLE_STAT4~.

The task must determine whether planner statistics improve real production queries enough to justify lifecycle work.

** Goals

- Compare the current no-statistics baseline with the same indexed data after a statistics operation.
- Require exact public query-result equality before timing each workload.
- Measure complete production query latency and query plans.
- Include cheap, selective, non-selective, expensive, and enrichment-heavy production queries.
- Record relevant ~sqlite_stat1~ and ~sqlite_stat4~ state.
- Measure the observed cost and database-size change of each tested statistics operation.
- Decide whether the production database lifecycle needs a statistics refresh policy.

** Non-goals

- Do not change public query output or error behavior.
- Do not add indexes.
- Do not change the query compiler.
- Do not update dependencies.
- Do not add production ~ANALYZE~ or ~PRAGMA optimize~ before benchmark evidence exists.
- Do not expand the experiment if the first gate gives a clear no-change result.

** Architecture

Use a dedicated measurement-only benchmark entry point in the existing query SQL benchmark module.

Keep the normal query SQL benchmark at output schema version ~13~.

The first experiment uses one prepared ~50'000~-result production benchmark database.

Create two benchmark copies from identical seeded data:

- baseline: current database state with no planner statistics
- candidate: the same database after full ~ANALYZE~

Full ~ANALYZE~ is the first gate because the bundled runtime enables ~SQLITE_ENABLE_STAT4~.

This gate tests the strongest available statistics state before lifecycle integration work starts.

If full ~ANALYZE~ gives no material benefit, stop the statistics experiment unless the data gives a specific reason to test another state.

If full ~ANALYZE~ gives a clear benefit, test ~PRAGMA optimize~ next as the lifecycle candidate.

SQLite recommends ~PRAGMA optimize~ for application-managed statistics refreshes.

The later comparison must include its bounded analysis cost and its resulting statistics state.

The experiment runner uses a neutral candidate state for this comparison.

Planner-statistics output schema version ~3~ records either ~ANALYZE~ or ~PRAGMA optimize~ as that candidate.

Schema version ~3~ also records downstream heading-tag and outline-validation plans for cheap non-TEMP heading relations.

** SQLite documentation findings

The official [[https://www.sqlite.org/lang_analyze.html][SQLite ANALYZE documentation]] says that statistics are optional planner input.

Statistics from ~ANALYZE~ are not refreshed automatically when database content changes.

The bundled build reports ~ENABLE_STAT4~.

Full ~ANALYZE~ can therefore create both ~sqlite_stat1~ and ~sqlite_stat4~ data.

SQLite cannot compute ~sqlite_stat4~ with a non-zero analysis limit.

The official [[https://www.sqlite.org/pragma.html#pragma_optimize][PRAGMA optimize documentation]] recommends ~PRAGMA optimize~ for current applications.

SQLite recommends it before closing short-lived database connections and after schema changes, especially after ~CREATE INDEX~.

Since SQLite 3.46.0, ~PRAGMA optimize~ uses a temporary analysis limit when it runs analysis work.

Its decision can also depend on query history from the current connection.

This behavior matters because orgfdb query connections are short-lived and read-only.

13. Record complete latency, statement profiles, compiled match plans, result counts, and TEMP-relation classification.
14. Review the evidence before any production lifecycle change.

** Test results

The local release benchmark completed after the v2 lifetime correction.

The full-~ANALYZE~ candidate used SQLite 3.53.2 with ~ENABLE_STAT4~.

The operation took 641.8 ms on the 50'000-result benchmark database.

The logical database size increased by 94'208 bytes.

It created 41 ~sqlite_stat1~ rows and 787 ~sqlite_stat4~ rows.

No recorded matched-relation query plan changed.

Median complete query latency changed as follows:

- ~cheap.heading-level~: 417.6 ms -> 293.8 ms (-29.65 %)
- ~selective.direct-property-1~: 3.29 ms -> 3.35 ms (+1.69 %)
- ~nonselective.effective-property-100~: 400.9 ms -> 401.7 ms (+0.19 %)
- ~expensive.multi-metadata-10~: 150.0 ms -> 148.2 ms (-1.19 %)
- ~enrichment-heavy.heading-level~: 1619.0 ms -> 1633.6 ms (+0.90 %)

The result is mixed.

One representative 50'000-result query has a large complete-latency gain.

The other four workloads have no material complete-latency gain.

This evidence does not justify full ~ANALYZE~ in production.

It also does not justify rejecting planner statistics yet.

The gate therefore permits one final lifecycle-candidate experiment with normal ~PRAGMA optimize;~.

SQLite recommends ~PRAGMA optimize~ for application-managed statistics.

Since SQLite 3.46.0, normal ~PRAGMA optimize~ applies a temporary analysis limit when it runs analysis work.

A non-zero analysis limit does not generate ~sqlite_stat4~.

The ~PRAGMA optimize~ experiment completed with the same five workloads and exact-output checks.

The operation took 38.3 ms on the 50'000-result benchmark database.

The logical database size increased by 8'192 bytes.

It created 39 ~sqlite_stat1~ rows and no ~sqlite_stat4~ rows.

No recorded matched-relation query plan changed.

Median complete query latency changed as follows:

- ~cheap.heading-level~: 415.1 ms -> 292.1 ms (-29.63 %)
- ~selective.direct-property-1~: 3.25 ms -> 3.28 ms (+0.85 %)
- ~nonselective.effective-property-100~: 400.4 ms -> 398.0 ms (-0.60 %)
- ~expensive.multi-metadata-10~: 152.2 ms -> 151.1 ms (-0.76 %)
- ~enrichment-heavy.heading-level~: 1604.2 ms -> 1623.9 ms (+1.23 %)

This result repeats the large simple-heading gain from full ~ANALYZE~.

The other four workloads remain effectively neutral.

The cheaper operation retains the only material gain without ~sqlite_stat4~.

This result makes ~PRAGMA optimize~ a viable lifecycle candidate.

The current plan evidence is incomplete.

The benchmark records the matched-relation plan, but that plan does not change for the improved workload.

The SQL profile places the improvement in ~query-heading-tags~ and ~validate-outline-path~.

Add one final plan-only extension for those downstream statements on cheap non-TEMP heading relations.

Do not add another statistics candidate.
