Benchmark predicate-driven SQL for direct metadata filters.

Test direct tags, direct properties, effective properties, and keywords at approximately 1%, 10%, 50%, and 100% selectivity.

Compare the current heading-driven ~EXISTS~ form with relation-driven joins and benchmark-only predicate-first indexes.

Record latency, query plans, statement counts, returned rows, and rows transferred to Rust.

Do not add a persistent index without clear benchmark evidence.

Audit the query compiler for related lookups that stored row state makes impossible.

* Planning

** Problem summary

Several direct metadata predicates start from ~headings~ and use a correlated subquery.

The current query-plan audit reports ~SCAN h0~ for these cases.

Selective metadata can make a relation-first query cheaper because SQLite can start from a small metadata result set.

The current indexes do not provide the same predicate-first access for every metadata family.

** Goals

- Benchmark direct tags, direct properties, effective properties, and keywords.
- Measure 1%, 10%, 50%, and 100% selectivity.
- Compare heading-driven ~EXISTS~ with relation-first SQL under current indexes.
- Compare relation-first SQL with benchmark-only predicate-first indexes.
- Record query plans and complete one-statement latency through Rust row collection.
- Record statement count, returned rows, and rows transferred to Rust.
- Keep experimental indexes outside the production schema.
- Audit safe compiler short-circuits for impossible related lookups.

** Non-goals

- Do not change production query SQL in this task.
- Do not add a persistent schema index in this task.
- Do not change public query output.
- Do not change metadata semantics.
- Do not benchmark regular-expression predicates in this task.

** Architecture

Use isolated copies of each existing presentation benchmark database.

Add synthetic benchmark marker rows only to the copies.

Each marker selects a deterministic prefix of level-1 headings.

Use separate marker names for each selectivity so every SQL shape reads the same rows.

Use ~CROSS JOIN~ in the relation-first candidate to keep the metadata relation as the outer loop.

The benchmark-only indexed copy adds predicate-first indexes after all marker rows exist.

Direct property candidates use ~effective_properties.local_value~ because that projection preserves resolved local property semantics.

** Execution plan

1. Extend the SQL benchmark output schema with metadata predicate strategy results.
2. Create isolated current-index and experimental-index database copies per result size.
3. Seed deterministic metadata rows for 1%, 10%, 50%, and 100% selectivity.
4. Measure heading-driven and relation-first SQL on the current-index copy.
5. Measure the same relation-first SQL on the experimental-index copy.
6. Require identical heading IDs from all three SQL shapes before timing.
7. Record ~EXPLAIN QUERY PLAN~ for every strategy and selectivity.
8. Add structured compiler audit findings to the benchmark output.
9. Run ~make ci~ when the Rust toolchain is available.
10. Run the release benchmark and document the measured decision.

** Risks & assumptions

The synthetic metadata rows exist only in benchmark database copies.

The benchmark isolates predicate matching and Rust ID collection.

It does not include later tag enrichment or final result shaping.

SQLite does not expose scanned-row counts through the current benchmark API.

The query plan and returned-row counts remain available for plan analysis.

** Open questions

- Which metadata families benefit from relation-first execution with current indexes?
- Which families need a predicate-first index before relation-first execution wins?
- At which selectivity does heading-driven execution become cheaper?
- Does any experimental index provide enough benefit to justify a separate production task?

~relation-driven-current-indexes~ beats ~heading-driven-exists~ in all measured cases.

~relation-driven-experimental-index~ is the fastest strategy in all measured cases.

Direct tags already have a useful predicate-first production index through ~idx_tags_tag~.

At ~50'000~ headings, the benchmark-only covering tag index adds only about 10% to 18% over the existing relation-first plan.

This result does not justify another persistent tag index.

Direct and effective properties still scan ~effective_properties~ with the current indexes.

The predicate-first property indexes remove this scan and produce large gains at every selectivity.

Keywords also scan the metadata relation with the current indexes.

The predicate-first keyword index removes this scan and produces large gains at every selectivity.

The property and keyword index candidates remain separate production decisions.

This benchmark measures predicate matching through Rust ID collection.

It does not include later enrichment and final result shaping.

Do not add the persistent property or keyword indexes from this task alone.

Run a complete production query A/B before the schema change.

** Decision

Use relation-driven SQL as the preferred candidate for direct tag equality predicates.

Reuse the existing ~idx_tags_tag~ index for this candidate.

Do not add ~tags(tag, heading_id)~ as another persistent index.

Treat these benchmark-only indexes as strong production candidates:

- ~effective_properties(key, local_value, heading_id) WHERE local_value IS NOT NULL~
- ~effective_properties(key, effective_value, heading_id)~
- ~keywords(keyword COLLATE NOCASE, value, heading_id)~

Require one complete production query A/B before adding these indexes to the schema.

The compiler audit found no new safe metadata lookup skip.

Keep the existing root static-truth optimization as the only measured impossible-lookup shortcut.
