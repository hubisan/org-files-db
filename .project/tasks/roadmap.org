* Phase 5: Query engine and optional full-text search

Goal of this phase: Build a simple, safe query layer that can later be extended toward an org-ql-like language.

FTS5 is optional and must only be required when FTS-specific functionality is enabled.

General rules:

- The query model is independent of CLI and SQL.
- SQL generation uses bound parameters.
- FTS-dependent operators must fail clearly when FTS5 is disabled.
- Direct parsed facts and effective/derived semantics must be clearly distinguished.

** TODO Define effective property semantics

Goal: Define how direct property rows are resolved into effective property values for query/API use.

Context: The ~properties~ table stores direct source facts only. It preserves duplicate definitions, append operators, property keyword defaults, category keywords, level 0 property drawers, and regular heading property drawers.

Parsing and indexing do not collapse rows and do not compute final values.

Definitions:

- Direct property :: A property row exactly as parsed from the source file and stored in the ~properties~ table.
- Effective property :: The resolved property value for a heading after applying overwrite, append, source precedence, and optional inheritance rules.
- Direct property query :: A query against raw/direct property rows.
- Effective property query :: A query against resolved property values.

Scope: This task defines semantics and implementation strategy. It may implement minimal query/API support if the query layer is ready, but it must not change the parser/indexer contract.

Direct property rows remain the source of truth.

Rules to define:

- Later direct definitions with the same key override earlier non-append definitions in effective mode.
- Rows with ~append = 1~ append to the current effective value, separated by a single space.
- If an append row appears before any base value for that key, define whether it starts the value or is ignored. Prefer starting the value.
- ~#+PROPERTY~ rows are buffer-level default/inherited property definitions.
- Level 0 property drawer rows are direct level 0 properties.
- ~#+CATEGORY~ rows are represented as level 0 ~CATEGORY~ properties with source ~category_keyword~.
- Regular heading property drawer rows are direct heading properties.
- In effective inherited mode, apply properties in this order:
  1. level 0 property keyword defaults
  2. level 0 category keyword
  3. level 0 property drawer
  4. ancestor heading property drawers from root to parent
  5. current heading property drawer
- Later rows within the same source/heading/key are applied in source order.
- Direct heading drawer properties override inherited/default values when they define the same key.
- ~append = 1~ on a child heading appends to the inherited/current value for the same key.
- Effective inheritance must be optional.
- Queries should be able to request direct-only behavior.

Examples:

*** Example: later PROPERTY keyword wins

#+begin_src org
  ,#+PROPERTY: keyword_overwritten_by_second invalid
  ,#+PROPERTY: keyword_overwritten_by_second valid
#+end_src

Direct rows:

#+begin_src text
KEYWORD_OVERWRITTEN_BY_SECOND = invalid, source = property_keyword, append = 0
KEYWORD_OVERWRITTEN_BY_SECOND = valid,   source = property_keyword, append = 0
#+end_src

Effective value:

#+begin_src text
KEYWORD_OVERWRITTEN_BY_SECOND = valid
#+end_src

*** Example: append operator

#+begin_src org
  ,#+PROPERTY: var foo=1
  ,#+PROPERTY: var+ bar=2
#+end_src

Direct rows:

#+begin_src text
VAR = foo=1, source = property_keyword, append = 0
VAR = bar=2, source = property_keyword, append = 1
#+end_src

Effective value:

#+begin_src text
VAR = foo=1 bar=2
#+end_src

*** Example: drawer overrides keyword default

#+begin_src org
  ,#+PROPERTY: owner Alice

  ,* Task
  :PROPERTIES:
  :owner: Bob
  :END:
#+end_src

Direct rows:

#+begin_src text
level 0: OWNER = Alice, source = property_keyword, append = 0
Task:    OWNER = Bob,   source = property_drawer, append = 0
#+end_src

Effective value for ~Task~ with inheritance enabled:

#+begin_src text
OWNER = Bob
#+end_src

*** Example: child append uses inherited value

#+begin_src org
  ,* Parent
  :PROPERTIES:
  :genres: Classic
  :END:

  ,** Child
  :PROPERTIES:
  :genres+: Baroque
  :END:
#+end_src

Effective value for ~Child~ with inheritance enabled:

#+begin_src text
GENRES = Classic Baroque
#+end_src

Open decisions:

- Decide whether effective properties should be computed in Rust query/API code, a SQL view, or a dedicated cache table.
- Prefer Rust query/API logic first unless SQL-only querying clearly requires a view or cache.
- Decide whether the first query model exposes both direct and effective property operators immediately, or starts with one clearly documented mode.
- Decide naming for query operators, for example:
  - ~(has-property "ID")~
  - ~(property "KEY" "VALUE")~
  - ~(direct-property "KEY" "VALUE")~
  - ~(effective-property "KEY" "VALUE")~

Acceptance criteria:

- Direct property rows remain unchanged.
- Direct property queries are clearly distinguished from effective property queries.
- Duplicate direct definitions are resolved only in effective mode.
- Later non-append definitions override earlier effective values.
- Append rows append to the current effective value.
- Append behavior without a prior base value is explicitly defined.
- Inheritance behavior is explicit and optional.
- Level 0 property behavior is documented.
- ~#+PROPERTY~, ~#+CATEGORY~, level 0 property drawers, ancestor drawers, and current heading drawers have defined precedence.
- Tests cover overwrite, append, append without prior base value, level 0 properties, drawer-over-keyword override, and child append with inheritance.

* Phase 7: Parallel indexing pipeline

Goal of this phase: Make rebuild fast on larger Org collections by parallelizing file parsing while keeping filesystem discovery, per-file context resolution, and SQLite writes deterministic.

Reason for separate phase:

- Parallel scanning/parsing affects indexer architecture, DB write ordering, error handling, resolver caches, and later watcher behavior.
- It should not be mixed into TODO keyword resolution or parser correctness tasks.
- New resolver code should already avoid global mutable state so this phase can be implemented cleanly later.

General rules:

- Keep parser inputs independent per file.
- Keep DB writes serial or explicitly batched inside controlled transactions.
- Do not share mutable parser state across files.
- Resolver caches must be explicit, bounded, and safe to use from a future parallel pipeline.
- Parallel behavior must be configurable or limitable.

*** Empty property

Title: Empty node property ~:KEY:~ is not parsed as NODE_PROPERTY unless trailing whitespace is present

Issue draft:

#+begin_src markdown
Hi, I noticed that Orgize does not seem to classify a `PROPERTIES` drawer as a `PROPERTY_DRAWER` when it contains an empty node property written without whitespace after the property colon.

### Minimal reproduction

```org
,* Test
:PROPERTIES:
:EMPTY:
:END:
```

### Actual Orgize parse result

Orgize parses this as a generic drawer:

```text
DOCUMENT@0..33
  HEADLINE@0..33
    HEADLINE_STARS@0..1 "*"
    WHITESPACE@1..2 " "
    HEADLINE_TITLE@2..6
      TEXT@2..6 "Test"
    NEW_LINE@6..7 "\n"
    SECTION@7..33
      DRAWER@7..33
        DRAWER_BEGIN@7..20
          COLON@7..8 ":"
          TEXT@8..18 "PROPERTIES"
          COLON@18..19 ":"
          NEW_LINE@19..20 "\n"
        DRAWER_CONTENT@20..28
          PARAGRAPH@20..28
            TEXT@20..28 ":EMPTY:\n"
        DRAWER_END@28..33
          COLON@28..29 ":"
          TEXT@29..32 "END"
          COLON@32..33 ":"
```

So the `:EMPTY:` line is not exposed as a `NODE_PROPERTY`.

### Expected behavior

Emacs Org treats `:EMPTY:` as a valid node property with an empty string value.

For the same input, `org-element-parse-buffer` produces a `property-drawer` with a `node-property` whose key is `EMPTY` and whose value is the empty string.

So I would expect Orgize to classify the drawer as a `PROPERTY_DRAWER` and expose the node property roughly as:

```text
PROPERTY_DRAWER
  NODE_PROPERTY
    key = "EMPTY"
    value = ""
```

### Comparison: trailing whitespace works

If there is whitespace after the second colon, Orgize does classify it as a property drawer:

```org
,* Test
:PROPERTIES:
:EMPTY: 
:NEXT: Value
:END:
```

Orgize output includes `PROPERTY_DRAWER` and `NODE_PROPERTY` entries.

This means the classification currently depends on trailing whitespace after the property key, but Emacs Org accepts both forms.

### Why this matters

Org property syntax allows empty properties, and Emacs Org represents `:EMPTY:` as a node property with an empty string value. Code using Orgize as the syntax source currently has to either ignore such valid Org properties or add a compatibility fallback for generic `PROPERTIES` drawers.

### Suggested fix

Allow node property lines without a value and without trailing whitespace after the property colon:

```org
:KEY:
```

to be parsed as valid `NODE_PROPERTY` entries with an empty string value.

#+BEGIN_SRC markdown
  Title: Diary timestamps in planning lines are parsed as paragraph text instead of PLANNING

  Hi, I noticed that Orgize does not seem to classify a planning line as `PLANNING` when the scheduled timestamp is a diary expression.

  ## Minimal reproduction

  ```org
  ,** Diary expression
  SCHEDULED: <%%(diary-float t 42)>
  ```

  ## Actual Orgize parse result

  Orgize parses the `SCHEDULED:` line as normal paragraph text containing a `TIMESTAMP_DIARY`:

  ```text
  DOCUMENT@0..54
    HEADLINE@0..54
      HEADLINE_STARS@0..2 "**"
      WHITESPACE@2..3 " "
      HEADLINE_TITLE@3..19
        TEXT@3..19 "Diary expression"
      NEW_LINE@19..20 "\n"
      SECTION@20..54
        PARAGRAPH@20..54
          TEXT@20..31 "SCHEDULED: "
          TIMESTAMP_DIARY@31..53
            L_ANGLE@31..32 "<"
            PERCENT2@32..34 "%%"
            L_PARENS@34..35 "("
            TEXT@35..51 "diary-float t 42"
            R_PARENS@51..52 ")"
            R_ANGLE@52..53 ">"
          TEXT@53..54 "\n"
  ```

  So the line is exposed as:

  ```text
  SECTION
    PARAGRAPH
      TEXT "SCHEDULED: "
      TIMESTAMP_DIARY
  ```

  instead of a `PLANNING` node.

  ## Expected behavior

  Emacs Org recognizes this as a planning line with a scheduled diary timestamp.

  For the same input, `org-element-parse-buffer` produces a headline with `:scheduled` set to a diary timestamp, and the section contains a `planning` element:

  ```elisp
  (headline
   (:raw-value "Diary expression"
    :level 2
    :scheduled
    (timestamp
     (:type diary
      :raw-value "<%%(diary-float t 42)>"
      :diary-sexp "(diary-float t 42)")))
   (section
    (planning
     (:scheduled
      (timestamp
       (:type diary
        :raw-value "<%%(diary-float t 42)>"
        :diary-sexp "(diary-float t 42)"))))))
  ```

  So I would expect Orgize to classify this roughly as:

  ```text
  HEADLINE
    HEADLINE_TITLE "Diary expression"
    PLANNING
      PLANNING_SCHEDULED
        TEXT "SCHEDULED:"
        TIMESTAMP_DIARY
  ```

  ## Comparison: normal scheduled timestamps work

  For a normal scheduled timestamp like this:

  ```org
  ,** Simple scheduled
  SCHEDULED: <2024-11-20 Wed>
  ```

  Orgize correctly exposes a `PLANNING` node:

  ```text
  HEADLINE
    HEADLINE_TITLE "Simple scheduled"
    PLANNING
      PLANNING_SCHEDULED
        TEXT "SCHEDULED:"
        TIMESTAMP_ACTIVE
  ```

  The issue seems specific to diary timestamps in planning lines.

  ## Why this matters

  Consumers using Orgize as the syntax source cannot reliably distinguish structured planning metadata from normal body text in this case.

  For example, an indexer that stores heading body text may correctly exclude `PLANNING` nodes from body text, but with the current parse result this valid planning line is treated as paragraph/body text instead.

  This also means scheduled diary timestamps are not exposed through the same planning API/path as normal scheduled timestamps.

  ## Suggested fix

  Allow planning keywords such as `SCHEDULED:`, `DEADLINE:`, and `CLOSED:` to accept diary timestamps where Org mode accepts them, for example:

  ```org
  SCHEDULED: <%%(diary-float t 42)>
  ```

  and expose them as `PLANNING` / `PLANNING_SCHEDULED` with a `TIMESTAMP_DIARY` child.

  Thanks for maintaining Orgize!

- ID-based path layout may depend on ~org-attach-id-to-path-function-list~.
- Attachment targets are commonly non-Org files such as PDFs, images, source files, or editor config files.
- The current ~files~ table represents indexed Org files, so it is not a complete target model for attachments.

- Do not implement attachment resolution in the current Phase 4 resolver.
- Store ~attachment:~ links as raw link facts.
- Mark ~attachment:~ links ~unsupported~ via the generic resolver fallback.
- Revisit attachment resolution only after deciding how to model non-Org target files and Org attachment configuration.
