*** Empty property

Title: Empty node property ~:KEY:~ is not parsed as NODE_PROPERTY unless trailing whitespace is present

Issue draft:

#+begin_src markdown
Hi, I noticed that Orgize does not seem to classify a `PROPERTIES` drawer as a `PROPERTY_DRAWER` when it contains an empty node property written without whitespace after the property colon.

### Minimal reproduction

```org
,* Test
:PROPERTIES:
:EMPTY:
:END:
```

### Actual Orgize parse result

Orgize parses this as a generic drawer:

```text
DOCUMENT@0..33
  HEADLINE@0..33
    HEADLINE_STARS@0..1 "*"
    WHITESPACE@1..2 " "
    HEADLINE_TITLE@2..6
      TEXT@2..6 "Test"
    NEW_LINE@6..7 "\n"
    SECTION@7..33
      DRAWER@7..33
        DRAWER_BEGIN@7..20
          COLON@7..8 ":"
          TEXT@8..18 "PROPERTIES"
          COLON@18..19 ":"
          NEW_LINE@19..20 "\n"
        DRAWER_CONTENT@20..28
          PARAGRAPH@20..28
            TEXT@20..28 ":EMPTY:\n"
        DRAWER_END@28..33
          COLON@28..29 ":"
          TEXT@29..32 "END"
          COLON@32..33 ":"
```

So the `:EMPTY:` line is not exposed as a `NODE_PROPERTY`.

### Expected behavior

Emacs Org treats `:EMPTY:` as a valid node property with an empty string value.

For the same input, `org-element-parse-buffer` produces a `property-drawer` with a `node-property` whose key is `EMPTY` and whose value is the empty string.

So I would expect Orgize to classify the drawer as a `PROPERTY_DRAWER` and expose the node property roughly as:

```text
PROPERTY_DRAWER
  NODE_PROPERTY
    key = "EMPTY"
    value = ""
```

### Comparison: trailing whitespace works

If there is whitespace after the second colon, Orgize does classify it as a property drawer:

```org
,* Test
:PROPERTIES:
:EMPTY: 
:NEXT: Value
:END:
```

Orgize output includes `PROPERTY_DRAWER` and `NODE_PROPERTY` entries.

This means the classification currently depends on trailing whitespace after the property key, but Emacs Org accepts both forms.

### Why this matters

Org property syntax allows empty properties, and Emacs Org represents `:EMPTY:` as a node property with an empty string value. Code using Orgize as the syntax source currently has to either ignore such valid Org properties or add a compatibility fallback for generic `PROPERTIES` drawers.

### Suggested fix

Allow node property lines without a value and without trailing whitespace after the property colon:

```org
:KEY:
```

to be parsed as valid `NODE_PROPERTY` entries with an empty string value.

Thanks for maintaining Orgize!
#+end_src

*** Diary timestamps in planning lines are parsed as paragraph text instead of PLANNING

#+BEGIN_SRC markdown
  Title: Diary timestamps in planning lines are parsed as paragraph text instead of PLANNING

  Hi, I noticed that Orgize does not seem to classify a planning line as `PLANNING` when the scheduled timestamp is a diary expression.

  ## Minimal reproduction

  ```org
  ,** Diary expression
  SCHEDULED: <%%(diary-float t 42)>
  ```

  ## Actual Orgize parse result

  Orgize parses the `SCHEDULED:` line as normal paragraph text containing a `TIMESTAMP_DIARY`:

  ```text
  DOCUMENT@0..54
    HEADLINE@0..54
      HEADLINE_STARS@0..2 "**"
      WHITESPACE@2..3 " "
      HEADLINE_TITLE@3..19
        TEXT@3..19 "Diary expression"
      NEW_LINE@19..20 "\n"
      SECTION@20..54
        PARAGRAPH@20..54
          TEXT@20..31 "SCHEDULED: "
          TIMESTAMP_DIARY@31..53
            L_ANGLE@31..32 "<"
            PERCENT2@32..34 "%%"
            L_PARENS@34..35 "("
            TEXT@35..51 "diary-float t 42"
            R_PARENS@51..52 ")"
            R_ANGLE@52..53 ">"
          TEXT@53..54 "\n"
  ```

  So the line is exposed as:

  ```text
  SECTION
    PARAGRAPH
      TEXT "SCHEDULED: "
      TIMESTAMP_DIARY
  ```

  instead of a `PLANNING` node.

  ## Expected behavior

  Emacs Org recognizes this as a planning line with a scheduled diary timestamp.

  For the same input, `org-element-parse-buffer` produces a headline with `:scheduled` set to a diary timestamp, and the section contains a `planning` element:

  ```elisp
  (headline
   (:raw-value "Diary expression"
    :level 2
    :scheduled
    (timestamp
     (:type diary
      :raw-value "<%%(diary-float t 42)>"
      :diary-sexp "(diary-float t 42)")))
   (section
    (planning
     (:scheduled
      (timestamp
       (:type diary
        :raw-value "<%%(diary-float t 42)>"
        :diary-sexp "(diary-float t 42)"))))))
  ```

  So I would expect Orgize to classify this roughly as:

  ```text
  HEADLINE
    HEADLINE_TITLE "Diary expression"
    PLANNING
      PLANNING_SCHEDULED
        TEXT "SCHEDULED:"
        TIMESTAMP_DIARY
  ```

  ## Comparison: normal scheduled timestamps work

  For a normal scheduled timestamp like this:

  ```org
  ,** Simple scheduled
  SCHEDULED: <2024-11-20 Wed>
  ```

  Orgize correctly exposes a `PLANNING` node:

  ```text
  HEADLINE
    HEADLINE_TITLE "Simple scheduled"
    PLANNING
      PLANNING_SCHEDULED
        TEXT "SCHEDULED:"
        TIMESTAMP_ACTIVE
  ```

  The issue seems specific to diary timestamps in planning lines.

  ## Why this matters

  Consumers using Orgize as the syntax source cannot reliably distinguish structured planning metadata from normal body text in this case.

  For example, an indexer that stores heading body text may correctly exclude `PLANNING` nodes from body text, but with the current parse result this valid planning line is treated as paragraph/body text instead.

  This also means scheduled diary timestamps are not exposed through the same planning API/path as normal scheduled timestamps.

  ## Suggested fix

  Allow planning keywords such as `SCHEDULED:`, `DEADLINE:`, and `CLOSED:` to accept diary timestamps where Org mode accepts them, for example:

  ```org
  SCHEDULED: <%%(diary-float t 42)>
  ```

  and expose them as `PLANNING` / `PLANNING_SCHEDULED` with a `TIMESTAMP_DIARY` child.

  Thanks for maintaining Orgize!
#+END_SRC

** TODO [#C] Model attachment link resolution?
:PROPERTIES:
:PRIORITY: Low
:RISK: Medium
:DB_SCHEMA_CHANGE: Maybe
:API_CONTRACT_CHANGE: Maybe
:END:

Attachment links are not resolved so far as it is cumbersome. 

Goal:

- Decide and later implement how ~attachment:~ links should be resolved.
- Keep ~attachment:~ links as raw source facts until the attachment contract is implemented.
- Avoid partial attachment resolution that only works for rare indexed Org attachment files.

Background:

- Org attachment links behave like file links relative to the current node's attachment directory.
- The attachment directory lookup order in Org is:
  - local or inherited ~DIR~ property
  - local or inherited deprecated ~ATTACH_DIR~ property
  - local or inherited ~ID~ property
- ~DIR~ and ~ATTACH_DIR~ take precedence over ~ID~.
- Inheritance depends on ~org-attach-use-inheritance~.
- ID-based attachment directories depend on ~org-attach-id-dir~.
- ~org-attach-id-dir~ defaults to ~data/~ and, when relative, is interpreted relative to the Org file directory.
- ID-based path layout may depend on ~org-attach-id-to-path-function-list~.
- Attachment targets are commonly non-Org files such as PDFs, images, source files, or editor config files.
- The current ~files~ table represents indexed Org files, so it is not a complete target model for attachments.

Current decision:

- Do not implement attachment resolution in the current Phase 4 resolver.
- Store ~attachment:~ links as raw link facts.
- Mark ~attachment:~ links ~unsupported~ via the generic resolver fallback.
- Revisit attachment resolution only after deciding how to model non-Org target files and Org attachment configuration.
