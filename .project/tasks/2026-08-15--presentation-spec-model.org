Goal: Define one structured input model for all UI-independent presentation configuration.

The model initially contains:

#+begin_example
PresentationSpec
  columns
  sort
  row_source
#+end_example

Use one specification rather than separate public column and sort configuration formats.

Support:

- ordered columns
- sorting
- optional row source
- width modes
- truncation
- outline-path options

Initial width modes:

- ~auto~
- ~max~
- ~fixed~

Design the width type so another mode such as percentage width can be added later without redesigning unrelated presentation types.

Initial truncation options:

- left
- middle
- right
- configurable marker

Outline-path options:

- separator
- include root
- include match

The initial ~row_source~ may execute only the normal one-result-to-one-row behaviour, but the type must be ready for later row expansion.

Do not include:

- Emacs faces
- colours
- text properties
- completion frontend concepts
- Emacs action names

Acceptance criteria:

- One complete presentation specification can be parsed and validated.
- Optional values have deterministic defaults.
- Unknown values produce useful errors.
- The type is independent of Emacs.

* Planning

** Problem summary

The query command now reserves ~presentation-json~, but the CLI has no structured presentation input model.

The next presentation stages need one stable specification for columns, sort rules, row source, widths, truncation, and outline paths.

** Goals

- Add one Rust ~PresentationSpec~ model.
- Parse the model from JSON.
- Reject unknown fields and enum values.
- Provide deterministic defaults for optional values.
- Add query-only ~--presentation-spec-json~ input.
- Keep the existing query JSON path unchanged.
- Keep presentation output unavailable until the response model exists.

** Non-goals

- Do not define the public presentation column registry.
- Do not extract column values.
- Do not sort query results.
- Do not calculate widths or truncate values.
- Do not define presentation rows, cells, or semantic roles.
- Do not add caching, JSONL, or streaming.
- Do not add Emacs-specific names or data.

** Architecture

Add a small presentation module that owns the input model and its type-level validation.

Use this JSON shape:

#+begin_src json
{
  "columns": [
    {
      "name": "outline-path",
      "width": {"mode": "max", "value": 80},
      "truncate": {"position": "right", "marker": "…"},
      "outline_path": {
        "separator": " » ",
        "include_root": false,
        "include_match": true
      }
    }
  ],
  "sort": [
    {"column": "outline-path", "direction": "asc"}
  ],
  "row_source": null
}
#+end_src

Column names remain strings in this task. The later column-registry task defines their public semantics.

The width object uses a ~mode~ plus an optional ~value~. This shape can add a percentage mode later without changing the surrounding model.

A non-null row source uses an object with a ~kind~ field. This keeps room for source-specific options later.

Recognize these row-source kinds from the start:

- ~tags~
- ~effective-properties~
- ~keywords~

This task only models them. The later row-expansion task implements their execution.
