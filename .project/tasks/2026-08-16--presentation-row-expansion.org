* Planning

** Problem summary

The presentation model already defines row sources, singular row columns, and structured row contexts.

The response builder still rejects every non-null ~row_source~.

** Goals

- Expand one query result into zero or more presentation rows.
- Support ~tags~, ~effective-properties~, and ~keywords~.
- Preserve the original result array without changes.
- Keep source order when the query result provides an order.
- Preserve duplicate keyword entries.
- Run expanded rows through the existing sort and layout stages.
- Keep row-source include inference in the Rust presentation registry.

** Non-goals

- Do not support more than one row source.
- Do not create Cartesian products.
- Do not add free-text search.
- Do not add parallel execution.
- Do not add presentation caching.

** Architecture

Add one row-expansion stage before presentation sorting.

Normal presentation creates one row with ~row_context = null~ for each result.

An active row source creates one row for each source entry. Each row keeps the original ~result_index~.

Use query result vectors directly so source order and keyword duplicates remain intact.

Return an error if required row-source data is missing from a supplied result.

Reject row sources for result kinds that do not expose row-source data.

- Effective-property values use the existing query result representation.
- Tags need no extra query include because structural file and heading results already contain them.
