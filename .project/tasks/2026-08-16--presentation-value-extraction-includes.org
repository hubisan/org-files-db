Goal: Move UI-independent column extraction and presentation include inference into Rust.

Derive data requirements from:

- displayed columns
- sort columns
- outline-path options
- row source where applicable

Explicit query includes supplied by callers must be combined with presentation-derived requirements rather than replaced.

This is important so a client can request additional structured data for actions even when that data is not displayed.

Examples:

- file columns may require path data
- source outline paths require source data
- target outline paths require target data

Do not encode knowledge of Emacs actions in Rust.

Acceptance criteria:

- Columns receive the data required to render them.
- Hidden sort columns receive the same include inference.
- Explicit caller includes and inferred includes are combined.
- One query execution produces the complete result data.
- No presentation-specific include table is required in Emacs.

* Planning

** Problem summary

The presentation registry defines value sources and include rules, but it does not extract logical values yet.

The CLI also validates presentation requirements without adding the required includes to query execution.

** Goals

- Extract logical values from structured ~QueryResultNode~ data.
- Preserve useful value types for later sorting and formatting.
- Apply outline-path configuration during outline extraction.
- Extract reserved row values from ~row_context~.
- Infer includes from displayed columns, hidden sort columns, and row sources.
- Combine explicit query includes with inferred includes.
- Use one query execution for explicit and presentation data.

** Non-goals

- Do not implement row expansion.
- Do not implement sorting.
- Do not calculate widths.
- Do not truncate or pad visible text.
- Do not emit the final ~presentation-json~ response.
- Do not encode Emacs action names or Emacs faces.

** Architecture

Add a typed logical presentation value between query results and final cells.

Keep text, integer, list, and outline values distinct. Later sorting can use these values without a second column extraction table.

Use the existing public column registry as the only mapping from column names to value sources, roles, and include requirements.

The CLI combines explicit includes with inferred includes after query validation and before query execution.

** Execution plan

** Risks & assumptions

- Structural query presentation does not have a search result representation, so ~rank~ extraction stays reserved.
- Synthetic file roots in heading results use their file title as the matched outline component.
- A missing optional field produces an empty logical value.
- A missing field that requires an inferred include is a presentation extraction error.
