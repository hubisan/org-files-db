* Planning

** Problem summary

The final presentation pipeline is sequential.

The completed payload task provides a fresh sequential production benchmark for ~presentation-json~ version 2.

At 50,000 original results, the expensive CPU stages differ by workload.

Expanded 150,000-row workloads spend the largest isolated stage time in sorting:

- ~headings.tags~: 219.10 ms median sorting
- ~headings.effective-properties~: 301.79 ms median sorting
- ~files.keywords~: 264.35 ms median sorting

The wide 50,000-row workload spends substantial time in value extraction and final formatting:

- ~headings.wide~: 51.87 ms median value extraction
- ~headings.wide~: 64.53 ms median truncation, padding, and row formatting

The baseline therefore identifies CPU-bound work before any parallel dependency is added.

** Goals

- Compare sequential and parallel work on identical in-memory query results.
- Test sort-key creation and sorting as one candidate area.
- Test value extraction with width reduction as one candidate area.
- Test final row formatting as one candidate area.
- Measure complete presentation latency for sort-only, layout-only, and combined candidates.
- Require exact ~PresentationResponse~ equality for every candidate.
- Measure 100, 1,000, 10,000, and 50,000 original results.
- Use the final version 2 presentation wire implementation as the baseline.

** Non-goals

- Do not parallelize SQLite query execution.
- Do not change presentation semantics or ordering.
- Do not change the production execution strategy in the first experiment.
- Do not add parallel JSON serialization.
- Do not add a cache or streaming path.

** Architecture

Use Rayon only in benchmark-only candidate methods during the first experiment.

The candidate keeps row expansion sequential because the baseline does not identify it as a dominant stage.

The parallel sort candidate performs sort-key extraction per row in parallel and uses a parallel stable sort with the existing comparator.

The comparator still uses ~original_index~ as the final key.

This preserves deterministic ordering for equal presentation sort values.

The parallel layout candidate extracts cells independently per row.

Each worker computes local natural widths for its row.

A deterministic sequential reduction combines the local widths after extraction.

Final row formatting mutates only the cells in one row and can run independently after widths are known.

The production ~build_response~ method remains sequential during the experiment.

** Execution plan

1. Add an isolated parallel-candidate benchmark that reuses existing benchmark databases.
2. Compare sequential and parallel stage latency on the same query results.
3. Compare sequential, sort-only, layout-only, and combined complete presentation latency.
4. Validate exact output equality before timing results are accepted.
5. Run the candidate benchmark at 100, 1,000, 10,000, and 50,000 original results.
6. Select only stages that improve large workloads without material small-workload cost.
7. If needed, define one deterministic row-count threshold from the benchmark evidence.
8. Integrate only the selected strategy into production.
9. Run the normal presentation benchmark again to measure final stage, presentation, serialization, and CLI latency.
10. Remove experiment-only code if it is not part of the final design.

** Risks & assumptions

The first parallel benchmark uses the global Rayon pool.

Its warm-up samples exclude one-time pool initialization from stage medians.

The final CLI benchmark must still include real process startup and first-use costs.

Parallel cell extraction creates per-row local width data before the deterministic width reduction.

The benchmark must reject this candidate if that allocation cost removes the CPU benefit.

Separate benchmark runs can contain operating-system noise.

The candidate benchmark therefore compares sequential and parallel implementations in one process on identical in-memory inputs.

** Open questions

- Does parallel sorting improve the 150,000-row expanded workloads enough to justify Rayon?
- Does parallel layout work improve ~headings.wide~ and the expanded workloads?
- Does combining parallel sort and layout work improve complete presentation latency?
- Which row-count threshold avoids small-workload overhead?
- Does the final CLI path retain enough of the isolated gain after Rayon pool startup?

** Test results

The v1 candidate benchmark uses 14 available CPUs and 14 Rayon worker threads.

All candidate responses equal the sequential response for every workload and size.

Forced parallel execution loses heavily at 100 and 1,000 results.

At 10,000 results, only ~headings.wide~ shows a strong complete-pipeline gain.

Its layout-only candidate changes complete presentation time by -44.6 %.

The expanded 30,000-row workloads do not show a material complete-pipeline gain at this size.

At 50,000 results, layout-only changes complete presentation time by:

- ~headings.normal~: -10.8 %
- ~headings.wide~: -40.7 %
- ~headings.tags~: +4.9 %
- ~headings.effective-properties~: +11.4 %
- ~files.keywords~: -4.4 %

At 50,000 results, parallel value extraction changes the isolated stage by:

- ~headings.narrow~: +58.2 %
- ~headings.normal~: -60.1 %
- ~headings.wide~: -66.1 %
- ~headings.tags~: -57.5 %
- ~headings.effective-properties~: -40.4 %
- ~files.keywords~: -10.3 %

Parallel formatting helps the large one-row-per-result normal and wide workloads.

It loses for the large expanded tag and effective-property workloads.

Parallel sorting helps the isolated 150,000-row expanded sorting stage by 41.5 % to 59.6 %.

The complete sort-only gain is smaller because sort-key creation and other stages remain significant.

The v1 data does not support one global all-parallel threshold.

** Candidate strategy for v2

Test one deterministic selective strategy before production integration.

Use parallel sorting only when the presentation has at least 100,000 rows.

Use parallel value extraction when either condition is true:

- the presentation has at least 200,000 cells
- the presentation has at least 8 columns and 100,000 cells

Use parallel final formatting only when there is one presentation row per query result and the layout condition is true.

This keeps 100 and 1,000 result workloads sequential.

It also keeps narrow 50,000-row presentations sequential for layout work.

The 10,000-result wide workload uses parallel extraction and formatting without parallel sorting.

The 50,000-result normal and wide workloads use parallel extraction and formatting.

The 150,000-row expanded workloads use parallel sorting and extraction but keep final formatting sequential.

The v2 benchmark must measure extraction-only, formatting-only, and this exact selective strategy.

Do not integrate the strategy into ~build_response~ until the v2 complete-presentation result confirms the threshold.
