* Planning

** Problem summary

~PresentationSpec~ currently stores column names as unrestricted strings.

This lets the input model accept arbitrary field names and cannot validate columns against the query result context.

The previous Emacs client also had a generic extractor fallback. That fallback exposed internal result fields accidentally and must not define the new public API.

** Goals

- Add one typed public presentation-column registry in Rust.
- Cover the stable heading, file, link, and reserved search columns from the previous Emacs client.
- Reserve singular tag, property, and keyword columns for row expansion.
- Validate displayed and sort-only columns through the same registry.
- Record supported result contexts, query include requirements, value sources, semantic-role rules, and column-specific option support centrally.
- Reject outline-path options on columns that do not support them.
- Make required includes derivable from the registry without applying include inference yet.
- Keep the existing query JSON path unchanged.

** Non-goals

- Do not implement presentation value extraction.
- Do not merge inferred includes into query execution yet.
- Do not implement semantic-role serialization.
- Do not implement sorting, widths, truncation, row expansion, or presentation response output.
- Do not add search presentation output.
- Do not expose old internal Emacs columns such as ~byte-start~, ~byte-end~, ~file-id~, ~parent-id~, ~link-path~, ~raw-target~, or ~raw-description~.

** Architecture

Replace free-form column-name strings in ~PresentationSpec~ with a typed ~PresentationColumn~ enum.

Each column maps to one central definition with:

- supported presentation result contexts
- required query includes
- a value-source identifier for later extraction
- a semantic-role rule for the later role task
- supported column-specific options
- an optional required row source for singular row-expansion columns

Use presentation result contexts that match the public client model:

- ~heading~ for ~headings~ queries, including synthetic file-root results
- ~file~ for ~files~ queries
- ~link~ for ~links~ queries
- ~search~ as reserved registry metadata for later search integration

The query CLI validates ~PresentationSpec~ against the parsed query target before query execution.

The registry exposes required includes. A later task combines these includes with explicit query includes and performs extraction.

** Execution plan

1. Add typed column, result-context, value-source, role-rule, and option-support types to ~src/presentation.rs~.
2. Add one central definition for every public column.
3. Change displayed and sort column names in ~PresentationSpec~ to the typed column enum.
4. Validate column-specific options and singular row-source requirements.
5. Add target-aware validation for displayed and sort-only columns.
6. Add include derivation from the same registry.
7. Apply target-aware validation in the query presentation CLI path.
8. Add unit and CLI tests for unknown columns, result contexts, sort-only columns, includes, and options.
9. Update ~docs/cli.org~ and ~docs/design/presentation.org~.
10. Run ~make ci~.

** Risks & assumptions

- Synthetic root rows belong to the public heading presentation context because they can appear in ~headings~ query results.
- ~rank~ remains reserved for later search presentation support. The current query-only presentation CLI cannot select the search context.
- ~file-title~ on heading results requires ~path~ data so a real heading can access the source file title.
- Role rules remain transport-independent hints in this task. The next semantic-role task defines the final typed role model.
- Row-source include inference itself belongs to the later row-expansion and include-inference work.
