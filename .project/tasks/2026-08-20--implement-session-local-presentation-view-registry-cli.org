Start this task after the eager presentation view cache validation is approved.

Add a session-local registry for named presentation views.

The running watcher owns the registry.

Emacs registers views through the CLI after it starts its cache-enabled integration.

A registered view contains all inputs that affect its presentation output.

At minimum, include:

- view name
- query
- query output mode
- explicit query includes
- presentation specification

Add a local control path between separate ~orgfdb~ CLI processes and the running watcher.

Add public commands for:

- registering or replacing a view
- reading a registered view
- removing a registered view

Use the ~orgfdb view~ command group.

Registration starts the initial cache build through the later rebuild coordinator.

Reading a view never starts a rebuild.

Keep the existing ~orgfdb query~ interface unchanged.

Do not persist view registrations across watcher sessions.

Acceptance criteria:

- Emacs can register a named view through ~orgfdb view~.
- Re-registering a changed definition replaces the old definition.
- Emacs can request and remove a registered view.
- View registrations belong only to the active watcher session.
- The watcher owns the authoritative registry state.
- The normal ~orgfdb query~ behavior remains unchanged.
- CLI documentation describes the new commands.
- ~make ci~ passes.

* Planning

** Problem summary

Separate ~orgfdb~ CLI processes need access to view definitions that belong to one watcher session.

The registry must stay in watcher memory. It must not become persistent configuration.

This task must not implement materialized cache storage or watcher rebuild workers.

** Goals

- Add a session-local registry for named presentation views.
- Store the query, output mode, explicit includes, query timezone, and presentation specification.
- Add a local control connection between ~orgfdb view~ commands and the active watcher.
- Add commands to register, show, and remove view registrations.
- Validate view definitions with the existing query and presentation validation rules.
- Keep identical registration requests idempotent.
- Give changed definitions a new registry revision.
- Start each watcher session with an empty registry.
- Remove the local control socket on clean watcher shutdown.

** Non-goals

- Do not materialize presentation payloads.
- Do not add persistent cache storage.
- Do not add rebuild coordination.
- Do not add rebuild cancellation.
- Do not persist view registrations across watcher sessions.
- Do not change ~orgfdb query~ behavior.
- Do not add a configurable control directory.

** Architecture

The watcher starts one local Unix control socket before it reports ~watcher ready~.

The control socket owns an in-memory registry for the watcher session.

The socket path uses a stable hash of the configured database path.

Use ~XDG_RUNTIME_DIR~ when it contains an absolute path.

Use the XDG cache directory as the fallback control location.

The server uses a private control directory and a user-only socket mode.

Each CLI request opens one connection, sends one JSON request, and receives one JSON response.

Use a protocol version so later cache tasks can extend the control messages safely.

The registry gives each new or changed definition a monotonic session revision.

An identical definition keeps its existing revision.

Use ~orgfdb view show~ to read the active registration in this task.

Reserve materialized presentation payload reading for the later cache tasks.

* Results

** Approach

The watcher now creates an in-memory presentation view registry for each watcher session.

A local Unix control socket connects separate ~orgfdb view~ processes to this registry.

The watcher keeps the registry handle for the full watcher lifetime.

The control server uses the same handle and removes its socket on clean shutdown.

~orgfdb view register~ validates the query and presentation specification before registration.

The registered definition also records the effective query timezone.

The registry sorts and deduplicates explicit includes before it compares definitions.

Identical definitions keep their revision. Changed definitions receive a new session revision.

~orgfdb view show~ returns the active registration without query or cache work.

~orgfdb view remove~ removes the registration from the active watcher session.

The current task does not add materialized payload storage or rebuild coordination.
