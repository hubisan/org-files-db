Start this task after view registration and cache storage are available.

Keep registered cache-enabled views current after database changes.

After each successful database generation change, mark all registered view caches stale.

Start full rebuilds without waiting for a view request.

Keep the normal watcher input loop responsive while rebuilds run.

Use separate rebuild worker processes.

Run different view rebuilds concurrently with a bounded active-worker count.

Queue excess registered views instead of starting every large rebuild at once.

Use the validation results as the initial concurrency evidence.

On the measured 8-CPU host, 3 concurrent large workers are comfortable and 5 remain practical.

Do not use 10 concurrent large workers as the default target.

If a newer generation appears, terminate or discard obsolete worker output.

Coalesce skipped intermediate generations into the newest required generation.

A view request for a stale or rebuilding view waits until the current cache is ready.

If the current rebuild fails, return an error for that view.

Never return the stale payload as the current view.

Acceptance criteria:

- Database changes start eager rebuilds without a view request.
- The watcher continues to process file changes while rebuild workers run.
- Different views rebuild concurrently with bounded worker concurrency.
- New generations make old rebuild work disposable.
- Obsolete payloads never become current.
- Intermediate generations can be skipped.
- A view request waits for the current generation when necessary.
- A failed current rebuild produces a view error.
- ~make ci~ passes.

* Planning

** Problem summary

The registry and cache storage exist, but no production component connects them.

Registered views need eager rebuilds after registration and database generation changes.

A rebuild must not block the watcher event loop.

** Goals

- Add a watcher-owned rebuild coordinator.
- Run full rebuilds in separate ~orgfdb~ worker processes.
- Limit concurrent rebuild workers.
- Queue additional views.
- Cancel obsolete workers when a newer generation or view revision appears.
- Publish only cache data that matches the worker target.
- Add a blocking ~orgfdb view read~ command for materialized payloads.
- Return an error when the current rebuild fails.

** Non-goals

- Do not add session cache cleanup.
- Do not add old-session recovery.
- Do not add relative-date refresh.
- Do not add incremental per-file cache updates.
- Do not persist view registrations.
- Do not change the normal ~orgfdb query~ path.

** Architecture

The watcher starts one rebuild coordinator after its startup reconciliation.

The coordinator owns a small manager thread and separate rebuild child processes.

Registry changes and successful watcher executions wake the manager thread.

The manager reads the current database identity and generation before it selects rebuild targets.

A target contains the registered view revision, ~database_id~, and ~generation~.

The default worker limit is at most three active rebuild processes.

Additional views stay queued until a worker slot is free.

A worker receives the registered view definition through stdin.

The worker uses the normal query and presentation pipeline against a database snapshot.

The worker verifies the target generation before and after presentation work.

The worker publishes through the existing cache storage API only when the target remains valid.

A newer target terminates the old child process and replaces queued work with the newest target.

~orgfdb view read~ polls the watcher control path until the current target is ready or failed.

The CLI then validates the cache envelope and streams the raw presentation JSON payload to stdout.

** Risks & assumptions

The watcher remains the only supported writer during normal cache-enabled operation.

A separate worker process gives the watcher a direct cancellation boundary.

A cache file from an obsolete target can exist briefly, but strict envelope validation makes it unusable for the current target.

Three active workers use the validation result as the initial safe default on larger hosts.

The worker limit decreases on hosts with fewer than three available CPUs.

* Results

** Approach

The implementation adds a watcher-owned rebuild coordinator.

The coordinator uses a manager thread and separate ~orgfdb~ worker processes.

Registration changes and successful watcher executions request a target refresh.

Each target contains the registered view, ~database_id~, and ~generation~.

The coordinator runs at most three rebuild workers at the same time.

Additional registered views remain queued until a worker slot becomes free.

A newer generation or view revision terminates obsolete work and queues only the newest target.

Each worker uses the normal query and presentation pipeline against one database snapshot.

The worker validates ~database_id~ and ~generation~ before and after presentation work.

The worker publishes through the existing cache storage API.

~orgfdb view read~ waits through the watcher control path until the current target is ready.

The command validates the cache envelope and streams the stored presentation payload directly to stdout.

A failed current rebuild returns an error instead of the previous stale payload.
