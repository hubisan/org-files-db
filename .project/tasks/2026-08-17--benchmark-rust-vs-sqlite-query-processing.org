* Planning

** Problem summary

Round 2 reduced avoidable SQLite and Rust ID round trips.

The remaining query cost is not fully attributed between SQLite execution, row decoding, Rust processing, and final result shaping.

The existing SQLite profile callback does not measure the complete Rust and SQLite wall-clock path.

The ~headings.path~ workload remains the main candidate for a boundary experiment because ancestor enrichment is expensive.

** Goals

- Add direct phase timings for representative query execution and result shaping.
- Record row-transfer and statement metadata where the current architecture exposes it safely.
- Compare the current recursive ancestor loader with a Rust-driven bounded ancestor loader.
- Preserve all public query output and stored-data error contracts.
- Use benchmark evidence before moving production work between SQLite and Rust.

** Non-goals

- Do not change the public query language.
- Do not change normal ~--format json~ output.
- Do not change ~presentation-json~.
- Do not move query matching, relational filtering, ~effective_tags~, or ~effective_properties~ calculation to Rust.
- Do not add indexes, dependencies, or selective shared TEMP relation production logic.

** Architecture

Keep production behavior unchanged while adding benchmark-only phase instrumentation around existing internal boundaries.

Expose lightweight timing data through internal benchmark hooks instead of public query APIs.

Measure SQL statement execution and row decoding separately when the loader structure permits that split without changing result semantics.

For the path experiment, keep the current recursive relation as one strategy.

Add a benchmark-only Rust-driven strategy that follows parent IDs from matched rows and uses runtime-limit-safe bulk ancestor loads.

Both path strategies reuse the same matched result snapshot and validate the same stored-data invariants.

** Execution plan

1. Inspect the query executor, result shaper, path loader, and current SQL benchmark hooks.
2. Add internal phase timing and row-transfer instrumentation with no public output changes.
3. Extend the SQL benchmark output schema with direct Rust and SQLite phase measurements.
4. Add the Rust-driven ancestor loader as a benchmark-only comparison strategy.
5. Add regression tests for path equivalence and corruption behavior where practical.
6. Update ~docs/query-sql-performance.org~ with the new benchmark protocol and decision rules.
7. Run ~make ci~ and the relevant benchmark smoke checks.
8. Record results and set the task to ~REVIEW~.

** Risks & assumptions

- Fine-grained timers can perturb small workloads, so phase timings run separately from normal latency samples.
- SQLite statement stepping and row decoding must be timed at explicit iterator boundaries.
- The Rust-driven ancestor strategy can lose its advantage if it needs many iterative parent fetches.
- Existing ~outline_path~ evidence remains authoritative for corruption detection.
- Benchmark-only hooks must not leak into the public query contract.

** Open questions

- Which existing loader boundaries permit useful SQL-versus-row-decoding timing without invasive refactoring?
- Does a Rust-driven ancestor strategy reduce end-to-end path latency for large result sets?
- Does the extra Rust-side grouping cost offset reduced recursive SQL work?

The path benchmark compares the production recursive query-derived loader with a benchmark-only Rust-driven bulk ancestor loader.

The benchmark requires exact path output equality before it records timings.

Production query matching, enrichment strategy, public query output, and production path loading remain unchanged.
