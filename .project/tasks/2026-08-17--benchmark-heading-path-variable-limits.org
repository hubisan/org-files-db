* Planning

** Problem summary

The Rust-driven heading path benchmark wins with the local SQLite variable limit of ~250000~.

The Rust-driven loader sends ancestor IDs back to SQLite in runtime-limit-safe batches.

Its advantage needs validation with smaller variable limits before the loader moves into production.

** Goals

- Add a benchmark option for explicit SQLite variable limits.
- Compare both heading path strategies under each requested limit.
- Record the requested limit, effective limit, chunk capacity, statement count, bound parameters, row transfer, and direct phase timings.
- Keep the existing benchmark behavior when no explicit path variable limits are requested.
- Keep production query behavior unchanged.

** Non-goals

- Do not replace the production recursive path loader in this task.
- Do not change public query output.
- Do not change query matching or enrichment SQL outside benchmark support.
- Do not add dependencies.

** Architecture

Extend the existing ~path_strategies~ benchmark instead of creating a second benchmark binary.

Use a fresh read-only connection for each requested variable limit.

Set ~SQLITE_LIMIT_VARIABLE_NUMBER~ on that connection before path loading.

Record both the requested limit and the effective runtime limit because SQLite can clamp a requested value to its compile-time maximum.

Run both path strategies against the same matched heading snapshot for each limit.

Require exact path output equality before recording timings.

** Execution plan

1. Extend benchmark options and CLI parsing with ~--path-variable-limits~.
2. Validate positive values that fit the SQLite limit API.
3. Run the path strategy pair once per requested variable limit.
4. Record requested and effective limits plus chunk capacity on each path strategy result.
5. Preserve the current single-limit behavior when the option is absent.
6. Update benchmark documentation with a focused ~50'000~-row command.
7. Add parser and benchmark option tests.
8. Run ~make ci~ and a focused release benchmark when the environment permits it.
9. Record results and set the task to ~REVIEW~.

** Risks & assumptions

- A low limit can increase statement count substantially for the Rust-driven loader.
- The recursive strategy uses very few bound parameters, so its timing is a stable reference.
- The matched query runs before path loading and uses only a small number of parameters.
- A requested limit can be higher than the SQLite compile-time maximum and can be clamped.

** Open questions

- Does ~rust-driven-bulk-ancestors~ still win at ~32766~?
- Does it still win at ~999~ despite the larger statement count?
- At which limit does batching cost become material?
