* Planning

** Problem summary

The current ~presentation-json~ response repeats object keys and presentation values for every row and cell.

The existing payload analysis shows that large presentation responses can reach tens of megabytes.

The task must reduce wire size without changing presentation semantics or normal ~--format json~ output.

A fresh baseline is required before any wire-format candidate is implemented.

** Goals

- Establish a fresh baseline with the stable query implementation.
- Cover small, large, expanded, narrow, and wide presentations.
- Measure payload bytes, serialization time, presentation processing time, and total CLI time.
- Compare compact wire candidates on identical ~PresentationResponse~ input.
- Require semantic equality before performance comparison.
- Keep the final wire format explicit and simple for an Emacs client.
- Update the presentation wire-format documentation after the final representation is selected.

** Non-goals

- Do not change normal ~--format json~.
- Do not add JSONL.
- Do not add streaming.
- Do not add a presentation cache.
- Do not add presentation parallelism.
- Do not change query semantics.
- Do not mix unrelated query or indexing work into this task.

** Architecture

Keep the production ~PresentationResponse~ as the semantic source during the investigation.

Use the existing ~orgfdb-presentation-benchmark~ for timing and complete CLI measurements.

Use ~orgfdb-presentation-payload-analysis~ for exact byte attribution.

The existing workload set covers normal and expanded presentations but has no explicit narrow or wide presentation case.

Add two benchmark-only workloads before the fresh baseline:

- ~headings.narrow~ uses one displayed cell per result.
- ~headings.wide~ uses many displayed heading cells per result without row expansion.

Run both workloads at the same result sizes as the existing normal and expanded workloads.

Do not change ~presentation-json~ in the baseline patch.

After the baseline is recorded, add candidate serializers only inside measurement infrastructure first.

Compare current objects, positional arrays with shared schemas, useful omission rules, and short remaining object keys.

Promote one representation to production only after semantic equality and end-to-end measurements support it.

** Execution plan

1. Add explicit narrow and wide presentation benchmark workloads.
2. Run one fresh release timing baseline on new benchmark databases.
3. Run the payload analyzer on the same benchmark databases.
4. Record payload sections and repetition for small and large results.
5. Select the smallest useful candidate set from the measured byte attribution.
6. Add isolated candidate serialization with semantic decode/equality checks.
7. Compare payload size, serialization time, presentation processing time, and total CLI time.
8. Select one simple representation only when the measurements justify it.
9. Update production ~presentation-json~ and wire-format documentation.
10. Remove experiment-only candidate code before review.

* Build

The first patch changed measurement coverage only.

It added explicit narrow and wide benchmark workloads.

The fresh baseline is complete.

The second patch adds an isolated wire-candidate benchmark.

The candidate benchmark does not change production ~presentation-json~ or normal ~--format json~.

It serializes the same in-memory ~PresentationResponse~ with five representations:

- current objects
- short keys for repeated row, row-context, and cell objects
- positional row, row-context, and cell arrays with shared schemas
- positional arrays with an explicit ~display_text = null~ equality sentinel
- the display-null representation with shared semantic-role indexes

All positional arrays keep fixed field positions.

The shared schema defines every row, row-context, and cell position once per payload.

A null ~display_text~ means exactly ~display_text == search_text~.

The role-index candidate emits one ordered ~role_values~ table.

A role value is either ~null~ or an index into that table.

The benchmark parses every candidate once before timing.

It compares metadata, original results, row references, row contexts, cell text, and roles with the source response.

The candidate gate selected positional arrays with the null display sentinel and role indexes.

The production patch changes ~presentation-json~ to wire version 2.

Version 2 keeps ~results~ as original query-result objects.

It emits one shared schema and uses positional arrays for rows, row contexts, and cells.

A cell always has three positions.

A null value at ~display_text~ means exactly ~display_text == search_text~.

A role is ~null~ or an integer index into the shared ~role_values~ table.

The production serializer is implemented on ~PresentationResponse~ so internal benchmarks measure the same wire path as the CLI.

The payload analyzer now measures the version 2 positional row and cell representation.

The temporary wire-candidate benchmark is removed after selection.

** Test results

The fresh release baseline completed on Linux x86_64.

It used 100, 1,000, 10,000, and 50,000 original results.

At 50,000 results, compact payload sizes range from 36.0 MB for ~headings.narrow~ to 95.9 MB for ~files.keywords~.

Field names alone use 16.8 MB to 39.1 MB across the 50,000-result workloads.

Field names use about 38 % to 47 % of each complete payload.

Field names plus JSON syntax use about 48 % to 58 % of each complete payload.

At 50,000 results, ~headings.wide~ uses 22.6 MB for cell structure.

Each 150,000-row expanded workload uses 18.6 MB for cell structure.

Exact duplicate ~search_text~ and ~display_text~ values use 0.75 MB to 5.1 MB across the same workloads.

The byte data makes repeated object structure the first candidate target.

The baseline also records complete presentation, serialization, and CLI timing for every workload.

At 50,000 results, serialization medians range from 68.4 ms to 181.4 ms.

Complete presentation medians range from 33.3 ms to 577.7 ms.

Complete CLI medians range from 782.0 ms to 2,007.0 ms.

The wire-candidate benchmark completed on Linux x86_64.

Every candidate passed semantic equality checks at 100 and 50,000 results.

At 50,000 results, the selected representation reduces payload size by 12.50 % to 40.84 % across the six workloads.

The absolute reduction ranges from 4.50 MB to 32.90 MB.

The null display sentinel adds 0.55 MB to 3.70 MB beyond positional arrays.

Role indexes add another 0.30 MB to 5.40 MB.

The selected representation serializes faster than version 1 for every 50,000-result workload in the candidate run.

The 100-result workloads also have smaller payloads and no serialization regression.

The production version 2 timing and payload-analysis runs completed on Linux x86_64.

The runs use the same corpus fingerprints as the version 1 baseline at 100, 1,000, 10,000, and 50,000 results.
