*** SQLite variable limit

Respect the actual SQLite runtime limit for bound variables.

Use ~SQLITE_LIMIT_VARIABLE_NUMBER~ as the authoritative connection limit.

Modern SQLite commonly uses a default limit of ~32766~ variables per SQL statement.

Older SQLite versions used a default limit of ~999~.

The runtime limit can also be lower than the compiled default.

Do not hard-code ~900~ as the normal chunk size.

Derive the safe ID capacity from:

#+begin_example
SQLITE_LIMIT_VARIABLE_NUMBER
- parameters used outside the ID list
= available ID parameters
#+end_example

Keep the implementation correct when the runtime limit is smaller.

Add tests that exercise a small configured variable limit.

*** Compare SQL strategies

Compare the current chunked ~IN (...)~ strategy with alternatives.

Evaluate at least:

- larger chunks based on the runtime variable limit
- temporary tables for result IDs
- SQLite joins against temporary ID relations
- common table expressions where useful
- fewer enrichment queries with broader joins
- additional persistent or materialized tables where measured query patterns justify them

Do not add a persistent materialized table without benchmark evidence.

For a materialized table, include these costs in the decision:

- rebuild cost
- incremental update cost
- database size
- write amplification
- schema complexity
- query improvement

Prefer database work when SQLite can perform the operation efficiently.

Prefer Rust post-processing when it removes expensive or repeated SQL work without increasing transferred data significantly.

Avoid moving work to Rust only to hide an inefficient SQL access pattern.

* Planning

** Problem summary

The presentation benchmark shows that query execution is the main latency source at large result sizes.

The current enrichment path uses a fixed chunk size of 900 IDs.

It also reloads data that the base query already returns.

Some loaders read all headings from matched files even when only matched headings need metadata.

Several loader queries sort rows even when Rust discards or replaces that order.

** Goals

- Audit the complete SQL path for heading, file, and link query results.
- Use the runtime ~SQLITE_LIMIT_VARIABLE_NUMBER~ value for ID chunks.
- Remove redundant SQL statements and avoidable row reads.
- Avoid reloading base query data for simple flat results.
- Load metadata only for matched headings and matched file roots when possible.
- Remove SQL sorting and joins that do not affect public result order.
- Preserve ordering where it is part of the public result contract.
- Add measurements for SQL statement counts and large-result query time.
- Compare chunked ~IN (...)~, ~json_each~, CTE, temporary IDs, and a query-derived join before changing the strategy again.
- Review existing materialized tables before adding new persistent projections.

** Non-goals

- Do not change public query semantics.
- Do not change the normal ~--format json~ contract.
- Do not add presentation caching.
- Do not add presentation parallelism.
- Do not add a persistent materialized table without measured evidence.
- Do not optimize the presentation wire format in this task.

** Architecture

Use the base query rows directly for flat result shaping when they already contain the required data.

A small flat metadata context loads only requested properties, effective properties, and keywords.

Complex includes and outline output keep the full enrichment context.

Use one helper to derive the safe ID chunk size from ~SQLITE_LIMIT_VARIABLE_NUMBER~.

Each ID-only loader uses that helper instead of a fixed 900-ID chunk.

Keep effective tags and effective properties as the existing persistent projections.

Add a measurement-only SQL benchmark that reuses the presentation benchmark databases.

The benchmark records production query time and actual statement counts from a separate SQLite profile run.

It compares runtime-limit ID chunks, CTE values, ~json_each~, TEMP IDs, and a query-derived join.

** Risks & assumptions

- The runtime SQLite variable limit can differ between linked SQLite builds.
- A larger ~IN (...)~ statement can reduce statement count but increase prepare cost.
- ~json_each~ removes the variable-count limit but adds JSON serialization and virtual-table work.
- Temporary ID tables add population work and need measurement before production use.
- Direct flat shaping must preserve the exact current JSON result structure.
- Link and outline includes need broader context and remain on the full enrichment path initially.
- Existing indexes and materialized projections already cover important query patterns.

* Results

** Approach

The implementation audits the base query compiler and every large-ID enrichment loader.

It replaces fixed 900-ID chunks with the runtime SQLite variable limit.

Simple flat results now use the base query rows instead of broad file and heading reloads.

Metadata loaders now restrict work to matched headings and matched file roots where possible.

The implementation removes unused joins and global SQL sorts from common query and enrichment paths.

Rust restores the same public ordering with small grouped sorts after collection.

The heading executor skips the synthetic-root branch when predicates cannot match level zero.

No new persistent materialized table was added without benchmark evidence.

A new benchmark profiles production SQL and compares five representative ID-relation strategies.
