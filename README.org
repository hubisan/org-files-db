** Current Architecture

The codebase now implements the end-to-end indexing flow described in =.project/tasks/todo.org=.

- =src/parser/= owns the internal parser trait, data model, diagnostics, and the Orgize implementation adapter
- =src/indexer.rs= orchestrates parsing, normalization, and DB writes
- =src/db/= owns the SQLite schema, reader, and writer layers
- =src/query.rs= contains query-side helpers used by the CLI and tests
- =src/cli.rs= exposes the supported rebuild, headings, and links commands
- =main.rs= remains thin and delegates directly to the CLI module

** Parser Contract Notes

- Orgize is the implementation parser in =src/parser/orgize_adapter.rs=.
- Emacs Org-mode is used as a reference oracle for tricky semantics when that helps confirm parser behavior.
- Unsafe Emacs Lisp and diary expressions must not be evaluated.
- TODO keyword precedence is:
  1. Org in-buffer =#+TODO= / =#+SEQ_TODO= / =#+TYP_TODO= declarations
  2. config defaults
- The parser and indexer produce synthetic level-0/root rows for file and document roots; =headings --json= includes them by default and =--no-root= excludes them.
- Planning lines populate the supported =scheduled=, =deadline=, and =closed= fields, while body timestamps remain available as parsed timestamp rows.

** Link Resolving Contract

- =links= stores raw Phase 3 link source facts and nullable Phase 4 resolution fields in the same row.
- Phase 3 source facts are =raw=, =raw_target=, =raw_description=, =link_type=, =path=, =search_option=, byte positions, and source context.
- Phase 4 resolver-owned fields are =path_absolute=, =target_file_id=, =target_heading_id=, =target_custom_id=, =target_id=, =resolution_status=, and =resolution_diagnostic=.
- =resolution_status = NULL= means the resolver has not populated the row yet.
- =resolved=, =broken=, =unresolved=, =ambiguous=, and =unsupported= are the stored resolution states.
- File-only links resolve to the target file's synthetic root heading when the file is indexed.
- File links to indexed files populate =path_absolute= and =target_file_id=; file links with =::*Heading= resolve heading titles in the resolved target file.
- Same-file =[[*Heading]]= links resolve headings in the source file.
- Same-file =[[#custom-id]]= links resolve =CUSTOM_ID= values in the source file, and file-context =[[file:target.org::#custom-id]]= links resolve =CUSTOM_ID= values in the resolved target file.
- Org =id:= links resolve =ID= values across indexed non-root headings.
- Heading-title star links trim surrounding whitespace, unescape bracket escapes such as =\[= and =\]=, and match case-insensitively.
- =CUSTOM_ID= and Org =ID= matching is case-insensitive and whitespace-sensitive; neither target type is trimmed before lookup.
- External =org-id-locations= are not supported, so missing indexed Org IDs remain =unresolved= with =id not found=.
- Supported file search options are only =::*Heading= and =::#custom-id=; other file search options such as =::42=, =::/regexp/=, and dedicated targets such as =::target= or =::<<target>>= are intentionally unsupported.

** DB Schema Versioning

- SQLite =PRAGMA user_version= is the on-disk schema version for =org-files-db= databases.
- =CURRENT_SCHEMA_VERSION= in =src/db/schema.rs= is the code-level source of truth for the current persistent schema version.
- Any persistent schema change must bump =CURRENT_SCHEMA_VERSION=.
- Changes to tables, columns, indexes, constraints, FTS tables, or other persisted schema structures require a version bump.
- Older supported databases are upgraded through the existing schema application and legacy migration path during DB open/initialization.
- Databases with a newer =user_version= than the running binary supports fail closed and are not opened or downgraded silently.
- Schema application, legacy migrations, and the final =PRAGMA user_version= update run inside one transaction; the transaction is committed only after all schema work succeeds.
- Successful schema application or migration updates =user_version= only after the schema work succeeds.
- Manual or local test databases may need to be rebuilt after a schema version bump.

** SQLite Schema Contract

- The schema definition lives in =sql/schema.sql= and is applied by =SchemaDefinition= in =src/db/schema.rs=.
- The current =v0.1= populated schema contract covers these tables:
  - =files=
  - =headings=
  - =todo_keywords=
  - =keywords=
  - =properties=
  - =tags=
  - =timestamps=
  - =timestamp_repeaters=
  - =heading_bodies=
  - =outline_path=
- =heading_fts= is optional. It is created only when rebuild/indexing enables FTS and the local SQLite build supports FTS5.
- =heading_fts= is a contentless derived/cache FTS5 table rebuilt from canonical relational facts. It indexes every canonical heading, including synthetic level-0 file roots, with =rowid = headings.id=.
- Heading titles remain canonical in =headings.title= and body text remains canonical in =heading_bodies.body_text=. Title-only FTS indexing uses an empty FTS body when canonical body persistence is disabled.
- =orgfdb search --json= is a read-only FTS5 convenience command over the trusted derived index. It requires the active config to leave =search.fts5_enabled = true= and requires persisted FTS trust metadata written by a successful rebuild.
- Search JSON rows include =kind=: =file= for synthetic level-0 file roots and =heading= for real headings.
- Databases created before the FTS trust metadata existed, or before level-0 roots were added to the FTS contract, must be rebuilt once before =orgfdb search --json= will trust the stored index.
- =links= stores raw Phase 3 link source facts plus nullable Phase 4 target fields and explicit resolution state columns. The current rebuild pipeline resolves file-like links to indexed files when possible, maps file-only links to the resolved target file's synthetic root heading, resolves =file:...::*Heading= against normalized heading titles in the resolved target file, resolves same-file =[[*Heading]]= fuzzy star links against normalized titles in the source file, resolves same-file =[[#custom-id]]= links against =CUSTOM_ID= properties in the source file, resolves file-context =file:...::#custom-id= links against =CUSTOM_ID= properties in the resolved target file, resolves Org =id:...= links against =ID= properties across indexed non-root headings, trims surrounding whitespace only for star heading-title targets, preserves significant surrounding whitespace for =CUSTOM_ID= and Org =ID= targets, and matches those targets case-insensitively via Rust-side Unicode lowercase comparison. Duplicate heading-title and =CUSTOM_ID= matches stay silent, duplicate Org =ID= matches become =ambiguous=, missing in-universe file or heading-title targets become =broken=, missing Org =ID= targets and outside-universe file targets become =unresolved=, and other link forms become =unsupported=.
- Read-only CLI queries such as =headings --json=, =query --json=, and =search --json= do not initialize missing databases, apply schema changes, run migrations, update =PRAGMA user_version=, or create optional artifacts such as =heading_fts=.
- Synthetic level-0/root rows are DB/indexing sentinels for file/document roots, not parser-level Org headings.
- Persisted synthetic root rows use =level = 0=, =parent_id = NULL=, and =byte_start = -1=.
- Rebuild/indexing creates one synthetic root row per indexed file and attaches file-level keywords, file-level properties, file tags, and other file-scope facts to that row.
- Real Org headings start at =level >= 1= and are stored under the synthetic root when they are top-level headings.
- =outline_path= includes the synthetic root row: depth =0= uses materialized path =0000= and breadcrumbs start with the root title.

** Configured Paths

- Relative configured paths are resolved against the config file location, not the current shell directory.
- =db_path= is normalized syntactically only. It is not required to exist during config loading.
- =files= and =dirs= are resolved syntactically during config loading, but rebuild/indexing validates that they exist and canonicalizes them before discovery.
- Rebuild-time canonicalization collapses equivalent configured paths, including paths that differ only by =..= segments or symlink traversal.
- Rebuild refuses to wipe an existing indexed database when discovery finds zero input files unless =--allow-empty= is passed explicitly.
- Read-only commands such as =headings --json= load the config without requiring configured source paths to exist.

** headings --json Contract

- =orgfdb headings --json= returns a top-level JSON array.
- Each row currently exposes these fields:
  - =id=: integer
  - =file_id=: integer
  - =file_path=: string
  - =parent_id=: integer or =null=
  - =level=: integer
  - =line_number=: integer or =null=
  - =byte_start=: integer
  - =byte_end=: integer
  - =title=: string
  - =title_raw=: string
  - =todo_keyword=: string or =null=
  - =todo_type=: string or =null=
  - =priority=: one-character string or =null=
  - =scheduled_raw=: string or =null=
  - =scheduled_ts=: integer Unix timestamp or =null=
  - =deadline_raw=: string or =null=
  - =deadline_ts=: integer Unix timestamp or =null=
  - =closed_raw=: string or =null=
  - =closed_ts=: integer Unix timestamp or =null=
  - =archivedp=: boolean
  - =footnote_section_p=: boolean
  - =all_tags=: JSON array of strings
- Synthetic level-0/root rows exist for file and document roots and are included by default.
- Passing =--no-root= excludes the synthetic level-0/root rows from the JSON output.
- =--include-root= is retained only as a compatibility no-op and is not needed for the default behavior.
- The public JSON contract uses =all_tags= as an array. Internal DB storage may still use =all_tags_json=, but that string is not part of the CLI API.
- For real headings, =title= is the cleaned semantic title, while =title_raw= preserves the source title area after the headline stars, including TODO keywords, priorities, and statistics cookies, but excluding trailing Org tags.
