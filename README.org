** Current Architecture Baseline

The current codebase is intentionally a minimal scaffold around the parser-first architecture described in =.project/tasks/todo.org=.

- =src/parser/= owns the internal parser trait, data model, diagnostics, and the Orgize implementation adapter
- =src/indexer/= orchestrates parser access without Orgize-specific logic
- =src/db/=, =src/query/=, and =src/cli/= are present as compilable placeholders for later tasks
- =main.rs= remains thin and delegates directly to the CLI module

** Parser Contract Notes

- Orgize is the implementation parser in =src/parser/orgize_adapter.rs=.
- Emacs Org-mode is used as a reference oracle for tricky semantics when that helps confirm parser behavior.
- Unsafe Emacs Lisp, diary expressions, and arbitrary =.dir-locals.el= forms must not be evaluated.
- TODO keyword precedence is:
  1. Org in-buffer =#+TODO= / =#+SEQ_TODO= / =#+TYP_TODO= declarations
  2. config defaults
- =.dir-locals.el= is ignored completely during indexing and rebuild.
- Emacs file-local =org-todo-keywords= are not supported.
- The parser and indexer produce synthetic level-0/root rows for file and document roots; =headings --json= includes them by default and =--no-root= excludes them.
- Planning lines populate the supported =scheduled=, =deadline=, and =closed= fields, while body timestamps remain available as parsed timestamp rows.

** DB Schema Versioning

- SQLite =PRAGMA user_version= is the on-disk schema version for =org-files-db= databases.
- =CURRENT_SCHEMA_VERSION= in =src/db/schema.rs= is the code-level source of truth for the current persistent schema version.
- Any persistent schema change must bump =CURRENT_SCHEMA_VERSION=.
- Changes to tables, columns, indexes, constraints, FTS tables, or other persisted schema structures require a version bump.
- Older supported databases are upgraded through the existing schema application and legacy migration path during DB open/initialization.
- Databases with a newer =user_version= than the running binary supports fail closed and are not opened or downgraded silently.
- Schema application, legacy migrations, and the final =PRAGMA user_version= update run inside one transaction; the transaction is committed only after all schema work succeeds.
- Successful schema application or migration updates =user_version= only after the schema work succeeds.
- Manual or local test databases may need to be rebuilt after a schema version bump.

** SQLite Schema Contract

- The schema definition lives in =sql/schema.sql= and is applied by =SchemaDefinition= in =src/db/schema.rs=.
- The current =v0.1= populated schema contract covers these tables:
  - =files=
  - =headings=
  - =todo_keywords=
  - =keywords=
  - =properties=
  - =tags=
  - =timestamps=
  - =timestamp_repeaters=
  - =heading_bodies=
  - =outline_path=
- =heading_fts= is optional. It is created only when rebuild/indexing enables FTS and the local SQLite build supports FTS5.
- =links= exists in the schema as a reserved/deferred table, but it is not part of the populated =v0.1= indexing contract yet.
- Read-only CLI queries such as =headings --json= do not initialize missing databases, apply schema changes, run migrations, update =PRAGMA user_version=, or create optional artifacts such as =heading_fts=.
- Synthetic level-0/root rows are DB/indexing sentinels for file/document roots, not parser-level Org headings.
- Persisted synthetic root rows use =level = 0=, =parent_id = NULL=, and =byte_start = -1=.
- Rebuild/indexing creates one synthetic root row per indexed file and attaches file-level keywords, file-level properties, file tags, and other file-scope facts to that row.
- Real Org headings start at =level >= 1= and are stored under the synthetic root when they are top-level headings.
- =outline_path= includes the synthetic root row: depth =0= uses materialized path =0000= and breadcrumbs start with the root title.

** Configured Paths

- Relative configured paths are resolved against the config file location, not the current shell directory.
- =db_path= is normalized syntactically only. It is not required to exist during config loading.
- =files= and =dirs= are resolved syntactically during config loading, but rebuild/indexing validates that they exist and canonicalizes them before discovery.
- Rebuild-time canonicalization collapses equivalent configured paths, including paths that differ only by =..= segments or symlink traversal.
- Rebuild refuses to wipe an existing indexed database when discovery finds zero input files unless =--allow-empty= is passed explicitly.
- Read-only commands such as =headings --json= load the config without requiring configured source paths to exist.

** headings --json Contract

- =orgfdb headings --json= returns a top-level JSON array.
- Each row currently exposes these fields:
  - =id=: integer
  - =file_id=: integer
  - =file_path=: string
  - =parent_id=: integer or =null=
  - =level=: integer
  - =line_number=: integer or =null=
  - =byte_start=: integer
  - =byte_end=: integer
  - =title=: string
  - =title_raw=: string
  - =todo_keyword=: string or =null=
  - =todo_type=: string or =null=
  - =priority=: one-character string or =null=
  - =scheduled_raw=: string or =null=
  - =scheduled_ts=: integer Unix timestamp or =null=
  - =deadline_raw=: string or =null=
  - =deadline_ts=: integer Unix timestamp or =null=
  - =closed_raw=: string or =null=
  - =closed_ts=: integer Unix timestamp or =null=
  - =archivedp=: boolean
  - =footnote_section_p=: boolean
  - =all_tags=: JSON array of strings
- Synthetic level-0/root rows exist for file and document roots and are included by default.
- Passing =--no-root= excludes the synthetic level-0/root rows from the JSON output.
- =--include-root= is retained only as a compatibility no-op and is not needed for the default behavior.
- The public JSON contract uses =all_tags= as an array. Internal DB storage may still use =all_tags_json=, but that string is not part of the CLI API.
